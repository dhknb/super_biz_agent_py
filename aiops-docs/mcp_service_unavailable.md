# MCP服务不可用告警处理方案

## 告警名称
- **告警名**: `MCPServiceUnavailable`
- **告警级别**: 严重
- **触发条件**: CLS或Monitor MCP服务连续5分钟无法访问，或工具调用失败率超过30%

## 问题描述
当MCP服务不可用时，可能导致：
- AIOps诊断无法查询日志和监控数据
- Agent只能给出降级后的通用建议
- 故障定位效率明显下降
- 线上诊断报告缺少关键证据

## 排查步骤

### 步骤1: 获取当前时间
**工具**: `get_current_time`
**目的**: 锁定MCP异常时间范围

### 步骤2: 查询应用侧MCP调用日志
**工具**: `query_logs`
**参数要求**:
- **地域**: `ap-guangzhou`
- **日志主题**: `application-logs`
- **时间范围**: 最近20分钟
- **查询条件**: `MCP OR tool call OR streamable-http OR connection error`

### 步骤3: 查询MCP服务本身日志
**工具**: `query_logs`
**参数要求**:
- **地域**: `ap-guangzhou`
- **日志主题**: `system-events`
- **时间范围**: 最近30分钟
- **查询条件**: `cls_server OR monitor_server OR port:8003 OR port:8004`

### 步骤4: 判断受影响能力
重点确认：
- 是CLS日志查询不可用，还是Monitor指标查询不可用
- 基础聊天能力是否正常
- 诊断报告是否已降级为仅本地知识库分析

## 常见原因分析

### 原因1: MCP进程退出
**特征**:
- 端口8003或8004不再监听
- 调用直接报连接失败
- 服务日志停在某个异常堆栈

**处理方案**:
1. 重启对应MCP服务
2. 检查崩溃前最后一段日志
3. 修复启动参数或依赖问题
4. 验证 `/mcp` 路径可访问

### 原因2: 工具后端依赖异常
**特征**:
- MCP服务仍在运行，但工具调用失败
- 某一类查询全部超时或报错
- 只影响日志或只影响监控能力

**处理方案**:
1. 检查MCP后端数据源状态
2. 修复日志平台或监控平台连通性
3. 增加超时和降级保护
4. 重试关键工具调用

### 原因3: 配置错误
**特征**:
- 最近修改过 `MCP_CLS_URL` 或 `MCP_MONITOR_URL`
- 只有部分环境失败
- 启动成功但请求地址错误

**处理方案**:
1. 核对环境变量和端口配置
2. 检查传输方式是否匹配
3. 回滚错误配置
4. 重启服务重新加载配置

### 原因4: 高并发导致服务超时
**特征**:
- 诊断高峰期工具调用变慢
- 部分请求成功，部分超时
- CPU或线程资源出现瓶颈

**处理方案**:
1. 限制并发诊断请求
2. 增加MCP服务实例或资源
3. 优化工具实现和超时阈值
4. 对非关键查询启用缓存

## 紧急处理措施

### 立即操作（5分钟内）
1. 恢复CLS和Monitor MCP服务
2. 对外说明AIOps能力可能降级
3. 对紧急故障改为人工辅助排查

### 短期措施（30分钟内）
1. 修复配置或后端依赖问题
2. 验证关键工具调用恢复
3. 抽样测试日志查询和指标查询
4. 补充失败重试和熔断机制

### 长期优化
1. 为MCP服务增加可用性监控
2. 建立工具成功率和时延指标
3. 区分CLS与Monitor的单独告警
4. 建立诊断降级和人工接管流程

## 验证步骤
1. 确认8003和8004服务恢复访问
2. 验证日志查询和指标查询成功
3. 运行一次AIOps诊断确认结果完整
4. 观察30分钟无新增MCP调用失败

## 相关告警
- `ServiceUnavailable`: 服务不可用
- `HighAPILatency`: API延迟过高
- `DependencyCallTimeout`: 依赖调用超时
