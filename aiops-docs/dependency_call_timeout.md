# 依赖调用超时告警处理方案

## 告警名称
- **告警名**: `DependencyCallTimeout`
- **告警级别**: 严重
- **触发条件**: 下游依赖调用超时率连续5分钟超过10%

## 问题描述
当依赖调用频繁超时时，可能导致：
- 接口响应整体变慢
- 线程、连接和队列资源被占满
- 聊天、检索、上传或诊断流程中断
- 局部故障演变为全站级故障

## 排查步骤

### 步骤1: 获取当前时间
**工具**: `get_current_time`
**目的**: 锁定超时高峰时间段

### 步骤2: 查询应用超时日志
**工具**: `query_logs`
**参数要求**:
- **地域**: `ap-guangzhou`
- **日志主题**: `application-logs`
- **时间范围**: 最近20分钟
- **查询条件**: `timeout OR read timed out OR connect timeout OR request timeout`

### 步骤3: 识别超时依赖
重点确认是否集中在：
- DashScope
- Milvus
- PostgreSQL
- Redis
- MCP工具服务

### 步骤4: 分析是否级联
重点确认：
- 是否导致上游接口5xx升高
- 是否触发重试风暴
- 是否与流量高峰同步出现

## 常见原因分析

### 原因1: 下游服务性能下降
**特征**:
- 某个依赖的耗时整体上升
- 请求最终成功但非常慢
- 高峰期更明显

**处理方案**:
1. 恢复下游服务性能
2. 暂时降低调用并发
3. 对慢依赖启用降级
4. 优化超时和重试参数

### 原因2: 网络抖动
**特征**:
- 不同实例表现不一致
- 同时出现连接超时和读超时
- 跨机房依赖更容易失败

**处理方案**:
1. 检查网络质量和DNS
2. 对比不同节点访问情况
3. 必要时切换网络路径或备节点
4. 缩短不必要的重试链路

### 原因3: 重试策略不合理
**特征**:
- 少量下游变慢引发大面积堆积
- 超时后继续高频重试
- 应用整体吞吐迅速下降

**处理方案**:
1. 降低重试次数
2. 增加指数退避
3. 为关键依赖启用熔断
4. 控制并发，避免故障放大

### 原因4: 线程池或连接池耗尽
**特征**:
- 上游等待时间很长
- 请求尚未真正发出就超时
- 高并发接口影响更大

**处理方案**:
1. 检查连接池和线程池占用
2. 释放异常卡住的请求
3. 优化池大小和超时配置
4. 拆分高成本操作到异步链路

## 紧急处理措施

### 立即操作（5分钟内）
1. 识别最慢的依赖并优先处理
2. 启用熔断、限流或降级
3. 暂停非核心批量任务

### 短期措施（30分钟内）
1. 修复下游性能或网络问题
2. 调整超时与重试参数
3. 观察接口RT和错误率联动变化
4. 防止重试风暴再次出现

### 长期优化
1. 为各依赖建立独立超时监控
2. 统一超时、重试和熔断规范
3. 建立异步化和削峰策略
4. 为关键路径设计降级能力

## 验证步骤
1. 确认依赖超时率恢复正常
2. 验证上游接口RT下降
3. 检查5xx和线程堆积同步缓解
4. 观察30分钟无明显反复

## 相关告警
- `HighAPILatency`: API延迟过高
- `API5xxSpike`: API 5xx激增
- `ServiceUnavailable`: 服务不可用
