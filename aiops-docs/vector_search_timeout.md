# 向量检索超时告警处理方案

## 告警名称
- **告警名**: `VectorSearchTimeout`
- **告警级别**: 严重
- **触发条件**: 向量检索请求平均耗时连续5分钟超过3秒，或超时率超过10%

## 问题描述
当向量检索超时时，可能导致：
- RAG问答响应明显变慢
- AIOps诊断无法及时召回相关案例
- 用户感知为“回答很慢”或“无结果”
- 上游接口线程被长期占用

## 排查步骤

### 步骤1: 获取当前时间
**工具**: `get_current_time`
**目的**: 锁定性能劣化时间区间

### 步骤2: 查询应用检索日志
**工具**: `query_logs`
**参数要求**:
- **地域**: `ap-guangzhou`
- **日志主题**: `application-logs`
- **时间范围**: 最近20分钟
- **查询条件**: `vector search OR retrieval OR timeout OR Milvus`

### 步骤3: 查询Milvus和系统性能日志
**工具**: `query_logs`
**参数要求**:
- **地域**: `ap-guangzhou`
- **日志主题**: `system-metrics`
- **时间范围**: 最近30分钟
- **查询条件**: `milvus OR cpu_usage:>80 OR memory_usage:>85 OR disk_io`

### 步骤4: 确认影响范围
重点确认：
- 所有检索都慢，还是特定query慢
- 仅Milvus慢，还是应用整体慢
- 是否与文档量突增或重建索引时间重叠

## 常见原因分析

### 原因1: Milvus负载过高
**特征**:
- 检索和写入都变慢
- CPU、内存、IO明显升高
- 高峰期更明显

**处理方案**:
1. 暂停非必要批量写入
2. 降低检索并发
3. 扩容Milvus资源
4. 优化索引参数和collection加载策略

### 原因2: 文档规模快速增长
**特征**:
- 最近新增大量文档
- 检索范围扩大后耗时上升
- 重建索引后性能变化明显

**处理方案**:
1. 评估分库分collection策略
2. 优化召回TopK和过滤条件
3. 清理无效或重复文档
4. 对大规模知识库做分层检索

### 原因3: 应用侧超时配置过短
**特征**:
- 实际检索完成，但应用提前超时
- 小流量时也偶发报错
- 与网络抖动同时出现

**处理方案**:
1. 核对Milvus客户端超时配置
2. 区分连接超时和查询超时
3. 适当调大阈值并补充重试
4. 记录超时请求样本

### 原因4: 查询改写或召回策略不合理
**特征**:
- 特定问题更容易超时
- query变得过长或召回范围过大
- 检索命中率不高但耗时很高

**处理方案**:
1. 优化query重写逻辑
2. 收紧召回数量和过滤条件
3. 避免无界检索
4. 对热点问题增加缓存

## 紧急处理措施

### 立即操作（5分钟内）
1. 暂停批量索引任务
2. 降低检索并发和TopK
3. 对前台提示知识检索可能变慢

### 短期措施（30分钟内）
1. 定位慢检索时间段和请求样本
2. 修复Milvus资源或配置问题
3. 优化过滤条件和召回策略
4. 观察检索耗时是否恢复

### 长期优化
1. 建立检索耗时和命中率监控
2. 规划知识库容量和分层索引策略
3. 为大规模导入设置隔离窗口
4. 为热点问题建立缓存和预热机制

## 验证步骤
1. 确认检索平均耗时恢复正常
2. 验证RAG问答返回速度改善
3. 检查超时率降到正常水平
4. 观察30分钟无再次性能抖动

## 相关告警
- `MilvusUnavailable`: Milvus不可用
- `HighAPILatency`: API延迟过高
- `SlowResponse`: 响应时间过长
