# API延迟过高告警处理方案

## 告警名称
- **告警名**: `HighAPILatency`
- **告警级别**: 严重
- **触发条件**: API P95响应时间连续5分钟超过3秒，或较基线升高2倍以上

## 问题描述
当API延迟过高时，可能导致：
- 用户感知服务卡顿
- SSE流式对话启动变慢
- 上传和诊断流程等待时间过长
- 上游重试进一步增加系统压力

## 排查步骤

### 步骤1: 获取当前时间
**工具**: `get_current_time`
**目的**: 锁定性能下降时间区间

### 步骤2: 查询接口访问日志
**工具**: `query_logs`
**参数要求**:
- **地域**: `ap-guangzhou`
- **日志主题**: `application-logs`
- **时间范围**: 最近20分钟
- **查询条件**: `latency OR duration OR slow request OR response time`

### 步骤3: 识别慢接口
重点关注：
- `/api/chat_stream`
- `/api/aiops`
- `/api/upload`
- `/api/documents`

### 步骤4: 关联依赖和资源指标
**工具**: `query_logs`
**参数要求**:
- **地域**: `ap-guangzhou`
- **日志主题**: `system-metrics`
- **时间范围**: 同上
- **查询条件**: `cpu_usage OR memory_usage OR disk_io OR network`

## 常见原因分析

### 原因1: 下游依赖变慢
**特征**:
- 接口耗时增加与依赖超时一致
- 错误率不一定升高，但用户明显变慢
- 聊天、检索和诊断都可能受影响

**处理方案**:
1. 优先定位最慢依赖
2. 对慢依赖启用降级
3. 缩短同步等待链路
4. 优化超时和缓存策略

### 原因2: CPU或内存资源紧张
**特征**:
- 高峰期延迟明显增加
- 应用实例资源接近上限
- GC、上下文切换或排队时间变长

**处理方案**:
1. 扩容实例
2. 限制高成本请求并发
3. 优化热点路径性能
4. 分离批处理和在线请求

### 原因3: 向量检索或模型调用耗时过长
**特征**:
- RAG、AIOps相关接口更慢
- 普通静态接口基本正常
- 复杂问题比简单问题慢很多

**处理方案**:
1. 优化召回和Prompt长度
2. 缓存热点问题结果
3. 对复杂请求设置分级处理
4. 为模型和检索链路单独限流

### 原因4: 批量任务挤占在线资源
**特征**:
- 上传大量文档或重建索引时RT升高
- RQ Worker、Milvus和API资源相互争抢
- 延迟波动明显但不一定报错

**处理方案**:
1. 错峰执行批量索引任务
2. 隔离在线与离线资源
3. 控制批量任务速率
4. 建立资源优先级

## 紧急处理措施

### 立即操作（5分钟内）
1. 限制高成本接口流量
2. 暂停批量索引或重建任务
3. 扩容在线实例

### 短期措施（30分钟内）
1. 识别最慢接口和依赖
2. 修复资源瓶颈或慢链路
3. 调整缓存、限流和超时配置
4. 验证P95响应时间改善

### 长期优化
1. 建立按接口和按链路的性能监控
2. 对RAG和AIOps链路做独立容量规划
3. 为批量任务建立隔离机制
4. 定期做性能压测和基线回归

## 验证步骤
1. 确认P95响应时间恢复正常
2. 验证核心接口体验恢复
3. 检查错误率未继续升高
4. 观察30分钟性能稳定
