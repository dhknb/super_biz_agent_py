# API 5xx激增告警处理方案

## 告警名称
- **告警名**: `API5xxSpike`
- **告警级别**: 紧急
- **触发条件**: API 5xx错误率连续5分钟超过10%，或短时间突增3倍以上

## 问题描述
当API 5xx错误激增时，可能导致：
- 用户请求大面积失败
- 聊天、上传、诊断等核心功能不可用
- 上游调用方重试放大故障
- 客诉和业务影响快速扩大

## 排查步骤

### 步骤1: 获取当前时间
**工具**: `get_current_time`
**目的**: 记录错误高峰时间

### 步骤2: 查询应用错误日志
**工具**: `query_logs`
**参数要求**:
- **地域**: `ap-guangzhou`
- **日志主题**: `application-logs`
- **时间范围**: 最近15分钟
- **查询条件**: `status:500 OR status:502 OR status:503 OR traceback`

### 步骤3: 按接口分类统计
重点关注：
- `/api/chat`
- `/api/aiops`
- `/api/upload`
- `/api/documents`

### 步骤4: 关联依赖异常
**工具**: `query_logs`
**参数要求**:
- **地域**: `ap-guangzhou`
- **日志主题**: `application-logs`
- **时间范围**: 同上
- **查询条件**: `Redis OR PostgreSQL OR Milvus OR DashScope OR MCP`

## 常见原因分析

### 原因1: 核心依赖故障
**特征**:
- 错误集中出现在某类接口
- 与数据库、Redis、Milvus等告警时间重叠
- 错误堆栈指向下游依赖

**处理方案**:
1. 先恢复关键依赖
2. 对受影响接口启用降级
3. 限制重试放大
4. 验证核心接口恢复

### 原因2: 新版本发布问题
**特征**:
- 发布后立刻出现
- 错误集中在新改动路径
- 回滚前版本可恢复

**处理方案**:
1. 立即回滚到稳定版本
2. 保留错误样本和请求参数
3. 排查配置或代码差异
4. 修复后再灰度发布

### 原因3: 请求流量突增
**特征**:
- 5xx伴随延迟上升
- 资源接近上限
- 重试流量进一步推高错误率

**处理方案**:
1. 扩容应用实例
2. 启用限流和熔断
3. 对高成本接口做降级
4. 持续观察错误率走势

### 原因4: 参数或数据异常
**特征**:
- 仅部分请求失败
- 特定文件、特定prompt或特定session更容易出错
- 业务日志中有明确输入异常

**处理方案**:
1. 快速定位异常输入模式
2. 增加参数校验和兜底处理
3. 拒绝危险请求或返回明确错误
4. 修复后回放样本验证

## 紧急处理措施

### 立即操作（5分钟内）
1. 判断是否需要回滚
2. 恢复关键依赖并限流
3. 优先保障核心接口可用

### 短期措施（30分钟内）
1. 识别错误最集中的接口
2. 修复依赖、配置或发布问题
3. 对异常请求模式加保护
4. 逐步恢复全部流量

### 长期优化
1. 建立按接口维度的5xx监控
2. 为关键依赖增加熔断降级
3. 完善发布前回归与灰度机制
4. 建立错误样本自动归档和复盘机制

## 验证步骤
1. 确认5xx错误率恢复到1%以下
2. 验证核心接口功能正常
3. 观察响应时间同步恢复
4. 监控30分钟无再次尖峰

## 相关告警
- `ServiceUnavailable`: 服务不可用
- `HighAPILatency`: API延迟过高
- `DependencyCallTimeout`: 依赖调用超时
