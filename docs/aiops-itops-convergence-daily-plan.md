# AIOps 向 ITOps Agent Platform 靠拢的每日执行计划

> 目标：基于当前 `super_biz_agent_py` 已有的 FastAPI、LangGraph、RAG、MCP 和告警首响能力，分阶段做成一个可演示、可扩展、可审计的 AIOps 运维智能体平台。
>
> 参考方向来自 ITOps Agent Platform 的真实产品形态：告警接入、AI 诊断、SOP/知识库检索、工具调用、人工审批、命令执行、结果验证、报告沉淀。

## 当前项目定位

当前项目不建议一开始照搬完整 ITOps 平台。更合理的路线是先把“告警首响分析助手”做扎实，再逐步扩展为“可审批的运维动作平台”。

现有优势：

- 已有 `app/api/aiops.py`、`app/services/aiops_service.py` 和 `app/agent/aiops/`，具备 LangGraph 规划、执行、重规划的基础。
- 已有 RAG v2、知识库、Milvus、文档解析链路，适合做 SOP、故障案例、巡检手册检索。
- 已有 MCP 客户端和 `mcp_servers/` 示例，适合向工具平台方向演进。
- 已有对话追踪、会话、消息、知识库等数据模型，可以复用为诊断任务、执行记录和审计记录的基础。

当前短板：

- 告警还没有形成标准化接入、归一化、任务化和状态流转。
- 诊断报告还需要结构化，不能只停留在模型自然语言输出。
- MCP 工具缺少统一注册、权限、风险等级、审批和审计。
- 自动修复不能贸然做，应先做“建议 -> 人工审批 -> 受控执行 -> 验证”的闭环。
- 前端工作台还需要面向 AIOps 场景重组，而不是只作为通用聊天入口。

## 30 天节奏总览

- 第 1-7 天：打牢告警首响 MVP，把一次告警变成一次可追踪诊断任务。
- 第 8-14 天：补齐告警接入、任务中心、结构化报告和前端工作台。
- 第 15-21 天：建设 MCP 工具治理、人工审批、工作流模板和审计能力。
- 第 22-30 天：做受控修复闭环、验证反馈、演示场景和项目包装。

## 每日任务

### Day 1：现状盘点与边界冻结

目标：明确第一版只做“告警首响 + 建议修复”，不直接生产自动修复。

要做：

- 梳理 `app/api/aiops.py`、`app/services/aiops_service.py`、`app/agent/aiops/` 的现有调用链。
- 梳理 `app/models/aiops.py` 里的告警模型是否足够表达来源、等级、主机、服务、指标、时间、原始 payload。
- 把 `docs/product-direction-aiops-first-response.md` 更新为唯一产品边界文档。
- 明确第一阶段验收口径：输入一条告警，输出证据、根因假设、处置建议、风险说明、下一步检查项。

验收：

- 文档能讲清楚当前版本做什么、不做什么。
- 能画出 `API -> Service -> Planner -> Executor -> Replanner -> Response` 的链路。

### Day 2：统一告警事件模型

目标：让所有后续能力围绕标准 `AlarmEvent` 工作。

要做：

- 检查并完善 `app/models/aiops.py`，统一告警字段命名。
- 增加 `alert_id`、`source`、`severity`、`resource_type`、`resource_id`、`metric_name`、`metric_value`、`labels`、`raw_payload`。
- 为常见来源预留适配空间：Prometheus、Zabbix、云监控、手工录入。
- 补充 Pydantic 校验和最小单元测试。

验收：

- 一条 Prometheus 风格告警和一条 Zabbix 风格告警都能归一化为同一模型。
- 模型测试通过。

### Day 3：告警诊断任务化

目标：把一次诊断从“接口返回”升级为“可追踪任务”。

要做：

- 设计 `aiops_incident` 或 `aiops_diagnosis_task` 数据表。
- 字段至少包含：任务 ID、告警 ID、状态、严重等级、当前阶段、诊断摘要、创建时间、更新时间。
- 在 `AIOpsService.diagnose()` 中生成任务 ID。
- 复用现有 trace/repository 能力记录每一步事件。

验收：

- 每次诊断都有唯一任务 ID。
- 能查询任务状态和诊断历史。

### Day 4：首响 Prompt 结构化

目标：让模型输出稳定结构，而不是散文式诊断。

要做：

- 调整 `app/agent/aiops/planner.py` 和相关 prompt。
- 输出结构固定为：告警理解、影响范围、需要收集的证据、工具调用计划、风险等级。
- 要求模型不要直接给高风险命令，只能给检查命令和建议。
- 为 planner 增加失败兜底：如果信息不足，返回需要补充的字段。

验收：

- 同一类告警多次执行，输出结构稳定。
- 缺少主机或服务信息时，不胡编主机信息。

### Day 5：证据采集最小闭环

目标：诊断报告必须有证据来源。

要做：

- 整理现有 MCP 工具：监控查询、日志查询、CLS 查询等。
- 为每个工具返回结果增加标准包装：工具名、输入参数、输出摘要、错误信息、耗时。
- 在 executor 中把工具调用结果沉淀到诊断上下文。
- 报告中明确区分“已验证事实”和“模型推断”。

验收：

- 至少能完成一次“告警 -> 工具查询 -> 证据摘要 -> 诊断结论”的闭环。
- 报告里可以看到证据来自哪个工具。

### Day 6：SOP/RAG 检索接入诊断

目标：让诊断不只依赖模型常识，而能检索项目知识库。

要做：

- 选定 3-5 篇运维 SOP 或故障案例导入知识库。
- 在 planner 或 service 层根据告警标签检索 SOP。
- 把检索结果作为诊断上下文传给模型。
- 报告中增加“参考 SOP/知识片段”。

验收：

- 对 Nginx、CPU、磁盘、服务不可用等常见告警能命中对应 SOP。
- 报告能引用知识库来源标题。

### Day 7：第一周演示与回归

目标：形成第一个可演示 MVP。

要做：

- 准备 3 条样例告警：CPU 高、磁盘满、服务不可用。
- 写集成测试覆盖 `/api/aiops` 诊断入口。
- 记录第一周演示脚本到 docs。
- 修复明显不稳定的输出和异常处理。

验收：

- 三条样例告警都能输出结构化首响报告。
- 测试可以稳定跑通。

### Day 8：告警接入 API

目标：让外部系统可以推送告警。

要做：

- 新增通用 webhook：`POST /api/aiops/alerts`。
- 支持手工 JSON、Prometheus Alertmanager 风格 payload、Zabbix 风格 payload。
- 入库原始 payload 和归一化后的 `AlarmEvent`。
- 返回告警 ID 和诊断任务 ID。

验收：

- 用 curl 可以提交三种格式告警。
- 重复告警能根据 fingerprint 或 labels 做基础去重。

### Day 9：告警列表与详情接口

目标：建设告警中心的后端基础。

要做：

- 新增告警列表查询、详情查询、状态更新接口。
- 支持按严重等级、来源、状态、时间范围筛选。
- 告警详情返回关联诊断任务、证据、报告。
- 定义状态流转：new、diagnosing、diagnosed、acknowledged、resolved、ignored。

验收：

- 可以查询最近告警列表。
- 单条告警能看到完整诊断上下文。

### Day 10：前端告警中心雏形

目标：把 AIOps 从聊天体验拉到运维工作台体验。

要做：

- 在现有 `static/` 或前端入口中增加“告警中心”页面。
- 展示告警列表、等级、状态、来源、创建时间。
- 点击告警进入详情页。
- 详情页展示首响报告、证据列表、建议动作。

验收：

- 不通过聊天，也能从告警中心完成一次诊断查看。
- 页面可以支撑演示。

### Day 11：诊断报告模板

目标：固定报告格式，方便后续审计和导出。

要做：

- 定义报告 JSON schema。
- 字段包含：summary、severity_assessment、evidence、root_cause_hypotheses、recommended_actions、risk_notes、next_checks。
- 模型输出后做解析和校验。
- 校验失败时自动降级为纯文本报告并记录错误。

验收：

- 报告既能给人看，也能被程序读取。
- 前端不再依赖解析大段自然语言。

### Day 12：诊断过程可观测

目标：让用户知道 AI 正在做什么。

要做：

- 为诊断阶段增加事件：planning、retrieving_knowledge、calling_tool、reasoning、reporting、done、failed。
- 支持接口或 SSE/WebSocket 返回阶段进度。
- 前端详情页显示时间线。
- 异常时展示失败阶段和错误摘要。

验收：

- 用户能看到一次诊断的完整时间线。
- 工具失败不会导致整条链路不可读。

### Day 13：评测样例集

目标：建立后续迭代的质量基线。

要做：

- 建立 `tests/fixtures/aiops_alerts/` 样例集。
- 每个样例包含告警 payload、期望命中的 SOP、期望报告要点。
- 编写自动评测脚本，检查结构字段和关键要点。
- 标记当前通过率。

验收：

- 至少 10 个告警样例。
- 每次改 prompt 或工具链都能跑评测。

### Day 14：第二周演示与产品复盘

目标：完成“告警中心 + 首响报告”的产品闭环。

要做：

- 准备演示脚本：外部告警推送 -> 告警中心 -> 自动诊断 -> 报告查看。
- 补齐 README 中 AIOps 部分的运行方式。
- 记录第二周问题清单和第三周范围。
- 删除或隐藏不稳定入口。

验收：

- 产品演示不依赖手动改数据库。
- 新用户能按 README 跑起最小链路。

### Day 15：MCP 工具注册表

目标：向 ITOps 的工具平台靠拢。

要做：

- 设计工具注册结构：tool_name、description、input_schema、risk_level、category、enabled。
- 把现有 MCP 工具纳入统一注册表。
- API 返回可用工具列表。
- planner 只允许选择注册表中的工具。

验收：

- 能查看系统当前有哪些可用工具。
- 未注册工具不能被 planner 调用。

### Day 16：工具风险分级

目标：为后续审批和执行打基础。

要做：

- 定义风险等级：read_only、safe_check、change_low、change_high、destructive。
- 给每个 MCP 工具标记风险等级。
- 默认只允许自动执行 read_only 和 safe_check。
- change 类工具必须进入建议或审批流程。

验收：

- AI 不能自动执行高风险命令。
- 高风险建议会被明确标红或进入审批状态。

### Day 17：建议动作模型

目标：把“修复建议”从文本变成结构化动作。

要做：

- 新增 `recommended_action` 数据结构。
- 字段包含：action_id、title、description、command_or_tool、risk_level、requires_approval、expected_result、rollback_hint。
- 报告中输出建议动作列表。
- 前端展示每个动作的风险和审批状态。

验收：

- 同一份报告中可以有多个建议动作。
- 每个动作都能说明为什么建议执行。

### Day 18：人工审批 MVP

目标：建立 HITL，人来决定是否执行。

要做：

- 新增审批记录表：approval_id、action_id、status、requested_by、approved_by、reason、created_at、updated_at。
- 新增创建审批、批准、拒绝接口。
- 前端增加批准/拒绝按钮。
- 审批操作写入审计记录。

验收：

- 高风险动作必须审批后才能进入执行阶段。
- 拒绝动作不会被执行。

### Day 19：受控执行接口

目标：只执行被审批的动作，并记录全过程。

要做：

- 增加 `execute_action` 服务方法。
- 执行前检查审批状态、风险等级、工具白名单。
- 执行时记录输入、输出、退出状态、耗时。
- 执行失败时返回可读错误，不继续链式执行。

验收：

- 未审批动作无法执行。
- 已审批的低风险测试动作可以完成执行并记录结果。

### Day 20：工作流模板 Lite

目标：从单步建议扩展到多步运维流程。

要做：

- 定义简单工作流模板：name、trigger、steps、approval_policy、verification_steps。
- 先内置 3 个模板：CPU 高排查、磁盘满排查、服务不可用排查。
- 每个模板只包含检查步骤和建议步骤，不做危险自动变更。
- planner 能根据告警类型推荐模板。

验收：

- 一条 CPU 告警能匹配 CPU 排查模板。
- 工作流步骤可以逐步展示。

### Day 21：第三周演示与安全复盘

目标：完成“工具治理 + 审批 + 受控执行”闭环。

要做：

- 演示：告警诊断 -> 推荐动作 -> 创建审批 -> 批准 -> 执行测试命令 -> 查看审计。
- 检查所有执行入口是否都有风险检查。
- 补充工具风险等级文档。
- 整理第四周受控修复范围。

验收：

- 系统具备最小 HITL 能力。
- 审计记录能回答“谁在什么时候批准并执行了什么”。

### Day 22：验证步骤模型

目标：执行后必须验证是否真的恢复。

要做：

- 新增 verification step：检查命令、指标查询、日志查询、服务状态检查。
- 每个 recommended action 绑定 expected_result 和 verification_steps。
- 执行后自动运行 read_only 验证步骤。
- 报告中展示验证结果。

验收：

- 执行动作后能看到“验证通过/失败/不确定”。
- 验证失败不会被标记为已恢复。

### Day 23：回滚提示与失败处理

目标：让修复链路可控。

要做：

- 每个 change 类动作必须包含 rollback_hint。
- 执行失败时生成失败报告。
- 不自动执行回滚，只生成回滚建议和审批单。
- 前端明确展示失败原因和下一步建议。

验收：

- 失败链路不会静默吞掉错误。
- 高风险回滚仍然需要人工审批。

### Day 24：知识反馈闭环

目标：把每次处理沉淀成案例。

要做：

- 诊断完成后生成“故障案例草稿”。
- 字段包含：现象、影响、证据、根因、处理动作、验证结果、复盘建议。
- 支持人工确认后写入知识库或导出 Markdown。
- 后续同类告警能检索到该案例。

验收：

- 一次处理完成后能生成案例草稿。
- 案例入库后能被 RAG 命中。

### Day 25：多 Agent 角色雏形

目标：向 ITOps 的多 Agent 产品形态靠拢，但保持实现简单。

要做：

- 先定义 4 个逻辑角色：告警分诊 Agent、证据采集 Agent、SOP 匹配 Agent、修复建议 Agent。
- 不急着做复杂多 Agent 框架，可以先用不同 prompt/function 拆分职责。
- 每个角色输出结构化结果。
- 报告中展示各角色贡献。

验收：

- 一次诊断能看出分诊、采集、匹配、建议四个阶段。
- 各阶段失败可以单独定位。

### Day 26：场景化演示数据

目标：准备一个完整业务级 Demo。

要做：

- 构造一个“服务不可用”场景：告警、指标、日志、SOP、建议动作、验证结果。
- 构造一个“磁盘空间不足”场景。
- 构造一个“CPU 持续高负载”场景。
- 所有数据都可以本地复现，不依赖真实生产系统。

验收：

- 三个场景可以连续演示。
- 每个场景都覆盖告警、诊断、建议、审批、执行、验证、报告。

### Day 27：前端体验打磨

目标：把演示体验做成“平台感”。

要做：

- 首页增加 AIOps 总览：今日告警、待审批、处理中、已恢复。
- 告警详情页增强时间线、证据卡片、建议动作卡片。
- 审批页展示风险等级、执行内容、回滚提示。
- 报告页支持复制或导出 Markdown。

验收：

- 用户不用看日志也能理解系统在做什么。
- 演示路径清晰：总览 -> 告警 -> 诊断 -> 审批 -> 验证 -> 报告。

### Day 28：端到端测试与稳定性

目标：减少演示和后续开发的不确定性。

要做：

- 写端到端测试覆盖核心闭环。
- 增加异常测试：工具超时、模型失败、知识库无结果、审批拒绝、执行失败。
- 检查数据库迁移和初始化脚本。
- 修复所有阻断演示的问题。

验收：

- 核心链路测试稳定通过。
- 异常场景有可读错误和状态回落。

### Day 29：文档与部署整理

目标：让项目看起来像一个完整产品，而不是实验代码。

要做：

- 更新 README 的 AIOps 平台介绍、架构图、运行步骤。
- 增加 `docs/aiops-demo-guide.md`。
- 整理 `.env.example` 中模型、Milvus、MCP、数据库配置。
- 检查 Docker 或本地启动脚本是否可用。

验收：

- 新用户能按文档跑起 Demo。
- 文档能解释本项目和 ITOps Agent Platform 的差异与演进方向。

### Day 30：里程碑验收与下一阶段规划

目标：完成第一个可展示的 AIOps 平台版本。

要做：

- 录制或准备完整演示流程。
- 对照本计划检查完成度。
- 列出下一阶段能力：资产管理、拓扑、巡检、变更管理、通知集成、更多监控源。
- 决定哪些功能进入 v0.2，哪些暂缓。

验收：

- 可以完整展示：告警接入 -> AI 诊断 -> SOP 检索 -> 工具证据 -> 建议动作 -> 人工审批 -> 受控执行 -> 验证 -> 报告沉淀。
- 项目有清晰下一步路线。

## 每周里程碑

### Week 1：告警首响 MVP

交付物：标准告警模型、诊断任务、结构化报告、SOP 检索、三个样例告警。

成功标准：输入告警后，系统能自动给出有证据的首响分析报告。

### Week 2：告警中心与报告工作台

交付物：告警 webhook、告警列表、详情页、诊断时间线、评测样例集。

成功标准：系统具备运维工作台雏形，不再只是聊天机器人。

### Week 3：工具治理与人工审批

交付物：MCP 工具注册表、风险分级、建议动作、审批记录、受控执行。

成功标准：系统能安全地从“建议”走到“人工批准后的执行”。

### Week 4：受控修复闭环与产品包装

交付物：验证步骤、失败处理、知识反馈、多 Agent 角色雏形、演示场景、部署文档。

成功标准：系统接近真实 AIOps 产品闭环，并能稳定演示。

## 建议优先级

必须先做：

- 标准告警模型。
- 诊断任务和状态流转。
- 结构化报告。
- RAG/SOP 证据接入。
- 工具调用记录。
- HITL 审批。

暂时不要急着做：

- 复杂 CMDB。
- 复杂网络拓扑。
- 完全自动修复。
- 多租户和细粒度 RBAC。
- 大而全的 Kubernetes、Docker、vCenter 管理平台。

原因：当前项目最有价值的切入点是“AI 首响 + 证据化诊断 + 审批式处置”。先把这个闭环做实，后面再扩展资产、巡检、变更、通知和更多工具集成。

## 每天固定工作习惯

- 开始前先跑相关测试，确认基线没有坏。
- 每天只推进一个清晰主题，不同时开太多分支。
- 每个功能都要有最小验收样例。
- 所有 AI 输出都尽量结构化，失败时要可降级。
- 所有工具调用都要记录输入、输出、耗时和错误。
- 所有可能改变系统状态的动作都必须先走审批。
- 每天结束更新当天完成情况、遗留问题和第二天第一件事。
