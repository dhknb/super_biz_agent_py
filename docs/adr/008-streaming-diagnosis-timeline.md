# ADR-008: 诊断过程可观测（SSE 流式时间线）

- 状态: 已接受
- 日期: 2026-07-23
- 关联: [[007]]、ADR-005（编排层）

## 背景

Day6 的  是同步接口：调用方 POST 一条告警后要一直等到
整条链路（归一化→建任务→检索→LLM→存报告）跑完才拿到结果。首响分析里
LLM 调用可能耗时数秒到数十秒，用户全程看不到进展，体验差，也不符合
产品方向文档「让用户看得见 AI 在做什么」的诉求。

## 决策

给编排器加一个流式变体 ，并新增 SSE 端点
：

1.  是异步生成器，在每个阶段 yield 一个事件：
   （或 ）。
2. 落库逻辑与  完全一致（同样的状态流转 + 事件留痕），
   只是额外把每步 yield 出去，做到「数据库留痕」与「实时推送」双写。
3. SSE 端点复用 aiops.py 已有的  范式
   （），收到
    或  事件即结束流。
4. 任何异常都 yield 一个  事件并把任务落到 FAILED，
   绝不让流无声中断（对齐「AI 输出必须可降级」纪律）。

## 备选方案

- **只靠轮询 GET /aiops/tasks/{id}**：前端定时查状态。实现简单，但延迟高、
  多余请求多，且拿不到「正在做什么」的细粒度阶段。保留它作为兜底查询，
  但不作为主要的进度反馈手段。
- **WebSocket**：双向通道，能力更强。但首响只需服务端单向推送，
  SSE 更轻、更贴合，且项目已有 SSE 范式，无需引入新依赖。

## 后果

正面：
- 用户能看到完整诊断时间线，体验从「干等」变成「实时可观测」。
- 复用既有 SSE 范式，零新依赖； 与  共享落库逻辑，无重复。
- 演示效果好（Day10 demo 直接用它讲故事）。

负面 / 代价：
-  与  有一部分结构相似的落库代码（可接受的重复，
  两者语义不同：一个返回值、一个流式，强行抽公共层反而更绕）。
- SSE 端点未做鉴权（与现有  一致），生产环境需补认证 —— 已在
  ADR-000 的「非目标」里明确留到后续。
