# ADR-003：结构化首响报告 schema 与「永不崩溃」的降级策略

- 状态：已接受
- 日期：2026-07-23
- 关联：[[002]]、[[000]]、产品方向文档 5.3 节

## 背景

现有 `/api/aiops` 的做法（见 `app/services/aiops_service.py` 的 `diagnose()`）是：
往 LLM 的 prompt 里塞一大段 Markdown 模板，明令「最终输出必须是纯 Markdown 文本，
不要包含 JSON 结构」。

这套做法有三个问题：

1. **前端 / 程序无法读取。** 报告是一大段自然语言，前端只能整块渲染，
   没法把「建议排障顺序」「证据」「待确认项」分区展示，也没法做统计。
2. **无法评测。** Day8 要做 RAG 评估脚本，需要程序化判断「报告是否包含某要点」，
   散文格式让自动评测几乎不可能。
3. **证据无法溯源。** 产品方向文档反复强调「区分已验证事实和模型推断」，
   散文里做不到结构化区分。

## 决策

新增 `app/models/aiops_report.py`，用 Pydantic 定义结构化报告：

- `FirstResponseReport`：报告主体，字段对齐产品方向文档 5.3 节
  （告警摘要 / 当前判断 / 建议排障顺序 / 证据 / 暂定根因 / 待确认项 / 风险升级）。
- `Evidence`：**每条证据带 `type`（verified_fact / model_inference）**，
  这是 Day5 证据溯源的地基。
- `RecommendedCheck`：建议排障项，带 `requires_human` 标记；
  按 ADR-000 边界，只产出检查 / 观察类建议，不产出高风险变更命令。

关键设计——**`parse_report()` 永不抛异常**：

无论模型返回什么（合法 JSON / 代码块包裹的 JSON / 纯文本 / 非法 JSON / 缺字段），
调用方永远拿到一个可用的 `FirstResponseReport`。解析失败时降级为
`is_degraded=True` 的纯文本报告，保留原始输出。这落实了
ADR-000 定的纪律「所有 AI 输出都尽量结构化，失败时要可降级」。

`FirstResponseReport.to_markdown()` 负责把结构化对象渲染回人类可读的 Markdown，
所以「给人看」和「给程序读」两个需求用同一份数据满足。

## 备选方案

1. **继续用纯 Markdown（现状）。** 否决：无法程序读取 / 评测 / 溯源。
2. **用 LangChain 的 `with_structured_output` 强制模型返回 schema。**
   保留将来采用，但**不作为唯一手段**——因为它在模型不配合时会抛异常，
   而我们需要「永不崩溃」的保证。所以先用「宽松解析 + 降级」兜底，
   Day5 接入真实链路时可以叠加 `with_structured_output` 作为第一道，
   `parse_report` 作为第二道防线。
3. **只解析不降级。** 否决：违背「AI 输出必须可降级」纪律。

## 后果

正面：
- 前端可分区渲染，评测脚本可程序化判断要点覆盖。
- 证据「事实 / 推断」区分落地，为 Day5 溯源铺路。
- 解析永不崩溃，诊断链路健壮性大幅提升。
- 17 个单测覆盖 4 种降级路径。

负面 / 代价：
- 报告字段是「我们规定的」，模型需要被 prompt 引导按此结构输出，
  Day5 改造 planner/replanner 时要同步调整 prompt。
- 降级报告对用户价值有限（只是原文回显），但好过整条链路崩掉。
