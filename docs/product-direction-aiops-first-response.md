# 产品方向：告警首响分析助手

## 1. 一句话定位

把当前项目的 AIOps 能力，从“通用智能诊断 Agent”收敛为面向一线值班工程师的“告警首响分析助手”。

当告警触发后，系统自动围绕单个告警事件收集上下文、检索 SOP、查询监控和日志，并生成一份带证据、带引用、可交接的首份排障检查清单。

这个方向的核心价值不是替代通用大模型聊天，而是把通用大模型拿不到、不能稳定串起来的企业内部上下文接起来：

- 告警事件。
- 服务、实例、时间窗、标签等告警元数据。
- 监控指标。
- 日志证据。
- SOP、历史故障文档、协议说明。
- 可审计的分析过程和报告产物。

## 2. 目标用户

第一阶段只服务一类用户：一线值班 / Oncall 工程师。

他们最直接的痛点是：告警来了以后，不知道第一步先查什么，需要在监控、日志、SOP、历史文档之间来回切换，排障路径容易依赖个人经验。

因此本产品第一阶段不追求“全能运维助手”，只解决一个高频问题：

> 告警触发后，快速给出第一轮排障路径和证据化分析结果。

## 3. 现有项目基础

当前项目已经具备不少底座能力：

- RAG 知识库问答：支持运维文档上传、切分、向量化和检索。
- AIOps 诊断接口：已有 `/api/aiops` 流式诊断入口。
- Plan-Execute-Replan 工作流：已有 Planner、Executor、Replanner 三段式诊断流程。
- MCP 工具接入：已有日志查询和监控数据工具服务。
- Markdown 报告生成：已有结构化诊断报告输出雏形。

这些能力适合继续保留，但产品表达需要改变。

当前表达偏“智能体能诊断问题”，更像技术展示；目标表达应该变成“告警来了，系统自动生成第一份可用排障清单”，更接近业务价值。

## 4. 与现有 AIOps 的关键区别

现有 AIOps 更像通用诊断引擎：

- 输入是一个宽泛任务，例如“诊断当前系统是否存在告警”。
- 计划步骤主要由模型临时生成。
- 结果重点是最终诊断报告。
- 触发方式以用户手动调用 API 为主。

告警首响分析助手应该是产品化场景：

- 输入是明确的 `AlarmEvent`。
- 主流程固定，节点内部允许模型辅助判断。
- 输出重点是“下一步排障检查清单 + 证据 + SOP 引用”。
- 后续支持告警事件自动触发、异步生成、归档和回放。

一句话概括：

> 现有 AIOps 是引擎；告警首响分析助手是第一个可落地产品形态。

## 5. MVP 范围

第一版 MVP 只做“单告警首响分析报告”。

### 5.1 输入

系统接收一个明确的告警事件对象，至少包含：

- `alert_name`：告警名称，例如 `HighCPUUsage`。
- `severity`：告警级别，例如 `warning`、`critical`。
- `service`：受影响服务。
- `instance`：受影响实例。
- `started_at`：首次触发时间。
- `ended_at`：恢复时间，可为空。
- `summary`：告警摘要。
- `labels`：业务标签、环境、集群、地域等扩展信息。

第一版可以先通过 API 手动传入告警事件，不急着接真实告警队列。

### 5.2 处理流程

MVP 推荐使用半固定链路：

```text
AlarmEvent
  -> 标准化告警上下文
  -> 查询同时间窗监控指标
  -> 查询同服务/实例日志
  -> 检索相关 SOP 和历史文档
  -> 汇总证据
  -> 生成排障检查清单
  -> 生成首响分析报告
```

这里的关键设计是：主流程固定，局部节点智能。

也就是说，不再完全依赖模型自由规划“我要先做什么”，而是让系统稳定执行一条企业可审计的排障链路；模型主要负责理解告警、选择查询参数、总结证据、组织报告。

### 5.3 输出

MVP 的核心输出不是“聊天回答”，而是一份可直接交给值班同学使用的 Markdown 报告。

推荐固定结构：

```markdown
# 告警首响分析报告

## 告警摘要

## 当前判断

## 建议排障顺序

## 监控证据

## 日志证据

## 相关 SOP 引用

## 暂定根因

## 待确认项

## 风险与升级建议
```

第一版重点放在“建议排障顺序”，因为用户已经明确选择了“排障检查清单”作为首要结果。

## 6. 非目标

为了避免项目发散，第一版明确不做这些事情：

- 不做全自动修复。
- 不直接执行生产变更。
- 不做多告警根因图谱。
- 不做复杂事故复盘系统。
- 不做完整 ITSM / 工单系统。
- 不做面向所有岗位的通用 AI 助手。

这些能力未来可以接入，但不是第一阶段的核心价值。

## 7. 产品价值判断

这个方向成立的原因是：通用大模型可以回答运维常识，但不能天然完成企业现场的闭环。

通用大模型缺少：

- 当前告警的真实事件数据。
- 当前服务的监控和日志。
- 企业内部 SOP。
- 文档版本和权限边界。
- 证据引用和审计链路。
- 固定报告模板和团队交接习惯。

本项目的价值应该放在这些地方：

- 帮值班同学少切系统。
- 帮新人按统一路径排障。
- 帮团队沉淀 SOP 和排障经验。
- 帮负责人看到告警处理过程是否有证据。
- 把“问 AI”变成“告警触发后自动生成可执行检查清单”。

## 8. 成功指标

MVP 阶段建议先看这些指标：

- 首响报告生成耗时：本地演示目标小于 30 秒。
- SOP 命中率：常见告警能命中至少 1 条相关 SOP。
- 检查清单可用率：人工评估 10 条告警中至少 7 条能指导下一步排查。
- 证据覆盖率：报告中至少包含监控、日志、SOP 三类证据中的两类。
- 幻觉控制：无证据时必须标记为“待确认”，不能给确定性根因。

后续产品化阶段再看：

- 平均排障首响耗时下降。
- 值班人员查询日志和 SOP 的手动操作次数下降。
- 新人处理标准告警的成功率提升。
- 报告被复制、转发、归档的比例。

## 9. 技术演进路线

### Phase 1：告警对象输入

目标：让 AIOps 从“任务 prompt 驱动”变成“告警事件驱动”。

建议动作：

- 新增 `AlarmEvent` 请求模型。
- 新增 `/api/aiops/alerts/analyze` 接口。
- 保留旧 `/api/aiops` 作为演示入口。
- 将固定诊断 prompt 改为基于告警对象构造上下文。

### Phase 2：半固定诊断流程

目标：减少模型自由规划带来的不稳定。

建议动作：

- 新增 `alert_context_node`。
- 新增 `metrics_evidence_node`。
- 新增 `log_evidence_node`。
- 新增 `sop_retrieval_node`。
- 新增 `first_response_report_node`。

当前 Planner / Executor / Replanner 可以暂时保留，但不要让它们承担全部主流程。

### Phase 3：SOP 引证和证据结构化

目标：让报告可信。

建议动作：

- 将 SOP 检索结果结构化为 `sources`。
- 报告中固定展示 SOP 标题、来源、命中片段。
- 每个结论尽量关联证据来源。
- 没有证据时输出“待确认”，不输出确定根因。

### Phase 4：异步任务化

目标：从手动工具变成告警处理流程的一部分。

建议动作：

- 新增分析任务表或轻量任务记录。
- 支持任务状态：`queued`、`running`、`succeeded`、`failed`。
- 支持按 `alert_id` 查询报告。
- 后续再接告警队列或 Webhook。

### Phase 5：质量评测

目标：证明它真的有用。

建议动作：

- 准备 10 条常见告警样例。
- 每条告警准备期望 SOP 和人工排障要点。
- 评估 SOP 命中、检查清单质量、证据覆盖、是否幻觉。
- 把评测结果作为后续优化依据。

## 10. 推荐对外话术

推荐产品名：

- 告警首响分析助手。
- Oncall 告警分析工作台。
- 告警自动排障报告助手。

推荐项目描述：

> 面向一线值班工程师的告警首响分析助手。系统在告警触发后自动关联监控、日志和 SOP，生成带证据引用的排障检查清单，帮助值班人员更快完成第一轮定位和交接。

不推荐继续主打：

- 智能体平台。
- 通用 AIOps Agent。
- 企业级 AI 助手。
- RAG + MCP + LangGraph 技术展示。

这些说法技术味很强，但不够贴近用户痛点。

## 11. 下一步开发建议

下一步不要急着重构全部 AIOps。

建议先做一个最小闭环：

1. 新增告警事件输入模型。
2. 新增单告警分析 API。
3. 在服务层构造固定排障上下文。
4. 复用现有 MCP 工具查询监控和日志。
5. 复用现有知识库工具检索 SOP。
6. 输出固定结构的首响分析报告。

完成这个闭环后，再考虑异步任务、自动触发、报告归档和评测体系。

第一阶段的验收标准很简单：

> 给系统一个 `HighCPUUsage` 告警，它能在一份报告里告诉值班同学：先查什么、为什么查、查到什么证据、参考哪条 SOP、哪些结论还需要人工确认。
