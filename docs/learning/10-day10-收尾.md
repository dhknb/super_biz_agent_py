## 1. 这天要解决什么问题

前 9 天代码都写完了、测试全绿了。但如果现在把仓库丢给别人（面试官、同事、未来的你自己），他会问三个问题：

1. **这东西怎么跑起来？** → 需要「演示指南」
2. **这仓库到底做了啥？** → 需要「README 更新」
3. **为什么这么设计？** → 需要「复盘」

Day10 就是回答这三个问题。代码是给机器执行的，文档是给人读的——**没有文档的代码，等于只完成了一半**。

## 2. 演示指南（demo-guide）：让别人 5 分钟跑起来

打开 `docs/aiops-demo-guide.md`。它的结构是：

```
前置条件（起依赖、跑迁移、灌知识库）
  ↓
演示 1：同步首响分析（一条 curl 拿到完整报告）
  ↓
演示 2：流式分析（SSE 看时间线）
  ↓
演示 3：查任务列表 / 详情
  ↓
设计决策（指向 ADR）
```

### 为什么演示指南要「可复制粘贴」

看这一段：

```bash
curl -X POST "http://localhost:9900/api/aiops/alerts/analyze" \
  -H "Content-Type: application/json" \
  -d '{
    "source": "manual",
    "payload": {
      "alert_name": "HighCPUUsage",
      "severity": "critical",
      "service": "order-api",
      "instance": "10.0.0.12:9100",
      "summary": "CPU 使用率持续超过 90%"
    }
  }'
```

**关键原则：读者不需要思考**。每条命令都能直接复制运行，不用「把 xxx 替换成你的值」。演示的目的是让人 30 秒内看到效果，任何需要动脑的地方都是障碍。

### 前置条件为什么重要

```bash
# 1. 启动依赖
docker compose -f vector-database.yml up -d
# 2. 跑数据库迁移
wsl .venv/bin/alembic upgrade head
# 3. 灌入 SOP 知识库
...
```

这三步少一步，演示就会失败。新人（包括未来的你）最容易卡在「环境没准备好」。把前置条件写全，就是替读者扫清障碍。

## 3. README 更新：门面

`README.md` 是仓库的第一印象。这次在 AIOps 段落做了一个**结构调整**：

```markdown
## 🎯 AIOps 智能运维

本项目提供两种 AIOps 能力：

1. **告警首响分析**（推荐）— 输入一条标准化告警，自动检索 SOP、
   生成带证据溯源的结构化首响报告。
2. **通用智能诊断** — 基于 Plan-Execute-Replan 的自主诊断。
```

### 为什么要「两种能力分层」

原本 README 只有「通用智能诊断」（旧的 `/api/aiops`）。这两周新增的首响分析是**更成熟、更推荐**的能力。所以：

- 把新能力放在**前面**、标「推荐」——引导读者用对的东西。
- 旧能力保留在后面——不破坏兼容，老接口还能用。

这体现一个工程判断：**新旧并存时，用文档引导，而不是粗暴删除旧代码**。删除是有成本的（可能有人依赖），而引导是零成本的。

### API 表格

```markdown
| 功能 | 方法 | 路径 | 说明 |
|------|------|------|------|
| 首响分析（同步）| POST | `/api/aiops/alerts/analyze` | 一次拿到结构化报告 |
| 首响分析（流式）| POST | `/api/aiops/alerts/analyze/stream` | SSE 推送诊断时间线 |
| 任务列表 | GET | `/api/aiops/tasks` | 列出诊断任务 |
| 任务详情 | GET | `/api/aiops/tasks/{id}` | 报告 + 证据 + 时间线 |
```

一张表把所有接口列清楚。读者扫一眼就知道系统能干什么——**信息密度高，是好文档的标志**。

## 4. ADR：这个项目最值钱的东西

ADR = Architecture Decision Record（架构决策记录）。这两周写了 **9 篇**，放在 `docs/adr/`。

### 什么是 ADR

一篇 ADR 记录一个「当时为什么这么选」的决策，固定结构：

```
状态（提议中/已接受/已废弃）
背景（当时面临什么问题）
决策（最终选了什么）
备选方案（考虑过哪些别的，为什么没选）
后果（这个决定带来的好处和代价）
```

### 为什么 ADR 是「简历弹药」

看 ADR-000 的一段（该看 `docs/adr/000-scope-first-response.md`）：

```markdown
## 备选方案
- A：照搬参考项目做执行平台。放弃 —— 追不上，且会做出一堆半成品。
- B：只做通用 RAG 问答增强。放弃 —— 没把已有 AIOps 资产用起来。
- C（选中）：RAG × AIOps 首响。用自己的长板补 AIOps 的证据短板。
```

普通候选人在面试里说：「我做了一个 AIOps 首响系统。」

写过 ADR 的你能说：「我在三个方向里选了 RAG×AIOps。因为参考项目的执行平台我两周追不上，而我的 RAG 检索是它的短板，所以我放大自己的长板做差异化。代价是放弃了自动修复能力。」

**后者展示的是「工程判断力」，这正是高级岗位要考察的。** 决策过程比决策结果更能体现水平。

## 5. 复盘 ADR-009：诚实地记录得失

最后一篇 ADR 是复盘。它诚实记录了：

- **做成了什么**：完整闭环、93 个测试、9 篇 ADR。
- **没做完什么**：真实检索质量还没验证（评估用的是「理想基线」——假 LLM/假 SOP，只证明管道对，不代表真实质量）。
- **踩了什么坑**：Day7 的 API Key 泄漏、「Edit 假成功」需要 `cat -A` 直读磁盘验证。
- **下一步**：起 Milvus 接真实检索，跑 `run_aiops_eval` 看真实数字。

### 为什么要诚实记录「没做完」

新手倾向于隐藏缺陷，只报喜。但成熟工程师知道：**明确说出「什么没做、为什么、下一步怎么做」，反而显得可信、可控。** 一个系统不可能十全十美，能清楚说出自己的边界和债务，才是真的懂它。

## 6. 「收官前跑全量测试」救了一命

Day10 最后跑全量回归时，**发现了 1 个失败**：`test_config.py::test_default_values`。

根因：Day7 蕾姆在 conftest 顶层设了假环境变量 `DASHSCOPE_API_KEY`，而这个测试断言「默认值应为空字符串」。假 env 污染了它。

修复：给测试加 `monkeypatch.delenv("DASHSCOPE_API_KEY")`，先清掉环境变量再测默认值。

### 教训

这是一个**跨越 3 天才暴露的回归**——Day7 埋下，Day10 才发现。如果不是养成了「收尾前跑一次完整测试套件」的习惯，这个 bug 就带着进简历演示了。

**纪律 > 记忆。** 你不可能记住每个改动的全部影响，但「每次收尾跑全量测试」这条纪律能兜住你。

## 7. 小结

Day10 学到的：

1. **演示指南要可复制粘贴**——读者不需要思考。
2. **README 是门面**——新旧能力用文档引导，不粗暴删除。
3. **ADR 是简历弹药**——记录「为什么这么选」，展示判断力。
4. **诚实复盘**——说清「没做完什么」反而可信。
5. **收尾跑全量测试**——纪律兜住跨天回归。
