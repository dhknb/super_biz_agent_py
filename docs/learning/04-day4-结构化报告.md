# 04 · Day4 结构化首响报告

> 这天要解决：**怎么让大模型（LLM）的输出变成程序能可靠使用的数据？**
>
> 该看的文件：`app/models/aiops_report.py`、`tests/unit/test_aiops_report.py`

---

## 一、这天要解决什么问题

Day3 我们把「一次诊断」变成了能落库的任务。但任务最终要产出一份**报告**。

最朴素的做法是：让大模型直接写一段 Markdown 文字返回。项目原来的
`aiops_service.py` 就是这么干的——prompt 里塞一大段模板，要求模型输出 Markdown。

这样有三个致命问题：

1. **程序读不了**。前端想单独渲染「建议排查步骤」区块，但报告是一大段文字，
   只能整段丢出去，没法结构化展示。
2. **不稳定**。同一个告警问两次，模型可能这次有「风险评估」段落、下次没有。
   格式全靠模型自觉。
3. **没法评估**。想统计「报告里有没有引用 SOP」，面对一段自由文本无从下手。

Day4 的目标：**定义一个固定的结构（schema），让模型按这个结构输出 JSON，
程序解析成对象**。同时——因为模型不一定听话——**解析失败要能降级**，
绝不让整条链路崩掉。

这就是工程里的一个核心思想：**契约（contract）**。我们和模型约定好数据长什么样。

---

## 二、先理解「schema / 契约」是什么

`schema`（模式）就是「数据的形状约定」。

举个生活例子：快递单。快递单上固定有「寄件人 / 收件人 / 电话 / 地址」这些格子。
不管谁寄快递，都往这些格子里填。这就是快递单的 schema。

我们要给「首响报告」设计一张这样的「单子」：

| 格子（字段） | 装什么 |
|------|------|
| `alert_summary` | 一句话说清发生了什么 |
| `current_judgment` | 当前判断 |
| `recommended_checks` | 建议排查步骤（列表）|
| `evidence` | 证据列表 |
| `root_cause_hypotheses` | 根因假设 |
| `pending_confirmations` | 待确认项 |
| `risk_notes` | 风险与升级建议 |

模型必须按这张单子填，程序才能可靠地取每个格子。

## 三、逐段讲解 `aiops_report.py`

### 3.1 证据类型枚举 —— 本项目的灵魂

```python
class EvidenceType(StrEnum):
    VERIFIED_FACT = "verified_fact"      # 已验证事实（来自工具/知识库）
    MODEL_INFERENCE = "model_inference"  # 模型推断
```

**这两个值是整个项目最值钱的设计。** 慢慢理解：

大模型有个坏毛病叫「幻觉」——它会一本正经地编造。比如你问它 CPU 为什么高，
它可能张口就说「因为数据库连接池耗尽」，但它根本没查过，纯猜的。

在运维场景这很危险：值班同学信了它的猜测，去改数据库配置，结果问题根本
不在那儿，越改越糟。

我们的对策：**给每条证据打标签**。
- 来自真实工具查询、知识库文档的 → 标 `VERIFIED_FACT`（已验证事实），可信。
- 模型自己脑补的 → 标 `MODEL_INFERENCE`（推断），仅供参考。

报告里把两者**分开展示**，值班同学一眼就知道哪些能信、哪些要自己再核实。

> 这就是为什么蕾姆一直说「这是你区别于那个 785-star 项目的核心」——
> 它能执行命令，但不会把知识证据化；我们会。

```python
class EvidenceSource(StrEnum):
    METRICS = "metrics"   # 监控指标
    LOGS = "logs"         # 日志
    SOP = "sop"           # 知识库 SOP
    MODEL = "model"       # 模型推断
    UNKNOWN = "unknown"
```

`source` 是「证据的来源渠道」，比 `type` 更细。type 说「可不可信」，
source 说「从哪来的」。

### 3.2 Evidence —— 一条证据

```python
class Evidence(BaseModel):
    type: EvidenceType                    # 事实还是推断
    source: EvidenceSource = ...          # 哪个渠道
    content: str                          # 证据内容
    source_title: Optional[str] = None    # 来源标题（如 SOP 文档名）
    excerpt: Optional[str] = None         # 原文片段
```

`source_title` 和 `excerpt` 就是**「溯源」**的载体：报告里不光说「根据 SOP」，
还能说「根据《CPU排查手册》里这一段：先用 top 定位进程」——可以追到出处。

### 3.3 RecommendedCheck —— 一条建议排查步骤

```python
class RecommendedCheck(BaseModel):
    order: int                            # 第几步
    action: str                           # 做什么
    reason: str                           # 为什么做
    command_hint: Optional[str] = None    # 可选的只读检查命令
    requires_human: bool = False          # 是否需要人工确认
```

注意 `command_hint` 的注释——**只能是只读检查命令**（看日志、查指标），
不能是重启、删除这种改变系统状态的命令。这呼应了 Day1 ADR-000 的边界：
不碰真实命令执行。

### 3.4 FirstResponseReport —— 完整报告

```python
class FirstResponseReport(BaseModel):
    alert_summary: str
    current_judgment: str
    severity_assessment: str = ""
    recommended_checks: list[RecommendedCheck] = Field(default_factory=list)
    evidence: list[Evidence] = Field(default_factory=list)
    root_cause_hypotheses: list[str] = Field(default_factory=list)
    pending_confirmations: list[str] = Field(default_factory=list)
    risk_notes: str = ""

    # 元信息：标记这份报告是正常产出还是降级产物
    is_degraded: bool = False
    raw_text: Optional[str] = None
```

前面几个字段就是那张「单子」。重点看最后两个：

- `is_degraded`：这份报告是不是「降级」来的。正常解析成功 = False；
  解析失败、走了兜底 = True。
- `raw_text`：降级时，把模型的原始输出原样保留在这里，不丢失信息。

> **`Field(default_factory=list)` 是什么？**
> 列表类型的字段，默认值不能直接写 `= []`（Python 有个著名的「可变默认参数」陷阱，
> 所有实例会共享同一个列表）。用 `default_factory=list` 表示「每次新建实例时，
> 调用 `list()` 生成一个新的空列表」，互不干扰。

### 3.5 to_markdown() —— 结构化对象转人类可读

```python
def to_markdown(self) -> str:
    if self.is_degraded and self.raw_text:
        return f"# 告警首响分析报告（降级）\n\n> ⚠️ 结构化解析失败...\n\n{self.raw_text}"

    lines = ["# 告警首响分析报告", ""]
    lines += ["## 告警摘要", "", self.alert_summary, ""]
    ...
    if self.evidence:
        lines += ["## 证据", ""]
        for ev in self.evidence:
            tag = "✅ 已验证" if ev.type == EvidenceType.VERIFIED_FACT else "🤔 推断"
            src = f"（来源：{ev.source_title}）" if ev.source_title else ""
            lines.append(f"- {tag} {ev.content}{src}")
```

这个方法把结构化对象**渲染成人能读的 Markdown**。注意它做的事：
- 降级报告特殊处理（加个「降级」标记 + 原始文本）。
- 证据按 type 显示不同图标（✅ 事实 / 🤔 推断）——把「可信度区分」直观呈现。

**为什么既要结构化对象、又要 Markdown？**
- 结构化对象（JSON）给**程序**用：前端渲染、评估脚本统计。
- Markdown 给**人**用：值班同学直接阅读、复制到工单。
- 一份数据，两种呈现，各取所需。

## 四、核心：解析 + 降级（防御式编程）

这是 Day4 最重要的工程思想。看 `parse_report`：

```python
def parse_report(raw_text: str) -> FirstResponseReport:
    """把模型输出解析为结构化报告；任何失败都降级为纯文本报告。"""
    json_block = _extract_json_block(raw_text)
    if json_block is None:
        return _degraded(raw_text)          # 找不到 JSON → 降级

    try:
        data = json.loads(json_block)
    except (json.JSONDecodeError, ValueError):
        return _degraded(raw_text)          # JSON 语法错误 → 降级

    if not isinstance(data, dict):
        return _degraded(raw_text)          # 不是对象 → 降级

    try:
        return FirstResponseReport.model_validate(data)
    except ValidationError:
        return _degraded(raw_text)          # 字段不符合 schema → 降级
```

### 4.1 什么是「防御式编程」

**假设外部输入一定会出错，提前为每种出错方式准备退路。**

这里的「外部输入」就是大模型的输出。模型可能：
- 返回一段纯文字，没有 JSON。
- 返回的 JSON 少个引号、语法错。
- 返回的是 JSON 数组不是对象。
- JSON 结构对但缺了必填字段。

`parse_report` 对**这四种出错方式各设了一道防线**，任何一种都导向 `_degraded`
（降级），**永远返回一个可用的 `FirstResponseReport`，绝不抛异常**。

### 4.2 为什么「不抛异常」这么重要

想象一下：如果 `parse_report` 遇到坏 JSON 直接崩溃，会怎样？

整条诊断链路会中断——用户 POST 一个告警，等半天，最后拿到 500 错误。
而实际上，模型可能只是格式没对齐，它的文字内容其实有用。

降级的意义：**格式坏了，但内容不丢**。把原始文本塞进 `raw_text`，
标记 `is_degraded=True`，用户还能看到模型说了什么，只是没有结构化而已。
系统「优雅地退化」，而不是「粗暴地崩溃」。

> 这就是「可降级（graceful degradation）」，是生产级系统的重要特征。
> 电梯坏了变楼梯，而不是把人困在里面。

### 4.3 _extract_json_block —— 从杂乱输出里抠 JSON

```python
def _extract_json_block(text: str) -> Optional[str]:
    # 情况2：被 ```json ... ``` 代码块包裹
    fence = re.search(r"```(?:json)?\s*(\{.*?\})\s*```", text, re.DOTALL)
    if fence:
        return fence.group(1)

    # 情况1/3：找第一个 { 到最后一个 } 的最大区间
    start = text.find("{")
    end = text.rfind("}")
    if start != -1 and end != -1 and end > start:
        return text[start : end + 1]
    return None
```

模型很爱「多嘴」，比如返回：

````
好的，这是分析结果：
```json
{"alert_summary": "..."}
```
希望对你有帮助！
````

真正的 JSON 被前后的废话和代码块围栏包着。这个函数用两招把它抠出来：
1. 先找 Markdown 代码块（正则匹配 ```json ... ```）。
2. 找不到就退而求其次，找第一个 `{` 到最后一个 `}` 的范围。

> 这是和大模型打交道的常见现实：它不会乖乖只给你 JSON，你得有「提取」的容错逻辑。

## 五、对照测试理解（tests/unit/test_aiops_report.py）

测试是最好的「用法说明书」。看几个关键用例：

```python
def test_parse_plain_json():
    report = parse_report(json.dumps(_valid_payload(), ensure_ascii=False))
    assert report.is_degraded is False            # 正常 JSON → 不降级
    assert report.evidence[0].type == EvidenceType.VERIFIED_FACT

def test_plain_text_degrades():
    report = parse_report("CPU 有点高，建议看看日志。")
    assert report.is_degraded is True             # 纯文本 → 降级
    assert report.raw_text == "CPU 有点高，建议看看日志。"

def test_invalid_json_degrades():
    report = parse_report("{ 这不是合法 json ")
    assert report.is_degraded is True             # 坏 JSON → 降级

def test_missing_required_field_degrades():
    bad = {"alert_summary": "只有摘要"}            # 缺 current_judgment
    report = parse_report(json.dumps(bad, ensure_ascii=False))
    assert report.is_degraded is True             # 缺字段 → 降级
```

四个用例正好对应 4.1 说的四种出错方式。读测试，你就知道
`parse_report` 到底承诺了什么行为。

> **学习方法**：以后看任何陌生代码，先看它的测试。测试用例 = 作者亲手写的
> 「这个函数在各种输入下应该怎么表现」，比读实现更快理解意图。

## 六、这天的核心收获

| 概念 | 一句话 |
|------|------|
| schema / 契约 | 和数据源（这里是 LLM）约定好数据的固定形状 |
| 结构化输出 | 让模型返回 JSON 而非自由文本，程序才能可靠使用 |
| 证据分级 | VERIFIED_FACT vs MODEL_INFERENCE，对抗大模型幻觉 |
| 溯源 | source_title + excerpt，结论能追到出处 |
| 防御式编程 | 假设输入会出错，为每种错法准备退路 |
| 优雅降级 | 出错时退化到可用状态，而非崩溃 |
| 一数据两呈现 | 结构化对象给程序，Markdown 给人 |
