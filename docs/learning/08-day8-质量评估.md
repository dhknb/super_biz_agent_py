# 08 · Day8 质量评估

> 这一天解决一个「RAG 岗分水岭」问题：**怎么证明你的检索/报告是好的？**
> 不能靠感觉说「还不错」，要能跑出一个数字：命中率 X%、覆盖率 Y%。

## 这天要解决什么问题

前 7 天蕾姆做出了「告警 → SOP 检索 → 结构化报告」的闭环。但有个致命问题：

> 这个报告到底**好不好**？换个 prompt 是变好了还是变差了？我怎么知道？

如果只能靠人眼看「嗯，这份报告看着还行」，那就是**拍脑袋**。工程化的做法是：
建一套**可量化、可复现**的评估，把「好不好」变成一个能对比的数字。

面试里这是 RAG 岗的分水岭题：「你怎么评估和优化 RAG 系统？」——
答得出「建评测集 + 量化指标 + 分层归因」就是懂，答「我看着调」就是不懂。

这是一个重要的工程习惯：**动手前先看现状**，别急着造轮子。

### 补课：什么是 Hit@K / MRR / Recall@K

这三个是**检索质量**的经典指标。假设你问一个问题，系统返回了 Top-K 个文档：

- **Hit@K**：Top-K 里**有没有**命中至少一个正确文档？（是/否 → 1/0）
- **Recall@K**：Top-K 里命中的正确文档数 / 所有正确文档数（覆盖了多少）
- **MRR**（Mean Reciprocal Rank）：第一个正确文档排在第几位的倒数。
  排第 1 → 1.0，排第 2 → 0.5，排第 3 → 0.33……越靠前越好。

它们衡量的是「**检索**准不准」，但衡量不了「**生成的报告**好不好」。
Day8 补的就是后者。

## 三个评估维度

蕾姆给首响报告设计了三个维度，都是纯函数打分：

| 维度 | 函数 | 衡量什么 |
|------|------|---------|
| SOP 命中率 | `score_sop_hit` | 报告证据里有没有命中期望的 SOP 关键词 |
| 报告要点覆盖率 | `score_point_coverage` | 报告全文覆盖了多少比例的期望排查要点 |
| 幻觉受控率 | `score_hallucination_controlled` | 没证据时有没有老实说「待确认」而非编造根因 |

### 补课：什么是「纯函数」

纯函数 = **相同输入永远得到相同输出，且没有副作用**（不改全局、不读文件、不调网络）。

```python
# 纯函数：给同样的 report 和 keywords，永远返回同样的 True/False
def score_sop_hit(report, expected_keywords) -> bool: ...

# 非纯函数：结果依赖当前时间/数据库/网络，同样输入可能不同输出
def get_current_score(): return db.query(...)  # ← 依赖外部状态
```

**为什么评估函数要写成纯函数？** 因为纯函数**极易测试**——喂固定输入，断言固定输出，
不需要 mock 任何东西。Day8 的评估器 17 个测试跑得飞快就是这个原因。

## 逐段讲解：三个打分函数

### 维度一：SOP 命中率

```python
def score_sop_hit(report: FirstResponseReport, expected_keywords: list[str]) -> bool:
    """报告的证据里是否命中任一期望 SOP 关键词。"""
    if not expected_keywords:
        return True  # 没要求命中，视为通过
    haystack = " ".join(
        f"{ev.content} {ev.source_title or ''} {ev.excerpt or ''}"
        for ev in report.evidence
    )
    return any(kw in haystack for kw in expected_keywords)
```

逐行拆：

- `if not expected_keywords: return True` —— 如果这条告警没设期望关键词，
  就不苛求，直接算通过。这是**边界处理**。
- `haystack = " ".join(...)` —— 把所有证据的 `content + source_title + excerpt`
  拼成一个大字符串（"干草堆"，haystack 是英文成语「大海捞针」里的草堆）。
- `any(kw in haystack for kw in expected_keywords)` —— 只要**任一**期望关键词
  出现在草堆里，就算命中。

**这里衡量的是**：Day5 检索到的 SOP 证据，是不是真的跟这条告警相关。
比如 CPU 告警，期望关键词是 `["CPU", "top", "进程"]`，如果检索到的证据里
一个都没有，`sop_hit=False`，说明检索跑偏了。

### 维度二：报告要点覆盖率

```python
def score_point_coverage(report, expected_points: list[str]) -> float:
    if not expected_points:
        return 1.0
    text = report.to_markdown()  # 把报告渲染成全文
    hits = sum(1 for point in expected_points if point in text)
    return hits / len(expected_points)  # 命中数 / 总数
```

- 把报告用 Day4 写的 `to_markdown()` 渲染成完整文本。
- 逐个检查期望要点（如 `["CPU", "进程", "日志"]`）是否出现在文本里。
- 返回**比例**：命中 2 个 / 共 3 个 = 0.67。

**这里衡量的是**：报告有没有覆盖到人工认为「该提到」的排查要点。
返回 float（0~1）而不是 bool，是因为覆盖是**程度**问题，不是有/无。

### 维度三：幻觉受控率（最有含金量）

```python
def score_hallucination_controlled(report) -> bool:
    has_verified = any(
        ev.type == EvidenceType.VERIFIED_FACT for ev in report.evidence
    )
    if has_verified:
        return True  # 有已验证事实撑腰，允许给根因
    # 没有任何已验证事实的情况下：
    if report.root_cause_hypotheses and not report.pending_confirmations:
        return False  # ← 无据却硬给根因、还不标"待确认" = 幻觉失控
    return True
```

这段是 Day5「事实 vs 推断」设计的**回收**。逻辑是：

- 如果报告里**有**至少一条「已验证事实」证据 → 它给根因假设是有依据的 → 受控。
- 如果**一条已验证事实都没有**，却给出了根因假设、还**不**放进「待确认项」
  → 这就是**无中生有编造根因** → 判定失控（返回 False）。

**为什么这个维度最值钱**：它把「幻觉控制」从一句口号变成了**可自动检测的规则**。
面试时你能说「我的评估会自动抓『无证据却给确定性根因』的样本」，这比空谈
「我们注意防幻觉」有力得多。

### 补课：什么是「幻觉」（hallucination）

大模型「幻觉」指它**一本正经地编造不存在的事实**。在 RAG/AIOps 场景里特别危险：
模型可能在没有任何日志/监控证据时，硬说「根因是数据库连接池耗尽」——
听起来很专业，但纯属编造，会误导值班工程师。

**控制手段**：要求模型「无证据就说不知道」，并在评估里**自动检测**它有没有遵守。

## 聚合：把多条样本合成一个报告

```python
def aggregate(cases: list[ReportCaseScore]) -> ReportEvalReport:
    if not cases:
        return ReportEvalReport(total=0, sop_hit_rate=0.0, ...)
    return ReportEvalReport(
        total=len(cases),
        sop_hit_rate=mean(1.0 if c.sop_hit else 0.0 for c in cases),
        avg_point_coverage=mean(c.point_coverage for c in cases),
        hallucination_control_rate=mean(
            1.0 if c.hallucination_controlled else 0.0 for c in cases
        ),
        cases=cases,
    )
```

- 把每条告警的三个维度分数，用 `mean`（平均）聚合成整体率。
- bool 用 `1.0 if x else 0.0` 转成数字再平均 → 得到「百分比」。
- 空集单独处理，避免 `mean([])` 报错（`mean` 对空列表会抛异常）。

## CLI：一条命令跑出基线

`run_aiops_eval.py` 把评估串成一条命令：

```
tests/fixtures/aiops_alerts/*.json（告警 + expected_*）
   ↓
normalize_alarm → FirstResponseService.analyze（注入假 LLM，离线可跑）
   ↓
score_case → aggregate
   ↓
打印 SOP命中率 / 要点覆盖率 / 幻觉受控率
```

跑出来长这样：

```
=== AIOps 首响报告质量评估 ===
样本数:            3
SOP 命中率:        100%
报告要点覆盖率:    100%
幻觉受控率:        100%
```

### 为什么用「假 LLM」跑基线

CLI 默认注入假 LLM + 假 SOP（完美命中），跑出的是**「理想基线」**。
这看起来「作弊」，但有明确意义：

> 它证明的是「**评估管道本身是对的**」——打分逻辑、数据流都通。
> 等接上真实 Milvus 检索 + 真 LLM，这些数字就会掉下来，反映**真实质量**。

这是评估的正确建立顺序：**先用理想数据确认管道无 bug，再用真实数据看真实分数**。
否则你分不清「分数低」是系统真的差，还是评估脚本自己有 bug。

## 蕾姆诚实的提醒

目前跑的是理想基线。**你下一步真正该做的**是：
1. 起 Milvus，把 `aiops-docs` 灌进去。

## 概念小结

| 概念 | 一句话 |
|------|--------|
| 评测集 | 一批 `(输入, 期望输出)`，是量化的前提 |
| Hit@K/MRR/Recall@K | 检索质量指标（准不准、全不全、靠不靠前）|
| 纯函数 | 相同输入→相同输出、无副作用，极易测试 |
| 幻觉 | 模型编造不存在的事实；要能自动检测 |
| 理想基线 | 用假数据先证明评估管道对，再上真实数据 |
