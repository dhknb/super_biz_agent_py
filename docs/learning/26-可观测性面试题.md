## 一、三根支柱

### Q1. 你项目里的可观测性是怎么分层的？指标、日志、追踪不是有重叠吗？

**考点**：能不能说出三者**边界**在哪。答不出边界的人，通常是"三样都接了，出故障时还是不知道看哪个"。

**标准回答**：

它们回答的是三个不同的问题，而且**互相答不了**——这是分层的唯一理由，不是为了凑齐"业界三根支柱"。

- **指标**回答「**整体**现在什么形状」：降级率多少、P99 是多少、熔断器开着没有。它答不了「张三那次查询为什么没给出 SOP」，因为指标里**按定义没有任何个体信息**——`degrade_total{reason="retrieval_failed"}` 涨了 30，你不知道是哪 30 次。
- **日志**回答「**这一次**为什么失败」：有 `request_id`，能顺着看到是 rewrite 挂了还是 validate 挂了。但你没法从日志问出「过去一小时降级率是多少」——那需要遍历几百万行做聚合，而且答案会随日志保留期滚动消失。
- **追踪（span）**回答「**这一次的时间花在哪**」：一次请求里 8 个节点各占多少毫秒、哪条并行分支拖慢了整体。日志里每条都有时间戳，理论上能拼出来，但实际拼不出——并行分支的日志是交错的，而且日志记的是"发生了什么"，不是"持续了多久"。

值班的实际动线是**指标发现异常 → span 定位到节点 → 日志定位到个体**。三步各缺一步的后果不同：

- 只有指标：知道"有问题"，不知道问题在哪。
- 只有日志：得先有人报障才会去看，故障发现完全依赖用户投诉。
- 只有 span：知道慢在哪个节点，不知道这是常态还是异常（没有基线）。

**真实代码**：

```python
# app/core/metrics.py:13
## 为什么指标和日志不能互相替代
#
# 它们回答的是两个不同的问题,而且**互相答不了**:
#
# - 日志回答「这一次为什么失败」——  有 request_id,能顺着 trace 一路看到
#   是 rewrite 挂了还是 validate 挂了。但你没法从日志问出
#   「过去一小时降级率是多少」,那需要遍历几百万行做聚合。
# - 指标回答「整体现在什么形状」—— 降级率、P99 耗时、熔断器开着没有。
#   但它答不了「张三那次查询为什么没给出 SOP」,因为指标里没有任何个体信息。
#
# 值班的实际动线是:指标发现异常 → 日志定位个体。
```

三者在本项目里的落点：

| 支柱 | 实现 | 存储 | 保留期 |
|---|---|---|---|
| 指标 | `prometheus_client` + `prometheus-fastapi-instrumentator` | Prometheus 内存/TSDB | 由 Prometheus 配置 |
| 日志 | loguru，控制台彩色文本 + 文件 JSON 行 | `logs/app_{date}.log` | 30 天（zip 压缩） |
| 追踪 | 自研 `span_scope` + `ChatRunSpan` 表 | MySQL | 随业务数据 |

**追问链**：

> **追问 1：为什么 span 自己写，不用 OpenTelemetry？**
>
> 因为需求的形状不一样。OTel 的价值在**跨服务**传播 trace context——服务 A 调 B 调 C，靠 W3C traceparent 头把三段串起来。本项目是单进程，跨进程的部分只有 RQ worker，而那部分我用 `request_id` 就串起来了（见 Q17）。
>
> 引入 OTel 的成本是：一套 SDK、一个 Collector 进程、一套采样配置，换来的是我用 200 行 `span_context.py` 已经有的东西，加上我现在用不到的跨服务传播。这是 YAGNI 的标准场景。
>
> 但我说清楚代价：**如果这个项目拆成多个服务，自研 span 立刻不够用**——手工传 trace_id 会漏，而且没有标准格式意味着接不了任何现成的 APM。那时候的迁移路径是明确的：`span_scope` 的接口（`__enter__` / `set_payload` / `__exit__`）和 OTel 的 span 是同构的，换实现不用改调用点。**自研的时候就按标准接口的形状写，是为了让将来能换掉它。**

> **追问 2：三样东西的成本一样吗？**
>
> 差一个量级。指标是最便宜的——每次埋点是几个整数操作，内存占用取决于时间序列数（这就是为什么 label 基数是死线，见 Q5）。span 次之：一次 append 到内存 list，跑完一次 `bulk_save_objects`。日志最贵：文件 IO + JSON 序列化，所以文件 handler 开了 `enqueue=True` 走异步写。
>
> 成本差异直接决定了埋点密度：指标可以每个降级都记，span 一个节点一条，而日志要控制在"每个关键决策点一条"——`logger.debug` 在生产是关掉的（`level="INFO" if not debug`）。

**拓展**：

三根支柱之外还有第四样，本项目也有但没归到可观测性里：**业务事实的持久化**。`ChatRunTrace` 表记的是"这次问答的输入输出和判定结果"，它不是观测数据，是业务数据——用于离线评估（第 23 篇的 golden set）、用于复盘、用于将来训练。区别在于**可观测数据可以采样丢弃，业务事实不行**。

把这两类混在一起是个常见错误：一旦把 trace 表当成"日志的结构化版本"，就会给它加采样，然后某天发现要复盘的那次刚好被采掉了。**判据是"这条数据丢了，是少一个样本，还是少一个事实"。**

### Q2. 你怎么决定一个信息该进指标、进日志、还是进 span？

**考点**：这是上一题的操作版。能给出**判据**的人，和只能给出例子的人，差距很大。

**标准回答**：

三个问题，顺序问：

**第一问：它的取值是有界的吗？** 无界的一律不能进指标的 label——`request_id`、用户问题、文件名、告警实例 IP。每个 label 值组合会生成一条独立时间序列常驻内存，无界 label 就是内存泄漏（Q5 详述）。这一问筛掉的东西大部分该进日志。

**第二问：需要聚合，还是需要单条？** 需要问"一小时内多少次"的进指标；需要问"那一次发生了什么"的进日志或 span。注意同一件事的**不同侧面**会分到不同地方：一次检索失败，"失败了"这个计数进指标（`retrieval_failures_total{code=...}`），"为什么失败"的完整报文进日志，"失败发生在哪个节点、耗时多少"进 span。

**第三问：它属于一次请求的时间结构吗？** 属于的进 span。span 的独特能力是**表达嵌套和并行**——四条检索分支同时跑，日志只能交错输出，span 能显示它们的重叠区间。

本项目里同一件事分三处的实际例子——检索分支失败：

```python
# ① 指标：可聚合的计数（app/agent/rag_v2/nodes.py 检索节点内）
count_retrieval_failure(code)          # retrieval_failures_total{code="retrieval_error"}

# ② state：给下游节点决策用（不是观测，是业务数据）
return {"retrieve_failures": [{"error": str(exc), "code": code}]}

# ③ span：谁失败了、失败了几条、耗时多少
#    app/agent/rag_v2/instrumentation.py:63
failures = patch.get("retrieve_failures")
if isinstance(failures, list) and failures:
    payload["retrieve_failure_count"] = len(failures)
    # 只留错误码不留完整报文：错误码可聚合,报文在日志里已经有了。
    payload["retrieve_failure_codes"] = sorted(
        {str(item.get("code")) for item in failures if isinstance(item, dict)}
    )
```

第三段那行注释是判据的直接应用：**span payload 里放 code 不放 message**，因为完整报文在日志里已经有一份了，再抄一遍是制造副本，而 span 表会跟着业务数据长期留存。

**追问链**：

> **追问 1：那 `error` 的完整文本为什么还要进 state？那不也是副本吗？**
>
> 是副本，但它有业务用途：`generate` 节点要读它生成 `partial_note` 告诉用户"有部分资料没查到"。它进 state 不是为了观测，是因为下游节点需要它做决策。**判据是"有没有代码读它"**——有代码读的是业务数据，只有人读的是观测数据。
>
> 顺带说一个我踩过的边界：`span_scope.__exit__` 里记 error 时截断到 500 字符（`str(exc)[:500]`）。因为异常消息可能包含整个 SQL 或整个 prompt，不截断的话 span 表会被单条记录撑爆。观测数据的存储必须有上界，这是和业务数据的另一个区别。

> **追问 2：有没有信息是三个地方都不该进的？**
>
> 有，而且这是最重要的一类：**用户原文和检索到的文档正文**。它们既是无界的（不能当 label），也是敏感的（进日志意味着日志文件里有用户数据，接了 Loki/ELK 之后传播范围更大）。
>
> 本项目的处理是：span payload 只记 `answer_length` 不记 `answer`，只记 `doc_count` 不记文档内容。真要复盘具体内容，去 `ChatRunTrace` 表——那是业务数据，有明确的访问边界和保留策略，而不是散落在日志文件里。

**拓展**：

这个判据链还有一个没做的第四问：**它需要多快被看见？** 指标的延迟是抓取间隔（通常 15–60s），日志是写入延迟（`enqueue=True` 之后是异步的，可能几百毫秒），span 是"跑完才落盘"（一次请求结束后）。

对绝大多数场景这个差异无关紧要，但有一类例外：**请求跑了一半就被杀掉时，span 全部丢失**——因为它们还在内存里等 flush。这是"内存收集 + 一次落盘"这个设计的代价（Q19 详述），也是我选择让指标在节点内就 `inc()` 而不是攒着一起报的原因：**最需要观测的那次请求，往往就是没能正常结束的那次。**

### Q3. 你项目里有多少个自定义指标？为什么这么少？

**考点**：指标数量是个陷阱题。答"我加了几十个"的人通常没想过维护成本，答"就四个"但说不出理由的人是没设计过。

**标准回答**：

四个自定义指标，加上 instrumentator 自动生成的一组 HTTP 指标。

| 指标 | 类型 | label | 回答什么问题 |
|---|---|---|---|
| `llm_call_duration_seconds` | Histogram | `node` | 哪个 LLM 调用点在变慢 |
| `degrade_total` | Counter | `reason` | 降级率多少、什么原因 |
| `retrieval_failures_total` | Counter | `code` | 检索失败的分布 |
| `circuit_breaker_state` | Gauge | `name` | 哪个下游被熔断了 |

少的理由是：**每个指标都是一个长期负债**。它要被维护（label 含义变了要改告警规则）、要占内存（时间序列常驻）、要被理解（值班的人得知道这个指标涨了意味着什么）。一个没人看的指标不是中性的，它是噪音——出故障时多一个要排除的干扰项。

我的加指标判据是：**这个指标涨了，我知道该做什么吗？** 答不出"该做什么"的指标不加。举反例：我没加 `documents_retrieved_total`（召回文档总数）。它看起来很自然，但它涨了或跌了我都不知道该干什么——召回条数由 `FINAL_TOP_K` 决定，波动只反映请求量。真正想知道的"召回质量"是离线评估的事（第 23 篇的 golden set），不是线上指标。

四个指标能覆盖的，恰好是第 25 篇那套可靠性设计的四个观测面：

- 慢（`llm_call_duration_seconds`）
- 降级（`degrade_total`）
- 依赖失败（`retrieval_failures_total`）
- 自我保护动作（`circuit_breaker_state`）

**追问链**：

> **追问 1：`degrade_total` 和 `retrieval_failures_total` 不重叠吗？检索失败也会导致降级。**
>
> 重叠，而且这个重叠是有意的。它们的**分母不同**：
>
> - `degrade_total{reason="retrieval_failed"}` 的单位是**一次请求**——这次问答降级了。
> - `retrieval_failures_total{code=...}` 的单位是**一次检索调用**——四条并行分支里挂了几条。
>
> 一次请求四条分支全挂，前者 +1、后者 +4。两个数一比就得到一个有用的量：**平均每次降级背后有几次调用失败**。全挂（比值 4）说明是下游整体不可用，只挂一条（比值 1）说明是个别子查询的问题。这个信息任何单一指标都给不出来。
>
> 这也是为什么 `count_degrade` 埋在汇聚点、`count_retrieval_failure` 埋在节点里——不是随手放的，是两个不同粒度的观测（Q11 详述）。

> **追问 2：为什么没有 QPS 和错误率指标？**
>
> 有，但不是我自己写的——`Instrumentator().instrument(app)` 自动生成 `http_requests_total{handler, status}`，QPS 和错误率都从它算。自己再写一个是重复。
>
> 这里有个第 25 篇的呼应：那个 `http_requests_total{status="5xx"}` 在 exception_handlers.py 的文档里被列为"状态码的消费者"，但**当时并不存在**。状态码说了真话，没有任何东西在听。加 instrumentator 这一行，那句注释才从设想变成事实。**改造留下的悬空引用要有人收尾，否则文档就开始骗人了。**

**拓展**：

没加但值得加的第五个指标：**`llm_tokens_total{node, kind}`**（kind = prompt / completion）。理由是成本可观测性——现在我知道 LLM 调用慢了，但不知道花了多少钱。而 token 数还有一个诊断价值：第 23 篇提到的 `chunk_max_size=800 × FINAL_TOP_K=6 ≈ 4800` 对 `budget=2800` 的参数失配，如果有 prompt token 指标，这个失配会**直接显示为 prompt token 长期贴着上限**，而不是伪装成知识库缺文档。

没加的原因不是不重要，是 `langchain` 的 token 统计要从 response 的 `usage_metadata` 取，而流式调用下这个字段的可靠性我还没验证过。**没验证过的数据源不如没有**——一个时对时错的成本指标会让人做出错误的容量决策。

### Q4. 可观测性代码失败了怎么办？

**考点**：这题在筛"有没有想过观测系统自己也会坏"。第 25 篇有一条对应的原则，这里是它在观测侧的应用。

**标准回答**：

原则一句话：**观测失败绝不能影响主流程**。用户要的是答案，「因为记不下耗时，所以这次回答失败了」是荒谬的因果。

本项目里这条原则有四处实现，形式不同但纪律一致：

```python
# ① span 记录：包住,失败只是少一条 span
# app/core/span_context.py:149
with suppress(Exception):  # 观测失败不能影响业务
    record_span(...)

# ② span 落盘：失败记日志,返回 0
# app/core/span_context.py:192
except Exception as exc:
    logger.warning(f"span 落盘失败（不影响主流程）: trace_id={trace_id}: {exc}")
    with suppress(Exception):
        db.rollback()
    return 0

# ③ 计时：try/finally 而不是 try/except —— 异常原样上抛
# app/core/metrics.py:148
start = time.perf_counter()
try:
    yield
finally:
    observe_llm_duration(node, time.perf_counter() - start)

# ④ 日志自身：setdefault 保证格式串的键永远存在
# app/utils/logger.py:39
record["extra"].setdefault("rid", get_request_id() or NO_REQUEST_ID)
```

第四条最容易被忽略，也最致命。格式串里写了 `{extra[rid]}`，一旦某条记录缺这个键，loguru 格式化时抛 `KeyError`——而**日志系统自身抛异常是最糟的故障**：它会掩盖真正的错误。你在排查一个问题，日志系统在这个问题上炸了，于是你看不到问题。`setdefault` 保证这个键永远存在。

第三条的 `try/finally` vs `try/except` 是个精确的选择：`finally` 记完时间**然后让异常继续飞**；如果写成 `except`，就变成"观测代码吞掉了业务异常"，这比观测失败严重一万倍。

**追问链**：

> **追问 1：`suppress(Exception)` 把所有异常都吞了，这不是反模式吗？**
>
> 在业务代码里是，在观测代码里不是——因为这里**吞掉之后没有任何后续动作依赖它**。第 25 篇讲过"吞掉是让错误消失，降级是让错误改变形态但不消失"，那条针对的是业务路径：吞掉检索异常会让上层以为检索成功了。
>
> 观测路径不同：少一条 span 之后，没有任何代码会因此做出错误决策。它的代价是"这次的观测数据不完整"，而不是"这次的业务结果不正确"。
>
> 但我留了一个口子——`flush_spans` 失败时是 `logger.warning` 而不是静默。**观测系统坏了这件事本身，要被另一个观测手段看见。** 现在这个手段是日志，不够好（Q28 讲改进方向）。

> **追问 2：`suppress` 里如果发生的是 `CancelledError` 呢？**
>
> 这是个真问题。`suppress(Exception)` 抓不到 `CancelledError`（它继承 `BaseException`），所以取消信号能正常穿过——这是对的，取消必须传播。
>
> 但 `flush_spans` 里的 `except Exception` 有个隐患：如果 flush 正在写库时请求被取消，`CancelledError` 会穿过 except、跳过 `db.rollback()`，留下一个未回滚的事务。这个我还没处理。正确的写法是 `finally` 里做清理，或者显式加 `except asyncio.CancelledError: db.rollback(); raise`。**能说出"我知道这里还有个洞"，比说"我全包住了"可信。**

**拓展**：

这条原则的反面是一个更难的问题：**观测系统坏了，谁来告诉我？** 现在的答案是"没人"——`degrade_total` 停止上报和"系统很健康所以没有降级"在 Prometheus 里长得一模一样（Counter 不涨）。

标准解法是 **heartbeat 指标**：一个恒定递增的 `app_up`，配一条 `absent()` 或 `rate() == 0` 的告警规则。这样"指标不再上报"本身成为一个可告警事件。这是 Prometheus 生态里"用 absent 检测缺失"的标准模式，本项目还没加——`up` 指标是 Prometheus 自己抓取时生成的，能覆盖"服务挂了"，但覆盖不了"服务活着但埋点代码坏了"。

## 二、指标设计与基数纪律

### Q5. 讲一下 Prometheus 的 label 基数问题。你项目里是怎么防的？

**考点**：这是指标最容易出的生产事故，也是区分"用过 Prometheus"和"理解 Prometheus"的分水岭。

**标准回答**：

先说机制：**每一个 label 值的组合都会在 Prometheus 里生成一条独立的时间序列，每条序列常驻内存。** 所以 label 的取值集合必须是**有界且很小**的。

数量级感受一下：一个指标带一个 `request_id` label，每天 10 万次请求就是 10 万条时间序列。每条序列的内存开销（含标签字符串、chunk 缓冲）是 KB 级，10 万条就是几百 MB——**一个指标就能把 Prometheus 打爆**。而且这个爆是不可逆的：序列一旦创建，即使不再有新样本，也要等过了保留期才会被回收。

本项目的 label 全部来自枚举或固定字符串：

```python
# app/core/metrics.py:41
# 本模块的 label 全部来自枚举或固定字符串:
# - node   → 五个节点名 + 少量服务名,有界
# - reason → DegradeReason 枚举,十来个值,有界
# - code   → 错误码,来自异常类名转换,有界
#
# **绝对不能**做 label 的:request_id、trace_id、用户问题、文件名、
# 告警实例 IP。这些是无界的,加进去就是内存泄漏 —— 那类信息属于日志。
```

三个 label 的有界性都不是巧合，是设计的结果：

- `reason` 来自 `DegradeReason` 这个 `StrEnum`，十个值，加新值要改枚举——**类型系统在帮你守住基数**。
- `code` 来自 `error_code_of()`，它把异常**类名**转成 snake_case，而类名集合是有界的。这是第 25 篇那个设计的连带收益：当初把 `code` 从异常类属性推导出来，理由是"可聚合"，而"可聚合"的实质就是"基数有界"。
- `node` 是节点名，五个。

反过来，本项目里**存在**无界标识，但它们全部走日志和 span：`request_id`、`trace_id`、用户问题、文档来源。

**追问链**：

> **追问 1：那 HTTP 指标的 path 怎么办？`/api/aiops/trace/{trace_id}` 这种路由，每个 trace_id 一条序列？**
>
> 这正是我引 `prometheus-fastapi-instrumentator` 的**唯一实质理由**。
>
> 手写中间件拿到的是 `request.url.path`，那是**展开后的真实路径**——`/api/aiops/trace/abc123`、`/api/aiops/trace/def456`……每个 trace_id 一条序列，几万次查询就把 Prometheus 打爆。而 instrumentator 会从 Starlette 的 route 对象取**路由模板**：
>
> ```python
> # app/main.py:97
> # 关键收益是 label 按**路由模板**聚合：
> #   http_requests_total{handler="/api/aiops/trace/{trace_id}", status="2xx"}
> ```
>
> 这个对比我在项目里写清楚了，因为它和另一个决定形成对照：**熔断器我没引 pybreaker，自己写了六十行**（第 25 篇），因为那六十行没有这种坑。而 HTTP 指标有——路由模板的提取要访问 Starlette 内部的 route 匹配结果，自己写既繁琐又容易在框架升级时坏掉。
>
> **判据不是"能不能自己写"，是"自己写会不会踩到一个不自己写就不会踩的坑"。**

> **追问 2：`code` 万一有人传了个自由文本进来呢？比如 `count_retrieval_failure(str(exc))`。**
>
> 那就爆了，而且类型系统拦不住——`code` 的签名是 `str`。这是当前设计的一个真实弱点：**约定靠注释和 review，没有强制。**
>
> 现在的缓解是 `code` 的唯一来源是 `error_code_of()`，调用点只有一处。更强的做法是把签名改成接受枚举而不是 `str`，让传自由文本变成类型错误。我没做的原因是 `error_code_of` 的返回值不是枚举（它从任意异常类名推导），要改就得把错误码也收进枚举，而那会让"未知异常"这种情况没法表达。
>
> 折中方案是运行时兜一层：`code` 不在已知集合里就归到 `other`，同时打一条 warning。这样基数天然有界，而且"出现了新错误码"这件事会被看见。这是我认为该加的，属于欠账。

> **追问 3：`labels()` 调用本身有成本吗？**
>
> 有，但很小。`prometheus_client` 里 `labels()` 是一次 dict 查找加一次锁，找到已存在的子指标就返回。第一次调用某个 label 组合时会创建新的子指标（这才是产生序列的时刻）。
>
> 有个实际影响：**一个 label 组合只要被 `labels()` 过一次，即使从未 `inc()`，它也会以 0 出现在 `/metrics` 里。** 这其实是有用的——`degrade_total{reason="circuit_open"} 0` 比这条序列完全不存在要好，因为 PromQL 里 `rate()` 一个不存在的序列返回空而不是 0，告警规则会失效。所以有些项目会在启动时**预热**所有 label 组合。本项目没做，是欠账之一。

**拓展**：

基数问题还有一个更隐蔽的形态：**多维 label 的乘法**。`llm_call_duration_seconds{node}` 现在只有一个 label，五个节点五条序列（乘以 Histogram 的桶数，实际是 5 × 13）。但如果我按追问加上 `model` 和 `status`，就变成 `5 × 3 × 2 × 13 = 390`。

Histogram 的乘数是最容易被忽略的：**每个 Histogram 的每个 label 组合会生成 `桶数 + 2` 条序列**（每个桶一条 `_bucket`，加 `_sum` 和 `_count`）。本项目 11 个桶边界 + `+Inf` = 12 个桶，所以每个 `node` 值是 14 条序列。这就是为什么给 Histogram 加 label 要比给 Counter 加更谨慎——**代价是十几倍。**

### Q6. 为什么用 Histogram 记耗时，不用 Gauge 或 Summary？

**考点**：三种类型的选择是有硬约束的，不是风格问题。答不出"多实例无法聚合"的人没在分布式环境用过。

**标准回答**：

三个都试得通语法，但只有 Histogram 能回答我要问的问题。

```python
# app/core/metrics.py:56
# - Gauge 只记「最后一次」,平均值和 P99 都算不出来,故障时最没用。
# - Summary 在客户端算分位数,多实例部署时**无法聚合**
#   (两个实例各自的 P99 求平均没有数学意义)。
# - Histogram 存的是分桶计数,可以跨实例相加再算分位数。
```

**Gauge 出局**是因为它只保留最后一次的值。故障时最想知道的是"慢请求占多少比例"，而 Gauge 给的是"最近那一次多少秒"——采样点完全随机，可能刚好抓到一个快的。

**Summary 出局**是因为分位数在客户端算。两个实例各自算出 P99 = 3s 和 P99 = 30s，你**没有任何办法**从这两个数得到全局 P99——分位数不可加。`avg(P99)` 是数学上无意义的操作（虽然 PromQL 允许你这么写，这是个陷阱）。

**Histogram 存的是分桶计数**，而计数是可加的：两个实例的 `le="5.0"` 桶分别是 100 和 200，全局就是 300。`histogram_quantile()` 从聚合后的桶算分位数，跨实例正确。

代价是要预先定好桶边界，而桶边界一旦定错，数据就永久性地丢了精度（不能事后重新分桶）。本项目的桶：

```python
# app/core/metrics.py:83
# 桶边界:密在 1~10s(正常区间,要能看出 P50/P90 的移动),
# 稀在 30~120s(异常区间,只需要知道「非常慢」的量级)。
_LLM_BUCKETS = (0.5, 1.0, 2.0, 5.0, 10.0, 20.0, 30.0, 45.0, 60.0, 90.0, 120.0)
```

选法不是抄默认值，是按**本项目的实际形状**选：

- 铺到 60 以上，因为 `llm_timeout_seconds = 60`。如果最大桶是 10s，所有慢调用都挤在 `+Inf` 里，而"慢到什么程度"恰好是排障最需要的信息——`+Inf` 只告诉你"超过 10 秒"，区分不了 11 秒和 59 秒。
- 有 90 和 120，因为总预算是 90s。90 这个桶边界让"卡到总预算耗尽"变成一个可以直接看出来的量。
- 密在 1–10s，因为那是正常区间，P50/P90 的移动要能看出来。这段如果太稀（比如只有 1 和 10），P90 从 2s 涨到 9s 这种明显的劣化会完全看不见。

**桶边界的选法就是"我打算问什么问题"的编码。**

**追问链**：

> **追问 1：失败的调用记不记？**
>
> 记，而且这是最重要的样本。
>
> ```python
> # app/core/metrics.py:127
> def observe_llm_duration(node: str, seconds: float) -> None:
>     """记一次 LLM 调用耗时。
>
>     失败的调用也要记 —— 超时是最重要的耗时样本。把它排除掉会得到一个
>     「一切正常」的 P99:所有慢请求都超时了,剩下的当然都很快。
>     """
> ```
>
> 这是个反直觉的点：只记成功调用的耗时，会得到一条**看起来非常健康**的 P99 曲线。因为所有慢的请求都超时失败了，被排除在样本之外，剩下的当然都快。故障越严重，这条曲线越漂亮——**指标在故障时反向说谎。**
>
> 实现上就是 `try/finally`（Q4 那条）：`finally` 保证无论成败都记一次。

> **追问 2：`max(0.0, seconds)` 那个夹取是防什么？**
>
> 防负数。`observe()` 收到负值时 `prometheus_client` 的行为是把它计入所有桶（因为 `-1 <= le` 对所有正 `le` 都成立），会污染整个分布。
>
> 而负值是可能出现的——如果计时用的是两个 `datetime` 相减而中间发生了 NTP 校时。本项目用 `time.perf_counter()`，理论上单调，所以这个夹取是纯防御。但它的成本是一次比较，而它防的是一类"污染了就没法清理"的数据损坏（Histogram 的桶计数是累积的，不能撤销）。**防御的性价比取决于损坏能不能撤销。**
>
> 同一个考虑在 span 那边也有：`span_scope` 用 `perf_counter` 而不是两个 `datetime` 相减，注释里明确写了"后者受系统时钟调整（NTP 校时）影响，可能算出负数耗时"。**测"过了多久"用 monotonic/perf_counter，记"什么时候"用 datetime**——这是第 25 篇熔断器里同一条规则的第三次应用。

> **追问 3：为什么 `node` 这个 label 里混了节点名和服务名？**
>
> 因为四个 LLM 调用点里有三个是 rag_v2 的图节点（rewrite / generate / validate_answer），第四个是 `first_response_service`——它不在图里。用同一个 label 是有意的：我要问的问题是"哪个 LLM 调用点在变慢"，而这四个都是调用点。为它们分两个指标会让"总的 LLM 耗时分布"变成两个查询求和。
>
> 代价是 label 的语义不够纯粹（"node" 这个名字对 first_response 是不准确的）。可以改叫 `call_site`，更准确。这是个我知道但没改的命名瑕疵——改 label 名意味着历史数据断档，而收益只是名字更好看。**指标一旦上线，label 名就成了兼容性负担。**

**拓展**：

Histogram 之外还有 **native histogram**（Prometheus 2.40+ 的实验特性），它不需要预定义桶边界，用指数桶自动适应数据范围。如果它稳定了，"桶边界定错就永久丢精度"这个问题就消失了。

现在还不能用的原因是它需要 Prometheus 和客户端库两侧都支持，而且存储格式变了，Grafana 侧的支持也在演进。**这属于"知道它存在、知道它解决什么问题、知道为什么还不能用"的技术，面试里提到能显示跟进度，但不该说成"我们用了"。**

### Q7. 为什么熔断器状态用 Gauge？为什么状态值是 0/1/2 而不是随便编号？

**考点**：类型选择的第二个案例，加上一个"为告警规则设计数据"的细节。

**标准回答**：

用 Gauge 是因为**熔断状态是一个当前值，不是累计量**：

```python
# app/core/metrics.py:108
# 用 Gauge 而不是 Counter:熔断状态是一个**当前值**(现在开着还是关着),
# 不是一个累计量。Counter 只能增,表达不了「又闭合了」。
circuit_breaker_state = Gauge(
    "circuit_breaker_state",
    "熔断器状态:0=closed, 1=half_open, 2=open",
    labelnames=("name",),
)
```

Counter 的语义是单调递增，用它记状态就只能记"打开过几次"——那是另一个（也有用的）指标，但答不了"现在开着吗"。

状态值按**严重程度递增**编号，这不是审美：

```python
# app/core/metrics.py:116
# 状态到数值的映射。为什么按「严重程度」递增而不是随便编号:
# 这样 `max_over_time(circuit_breaker_state[1h]) >= 2` 就能直接写成告警规则,
# 不需要在告警表达式里做字符串匹配。
_STATE_VALUES = {
    CircuitState.CLOSED: 0,
    CircuitState.HALF_OPEN: 1,
    CircuitState.OPEN: 2,
}
```

顺序编号让 PromQL 里的**比较运算直接有语义**：

- `circuit_breaker_state >= 2` → 熔断打开（告警）
- `circuit_breaker_state >= 1` → 不健康（含半开，可以做 warning 级）
- `max_over_time(...[1h]) >= 2` → 过去一小时内曾经打开过（抓瞬时熔断）

如果编号是随机的（比如 closed=1, open=0），这三条查询全都得写成 `== 具体值` 的枚举，而且加一个新状态（比如 `FORCED_OPEN`）就得改所有告警规则。

**这是「为下游消费者设计数据」的一个小例子**：指标的形状要让告警表达式尽量简单，因为告警规则是最容易写错、也最难测试的一环。

**追问链**：

> **追问 1：为什么不用 label 表示状态，比如 `circuit_breaker_state{name="llm", state="open"} 1`？**
>
> 这是 Prometheus 里常见的另一种编码（叫 "info metric" 或 state set 模式），也能用，但有两个问题：
>
> 一是**基数翻三倍**：每个熔断器变成 3 条序列。现在两个熔断器，差别不大，但这个模式没有上界纪律。
>
> 二是**状态切换时的残留**：熔断器从 open 变 closed，你得记得把 `{state="open"}` 那条设成 0，否则它会一直显示 1。用数值编码就没有这个问题——一条序列，值变了就是变了。这类"忘记清理旧 label"的 bug 在生产里很常见，表现是告警一直响而实际早就恢复了。
>
> `state` 做 label 的优势是可读性（Grafana 里直接显示 "open" 而不是 2）。我的取舍是可读性用 metric 的 help 文本解决（`"0=closed, 1=half_open, 2=open"` 就写在描述里），基数和正确性优先。

> **追问 2：Gauge 什么时候刷新？状态变化的时候吗？**
>
> 不是——是**抓取的时候**，这是本项目最不直觉的一个设计：
>
> ```python
> # app/core/metrics.py:171
> def refresh_circuit_breaker_metrics() -> None:
>     """把所有熔断器的当前状态刷进 Gauge。
>
>     为什么在**抓取时**刷新,而不是在状态变化时刷新:
>
>     熔断器的状态转换有一条是**惰性**的 —— OPEN 到 HALF_OPEN 不是由
>     某个事件触发,而是「冷却期满之后被人读到」才发生
>     (见 CircuitBreaker._maybe_half_open)。如果只在 record_failure /
>     record_success 里更新 Gauge,那么一个打开后再没有流量的熔断器
>     会永远显示 OPEN,即使它早就该进半开了。
>
>     抓取时刷新则顺带调用了 snapshot(),那个调用本身会推进状态机,
>     所以指标和真实状态永远一致。
>     """
> ```
>
> 这是一个**被观测对象的实现细节，反向决定了观测的时机**的例子。熔断器的 OPEN→HALF_OPEN 是惰性转换（第 25 篇 Q27），没有事件可以挂钩。如果按"状态变化时更新"的直觉写，会得到一个在**低流量时永久错误**的指标——而低流量恰好是熔断打开后的必然状态（请求都被拒了）。
>
> 抓取时刷新还有个额外好处：`snapshot()` 这个调用本身会推进状态机，所以观测行为顺带让状态机保持了新鲜。这在纯粹的观测设计里算"副作用"，但在这里是正确的——**惰性状态机需要有人去读它**。

> **追问 3：那为什么不用 `.expose(app)`？**
>
> 因为需要这个刷新钩子：
>
> ```python
> # app/main.py:114
> # 为什么不用 Instrumentator 自带的 `.expose(app)`：
> # 我们需要在每次抓取前刷一遍熔断器状态（见 app/core/metrics.py 的
> # refresh_circuit_breaker_metrics —— OPEN→HALF_OPEN 是惰性转换，
> # 不刷就会永远显示 OPEN）。`.expose()` 直接吐 registry，没有这个钩子。
> ```
>
> 所以 `/metrics` 是手写的路由，里面先 `refresh_circuit_breaker_metrics()` 再 `generate_latest()`。这是"用库但不全用"的一个例子——HTTP 指标用它的（因为路由模板提取有坑），端点自己写（因为需要钩子）。

**拓展**：

Gauge 在多进程部署下有个坑本项目还没遇到：**gunicorn 多 worker 时，每个进程有自己的 registry**，Prometheus 抓到的是随机某个进程的值。`prometheus_client` 提供了 `multiprocess` 模式（用共享目录聚合），但 Gauge 在那个模式下必须指定聚合方式（`multiprocess_mode="max"` 之类）——因为"两个进程各自的熔断器状态"要合成一个值，而合成规则得你自己定。

对熔断器来说正确的聚合是 `max`（任一进程熔断了就该告警），但这也暴露了一个更根本的问题：**本地熔断器在多进程下本来就是各自独立的**，五个 worker 要各自失败 5 次才全部熔断。这是第 25 篇提到的"集群级熔断"欠账在观测侧的投影——指标聚合方式的困难，往往是被观测设计本身的困难的镜像。

### Q8. `count_degrade(None)` 为什么归到 `unknown`，而不是直接丢弃？

**考点**：一个很小的分支，但它体现的是"指标要能发现自己的缺陷"这个思路。

**标准回答**：

```python
# app/core/metrics.py:155
def count_degrade(reason: str | None) -> None:
    """记一次降级。

    reason 为 None 时归到 `unknown`,而不是丢弃:
    「降级了但没说原因」本身就是一个需要被看见的信号 ——
    它意味着某条降级路径忘了填 degrade_reason。丢弃的话,
    降级总数会小于真实值,而这个偏差没有任何地方能发现。
    """
    degrade_total.labels(reason=reason or "unknown").inc()
```

两个理由，第二个更重要：

**一，`unknown` 本身是一个可告警的信号。** 第 25 篇讲过降级必须带原因，理由是原因指向修复方向。那么"降级了但没原因"意味着有一条降级路径漏填了 `degrade_reason`——这是代码缺陷，而 `degrade_total{reason="unknown"}` 大于 0 就是它的告警。

**二，丢弃会让偏差不可发现。** 如果 `reason is None` 就 `return`，降级总数会小于真实值。而这个偏差**没有任何地方能发现**：你看到的总数是自洽的，各个原因加起来正好等于总数，只是总数本身错了。**一个自洽但错误的数据，比一个明显不完整的数据危险得多。**

空字符串同理——`reason or "unknown"` 里的 `or` 同时兜住了 `None` 和 `""`。测试把这两种都锁住了：

```
# tests/unit/test_metrics.py
test_none_reason_goes_to_unknown_not_dropped
test_empty_string_also_goes_to_unknown
```

**追问链**：

> **追问 1：`_derive_degradation` 返回 `(True, None)` 的情况是什么？**
>
> 在 `instrumentation.py:111`：patch 里有 `retrieve_failures` 但没有 `degrade_reasons`。
>
> ```python
> if patch.get("retrieve_failures"):
>     return True, None
> ```
>
> 这是**故意留的**：检索分支失败时，"算不算整体降级"的判定权在 `dedup`（第 24 篇讲的 fan-in 才能看全局），所以单个检索分支的 patch 里只有失败记录，没有降级原因。埋点层看到有失败就认定"这次执行不算干成活"，但它确实不知道原因该填什么。
>
> 所以 `unknown` 在这里不完全是缺陷，也有一部分是**架构决定的正常情况**。这削弱了"unknown > 0 就告警"的可用性——它会有一个正常的基线值。更好的做法是给这种情况一个专门的 reason（比如 `branch_failed`），把 `unknown` 留给真正的漏填。这是个我识别出来但没改的设计瑕疵。

> **追问 2：那有没有可能同一次降级被记两次？**
>
> 有可能，而且这是当前设计的一个已知偏差。`_apply` 在每个节点的包装器里跑，如果 `retrieve_failures` 通过 reducer 累积到了后续节点的 patch 里，后面的节点也会看到它，于是 `count_degrade` 再涨一次。
>
> 实际上不会——因为 `_derive_degradation` 读的是**patch**（这个节点返回了什么），不是 state（累积了什么）。`retrieve_failures` 只出现在检索节点自己的 patch 里，`dedup` 的 patch 里没有它。
>
> 但这个正确性依赖于"节点不回传自己没改的字段"这条约定，而 TypedDict `total=False` 不强制它。**这属于"现在是对的，但对的原因是一条没被检查的约定"**——第 24 篇讲 `total=False` 会静默接受拼错的键，是同一个松散性的另一面。

**拓展**：

这题背后是一个更一般的原则：**指标应该能观测自己的完整性**。`unknown` 桶、`other` 桶、`+Inf` 桶都属于这一类——它们的存在不是为了记录有用信息，而是为了让"有信息没被正确分类"这件事可见。

同一思路在本项目还有一处：`count_retrieval_failure(code)` 里也有 `code or "unknown"`。而 Q5 追问 2 里说的"未知 code 归到 other"是这个思路的延伸——**分类兜底桶既控制基数，又暴露分类缺陷，一个改动办两件事。**

### Q9. 为什么所有指标定义都集中在一个模块？

**考点**：这题有一个纯技术性的硬约束答案，答不出来的人大概没被这个错误咬过。

**标准回答**：

除了 DRY 这类常规理由，这里有一条**硬约束**：

```python
# app/core/metrics.py:26
## 为什么全部指标定义集中在这一个模块
#
# 跟 app/core/breakers.py 同一个理由,但多一条硬约束:
# **prometheus_client 的默认 registry 是全局单例,同名指标注册两次直接抛
# `Duplicated timeseries in CollectorRegistry`。**
#
# 散在各模块里定义的话,两个模块各写一个 `Counter("degrade_total", ...)`
# 就会在 import 期炸掉 —— 而且是那种「本地跑单个测试没事、
# 一起 import 才炸」的故障。
```

`prometheus_client` 的默认 registry 是**全局单例**，同名指标注册两次直接抛 `Duplicated timeseries in CollectorRegistry`。

这个故障的形态很讨厌：它发生在 **import 期**，而且只在两个模块**同时**被 import 时才触发。所以本地跑单个测试文件永远没事，跑全量测试或者启动服务才炸。而且报错位置指向第二个 import 的模块，看起来像那个模块的问题，实际是重复定义。

集中定义之后，这个错误**在物理上不可能发生**——同一个模块里写两个同名变量，第二个会覆盖第一个，Python 层面就拦住了（虽然是静默覆盖，但至少不会在运行时炸）。

这是"用结构消除一类错误"，比"约定不要重复定义"强得多：约定要靠人记住，结构不用。

**追问链**：

> **追问 1：那测试里怎么隔离？指标是全局状态。**
>
> 这是个真问题，而且比熔断器更麻烦。熔断器有 `reset_all_breakers()`，但 Counter **没有 reset**——它的语义就是单调递增，`prometheus_client` 故意不提供清零。
>
> 所以测试不能断言绝对值，只能断言**增量**：先读一次当前值，执行，再读，比差值。本项目的测试就是这么写的（`test_counts_by_reason` 那组）。
>
> 这个约束反过来影响了指标的可测性设计：`count_degrade` 这类函数必须是**纯埋点**（除了 `inc()` 什么都不干），否则测试就得同时处理"副作用"和"读不到绝对值"两个麻烦。**全局状态不可清零，就必须让操作足够简单以便用增量验证。**

> **追问 2：多个 registry 不行吗？每个模块一个。**
>
> 技术上行，但会失去唯一的好处——`generate_latest()` 默认导出默认 registry，多 registry 就得手工合并，而合并时又要处理重名。等于把问题从"import 期炸"挪到"导出时错"，后者更难发现。
>
> 多 registry 真正的用途是**测试隔离**：给测试用一个临时 registry，跑完扔掉。本项目没这么做，因为要改所有指标的定义方式（每个都得接受 registry 参数），成本大于收益——增量断言已经够用。

**拓展**：

集中定义有一个副作用值得说：`app/core/metrics.py` 变成了一个**被广泛 import 的底层模块**，而它 import 了 `app.core.circuit_breaker`（为了 `all_breakers()`）。这条依赖让"指标模块"和"熔断器模块"耦合了。

现在没出问题，但它的方向是危险的：如果哪天熔断器要上报自己的指标，就会形成循环 import。正确的解法是**反转依赖**——让 `/metrics` 端点去问熔断器要状态，而不是让指标模块 import 熔断器。也就是把 `refresh_circuit_breaker_metrics` 从 `metrics.py` 挪到一个更上层的接线模块（`main.py` 或一个 `observability.py`）。

这属于"知道方向不对但还没到痛点"的债。**底层模块之间的横向依赖，是循环 import 的前兆。**

### Q10. 你的指标能回答哪些实际问题？举几个真实的查询。

**考点**：这题在验证前面几题不是背的。能写出 PromQL 并说清每条查什么的，就是真用过。

**标准回答**：

按值班动线排，五条：

**① 现在健康吗（大盘首屏）**

```promql
# 降级率:降级次数 / 请求数
sum(rate(degrade_total[5m])) / sum(rate(http_requests_total{handler=~"/api/chat.*"}[5m]))
```

分母要限定 handler，否则 `/health` 和 `/metrics` 的流量会把降级率稀释到接近 0——这类"分母污染"是自建大盘最常见的错误。

**② 降级是什么原因（第一步定位）**

```promql
topk(3, sum by (reason) (rate(degrade_total[5m])))
```

按 `reason` 分组直接给出修复方向（第 25 篇 Q6 那套划分的兑现）。看到 `retrieval_failed` 去查 Milvus，看到 `retrieval_empty` 去补文档，看到 `circuit_open` 查我们自己的熔断器。

**③ 是不是某个依赖挂了（排除法）**

```promql
max_over_time(circuit_breaker_state[10m]) >= 2
```

用 `max_over_time` 而不是瞬时值，因为熔断可能已经恢复了但故障值得知道。这就是 Q7 那个"按严重程度编号"的兑现——不用写字符串匹配。

**④ 慢在哪个环节**

```promql
histogram_quantile(0.95,
  sum by (le, node) (rate(llm_call_duration_seconds_bucket[5m])))
```

`sum by (le, node)` 是 Histogram 聚合的标准写法：先按 `le` 和你关心的维度求和，再算分位数。**顺序不能反**——`avg(histogram_quantile(...))` 是错的（分位数不可平均，Q6 讲过）。

**⑤ 检索失败的形态**

```promql
sum(rate(retrieval_failures_total[5m])) / sum(rate(degrade_total{reason="retrieval_failed"}[5m]))
```

这条是 Q3 追问 1 里那个"两个指标分母不同"的实际用法：比值接近 4 说明四条分支全挂（下游整体不可用），接近 1 说明只挂个别分支（子查询个体问题）。**这个信息是两个指标交叉才有的，任何单一指标给不出来。**

**追问链**：

> **追问 1：这些查询你都实际跑过吗？**
>
> 诚实的答案是：PromQL 我验证过语法和聚合顺序，但**没有在真实的 Prometheus 上跑过完整时序**——因为这套指标是刚加上的，还没有积累到能出图的历史数据。
>
> 所以我能保证的是"指标的形状支持这些查询"（label 有界、类型选对、桶铺够），不能保证"阈值定得对"。阈值需要基线，基线需要时间。这也是第 25 篇 Q29 里 P2 那条"降级原因的指标基线"的意思。
>
> **说清"设计验证过、数值没验证过"比笼统说"我做了监控"更可信。**

> **追问 2：告警规则写了吗？**
>
> 没有，这是当前最大的缺口。指标只是**能被查询**，而告警是**主动推送**——没有告警规则，这套指标的价值只在"有人打开大盘看"的时候才存在，而故障通常发生在没人看的时候。
>
> 差的不只是规则文件，还有三件配套的：告警的分级（哪些叫醒人、哪些等上班）、抑制规则（熔断打开时会同时触发降级率告警，不该发两条）、以及最容易被忽略的——**告警规则本身的测试**（Prometheus 有 `promtool test rules`，可以对着构造的时序断言告警是否触发）。
>
> 我把这个排在演进优先级里，理由和第 25 篇一样：**先补"故障时看不见"的，再补"看得见但不够准"的。** 现在的状态是"能看见但要人主动看"，比看不见好，但离能自动发现还差一层。

**拓展**：

指标之上还差一层**SLO**。有了这五条查询之后，下一步是定义 SLI（比如"非降级成功率"= 1 - 降级率），设一个目标（99%），然后用错误预算来决定资源分配——预算烧完了就停新功能补稳定性。

这个做法的价值不在数学，在**它把"要不要投入稳定性"从争论变成了计算**。现在这个决定靠我的判断，而判断在压力下会让位于交付进度。缺的还是历史数据：`degrade_total` 才刚开始积累，没有基线的 SLO 只是拍脑袋，而拍出来的目标会被当成摆设。

## 三、埋点位置

### Q11. 埋点位置是怎么定的？为什么 `count_degrade` 和 `count_retrieval_failure` 埋在不同的地方？

**考点**：这题是整篇最有技术含量的一题。两个看起来同类的埋点放在不同层，而且理由不是"顺手"。

**标准回答**：

判据一句话：**埋点位置由「哪里能拿到最完整的信息」决定，不是由「哪里最方便」决定。**

同一条判据推出两个不同的位置：

**`count_degrade` 埋在汇聚点**（`instrumentation.py:_apply`），因为那里是 rag_v2 全部降级判定的**唯一**汇聚处：

```python
# app/agent/rag_v2/instrumentation.py:149
def _apply(span: span_scope, patch: Any) -> None:
    """把从 patch 推导出的计数与状态写进 span,并顺手记一次降级指标。

    为什么 degrade_total 埋在这里,而不是在五个节点各自的降级分支里:

    这里是 rag_v2 全部降级判定的**唯一**汇聚点 —— `_derive_degradation`
    已经把「什么算降级」这条规则收敛完了。指标跟着它走,
    就自动获得两个性质:
      1. 新增节点自动被统计,不会有人忘记加 `count_degrade`(DRY + 开闭原则)。
      2. **指标与 span 永远同源**。如果各节点自己埋,迟早出现
         「span 表里记了降级、degrade_total 没涨」这种对不上的情况,
         而排障时两个数据源互相矛盾比没有数据更糟 ——
         你不知道该信哪个,只能两边都不信。
    """
    span.set_payload(**_derive_payload(patch))
    degraded, reason = _derive_degradation(patch)
    if degraded:
        span.mark_degraded(reason)
        count_degrade(reason)
```

第二条理由是关键：**span 和指标从同一个判定里派生**，所以它们永远一致。如果各节点自己 `count_degrade`，迟早出现"span 表里记了降级、`degrade_total` 没涨"——而排障时两个数据源互相矛盾**比没有数据更糟**，因为你不知道该信哪个，只能两边都不信。

**`count_retrieval_failure` 留在节点里**，因为只有那里拿得到 `code`。`code` 来自 `error_code_of(exc)`，而 `exc` 只存在于 `except` 块的作用域里。汇聚点看到的是 patch 里的 `retrieve_failures`，那里面虽然也有 code，但已经是"聚合后的列表"——在节点里埋能保证**每次失败一个样本**，在汇聚点埋只能得到"这次有几条失败"。

两个位置对应两个粒度，这也是 Q3 追问 1 里那个交叉查询能成立的前提。

**追问链**：

> **追问 1：为什么在 `add_node` 的入口包一层，而不是在每个节点里写计时？**
>
> ```python
> # app/agent/rag_v2/instrumentation.py:3
> ## 为什么在这里包，而不是在每个节点里写计时代码
> #
> # 节点有五个（rewrite / retrieve_each / dedup / generate / validate_answer），
> # 在每个节点体内写 `t0 = time.perf_counter()` 是五份重复代码，
> # 而且新增节点时一定会有人忘记加（DRY）。
> #
> # 在 `graph.add_node` 的入口包一层，覆盖面是「所有注册进图的节点」，
> # 漏不掉。节点本身的代码一行不用改 —— 它们仍然是纯粹的 `state -> patch`，
> # 不知道 span 的存在。
> ```
>
> 关键是**覆盖面的定义方式**：包在注册点，覆盖面是"所有注册进图的节点"，这是一个**结构上封闭**的集合。而"在每个节点里写"的覆盖面是"我记得改的那些节点"，是一个开放集合，会随时间漏。
>
> 这也是 SOLID 里的 O：对扩展开放（加节点自动被埋点），对修改关闭（不用改节点实现）。

> **追问 2：`_derive_payload` 为什么只认几个已知的键？把整个 patch 序列化进去不是信息更全？**
>
> ```python
> # app/agent/rag_v2/instrumentation.py:39
> # 只认已知的几个键，其余忽略 —— span payload 是给人看的摘要，
> # 不是 state 的全量镜像。把整个 patch 序列化进去，
> # 等于把 6 篇文档正文抄进 span 表，那是在制造第四份副本。
> ```
>
> "第四份副本"是实指：文档正文已经在 Milvus（原始）、在 state（本次运行）、在 `ChatRunTrace`（业务留存）里各有一份，span 表再存一份是第四份。而 span 表是按节点行数增长的（一次请求 8 行），存正文会让它比业务表还大。
>
> 所以 payload 里全是**计数和分数**：`doc_count`、`sub_query_count`、`answer_length`、`coverage_score`。这是有意的信息损失——**观测数据要能回答"形状对不对"，不需要能重建内容。**

> **追问 3：`validation` 里为什么 `blocked` 和 `validated` 两个都要记？**
>
> ```python
> # app/agent/rag_v2/instrumentation.py:77
> # 质检的三个关键判定：分数 + 是否拦截 + 是否真的校验过。
> # blocked 和 validated 必须都记：前者是「过没过」，
> # 后者是「有没有验」，质检器自己挂掉时两者含义完全不同。
> ```
>
> 因为 `blocked=False` 有两个完全不同的含义：**验过了，通过了**，或者**质检器自己挂了，没验**。只记 `blocked` 的话，质检失效会伪装成"质检全部通过"——一个越坏越好看的指标（和 Q6 追问 1 里"只记成功调用的 P99"是同一类陷阱）。
>
> 加上 `validated` 之后，`validated=False` 就是质检失效的直接证据。这是第 25 篇 `RetrievalStatus` 三态那条设计（消灭静默返回空列表）在质检环节的同形应用：**「没做」和「做了但结果为否」必须能区分。**

**拓展**：

`_derive_payload` 的"只认已知键"有个逃生舱：节点可以在 patch 里塞 `_span` 字段补自己专属的计数，埋点层 `payload.update(hint)` 之后再把这个键摘掉。

这个设计的取舍写在模块文档里："记的东西是通用的，不是每个节点最想记的"。接受这个代价是因为**通用规则的覆盖面是自动的，专属规则的覆盖面要靠人维护**。`_span` 逃生舱的存在让"确实需要专属指标"这种情况有路可走，但走这条路是显式的、可见的——比让每个节点都自己决定记什么要好。

### Q12. `_strip_hint` 是干什么的？为什么要把 `_span` 摘掉？

**考点**：一个小函数，但它体现的是"内部约定不该泄漏成对外契约"。

**标准回答**：

`_span` 是埋点层和节点之间的**内部约定**，用于节点补充专属计数。摘掉它是因为不摘会泄漏到对外可见的地方：

```python
# app/agent/rag_v2/instrumentation.py:173
def _strip_hint(patch: Any) -> Any:
    """把 `_span` 提示键从 patch 里摘掉，不让它进入图状态。

    RAGState 是 TypedDict(total=False)，多塞一个未声明的键不会报错，
    但会跟着 state 一路传下去，最终出现在 astream 的快照里 ——
    埋点的内部约定不该泄漏成对外可见的状态字段。
    """
    if isinstance(patch, dict) and _SPAN_HINT_KEY in patch:
        return {key: value for key, value in patch.items() if key != _SPAN_HINT_KEY}
    return patch
```

链条是这样的：`TypedDict(total=False)` 不校验未声明的键 → `_span` 会被 reducer 合进 state → state 通过 `astream(stream_mode="values")` 吐出完整快照 → SSE 把快照发给前端。于是一个埋点内部字段变成了 **API 的一部分**。

而 API 的一部分意味着：前端可能开始读它，然后它就不能改了。**没人决定过要暴露它，它只是漏出去了——这是最糟的 API 演进方式。**

用下划线前缀 + 埋点层负责剔除，是两道防线：前缀表达"这是内部的"（约定），剔除保证它出不去（机制）。

**追问链**：

> **追问 1：返回新 dict 而不是 `del patch["_span"]`，为什么？**
>
> 因为 patch 是节点返回的对象，节点内部可能还持有它的引用。原地删除是在改别人的东西——第 24 篇讲的"节点契约是 `state -> patch`，不要原地修改"在这里同样适用，只是方向反了（这次是埋点层不要改节点的返回值）。
>
> 成本是一次浅拷贝，而且只在真的有 `_span` 时才拷（`if` 先判断）。**没有 hint 的常规路径零开销**，这是有意的——埋点层在热路径上，不该给不用这个功能的节点加成本。

> **追问 2：`_copy_identity` 为什么不用 `functools.wraps`？**
>
> ```python
> # app/agent/rag_v2/instrumentation.py:185
> # 不用 `functools.wraps`：它会连 `__wrapped__` 一起设上，
> # 而 LangGraph 在某些版本里会顺着 `__wrapped__` 去取原函数签名，
> # 从而绕过包装。只复制展示用的两个属性，够了也更安全。
> ```
>
> `functools.wraps` 会设 `__wrapped__` 指向原函数，而这是 Python 生态里"透过包装看原件"的标准协议——`inspect.signature` 就会顺着它走。LangGraph 在某些版本里会用这个协议取节点签名，结果是**它拿到了原函数并直接调用，完全绕过我的包装**。
>
> 这个故障的形态特别恶劣：**没有任何报错，只是 span 表里少了这个节点。** 你会以为这个节点很快（没有耗时记录），或者以为埋点漏了配置。
>
> 所以只复制 `__name__` 和 `__doc__`——那两个是给人看的（日志、图可视化里显示节点名），复制它们没有副作用。**用 `functools.wraps` 是默认正确的，除非包装本身不希望被穿透。**

> **追问 3：为什么要分同步和异步两个包装器？**
>
> ```python
> # app/agent/rag_v2/instrumentation.py:123
> # 同时支持同步节点（dedup）与异步节点（其余四个）：
> # `inspect.iscoroutinefunction` 判一次，各自返回对应的包装器。
> # 不能只写 async 版本 —— 那会把同步节点的返回值变成协程，
> # LangGraph 拿到一个没 await 的协程，图会直接崩。
> ```
>
> 如果只写 `async def async_wrapper`，包装一个同步节点（`dedup`）之后，调用它返回的是**协程对象**而不是 patch。LangGraph 拿这个协程去喂 reducer，`operator.add` 就会试图把 list 和 coroutine 相加，报 `TypeError: unsupported operand type(s) for +: 'list' and 'coroutine'`。
>
> 这个报错的位置离病因很远——它出现在 reducer 里，而病根在包装器。**"报错位置离病因远"是这类透明包装陷阱的共同特征**，也是为什么这两处（`__wrapped__` 和 sync/async）都值得在代码里留注释：它们不是防御性编程，是防"下一个人花两小时才找到原因"。

**拓展**：

`_SPAN_HINT_KEY = "_span"` 这个约定还缺一层保护：**没有任何机制阻止节点声明一个叫 `_span` 的正式状态字段**。现在靠的是"下划线前缀表示内部"这个 Python 惯例，而惯例不是强制。

更强的做法是把 hint 从 patch 里挪出去——让节点通过 ContextVar 或者显式的 span 句柄来补充 payload，而不是塞进返回值。这样它在物理上不可能污染 state。没这么做是因为 ContextVar 方案要求节点知道 span 的存在，破坏了"节点不知道埋点"这条更重要的性质。**两个都想要的话得引入依赖注入，成本超过收益。**

### Q13. 为什么 `_derive_degradation` 要看 patch，而不是只看有没有抛异常？

**考点**：这题把第 25 篇的"节点从不抛异常"和本篇的埋点连了起来。答不出来说明没意识到降级设计会反过来废掉观测。

**标准回答**：

因为**本项目的节点是刻意不抛异常的**，只按异常判定会得到一组恒为 0 的指标。

```python
# app/agent/rag_v2/instrumentation.py:92
def _derive_degradation(patch: Any) -> tuple[bool, str | None]:
    """判断这次执行算不算降级，以及降级原因。

    为什么要看 patch 而不只看有没有抛异常：
    项目里的节点是**刻意不抛**的 —— retrieve_each 兜住检索异常、
    generate 兜住 LLM 异常，都返回一个「成功的」patch。
    只按异常判定的话，这些节点永远是 OK，
    检索失败率、LLM 失败率两个指标恒为 0，而故障是真实发生了的。
    """
```

链条是：为了可用性，节点吞掉异常并降级（第 24 篇 Q8）→ 于是从异常的角度看，每个节点都成功了 → 于是 span 全是 OK、`degrade_total` 恒为 0 → **一个看起来永远健康的系统，而用户在收降级答案。**

所以判定必须从**返回值**里读："有 `degrade_reasons` 就是降级"、"有 `retrieve_failures` 就是没干成活"。这也是 `SpanStatus` 需要第三个值 `DEGRADED` 的原因——OK/ERROR 两态装不下"没抛异常但也没干成活"。

一般结论：**降级设计和可观测性设计是耦合的，不能只做一半。** 你一旦决定让节点吞异常，就同时欠下了"观测必须改成看返回值"这笔债。只做前半部分的系统，故障时最安静。

**追问链**：

> **追问 1：那节点如果真的抛了异常呢？**
>
> `span_scope.__exit__` 会接住，记 `ERROR` 加 `error_code`，然后**原样放行**：
>
> ```python
> # app/core/span_context.py:143
> def __exit__(self, exc_type, exc, tb) -> bool:
>     duration_ms = int((time.perf_counter() - self._perf_start) * 1000)
>     if exc is not None:
>         self._status = SpanStatus.ERROR
>         self._payload["error_code"] = error_code_of(exc)
>         self._payload["error"] = str(exc)[:500]
>     with suppress(Exception):  # 观测失败不能影响业务
>         record_span(...)
>     return False  # 不吞异常
> ```
>
> `return False` 那行是关键：`__exit__` 返回真值会**吞掉异常**。这里必须返回 False，而且注释写明了原因——这是一行"看起来可以删、删了就出大事"的代码。
>
> 所以三种状态各有来源：OK（正常返回）、DEGRADED（返回值里有降级痕迹）、ERROR（真抛了）。三态覆盖完整。

> **追问 2：`degrade_reasons` 是个 list，为什么只取第一个？**
>
> ```python
> reasons = patch.get("degrade_reasons")
> if reasons:
>     first = str(reasons[0]) if isinstance(reasons, list) and reasons else None
>     return True, first
> ```
>
> 因为 `count_degrade` 的 label 只能是一个值——指标的一次 `inc()` 对应一个 label 组合。多原因同时成立时（第 25 篇 Q9 追问里提过：`partial_retrieval` 和 `evidence_insufficient` 经常并存），只能记一个。
>
> 取第一个的代价是**丢失了并发原因的信息**。可选的替代方案是给每个原因都 `inc()` 一次，那样 `degrade_total` 的总和会大于降级请求数——指标语义从"降级次数"变成"降级原因出现次数"。两种都能自圆其说，但第二种会让 Q10 里那条降级率查询（除以请求数）算出大于 1 的值。
>
> 我选了保持"一次降级一个计数"，把多原因的完整信息留给 span payload（那里可以存 list）。**指标要单值以保持可算术性，明细留给 span。**

> **追问 3：`str(exc)[:500]` 的截断会不会丢关键信息？**
>
> 会丢，但这是有意的。完整报文在日志里有一份（异常向上抛之后被 exception handler 记了），span 里存的是"排障时够用的摘要"。
>
> 500 这个数是估的：够装下一条典型的连接错误或校验失败，装不下一整个 SQL 或 prompt。选一个上界比不选重要——**观测数据的单条大小必须有上界**，否则一个异常消息里带了整个 prompt 的场景就能让 span 表膨胀几个数量级，而 span 表是随业务数据长期留存的。

**拓展**：

三态之外还缺一个 `CANCELLED`。总预算超时（第 25 篇 Q19）会取消正在跑的节点，`asyncio.CancelledError` 继承 `BaseException`，能穿过 `except Exception`，所以它会走到 `__exit__` 的 `exc is not None` 分支，被记成 **ERROR**。

结果是"generate 花了 85 秒把预算吃光"表现为"validate 节点报错"。真实的锅在 generate，报出来的是 validate。而这个误导会污染节点级失败率——一个慢节点会让它后面所有节点的健康度变差。

补法是在 `__exit__` 里先判 `exc_type is asyncio.CancelledError` 单独标 CANCELLED。这和第 25 篇熔断器里 `except asyncio.CancelledError: raise`（防止把取消记成下游失败）是**同一个问题在观测侧的镜像**：取消是我们自己的决定，不该记到被取消者头上。

### Q14. 埋点会不会影响性能？你量过吗？

**考点**：这题看你是否区分"热路径"和"冷路径"，以及有没有诚实地说"没量过"。

**标准回答**：

先说结论：**没有专门做过 benchmark**，但我能论证各处埋点的成本量级，并且设计时就把它压在了可忽略的范围。

分三类看：

**① 指标埋点：纳秒级，无 IO。** `Counter.inc()` 是一次 dict 查找（找 label 组合对应的子指标）加一次原子加。`Histogram.observe()` 多一个桶查找（线性扫 12 个边界）。这些和它们观测的对象比——一次 LLM 调用是**秒**级——差了九个数量级。

**② span 收集：一次 list append。** 这是"内存收集 + 一次落盘"这个设计的直接收益（Q19 详述）：跑的时候几乎零成本，落盘集中到一次。

**③ 日志：最贵，所以做了两件事。** 文件 handler 开 `enqueue=True` 走独立线程异步写，避免 IO 阻塞请求；生产环境 `level="INFO"`（`debug` 关闭时），把 `logger.debug` 全部编译掉——loguru 在 level 不满足时会提前返回，不会走格式化。

真正需要小心的不是这三个，是**埋点代码本身的复杂度**。`_derive_payload` 在每个节点返回时跑一遍，它做的是几次 `isinstance` 和 `len()`——如果有人在这里加一个 `json.dumps(patch)` 来"记得更全"，成本会从纳秒跳到毫秒，而且是在每个节点上。这就是 Q11 追问 2 里"只认已知键"的性能侧理由。

**追问链**：

> **追问 1：`observe_llm_call` 是个上下文管理器，`with` 语句本身有成本吗？**
>
> 有，但可以忽略：一次 `__enter__`/`__exit__` 调用，加上 `contextmanager` 装饰的生成器多一层 `next()`。合起来微秒级以下，而它包裹的是秒级的 LLM 调用。
>
> 抽成上下文管理器的理由是正确性而不是性能：
>
> ```python
> # app/core/metrics.py:139
> # 为什么抽成上下文管理器:四个 LLM 调用点(rewrite / generate /
> # validate_answer / first_response)都需要计时,各写一遍
> # `t0 = perf_counter()` ... `observe(perf_counter() - t0)` 是四份重复,
> # 而且异常路径上那一行极容易漏 —— 漏掉的恰好是超时那次,
> # 也就是唯一真正需要被记下来的那次(DRY)。
> ```
>
> 手写计时的失败模式是**只在成功路径记**——因为 `except` 里那行最容易忘。而漏掉的恰好是超时那次，也就是唯一真正需要被记下来的那次（Q6 追问 1 那个"越坏越好看的 P99"）。`try/finally` 把这件事变成结构保证。

> **追问 2：span 落盘是同步的吗？会不会拖慢响应？**
>
> 是同步的，在图跑完之后、返回响应之前，一次 `db.add_all` + `commit`。所以它确实在响应路径上，成本是一次数据库往返（本地 MySQL 几毫秒）。
>
> 对比它替代的方案——8 个节点各自 commit 一次就是 8 次往返，这正是 AIOps 时间线犯过的错（模块文档里写着）。所以现在的做法已经是优化后的形态。
>
> 要彻底从响应路径上移下来，得改成"塞进队列，后台 worker 落盘"。没做的原因是：多引入一个失败点（队列），换来几毫秒。而且第 4 题那条原则已经保证了 flush 失败不影响主流程，所以**最坏情况是响应慢几毫秒，不是响应失败**。这个风险敞口小到不值得引入队列。

> **追问 3：既然没量过，怎么保证不出问题？**
>
> 靠三条纪律，而不是靠测量：
>
> 一，**埋点不做 IO**（除了集中的那一次 flush 和异步的日志）。
> 二，**埋点不做序列化**（`_derive_payload` 只取计数，不 dumps）。
> 三，**埋点不改变控制流**（`try/finally` 而不是 `try/except`，`return False` 不吞异常）。
>
> 这三条守住，性能问题在结构上就不会出现。真要出问题，最可能的来源是**基数爆炸**（Q5）——那不是 CPU 问题，是 Prometheus 侧的内存问题，而它的表现是 Prometheus 挂掉而不是我们的服务变慢。
>
> **诚实的说法是"我论证了成本量级，没有 benchmark 数据"**，而不是含糊地说"性能没问题"。

**拓展**：

真要量的话，方法是明确的：用 `pytest-benchmark` 对 `instrument_node` 包装前后的空节点做对比，隔离出纯埋点开销。这个测试的价值不在于知道当前数字，而在于**它能拦住将来某次"顺手加个 dumps"的改动**——性能回归测试的主要作用是防退化，不是给出绝对值。

没做是因为当前的性能瓶颈明确在 LLM 调用（秒级）和检索（百毫秒级），埋点的纳秒级开销不在优化视野里。**在瓶颈明确的系统里，为非瓶颈写性能测试是把维护成本花在不会发生的问题上。** 但如果哪天节点数量涨到几十个、或者出现高 QPS 的轻量接口，这个判断就要重新做。

## 四、结构化日志

### Q15. 你的日志是怎么加上 `request_id` 的？为什么不在每个调用点自己 bind？

**考点**：切面思维。这题的答案里有一个 loguru 的具体 API 陷阱，答出来说明真写过而不是抄的。

**标准回答**：

用 `logger.configure(patcher=...)` 装一个全局切面，给每条日志记录补上 `extra["rid"]`，格式串里用 `{extra[rid]}` 输出。**业务代码一行都不用改。**

```python
# app/utils/logger.py:30
def _patch_request_id(record: dict) -> None:
    """给每条日志补上 rid 字段。

    用 setdefault 而不是直接赋值，有两个原因：
    1. 保留调用方的显式意图 —— `logger.bind(rid="job-123")` 不该被覆盖。
    2. 防 KeyError —— 格式串里写了 `{extra[rid]}`，一旦某条记录缺这个键，
       loguru 格式化时会抛 KeyError，而**日志系统自身抛异常是最糟的故障**：
       它会掩盖真正的错误。setdefault 保证这个键永远存在。
    """
    record["extra"].setdefault("rid", get_request_id() or NO_REQUEST_ID)
```

不让每个调用点自己 bind 的理由是覆盖面：

```python
# app/utils/logger.py:12
# 为什么必须用 patch 而不是让每个调用点自己 bind：
# 项目里有数百处 logger 调用，还有 langchain / uvicorn 等第三方库的日志。
# patch 是唯一的「一处实现，全局生效」的切面（DRY）。
```

数百处调用点，加上**第三方库的日志**——langchain、uvicorn 的日志我根本没法去改它们的调用点。patcher 是唯一能覆盖到它们的位置。

这和 Q11 里 `instrument_node` 包在注册点是同一个思路：**把横切关注点挂在唯一的必经之处，覆盖面就从"我记得改的"变成"结构上封闭的"。**

**追问链**：

> **追问 1：`patcher` 和 `logger.patch()` 有什么区别？**
>
> 这是个真实的坑，我在注释里专门写了：
>
> ```python
> # app/utils/logger.py:54
> # 注册 patcher：必须在 add() 之前，否则已注册的 handler 拿不到 rid。
> # 注意关键字是 patcher（不是 patch）—— loguru 里 `logger.patch()` 是返回
> # 新 logger 的方法，而 `configure(patcher=...)` 才是给全局装切面。
> ```
>
> 两个陷阱叠在一起：
>
> 一，**名字近似**。`logger.patch(fn)` 返回一个**新的** logger 对象，原 logger 不受影响——写成 `logger.patch(_patch_request_id)` 而不接收返回值，等于什么都没做，而且不报错。`configure(patcher=...)` 才是给全局装。
>
> 二，**顺序敏感**。`configure(patcher=...)` 必须在 `add()` 之前，否则已注册的 handler 拿不到 rid，格式化时直接 `KeyError`。
>
> 两个都是"不报错但不生效"或"报错但原因在别处"的形态，所以值得在代码里留注释。

> **追问 2：为什么用 `setdefault` 而不是直接赋值？**
>
> 两个理由，注释里都写了，第一个是设计意图，第二个是防御：
>
> **保留调用方的显式意图**：`logger.bind(rid="job-123")` 是调用方明确要求用这个 rid，切面不该覆盖它。RQ worker 里就用得上——那边没有 HTTP 请求上下文，可以显式 bind 一个 job 标识。
>
> **防 KeyError**：格式串里写了 `{extra[rid]}`，缺这个键 loguru 会抛。而**日志系统自身抛异常是最糟的故障**——你在排查一个问题，日志系统在这个问题上炸了，于是你看不到问题。这是 Q4 那条"观测失败不能影响主流程"在日志侧最尖锐的形态：其他观测失败是少一条数据，日志系统失败是**遮住真正的错误**。

> **追问 3：`get_request_id() or NO_REQUEST_ID` 那个兜底为什么用 `"-"`？**
>
> 因为日志是**给人按列读的文本**。用空串或 `None` 会让这一列时宽时窄，`grep`/`awk` 按列切分会错位。`"-"` 是日志领域约定俗成的占位符（Nginx access log 就这么干），宽度稳定、肉眼可辨。
>
> 而同一个"没有值"进数据库时用的是 `NULL`——`get_request_id_or_none()` 专门做这个转换。理由在第 25 篇 Q23 讲过：`"-"` 进数据库会变成一个真实值，`GROUP BY request_id` 时所有无上下文的行会聚成一个虚假的"请求 `-`"分桶。**同一个语义在两个消费者那里要用不同的表示，这个判断有一处实现（`get_request_id_or_none`）而不是散在各个写库点。**

**拓展**：

`rid` 在格式串里的位置也是设计过的：

```python
# app/utils/logger.py:60
# rid 放在 level 之后、模块之前：一眼能看到「这条属于哪个请求」
```

排障时的实际动作是**竖着扫一列**找同一个 rid 的行。放在固定的第三列，眼睛不用移动；放在行尾就得跟着 message 长度左右扫。

这属于"给人设计的可观测性"——和 Q7 里"状态值按严重程度编号方便写告警"是同一类考虑，只是消费者从 PromQL 换成了人眼。**观测数据的形状要迁就消费者的读取方式，而人眼的读取方式是"固定位置纵向扫描"。**

### Q16. 为什么控制台输出彩色文本，文件输出 JSON？两套格式不冗余吗？

**考点**：能不能说清"两个不同的消费者"。答"为了好看"就废了。

**标准回答**：

不冗余，因为**读它们的是两类完全不同的消费者，需求互相冲突**。

```python
# app/utils/logger.py:16
# 2. **文件输出 JSON 化**
#    控制台保留彩色文本给人看，文件用 `serialize=True` 输出 JSON 给机器看。
#    纯文本日志要接 Loki/ELK 必须先写正则解析，字段一变解析就崩；
#    JSON 行天然结构化，`rid` / `level` / `module` 直接就是可查询字段。
```

**控制台的消费者是开发者的眼睛。** 需求是信息密度和扫读速度：颜色区分 level（ERROR 一眼跳出来）、固定列宽便于纵向扫描、单行短到不换行。JSON 在终端里是灾难——一条日志占满整屏，肉眼没法批量扫。

**文件的消费者是日志系统。** 需求是可解析：Loki/ELK 要按 `rid` 过滤、按 `level` 聚合。纯文本必须先写正则,而正则和格式串是**两处需要同步的定义**——格式串里加一个字段，正则不改就全崩，而且是静默崩（解析失败的行被丢弃或塞进 `_grokparsefailure`）。JSON 行天然结构化，加字段不影响已有查询。

所以这不是"一份数据两种格式"，是**两个不同用途的输出**。真正冗余的做法是只留一种：只有彩色文本，接日志系统就得写正则；只有 JSON，本地开发就没法读日志。

**追问链**：

> **追问 1：`serialize=True` 的时候 `format` 还起作用吗？**
>
> 部分起作用，这里有个容易踩的点，注释里写了：
>
> ```python
> # app/utils/logger.py:89
> # serialize=True 输出 JSON 行，record.extra.rid 可直接被日志系统索引。
> # 注意：serialize 时 format 不参与最终输出（loguru 输出完整 record 的 JSON），
> # 但仍保留 format 以便 message 字段渲染一致。
> ```
>
> loguru 在 `serialize=True` 时输出的是**整个 record 的 JSON**，`format` 不决定最终结构。所以有人会以为可以删掉 `format`——但保留 `format="{message}"` 能让 `message` 字段的渲染保持一致。这属于"看起来是死代码，实际有作用"的配置，值得留注释。

> **追问 2：`enqueue=True` 是干什么的？有什么代价？**
>
> 让文件写入走独立线程，避免 IO 阻塞请求线程。收益明确：日志写盘不进响应路径。
>
> 代价有两条，我知道但接受：一是**进程崩溃时队列里未落盘的日志会丢**——而崩溃前的最后几条日志往往是最重要的。二是多一个线程和一个队列，多一份内存。
>
> 第一条的缓解是关键日志同时进了控制台（同步的，`sys.stdout` 那个 handler 没开 enqueue），所以进程崩溃时控制台那份还在。这也解释了为什么两个 handler 的配置不一样——**不是随手写的，是各自按自己的失败模式配的。**

> **追问 3：`retention="30 days"` 这个数怎么定的？**
>
> ```python
> # app/utils/logger.py:80
> # 保留 30 天：故障 case 常常几周后才被复盘追问，7 天太短，
> # 等真要查的时候日志已经被删了。压缩后单日体积很小，30 天完全可接受。
> ```
>
> 定它的依据是**日志被查询的真实时间分布**，不是存储成本。故障复盘、客户回访、季度总结这些场景都是事后几周才发生的。7 天（很多项目的默认值）的问题是：日常排障用不到那么久（当天就查完了），而真正需要翻旧日志的场景又都超过 7 天——**7 天恰好落在两个需求之间，两边都不满足。**
>
> 30 天 + zip 压缩的成本很低。这是个"成本低到不需要精算、按需求上界取值"的参数。

**拓展**：

现在缺的一环是**日志和 span 的关联查询**。两边都有 `request_id`，理论上能关联，但实际操作是"在日志系统里查 rid，再去数据库查 span"——两个工具、手工拼接。

补法是在 span 落盘时把 `trace_id` 也写进日志一条 INFO，这样从日志能直接跳到 trace。更彻底的做法是接 OpenTelemetry，让 trace_id 进日志字段（`trace_id` 是 OTel 日志规范里的标准字段），然后在 Grafana 里点日志直接跳 trace。

没做的原因是当前排障量小，手工拼接可以接受。但这是**可观测性"最后一公里"的典型缺口**：三根支柱各自都建好了，支柱之间的跳转还得靠人。

### Q17. 生产环境的日志级别怎么控制？`DEBUG` 日志会不会拖慢系统？

**考点**：日志成本意识，以及 level 过滤发生在什么时机。

**标准回答**：

控制台的 level 跟着 `config.debug` 走，文件固定 INFO：

```python
# app/utils/logger.py:70
level="DEBUG" if config.debug else "INFO",   # 控制台
...
level="INFO",                                 # 文件
```

**`DEBUG` 日志在生产环境几乎零成本**，因为 loguru 在 level 不满足时会提前返回，**不会执行格式化**。所以 `logger.debug(f"...")` 里的 f-string——

等一下，这里有个真实的坑：**f-string 是在传参前就求值的**。`logger.debug(f"检索结果: {docs}")` 里的 f-string 无论 level 如何都会被求值，只是求值后的字符串被丢弃。如果 `docs` 是个大对象、`__repr__` 很贵，那这个成本是实实在在花掉的。

loguru 的解法是**惰性格式化**：`logger.debug("检索结果: {}", docs)`，参数原样传，只在真要输出时才格式化。项目里大部分调用点用的是 f-string（历史写法），所以这个优化没有全面落实——**这是一个我知道但没改的点**，因为 `logger.debug` 的调用点不多，且参数都是小对象（计数、id），实测没有可观测的影响。

真正需要小心的是 `logger.debug` 里包裹**昂贵计算**的情况，比如 `logger.debug(f"state: {json.dumps(state, ensure_ascii=False)}")`——这行在生产环境会白跑一次 `json.dumps`，而 state 里有 6 篇文档正文。这类写法必须改成惰性形式或用 `if config.debug:` 包住。

**追问链**：

> **追问 1：为什么文件的 level 固定 INFO，不跟着 debug 走？**
>
> 因为文件日志的用途是**事后排障**，而 DEBUG 级别的量级会让 30 天保留期不可行——DEBUG 通常比 INFO 多一到两个数量级。
>
> 更重要的是信噪比：事后翻日志找的是"发生了什么"，DEBUG 里大量的中间状态会把关键行淹掉。而实时调试时开发者看的是控制台，那里有 DEBUG。**两个 handler 的 level 不同，正是因为它们服务不同的时间尺度**：控制台是"现在"，文件是"事后"。

> **追问 2：`diagnose` 那个参数是什么？为什么控制台跟 debug 走、文件固定 True？**
>
> ```python
> backtrace=True,           # 显示完整异常栈信息
> diagnose=config.debug,    # 控制台：Debug 模式下显示变量值
> ...
> diagnose=True,            # 文件：显示变量值，便于调试
> ```
>
> `diagnose=True` 让 loguru 在异常栈里打印**每一帧的局部变量值**。排障时极有用，但它会**打印出变量里的敏感数据**——API key、用户输入、数据库连接串。
>
> 控制台跟 `config.debug` 走是对的：生产环境控制台日志经常被收集到共享的日志平台，变量值泄漏面大。
>
> 文件固定 `True` 这个选择我要标一下：它意味着**生产环境的日志文件里可能有 API key**（比如构造 LLM 客户端时抛异常，`api_key` 会在栈帧里）。文件在本机、权限受控，所以风险比控制台小，但这不是零风险——日志文件会被打包发给人排查。
>
> **更稳妥的配置是文件也跟 `config.debug` 走**，代价是生产环境的异常栈少了变量值。这是个我倾向于改的点，属于"当前配置有意识地偏向了排障便利，但安全侧的账没结清"。

> **追问 3：第三方库的日志怎么处理？langchain 那些 INFO 会不会很吵？**
>
> 会，而且我没做拦截。`logger.remove()` 只清掉 loguru 自己的 handler，第三方库用的是标准库 `logging`——它们的日志默认不经过 loguru，除非做 `InterceptHandler` 桥接。
>
> 当前状态是：第三方库的日志走标准库的默认配置（uvicorn 自己配了 handler，所以能看到访问日志），loguru 管我们自己的日志。两套并行，格式不统一，第三方库的日志**没有 rid**。
>
> 这是个真实缺口：langchain 报的错（比如重试、token 超限）不带 request_id，没法跟我们的日志关联。补法是标准的——装一个 `InterceptHandler` 把 `logging` 的记录转发给 loguru，这样 patcher 也会给它们补上 rid。没做是因为目前 langchain 的日志量小、且关键失败我们自己也记了一遍。

**拓展**：

日志级别的使用纪律比配置更重要，项目里的实际约定是：

- `ERROR`：需要人介入的失败。第 25 篇 Q13 讲过这个判据——**4xx 用 warning 不用 error**，因为客户端传错参数不该污染错误率告警。
- `WARNING`：降级了但兜住了。所有"失败但有兜底"的路径都在这一级——span 落盘失败、summary 生成失败、MCP 加载失败。
- `INFO`：状态变迁。请求开始/结束、任务入队/完成、熔断器开合。
- `DEBUG`：中间值。

这套纪律的价值在于**告警可以直接建在 level 上**：`ERROR` 数量突增就是要人看的事。如果 level 用得随意（把预期内的失败记成 ERROR），这条告警就会因为噪声太多而被关掉——**而被关掉的告警比没有告警更糟，因为它给了一种"我们有监控"的错觉。**

## 五、span 级追踪

### Q18. 你为什么要自己写 span，不直接用 OpenTelemetry？

**考点**：技术选型的成本收益，以及能不能说清自研版本的**边界**。

**标准回答**：

因为我需要的不是"分布式追踪"，是**一次 RAG 运行的节点耗时明细，能被业务接口查询**。这两件事的重叠只有一部分。

OTel 的核心价值是**跨服务传播 trace context**——服务 A 调 B 调 C，把三段拼成一条链路。而本项目是单进程：一次请求的全部工作都在一个 Python 进程里（Milvus 和模型服务是外部依赖，不是我们的服务）。**跨进程传播这个最大的收益，在这里用不上。**

而我需要的东西 OTel 给不了，或者说要额外做：

**span 要能被业务接口查。** `/api/aiops/trace/{trace_id}` 是产品功能——前端展示"这次诊断每一步花了多久"。OTel 的 span 进的是 Jaeger/Tempo，从业务接口查它得走另一套 API、另一套鉴权。而我的 span 在 MySQL 里，和 `ChatRunTrace` 同库，一次 join 就出来。

**span 要和业务数据同生命周期。** trace 记录随对话保留，span 是它的明细。用 OTel 的话 trace 在业务库、span 在追踪系统，两边的保留策略不同——追踪系统通常只留几天，而业务侧几周后还要复盘。**明细比主记录先过期，等于没有明细。**

成本侧：自研的实现是 `span_context.py` 209 行 + `instrumentation.py` 194 行，其中真正的机制部分（ContextVar 收集 + 一次 flush）不到一百行。引 OTel 要装 SDK、配 exporter、跑 collector、再接一个后端存储——**为了一个单进程应用的节点计时，多三个运行时组件。**

**追问链**：

> **追问 1：那如果以后拆成多个服务呢？**
>
> 那就该换成 OTel，而且触发信号很明确：**出现第二个我们自己写的、会被本服务调用的服务**。到那时"跨服务传播"从零收益变成核心收益，自研的部分就该退回到只做业务展示。
>
> 迁移路径也不难：`span_scope` 是一个上下文管理器接口，内部换成 `tracer.start_as_current_span()` 而调用点不动。这是把机制包在一个窄接口后面的好处——**换实现的成本取决于接口有多窄，不取决于实现有多复杂。**
>
> 现在就上 OTel 的问题不是"以后用不上"，是**以后的形态还不确定**：拆成什么样、用不用 service mesh（有的话 trace 是 mesh 层自动注入的）、后端选 Jaeger 还是 Tempo。现在选的这些，到时候大概率要重选一遍。

> **追问 2：自研版本相比 OTel 缺了什么？**
>
> 我列得出来，这比声称"够用了"更有说服力：
>
> **缺 span 的父子关系。** 我的 span 是一个**平铺的 list**，没有 parent_span_id。所以四条并行检索的 span 和 dedup 的 span 在结构上是平级的，看不出"这四条是 dedup 的上游"。展示时只能按时间排，不能画成火焰图。补它需要在 ContextVar 里再存一个"当前 span 栈"——不难，但当前的节点结构是扁平的五个节点，父子关系的信息量不大。
>
> **缺采样。** 全量记录。QPS 上去之后 span 表会成为写入热点。OTel 的 sampler 是现成的（头部采样、尾部采样），自研的话要自己写。当前 QPS 低，全量是可行的，而且**全量对排障更友好**——采样的坏处是"出问题那次恰好没采到"。
>
> **缺跨语言/跨库的自动埋点。** OTel 有 instrumentation 库，能自动给 requests、SQLAlchemy、redis 埋点。我的 span 只覆盖 LangGraph 节点——**数据库查询、Milvus 调用的耗时不在 span 里**，只能从节点总耗时里推断。这是当前最实际的缺口：一个 retrieve 节点花了 3 秒，我看不出是 Milvus 慢还是 BM25 慢。

> **追问 3：`trace_id` 和 `request_id` 是两个东西？**
>
> 是，而且区别值得说清：
>
> - `request_id`：一次 HTTP 请求的标识，在中间件生成，进日志、进响应头。**每个请求都有。**
> - `trace_id`：一次 RAG/诊断运行的标识，是 `ChatRunTrace` 表的主键，落库时生成。**只有跑了图的请求才有。**
>
> 关系是一对一或一对零（健康检查有 request_id 没 trace_id）。span 表里**两个都存**：
>
> ```python
> # app/core/span_context.py:177
> rows = [
>     ChatRunSpan(
>         trace_id=trace_id,
>         request_id=request_id,
>         ...
> ```
>
> 存两个的理由：`trace_id` 用于业务查询（前端按 trace 展示时间线），`request_id` 用于关联日志（从日志里的 rid 找到对应的 span）。**一个对内一个对外，缺哪个都会断一条链路。**

**拓展**：

"要不要用 OTel"这个问题的正确提法是**"我要解决的问题里，跨服务传播占多大比重"**。占大头就用，占零头就自研。而这个比重是由架构决定的，不是由技术潮流决定的。

同样的判断在这个项目里出现过三次，结论各不相同：熔断器自研（六十行，没有 pybreaker 的坑）、指标用 `prometheus_client` + `prometheus-fastapi-instrumentator`（路由模板那个坑值得引库，Q5 追问 1）、追踪自研（跨进程收益为零）。三次都是同一个方法：**先找出"这个库唯一无法被替代的价值"，再看那个价值在我的场景里值多少。**

### Q19. span 为什么是"内存收集 + 一次落盘"，不让节点直接写库？

**考点**：这题有三个独立的硬约束，能说出两个就算好，三个说明真的想过。

**标准回答**：

三个硬伤，任何一个都足以否掉"节点直接写库"：

```python
# app/core/span_context.py:5
1. **拿不到 trace_id。** `ChatRunTrace` 的主键是**跑完落库时**才生成的。
   节点执行期间那行记录还不存在，span 无处挂靠。
2. **节点拿不到 Session。** LangGraph 的节点签名是 `state -> patch`，
   要塞一个 db session 进去，就得让它穿过 state 或改所有节点的签名 ——
   而 state 是要被序列化的，往里塞 Session 是自找麻烦。
3. **写库次数爆炸。** 一次请求 8 个节点（含 4 条并行检索），
   每个节点各 commit 一次就是 8 次往返。这正是 AIOps 时间线犯过的错。
```

第一个是**时序**问题：span 要挂在 trace 上，而 trace 的 id 在图跑完之后才有。节点执行时那行记录不存在。

第二个是**架构**问题：往 state 里塞 Session 违反第 24 篇 Q11 那条——state 必须可序列化、Session 是请求生命周期的、SQLAlchemy Session 跨线程不安全。而节点会在 `to_thread` 里跑。

第三个是**性能**问题：8 次数据库往返换 1 次。注释里那句"这正是 AIOps 时间线犯过的错"是实话——先做的那套时间线就是每步写一次，改这套时才没重犯。

所以形态是：跑的时候只 `list.append`（纳秒级），跑完拿到 trace_id 后一次 `bulk` 写入 + 一次 commit。

**追问链**：

> **追问 1：内存收集靠什么实现？并行分支怎么共享同一个 list？**
>
> ContextVar，而这里有一个必须精确理解的语义（第 24 篇 Q25 详述过，这里是它的落地）：
>
> ```python
> # app/core/span_context.py:18
> `asyncio.to_thread` 和 LangGraph 内部 spawn 任务时，都会
> `contextvars.copy_context()`。拷贝的是**变量到对象的绑定关系**，
> 不是对象本身 —— 父子上下文里的 `_SPAN_COLLECTOR` 指向**同一个 list**。
>
> 推论有两条，方向相反，必须都记住：
> - 子上下文里 `list.append(...)` → 父上下文**看得见**（同一个对象被改了）✓
> - 子上下文里 `_SPAN_COLLECTOR.set(...)` → 父上下文**看不见**（只改了子的绑定）✗
> ```
>
> 于是纪律是：**只在请求入口 set 一次，之后全程只 append。** `record_span` 里绝不调 `.set()`。
>
> 违反的后果是"本地单测能过、并发下才丢"——串行跑的时候没有 fan-out，`set` 也能工作；四条并行检索一上来，每条在自己的子上下文里 `set` 一个新 list，父上下文那个 list 空着，**四条检索的 span 全部丢失**。而这是最需要 span 的场景（诊断哪条分支慢/失败）。

> **追问 2：`collected_spans()` 为什么返回副本？**
>
> ```python
> def collected_spans() -> list[dict[str, Any]]:
>     """取本次已收集的 span 明细（副本，防止调用方误改内部状态）。"""
>     spans = _SPAN_COLLECTOR.get()
>     return list(spans) if spans else []
> ```
>
> 因为返回内部 list 的引用，调用方一个 `.clear()` 或 `.pop()` 就能改掉收集器的状态，而这个修改会**跨上下文可见**（就是上一问那个"同一个对象"的另一面）。
>
> 这是"共享可变对象"的固有风险：ContextVar 拷贝语义让 append 能跨上下文工作，代价就是任何对这个 list 的修改都跨上下文生效。返回副本把这个风险封在模块内部——**能力和风险来自同一个机制，所以要在出口处收窄。**

> **追问 3：`reset_span_collection` 为什么用 `reset(token)`？**
>
> ```python
> def reset_span_collection(token: Token) -> None:
>     """还原到收集开始前的状态。
>
>     用 reset(token) 而不是 set(None)：嵌套调用时后者会把外层的收集器也清掉。
>     """
>     with suppress(Exception):
>         _SPAN_COLLECTOR.reset(token)
> ```
>
> 和第 25 篇 Q23 追问 2 里 `request_id` 的理由完全一样：`reset(token)` 恢复"进入前的值"，`set(None)` 是无条件覆盖。嵌套场景下后者会把外层的收集器清掉，外层后续的 span 全部丢失。
>
> 外面那个 `with suppress(Exception)` 也是有意的——`reset` 在跨上下文调用时会抛 `ValueError`（token 属于另一个 Context）。清理路径上抛异常会盖掉主流程的异常，所以吞掉。**这是 Q4 那条原则在清理路径上的应用。**

**拓展**：

这个"收集 + 一次 flush"的模式还有个没利用的好处：**flush 之前 span 在内存里，可以被读取和加工**。比如可以在落盘前算出"最慢的节点是哪个"写进 trace 记录，这样列表页不用 join span 表就能显示慢点。

没做是因为没有这个查询需求。但它说明一件事：把观测数据先收集在内存里，比逐条直写多了一个**加工窗口**。逐条直写的架构里，任何跨 span 的计算都得事后从数据库捞回来算。

### Q20. `span_scope` 为什么写成类，而不是 `@contextmanager` 装饰的生成器？

**考点**：细节题，看是否理解"with 体内需要回调"这个需求。

**标准回答**：

因为要**暴露方法给 `with` 体内调用**：

```python
# app/core/span_context.py:111
class span_scope:
    """给一段代码计时并在退出时记一条 span。

    用类而不是 `@contextmanager` 装饰的生成器，是因为要暴露
    `set_payload` / `mark_degraded` 给 with 体内调用 ——
    节点跑完才知道自己召回了几条、有没有降级。
    """
```

`@contextmanager` 的生成器只能 `yield` 一个值出去，之后 with 体和生成器就没有交互通道了。而这里的需求是**双向**的：进入时开始计时，退出时记录，但**中间**要接收 with 体给的信息。

用法是这样的（`instrumentation.py:130`）：

```python
with span_scope(node) as span:
    patch = await func(*args, **kwargs)
    _apply(span, patch)      # ← 这里回填 payload 和降级状态
    return _strip_hint(patch)
```

`_apply` 调 `span.set_payload(...)` 和 `span.mark_degraded(...)`。信息在**节点执行完之后**才有——召回了几条、有没有降级，都得等 patch 出来。所以必须有一个能被回调的对象。

对比 `observe_llm_call`（`metrics.py:136`）就是 `@contextmanager`——因为它只需要计时，不需要接收信息：

```python
@contextmanager
def observe_llm_call(node: str) -> Iterator[None]:
    start = time.perf_counter()
    try:
        yield
    finally:
        observe_llm_duration(node, time.perf_counter() - start)
```

**两种写法在同一个项目里并存，判据是"with 体需不需要往回传信息"。**

**追问链**：

> **追问 1：`__exit__` 返回 `False` 是必须的吗？**
>
> 必须，而且这是最容易出事的一行。`__exit__` 返回真值会**吞掉异常**——with 体里抛的异常就地消失，调用方以为一切正常。
>
> ```python
> return False  # 不吞异常
> ```
>
> Python 里 `def __exit__(...)` 不写 return 语句时返回 `None`（假值），行为正确。但显式写 `return False` 加注释有价值：它告诉后来人"这个返回值是被考虑过的"，防止有人为了"顺手让异常不打断流程"改成 `True`。
>
> 一般原则是 Q4 那条的具体化：**观测设施是旁路，不改变控制流。** `try/finally` 而不是 `try/except`，`return False` 而不是 `True`，都是这条原则的不同表达。

> **追问 2：为什么用 `perf_counter` 计时，却用 `datetime` 记开始时刻？**
>
> 因为这是两个不同的问题——**"过了多久"和"什么时候"**：
>
> ```python
> self._started_at = datetime.now(UTC).replace(tzinfo=None)
> # 用 perf_counter 而不是两个 datetime 相减：
> # 后者受系统时钟调整（NTP 校时）影响，可能算出负数耗时。
> self._perf_start = time.perf_counter()
> ```
>
> `duration_ms` 要的是**间隔**，必须用单调时钟——两个 `datetime` 相减会被 NTP 校时污染，可能算出负数。`started_at` 要的是**墙上时间**，因为它要展示给人看、要和其他系统的时间戳对齐，`perf_counter` 的值是个没有绝对意义的浮点数。
>
> 所以两个都存，各用合适的时钟。第 25 篇熔断器里 `time.monotonic()` 是同一个判断的另一半：**测"过了多久"用 monotonic，记"什么时候"用 time。**

> **追问 3：`replace(tzinfo=None)` 是什么意思？为什么要去掉时区？**
>
> 因为数据库列是 naive datetime（`DateTime` 而非 `DateTime(timezone=True)`），存 aware datetime 会被驱动层处理成本地时间或直接报错，取决于驱动。
>
> 做法是**先转成 UTC 再去掉 tzinfo**——`datetime.now(UTC)` 拿到的是带时区的 UTC 时刻，`.replace(tzinfo=None)` 把它变成"值是 UTC、但不声明时区"的 naive datetime。这样数据库里存的全是 UTC，跨时区部署时不会错。
>
> 如果写成 `datetime.now()`（不带 UTC），拿到的是**本地时间的 naive datetime**——在开发机（UTC+8）和生产机（UTC）上存的值会差 8 小时，而且这个错误在单机部署时完全看不出来。**"数据库存 UTC、展示时转本地"是唯一不会在部署环境变化时出错的约定。**

**拓展**：

`mark_degraded` 里有个小细节值得说：

```python
def mark_degraded(self, reason: str | None = None) -> None:
    """标记「节点没抛异常，但也没干成活」。"""
    self._status = SpanStatus.DEGRADED
    if reason:
        self._payload.setdefault("degrade_reason", reason)
```

用 `setdefault` 而不是赋值——**如果节点已经通过 `set_payload` 显式给了 `degrade_reason`，不覆盖它**。和 `logger` patcher 里 `setdefault` 的理由一样（Q15 追问 2）：切面提供兜底，不覆盖调用方的显式意图。

这个模式在项目里出现了三次（logger patcher、mark_degraded、`_derive_payload` 里 hint 的 `update`），都是同一条规则：**自动化的层负责"没人管的时候填上"，不负责"纠正别人填的"。** 反过来做的话，显式指定就失去意义了。

### Q21. 并行分支里的 span 是怎么收集到一起的？ContextVar 在并发下不是各自独立的吗？

**考点**：这题是本篇技术含量最高的一道。`ContextVar` 在 `to_thread` / `create_task` 下的拷贝语义，答错就会写出一个「本地单测全绿、上线后并发下静默丢数据」的 bug。

**标准回答**：

先说结论：**`copy_context()` 拷贝的是「变量到对象的绑定关系」，不是对象本身。**

`asyncio.to_thread` 和 LangGraph 内部 spawn 任务时都会做一次 `contextvars.copy_context()`。拷完之后，父上下文和子上下文里的 `_SPAN_COLLECTOR` 指向的是**同一个 list 对象**。于是有两条方向相反的推论，必须同时记住：

- 子上下文里 `list.append(...)` → 父上下文**看得见**。因为改的是那个共享对象本身。
- 子上下文里 `_SPAN_COLLECTOR.set(...)` → 父上下文**看不见**。因为改的只是子上下文里的绑定关系。

这两条推论直接决定了整个模块的纪律：**只在请求入口 `set` 一次，之后全程只 `append`。**

所以 `start_span_collection()` 必须在 API 层调用，不能在图内部调用；`record_span()` 里绝对不能出现 `.set()`。违反哪一条都是同一个后果：四条并行检索分支各自 `set` 出一个自己的 list，往里 append 得好好的，然后随着子上下文一起消失——父上下文里那个 list 始终是空的。

这个 bug 最难的地方在于**它在串行下不会发生**。单测里 `pytest` 直接 await 一个节点，没有 `copy_context`，父子就是同一个上下文，`set` 也能被看见。测试全绿，上线之后四条检索 span 一条都不见。

**真实代码**：

```python
# app/core/span_context.py:56

# 值是「本次运行已记录的 span 明细」列表；None 表示当前不在被追踪的运行里
# （比如脚本直调节点、单测），此时 record_span 直接空转。
_SPAN_COLLECTOR: ContextVar[list[dict[str, Any]] | None] = ContextVar(
    "chat_run_span_collector", default=None
)


def start_span_collection() -> Token:
    """开始收集本次运行的 span，返回用于还原的 token。

    必须在请求入口调用（而不是在图内部）：见模块文档里 ContextVar 的语义 ——
    只有在**父上下文**里 set，后续 fan-out 出去的所有子上下文才能共享同一个 list。
    """
    return _SPAN_COLLECTOR.set([])


def record_span(node: str, *, duration_ms: int, ...) -> None:
    """记录一条 span。不在收集上下文里时静默跳过。

    注意这里只 append，不 set —— 这是并行分支下不丢数据的前提。
    """
    spans = _SPAN_COLLECTOR.get()
    if spans is None:
        return
    spans.append({...})
```

**追问链**：

> **追问 1：`default=None` 而不是 `default=[]`，为什么？**
>
> 两个理由，一个是安全，一个是语义。
>
> 安全上，`ContextVar` 的 default 是**在定义时求值一次**的，所有从没 `set` 过的上下文共享同一个 list 对象。那意味着任何不在请求里的 `record_span` 调用（脚本、单测、定时任务）都会往这个模块级 list 里 append，**永不清空**——既是内存泄漏，也是跨请求污染。这跟 Python 函数的可变默认参数是同一个坑。
>
> 语义上，`None` 表达的是「当前不在被追踪的运行里」，跟「在运行里但还没记过 span」是两种不同的状态。`record_span` 用 `if spans is None: return` 空转掉前者，所以脚本里直调节点不会报错也不会留垃圾。用 `[]` 的话这两个状态就区分不开了。

> **追问 2：这个 bug 怎么测？**
>
> 测试**必须显式跨越上下文边界**，否则测不到。两条路径都要覆盖：
>
> ```python
> # 路径一：to_thread（同步检索走这条）
> await asyncio.to_thread(lambda: record_span("x", ...))
> assert len(collected_spans()) == 1
>
> # 路径二：create_task（LangGraph 内部扇出走这条）
> await asyncio.gather(*[asyncio.create_task(node()) for _ in range(4)])
> assert len(collected_spans()) == 4
> ```
>
> 第二条断言的数字是 4 而不是 `>= 1`——这才能抓到「只有最后一条活下来」这类部分丢失。`tests/unit/test_metrics.py:154` 那个 `test_works_across_await` 是同一个思路的最小版本。
>
> 更一般的教训是：**并发相关的代码，串行测试的通过毫无信息量。** 测试必须重现那个让 bug 成立的结构。

> **追问 3：为什么 `reset_span_collection` 用 `reset(token)` 而不是 `set(None)`？**
>
> 因为要支持嵌套。`reset(token)` 恢复的是「进入这个作用域之前的值」，`set(None)` 是无条件清空。如果一次请求里嵌套开了两层收集（比如批量接口，外层收集整批、内层收集单条），用 `set(None)` 的话内层退出时把外层的收集器也一起清了，后面所有 span 静默丢失。`ContextVar` 提供 token 机制正是为了这个，不该绕过它。
>
> 这跟 25 篇里 `request_id_scope` 用 `reset(token)` 是同一条规则——**只要一个 ContextVar 有可能被嵌套设置，就必须用 token 还原。**

**拓展**：

`collected_spans()` 返回的是 `list(spans)` 而不是 `spans` 本身，这是同一套防御的延伸：调用方拿到内部 list 的引用之后，一次 `.clear()` 或 `.sort()` 就能悄悄改掉收集状态。返回副本的成本是一次浅拷贝（几十个元素），收益是这个模块的内部状态**只能通过它自己的接口改**。

这类「共享可变对象」的坑在 Python 里反复出现：可变默认参数、`ContextVar` 的可变 default、从 ORM 读出来的对象被直接改（25 篇里那条「repository 层读出来的对象视为只读」的评审规则）。它们的根都一样——**Python 传的是引用，而「谁拥有这个对象」这件事语言不帮你管**，只能靠约定。所以约定要写下来，而不是指望每个人都想得到。

### Q22. `instrument_node` 这个装饰器踩过什么坑？

**考点**：装饰器包装框架回调时的两类经典失误。这题能筛出「写过装饰器」和「装饰器在框架里出过事」的区别。

**标准回答**：

两个坑，都是**报错位置离原因很远**的那种。

**坑一：不能只写 `async def` 包装器。**

五个节点里 `dedup` 是同步的，其余四个是异步的。如果统一用 `async def` 包装，同步节点被包完之后返回的是一个**没有被 await 的协程对象**。LangGraph 拿到它，当成节点返回的 patch 交给 reducer，于是报：

```
TypeError: unsupported operand type(s) for +: 'list' and 'coroutine'
```

这个报错出现在 reducer 里，而错误的原因在装饰器里——中间隔着整个 LangGraph 的调度逻辑。第一次见基本不可能猜到是包装器写错了。所以 `inspect.iscoroutinefunction` 判一次，两个包装器各写一份。这是**唯一**能接受的重复：两份代码的差别只有 `await`，但合并它们的任何技巧都会引入更难懂的东西。

**坑二：不能用 `functools.wraps`。**

`functools.wraps` 除了复制 `__name__` / `__doc__`，还会设一个 `__wrapped__` 指向原函数。而 LangGraph 在某些版本里会顺着 `__wrapped__` 去取原始函数（为了拿到真实签名做参数注入）——**拿到之后调的就是没被包装的原函数**，埋点被完全绕过。

这个坑比坑一更阴险：它不报错。图跑得好好的，答案也对，只是 span 表里空空如也。而且是「有些节点有 span、有些没有」这种最容易被解释成「哦可能那个节点太快了」的形态。

所以只手动复制展示用的两个属性，不设 `__wrapped__`。

**真实代码**：

```python
# app/agent/rag_v2/instrumentation.py:117

def instrument_node(node: str, func: Callable[..., Any]) -> Callable[..., Any]:
    """给单个节点函数包上 span 计时。

    同时支持同步节点（dedup）与异步节点（其余四个）：
    `inspect.iscoroutinefunction` 判一次，各自返回对应的包装器。
    不能只写 async 版本 —— 那会把同步节点的返回值变成协程，
    LangGraph 拿到一个没 await 的协程，图会直接崩。
    """
    if inspect.iscoroutinefunction(func):

        async def async_wrapper(*args: Any, **kwargs: Any) -> Any:
            with span_scope(node) as span:
                patch = await func(*args, **kwargs)
                _apply(span, patch)
                return _strip_hint(patch)

        _copy_identity(async_wrapper, func)
        return async_wrapper

    def sync_wrapper(*args: Any, **kwargs: Any) -> Any:
        with span_scope(node) as span:
            patch = func(*args, **kwargs)
            _apply(span, patch)
            return _strip_hint(patch)

    _copy_identity(sync_wrapper, func)
    return sync_wrapper


# app/agent/rag_v2/instrumentation.py:185
def _copy_identity(wrapper, func) -> None:
    """保留原函数的名字与文档。

    不用 `functools.wraps`：它会连 `__wrapped__` 一起设上，
    而 LangGraph 在某些版本里会顺着 `__wrapped__` 去取原函数签名，
    从而绕过包装。只复制展示用的两个属性，够了也更安全。
    """
    wrapper.__name__ = getattr(func, "__name__", "node")
    wrapper.__doc__ = getattr(func, "__doc__", None)
```

**追问链**：

> **追问 1：为什么在 `add_node` 的注册点包，不在节点函数上加 `@instrument` 装饰器？**
>
> 因为注册点是**唯一**的收口。用装饰器的话，新增一个节点时忘记加装饰器不会有任何报错——图跑得好好的，只是少一条 span，而且没人会发现。在 `graph.add_node` 的入口包一层，覆盖面是「所有注册进图的节点」，物理上漏不掉。
>
> 这跟 25 篇里「分类逻辑集中到四个函数」是同一个思路：**把「必须做的事」放在「不做就跑不起来的地方」，而不是放在「需要记得做的地方」。** 靠人记住的约定，规模一大必然有漏。

> **追问 2：包装之后节点的类型签名还对吗？mypy 怎么处理？**
>
> 现在的签名是 `Callable[..., Any]`，等于放弃了类型检查——这是我承认的妥协。想保住类型，得用 `ParamSpec` + `TypeVar`：
>
> ```python
> P = ParamSpec("P")
> R = TypeVar("R")
> def instrument_node(node: str, func: Callable[P, R]) -> Callable[P, R]: ...
> ```
>
> 但同步/异步双分支下这个签名会变得相当难写（返回类型在两个分支里语义不同），而这个函数只有一个调用点、五个入参，类型收益很小。所以我选了 `Any` 并把理由留在这里。**知道自己放弃了什么，跟没意识到，是两件事。**

> **追问 3：`span_scope.__exit__` 返回 `False`，这个细节有什么讲究？**
>
> `__exit__` 返回真值等于**吞掉异常**。span 是旁路观测，绝不能改变控制流——节点抛了异常，它得原样抛到 LangGraph 那里去，否则图的行为就被埋点改变了。所以显式 `return False`，并且加了注释「不吞异常」。
>
> 同时注意里面那句 `with suppress(Exception)` 包住的只有 `record_span` 一行：**观测自己失败要吞，被观测的业务异常不能吞。** 这两个方向在同一个 `__exit__` 里，写反一个就完全变味了。

**拓展**：

这两个坑有个共同形态：**框架会对你交给它的函数做反射**。`__wrapped__`、`__signature__`、`__annotations__`、是不是协程函数——框架读这些元信息来决定怎么调用你。所以给框架回调加装饰器，跟给普通函数加装饰器不是一个难度：你不只要保证「调用行为一致」，还要保证「**被反射出来的样子**一致」。

判断方法很直接：包装之后跑一次真实链路，然后确认埋点数据真的产生了。不能只看「没报错」——坑二的表现恰恰就是不报错。这也是为什么 span 表本身值钱：它是埋点层**自己的**健康检查，一个节点长期没有 span 就是在说包装出问题了。

## 六、`/metrics` 端点

### Q23. `/metrics` 为什么自己写，不用 `Instrumentator` 自带的 `.expose(app)`？

**考点**：能不能说出一个具体的、非「我想自己控制」的理由。

**标准回答**：

因为**每次抓取前必须先刷一遍熔断器状态**，而 `.expose()` 直接吐 registry，没有这个钩子。

原因在熔断器的状态机里：`OPEN → HALF_OPEN` 这条转换是**惰性**的——它不由任何事件触发，而是「冷却期满之后被人读到」才发生（`CircuitBreaker._maybe_half_open`）。如果只在 `record_failure` / `record_success` 里更新 Gauge，那么一个打开之后**再没有流量**的熔断器会永远显示 OPEN，即使它早就该进半开了。

而「打开之后没有流量」恰恰是最常见的情况：熔断器一开，请求全部快速降级，不再打下游，也就不再有 `record_*` 调用。指标就此冻结在 OPEN。值班的人看到的是「熔断器还开着」，实际上系统可能早就恢复了。

抓取时刷新则顺带调用了 `snapshot()`，而那个调用本身会推进状态机，所以**指标和真实状态永远一致**。

这是一个「指标的正确性依赖于读取时机」的例子。一般来说指标应该是被动上报的，但当被观测对象本身有惰性状态转换时，就必须在读的时候推一把。

**真实代码**：

```python
# app/core/metrics.py:171
def refresh_circuit_breaker_metrics() -> None:
    """把所有熔断器的当前状态刷进 Gauge。

    为什么在**抓取时**刷新,而不是在状态变化时刷新:

    熔断器的状态转换有一条是**惰性**的 —— OPEN 到 HALF_OPEN 不是由
    某个事件触发,而是「冷却期满之后被人读到」才发生
    (见 CircuitBreaker._maybe_half_open)。如果只在 record_failure /
    record_success 里更新 Gauge,那么一个打开后再没有流量的熔断器
    会永远显示 OPEN,即使它早就该进半开了。

    抓取时刷新则顺带调用了 snapshot(),那个调用本身会推进状态机,
    所以指标和真实状态永远一致。
    """
    for breaker in all_breakers():
        snapshot = breaker.snapshot()
        state = CircuitState(str(snapshot["state"]))
        circuit_breaker_state.labels(name=breaker.name).set(_STATE_VALUES[state])
```

```python
# app/main.py:110

async def metrics() -> Response:

        return Response(status_code=404)
    body, content_type = render_metrics()

```

**追问链**：

> **追问 1：抓取时才刷新，那两次抓取之间的状态变化不就丢了吗？**
>
> 会丢，但对 Gauge 来说这是**定义内**的行为。Gauge 记的是「当前值」，采样率决定了时间分辨率——Prometheus 15 秒抓一次，就只能看到 15 秒粒度的状态。中间开了又关的抖动看不见。
>
> 如果需要「一共开过几次」，那是 Counter 的活，得再加一个 `circuit_breaker_trips_total`。这两个指标回答的不是同一个问题：Gauge 答「现在怎么样」，Counter 答「一共发生过多少次」。想知道「过去一小时开过没有」，用 `max_over_time(circuit_breaker_state[1h])` 就行——这也是状态值按严重度递增编号的收益。

> **追问 2：`Instrumentator().instrument(app)` 为什么必须在路由注册之后调用？**
>
> 因为它要遍历 `app.routes` 才知道有哪些路由模板。在路由注册之前调用，遍历到的是空列表，**全部业务接口都不会被埋点**——而且不报错，`/metrics` 里照样有 `http_requests_total`，只是里面只有框架自带的那几个路由。
>
> 这是又一个「不报错的静默失败」。检查方法是上线后确认 `http_requests_total` 里真的有业务 handler 的 label 值。`tests/unit/test_metrics.py:366` 那个 `test_http_metrics_use_route_template_not_real_path` 顺带锁住了这件事。

> **追问 3：引 `prometheus-fastapi-instrumentator` 这个库，跟你在 25 篇说「熔断器不引 pybreaker」是不是矛盾？**
>
> 不矛盾，判据是一致的：**这个库解决了一个我自己写会踩的坑，pybreaker 没有。**
>
> 手写 HTTP 中间件拿到的是 `request.url.path`，也就是**展开后的真实路径**。`/api/aiops/trace/abc123` 每一个 trace_id 都会生成一条独立时间序列，几万次查询就把 Prometheus 打爆。而这个库会从 Starlette 的 route 对象里取**模板**（`/api/aiops/trace/{trace_id}`）。这个取模板的逻辑要自己写并覆盖各种路由形态（挂载的子应用、正则路由、404），不划算。
>
> 熔断器那六十行没有类似的隐藏复杂度——状态机就是几个整数和一把锁，自己写完全可控。所以判据不是「能不能自己写」，而是「**自己写会不会踩到一个不好发现的坑**」。

**拓展**：

`render_metrics()` 返回 `(body, content_type)` 而不是直接返回 `Response`，是为了让这个函数**不依赖 FastAPI**。它现在可以被单测直接调用、断言 body 里包含哪些指标名（`test_contains_all_custom_metrics`），也能被将来的其他导出方式复用（比如 push 到 Pushgateway）。让核心逻辑不依赖 web 框架，成本是多一层解包，收益是可测性——这跟 25 篇里 `apply_retry_policy` 在 RQ 上下文外返回纯裁决是同一个模式。

### Q24. `/metrics` 端点的安全问题，你考虑过吗？

**考点**：能不能意识到监控端点本身是攻击面，以及能不能说清「防在哪一层」。

**标准回答**：

考虑过，而且这是个真实的暴露面：这个端点**无鉴权**，吐出的是系统的内部形状——有哪些节点、耗时分布、降级率、熔断器状态、请求量。

对侦察者的价值很具体：从 `degrade_total{reason="retrieval_failed"}` 的跳变能推断「他们的向量库正在挂」；从 `circuit_breaker_state{name="llm"}` 能看出模型服务的健康状况；从 `llm_call_duration_seconds` 的桶分布能估算出后端用的模型规模。这些都不是敏感数据，但拼起来是一份**实时的系统状态报告**——而攻击时机的选择恰好依赖这个。

我的处置是三层，**关键是没有一层是在应用里加鉴权**：

1. **网关/ACL 层限制来源。** 只让内网的 Prometheus 可达。这是主要防线。
2. **`config.enable_metrics_endpoint` 开关。** 出事了不用发版就能关掉——这是应急手段，不是日常防线。
3. **关闭时返回 404 而不是 403。** 语义上「关掉之后这个端点不存在」。403 会告诉扫描者「这里有个 `/metrics`，只是你没权限」，反而**确认了目标的存在**。

为什么不在应用里加 token 或 Basic Auth：那会让抓取端的配置复杂化——密码要发给 Prometheus、要跟着轮转、多个环境多套凭据。而来源限制在网关层做既标准又彻底，运维成本还低。**这是一个「安全应该防在哪一层」的判断，不是「安不安全」的判断。**

`include_in_schema=False` 是同一个思路的延伸：不进 OpenAPI 文档。它不是给人调的业务接口，列在 `/docs` 里只会让读文档的人误以为这是一个可以对外提供的能力。

**真实代码**：

```python
# app/main.py:110
@app.get("/metrics", include_in_schema=False)
async def metrics() -> Response:
    """Prometheus 抓取端点。

    ⚠️ 安全：这个端点**无鉴权**，吐出的是内部形状（有哪些节点、
    耗时分布、降级率、熔断器状态、请求量）。对侦察者有用 ——
    比如从 degrade_total 的跳变推断我们哪个依赖正在挂。
    **生产环境必须在网关/ACL 层限制来源**，只让内网的 Prometheus 可达。
    不在应用里加 token 是因为那会让抓取端配置复杂化（密码要发给
    Prometheus 并跟着轮转），而来源限制在网关层做既标准又彻底。
    config.enable_metrics_endpoint 是最后一道保险：出事了不用发版就能关。
    """
    if not config.enable_metrics_endpoint:
        # 404 而不是 403：关掉之后这个端点在语义上就**不存在**。
        # 403 会告诉扫描者「这里有个 /metrics，只是你没权限」，
        # 反而确认了目标的存在。
        return Response(status_code=404)

    body, content_type = render_metrics()
    return Response(content=body, media_type=content_type)
```

**追问链**：

> **追问 1：那如果没有网关呢？直接裸奔在公网上的部署怎么办？**
>
> 那就必须关掉，或者绑到只监听 `127.0.0.1` 的独立端口上——后者是 Go 生态常见的做法（业务端口和 admin 端口分开）。
>
> 我要承认一件事：**这个设计有一个前提假设，就是「生产环境有网关」。** 假设写在注释里了，但代码本身不强制它。更稳的做法是让开关的**默认值**是关闭，需要监控的环境显式打开——现在是默认打开，也就是「默认不安全，靠部署纪律兜」。这是个我知道但没改的取舍：改成默认关会让本地开发和测试都要多配一个环境变量，而这个项目的部署形态是确定的内网。**说清楚假设，比声称没有假设要好。**

> **追问 2：指标里会不会不小心泄漏用户数据？**
>
> 这个风险跟基数纪律是**同一件事的两面**。所有不能当 label 的东西——用户问题、request_id、文件名——恰好也都是不该出现在指标里的隐私数据。所以基数纪律顺带就是一道隐私防线：label 值必须来自枚举或固定字符串集合，用户输入在物理上进不来。
>
> 唯一要留意的是 HTTP 指标的 `handler` label。如果有路由把用户 ID 写在路径里而**没有**用路径参数（比如手工拼的路径），模板化就失效了。项目里所有动态路径都是 `{trace_id}` 这种参数形式，所以没这个问题——但这是需要主动检查的，不是自动成立的。

> **追问 3：Prometheus 抓取失败了你怎么知道？**
>
> 靠 Prometheus 自己的 `up{job="..."}` 指标——它会给每个抓取目标记一个 0/1。这是监控系统的自省能力：**监控自己挂了这件事，只能靠监控之外的东西来发现。**
>
> 我目前没有配这条告警，这是缺口。而且它属于最坑的那一类缺口：监控挂了之后，所有其他告警都会安静下来，看起来像「一切正常」。**告警系统的沉默是有二义性的**——可能是真没事，也可能是它自己死了。区分这两者需要一个反向的心跳（dead man's switch）：定期主动触发一次假告警，如果没收到就说明链路断了。

**拓展**：

再往前是**指标的分级暴露**：业务指标（QPS、降级率）可以给更多人看，运行时形状（节点名、耗时分桶）只给 SRE。实现上是两个 registry、两个端点。当前规模不需要——只有一个消费者。

另一个方向是 **Pushgateway**。当前是 pull 模式，Prometheus 主动来抓。但 RQ worker 是短生命周期进程，抓取周期内可能已经退出了，它的指标就永远采不到。这是 pull 模型的固有盲区，标准解法是让短任务把指标 push 到 Pushgateway。项目现在 worker 是常驻的，所以没这个问题——但如果将来改成按需拉起，worker 侧的指标会静默消失，而**「指标不见了」和「没有发生」在图上长得一模一样**。

### Q25. 一次线上故障，你的排查动线是什么样的？

**考点**：这些设施到底能不能连成一条可用的动线。答不上来说明只是在堆工具。

**标准回答**：

以一个真实形态举例：用户反馈「刚才问的问题答得很敷衍，像是没查到东西」。

**第一步，看指标确认范围**（这是个体问题还是整体问题）：

```promql
# 降级率是不是涨了
sum(rate(degrade_total[5m])) by (reason)
```

- 如果 `retrieval_empty` 是主要原因 → 知识库确实缺内容，是数据问题，不用查代码。
- 如果 `retrieval_failed` 涨了 → 检索链路故障，接着看 `circuit_breaker_state{name="retrieval"}` 和 `retrieval_failures_total` 的 `code` 分布。
- 如果**什么都没涨** → 这是个体问题，指标到此为止，转日志。

这一步的价值是**排除**：整体指标平稳，就不用去查基础设施，直接奔个体。反过来如果降级率飙了，那用户的反馈只是一个症状样本，真问题在下游。

**第二步，用 request_id 拉个体链路**。让用户提供响应里的 `request_id`（错误响应体和 `X-Request-ID` 头都有），然后：

```bash
grep '"rid": "a3f8..."' logs/app_2026-09-05.log | jq .
```

因为文件日志是 JSON 行，`rid` 是可索引字段，一个 ID 能拉出这次请求的全部日志——包括第三方库的（patcher 是全局切面）。如果是 worker 侧的问题，同一个 ID 还能横跨进程串起来（25 篇 Q23 的 `request_id_scope`）。

**第三步，用 span 表看时间线**。日志告诉我「哪一步报了什么」，span 表告诉我「每一步花了多久、召回了几条、有没有降级」：

```sql
SELECT node, status, duration_ms, payload
FROM chat_run_spans WHERE trace_id = '...' ORDER BY started_at;
```

典型的读法：四条 `retrieve_each` 里三条 OK 一条 DEGRADED，`payload.retrieve_failure_codes` 说明是哪个错误码；`dedup` 的 `deduped_count` 只有 2 条，`generate` 的 `answer_length` 很短——那就串起来了：一条分支失败导致召回不足，答案自然敷衍。**这个结论是三个数据源各出一块拼出来的，单看任何一个都得不到。**

**为什么这条动线成立**，就是三根支柱各自的不可替代性：

| 步骤 | 用什么 | 回答什么 | 为什么别的答不了 |
|---|---|---|---|
| 定范围 | 指标 | 整体现在什么形状 | 日志要遍历几百万行做聚合 |
| 找个体 | 日志 | 这一次为什么失败 | 指标里没有任何个体信息 |
| 看瓶颈 | span | 时间花在哪、每步产出多少 | 日志里没有结构化的耗时和计数 |

**追问链**：

> **追问 1：如果用户提供不了 `request_id` 呢？**
>
> 退化成按时间窗 + 会话 ID 找。`session_id` 在 `ChatRunTrace` 表里，能反查出这个会话最近的几次 `trace_id`，再用 `trace_id` 关联 span 表。
>
> 这也是为什么响应体里要**主动带上** `request_id`（25 篇 Q15 的三个附加字段之一）——不指望用户从响应头里翻，要让它出现在用户能看见、能复制的地方。**可排查性的一部分是「让报障的人手里有线索」**，而这件事必须在设计响应体的时候就想到，事后加不上。

> **追问 2：这条动线里最容易断的是哪一环？**
>
> 第二步到第三步的关联，也就是 `request_id` ↔ `trace_id`。`ChatRunSpan` 上同时有这两个字段，所以能双向查——但这是**刻意设计**的结果，不是自然成立的。如果 span 只有 `trace_id`，那就得先从日志里找到 trace_id 再去查 span，多一跳，而且日志里如果没打 trace_id 就彻底断了。
>
> 一般规则：**追踪 ID 的关联关系必须落在同一行记录里**，靠"两个表按时间对齐"是不可靠的（并发下时间戳分不出谁是谁）。

> **追问 3：这套动线你实际用过几次？**
>
> 用过，但基本都是本地和预发环境定位自己的 bug——第 23 篇里那个 Hit@1=0 的排查就是这条动线的完整应用（指标看整体、日志看个体、逐层往下切）。生产环境的真实故障样本还很少，所以我不敢说这套动线经过了充分检验。
>
> 我能确定的是**它在设计上是闭合的**：每一步都有下一步需要的关联键。但「设计上闭合」和「真故障时够用」之间还有距离，这个距离只能靠真实故障来填——而这也是 Q26 那个问题的由来：可观测性代码的默认状态也是「从未在真实故障中执行过」。

**拓展**：

这条动线还缺一个入口：**告警**。现在是「用户报障 → 我去查」，理想是「指标异常 → 告警 → 我先看到」。差别不在工具，在于有没有告警规则和阈值——而阈值需要历史数据来定（25 篇 Q29 的 P2）。所以顺序是：先积累指标 → 再定基线 → 再配告警。跳过前两步直接配告警，只会得到一堆被静音的规则。

## 七、可观测性的验证

### Q26. 指标怎么测？`prometheus_client` 的默认 registry 是全局单例，测试之间不会互相污染吗？

**考点**：知不知道全局状态给测试带来的具体麻烦，以及标准解法。

**标准回答**：

会污染，而且这是写指标测试的第一个坑：**Counter 只增不减，测试之间的值会累积。** 断言 `degrade_total{reason="llm_error"} == 1` 在单跑时通过，在全量跑时失败——因为前面的测试已经把它加到 3 了。而且失败顺序还依赖测试的执行顺序，是最难查的那类。

解法是**取差值，不断言绝对值**：

```python
before = REGISTRY.get_sample_value("degrade_total", {"reason": "llm_error"}) or 0
count_degrade("llm_error")
after = REGISTRY.get_sample_value("degrade_total", {"reason": "llm_error"}) or 0
assert after - before == 1
```

两个细节：用 `REGISTRY.get_sample_value()` 而不是读 `counter._value`——前者是官方支持的接口，后者是私有属性，会跟着库版本变。`or 0` 是因为一个从未被 `.labels()` 过的组合返回 `None` 而不是 0（时间序列还不存在），这个 `None` 会让减法直接抛 `TypeError`。

**Gauge 反而好测**，因为它是 set 语义，绝对值可以直接断言（`test_closed_is_zero`、`test_open_is_two`）。这是 Gauge/Counter 在可测性上的差别，选型时没人提但实际写测试时会遇到。

另一件必须做的事是**熔断器状态的隔离**：`_REGISTRY` 里的熔断器实例是模块级全局的，一个测试把它打到 OPEN，后面所有测试都在 OPEN 状态下跑。所以有一个 autouse fixture 在每个测试前后调 `reset_all_breakers()`。这也是 `circuit_breaker.py` 为什么要提供这个函数——**它存在的唯一理由是测试隔离**，生产代码里没有任何地方调它。

**追问链**：

> **追问 1：为什么不给每个测试用一个独立的 registry？**
>
> 可以，`CollectorRegistry()` 能建新实例。但那要求指标定义支持注入 registry，也就是把模块级的 `Counter(...)` 改成工厂函数。这个改造会把生产代码搞复杂，只为了测试方便——而取差值这个办法零成本就解决了同一个问题。
>
> 判据是：**测试的困难要不要传导到生产代码，取决于这个困难是不是在指向一个真实的设计问题。** 这里不是——指标本来就该是全局单例（Q9 的理由），测试麻烦是这个正确设计的附带代价，不是设计错误的征兆。

> **追问 2：`test_works_across_await` 在测什么？**
>
> 测 `observe_llm_call` 这个上下文管理器跨 `await` 之后计时仍然正确。因为它用的是 `time.perf_counter()`，而 `with` 块内部有 `await`——协程被挂起再恢复的这段时间要算进去（那正是等待 LLM 响应的时间）。
>
> 这个测试的实际价值是**锁住"耗时包含等待时间"这个语义**。如果有人以后改成用 CPU 时间（`process_time`），这个测试会失败——而那个改动在同步代码里看不出问题，只在 async 下测出来，因为 async 挂起期间 CPU 时间不走。

> **追问 3：`test_open_breaker_records_no_sample` 是什么意思？熔断打开时不记耗时？**
>
> 对，这是一个刻意的区分：**超时要记，熔断拒绝不记。**
>
> 理由是耗时分布回答的问题是"调用下游要多久"。熔断快速拒绝的耗时接近 0（根本没出网），把它记进去会**稀释分布**——下游全挂时，熔断器把请求全拒了，P99 反而变得非常漂亮，图上看起来"一切都很快"。而超时必须记，因为那是真实发生的、最慢的那次调用。
>
> 区分标准是：**这次真的碰到下游了吗？** 碰到了就记（不管成败），没碰到就不记。这跟 `observe_llm_duration` 文档里那句"把失败调用排除掉会得到一个『一切正常』的 P99"是同一个道理的两面——一面是不该排除的别排除，一面是不该纳入的别纳入。

**拓展**：

指标测试有一类做不到的事：**验证指标的语义对不对**。测试能保证"调了 `count_degrade("x")` 之后计数涨了 1"，但保证不了"每一次真实降级都调到了 `count_degrade`"。后者是覆盖问题，不是正确性问题，单测按定义测不到。

能部分缓解的办法是把埋点收敛到汇聚点（Q11）——汇聚点有测试覆盖，就等于覆盖了所有走这条路的节点。这是"集中埋点"除了 DRY 之外的第二个收益：**它把一个覆盖问题转化成了一个正确性问题**，而后者是可测的。

### Q27. 你的测试里，哪些是在"锁住设计承诺"？举几个例子。

**考点**：能不能区分"测试代码在干什么"和"测试代码在防什么"。这是测试设计的分水岭。

**标准回答**：

大部分测试在验证功能，少数测试在**防止某个设计决策被后人无意中撤销**。后者更值钱，因为功能坏了会立刻暴露，而设计承诺被撤销往往悄无声息。

项目里有六个这样的测试，每一个都对应一条写在注释里的承诺：

**1. `test_records_a_sample_even_when_the_call_fails`**
承诺：失败的调用也要记耗时。
防的是：有人觉得"失败的调用记耗时没意义"，把 `try/finally` 改成 `try/except/else`。改完之后所有测试还是绿的——除了这一个。而这个改动的后果是超时样本全部消失，P99 变成一个骗人的数字。

**2. `test_exception_propagates_unchanged`**
承诺：埋点是旁路观测，不改变控制流。
防的是：有人在 `finally` 里加了 `return` 或者把异常吞了。这个测试断言异常原样抛出——它保护的其实是**业务代码的正确性**，而不是埋点的正确性。

**3. `test_none_reason_goes_to_unknown_not_dropped`**
承诺：降级了但没说原因，本身是一个需要被看见的信号。
防的是有人做"防御性编程"——`if reason: count_degrade(reason)`，看起来更严谨，实际上让降级总数悄悄小于真实值，而这个偏差没有任何地方能发现（Q8）。**这个测试防的是一个看起来是改进的改动**，这类改动最需要测试来挡。

**4. `test_values_are_ordered_by_severity`**
承诺：熔断状态值按严重度递增（0/1/2）。
防的是有人重排枚举顺序或者改成别的编号。一旦顺序乱了，`max_over_time(...) >= 2` 这条告警规则会静默失效——**告警规则依赖指标编码，而这个依赖不在代码里，只在 Prometheus 配置里**。测试是唯一能把它固定住的地方。

**5. `test_refreshes_breaker_state_on_each_render`**
承诺：每次抓取都要刷新熔断器状态。
防的是有人把 `/metrics` 简化成 `.expose(app)`，理由是"少写几行"。改完之后指标会冻结在 OPEN（Q23），而这个问题只在"熔断打开后没有流量"这个特定场景下出现，几乎不可能被手工发现。

**6. `test_http_metrics_use_route_template_not_real_path`**
承诺：HTTP 指标按路由模板聚合，不按真实路径。
防的是有人为了"更详细"而改成真实路径，或者把 `Instrumentator().instrument(app)` 挪到路由注册之前。后者会导致业务接口全部漏埋点，而且**不报错**。

**这六个测试的共同形态**：它们锁住的都是"看起来可以简化、实际不能简化"的地方。判断一段代码是否需要这种测试，问一句：**如果一个不了解背景的人来"优化"这段代码，他会怎么改？改完之后什么会静默地坏掉？** 会静默坏掉的，就需要一个测试挡在那。

**追问链**：

> **追问 1：注释里已经写了理由，为什么还需要测试？**
>
> 因为注释**不会失败**。它只在有人主动读的时候起作用，而"顺手优化一下"的人恰好是不读注释的那批人。测试是唯一在 CI 里会红的东西。
>
> 更实际的一点：注释解释了"为什么现在这样写"，测试断言了"改成别的样子就是错的"。前者是文档，后者是约束。**一条重要的设计决策应该同时有这两样**——注释给读代码的人，测试给改代码的人。

> **追问 2：这类测试会不会让重构变得困难？**
>
> 会，而且这正是它的目的——但要区分两种困难。锁住**行为**的测试（"失败也要记样本"）不阻碍重构，你可以随便改实现，只要行为不变；锁住**实现细节**的测试（断言内部调用了哪个私有方法）才会阻碍重构。
>
> 上面六个都是前者：它们断言的是可观测的结果（样本数、异常传播、label 值、状态数值），不碰实现。所以把 `observe_llm_call` 整个重写都行，只要还满足这几条。**测行为不测实现**，这条老规矩在锁承诺的场景下尤其要守住。

> **追问 3：这些承诺，你是先写测试还是先写代码？**
>
> 实话说是先写代码、写注释，然后在写注释的过程中意识到"这条如果被人改了会静默坏掉"，才补的测试。
>
> 我觉得这个顺序反而是合理的：**"哪些决策需要被锁住"这个判断，需要先把决策做出来才能做。** 严格 TDD 在这类场景下反而别扭——你在写代码之前并不知道哪里会有一条脆弱的隐含约定。写注释是个很好的触发器：**如果一条注释在解释"为什么不能改成 X"，那就该有个测试断言 X 是错的。**

**拓展**：

这套思路可以再推一步：把承诺和测试的对应关系**显式写下来**。比如注释里写 `# 承诺：失败也要记样本（test_records_a_sample_even_when_the_call_fails）`，双向可查。成本是维护这个引用，收益是改代码的人能立刻看到"这行有测试盯着，先去看那个测试再改"。

我现在没做，因为函数名已经足够自解释（`test_none_reason_goes_to_unknown_not_dropped` 这个名字本身就是承诺的完整陈述）。**测试名写成完整的断言句，比加交叉引用更省事** —— 这也是这批测试名都那么长的原因。

### Q28. 可观测性代码自己坏了，你怎么发现？

**考点**：这是元层面的问题。答得出来说明真的想过这套设施的可靠性，而不只是装了工具。

**标准回答**：

这是可观测性最阴险的地方：**它坏了的表现是"一切正常"。**

对比一下。错误处理坏了（25 篇 Q28），故障时兜不住，用户会报障——难受但至少有信号。可观测性坏了，故障时图上一片绿、告警一声不响，而这跟真的没事**长得一模一样**。所以它需要的不是"更仔细的测试"，而是**一套能自证的机制**。

我能用的有四层，从弱到强：

**第一层，指标自身的存在性。** 一个指标长期为 0，有两种可能：真的没发生，或者埋点坏了。这两种要能区分。区分办法是**看它的对照指标**：`degrade_total` 全是 0 而 `llm_call_duration_seconds_count` 在涨，说明流量正常但降级从未发生——可信。如果两个都是 0，那是没流量，不能得出任何结论。**"零值有二义性"是读指标的基本纪律**，而消歧总是靠另一个指标。

**第二层，span 表是埋点层自己的健康检查。** 每次请求应该产生固定数量的 span（五个节点 + 四条并行检索）。如果某个 `node` 长期不出现在 span 表里，就是它的包装出了问题——比如 Q22 那个同步节点被 async 包装的坑。这个检查可以写成一条 SQL：按 `node` 分组统计最近的记录数，缺哪个一眼看出来。

**第三层，Prometheus 自己的 `up` 指标。** 抓取失败时它是 0。这是监控系统的自省——**监控自己挂了，只能靠监控之外的东西发现**。我目前没配这条告警，是个明确的缺口。

**第四层，dead man's switch。** 定期主动触发一次"应该产生指标变化"的操作（比如一个健康检查查询），断言指标真的动了。如果没动，说明整条链路断在某处。这是唯一能覆盖"埋点、上报、存储、查询全链路"的办法，也是我完全没做的一层。

**我目前实际有的是第一层和第二层**（而且是手工看，不是自动的），第三层第四层都是缺口。所以诚实的回答是：**这套设施本身还没有自证能力，它的正确性目前依赖单元测试和人工检查。**

**追问链**：

> **追问 1：单元测试不够吗？23 个测试全绿。**
>
> 不够，因为单测覆盖的是"函数被调用时行为对不对"，覆盖不了"该调用的地方有没有调"。Q22 那两个装饰器坑最能说明问题——`instrument_node` 的单测可以全绿，但如果注册时漏包了一个节点，或者被 `__wrapped__` 绕过了，测试完全测不到。
>
> 更根本的一点：**单测跑在测试进程里，而可观测性的价值在生产进程里。** 测试环境的 ContextVar 传播（Q21）、多 worker 的指标聚合、Prometheus 的抓取周期，这些都是单测按定义碰不到的。所以我的说法是"单测保证了组件的正确性，没保证系统的连通性"。

> **追问 2：那你怎么知道现在生产上这套东西是好的？**
>
> 严格说我不知道，我只有间接证据：`/metrics` 抓下来有内容、span 表在增长、日志里 `rid` 不是全 `-`。这些能证明"链路是通的"，证明不了"没有漏埋的地方"。
>
> 我觉得这是个值得说清楚的边界。可观测性的完整验证需要**故障演练**：主动切断 Milvus，然后断言 `degrade_total{reason="retrieval_failed"}` 真的涨了、span 里真的有 DEGRADED、日志里真的能用 request_id 串起来。这三条断言合起来才是"这套设施在真故障时能用"的证明，而单测给不出这个证明。这也是 25 篇 Q28 里提到的同一件事——**降级设计和可观测性设计是耦合的，验证也必须一起做。**

> **追问 3：可观测性的成本怎么控制？会不会越加越多？**
>
> 会，而且这是个真问题。控制手段是给三根支柱各自定一条准入规则：
>
> - **指标**：新增一个指标要能回答"哪条告警规则或哪个排障动作需要它"。答不出来就不加（Q3 那个"六个指标"的克制来源）。
> - **日志**：INFO 级别的量要能被"每条都有人可能读"这个标准兜住。做不到就降 DEBUG。
> - **span**：payload 只记摘要不记内容（Q12），否则会变成 state 的第四份副本。
>
> 共同点是**每一项都要有明确的消费者**。没有消费者的观测数据不是"以后可能有用"，而是纯成本——占存储、占内存、增加认知负担，还会在真正需要的时候淹没有用的信号。**观测数据的价值不在于多，在于每一条都被人看过。**

**拓展**：

再往前一步是给可观测性设施本身定 SLI：比如"埋点覆盖率"（有 span 的请求数 / 总请求数）、"日志完整率"（有 rid 的日志行 / 总行数）。这些数字本身也是指标，可以像业务指标一样监控。

听起来有点递归——**监控监控系统**。但这个递归是有底的：最外层必须有一个不依赖本系统的东西（外部拨测、dead man's switch、或者干脆是人的例行检查）。任何自洽的监控体系最终都需要一个外部锚点，否则"全绿"这个状态永远无法被证伪。

## 八、演进与总结

### Q29. 这套可观测性，你觉得最大的缺口在哪？下一步做什么？

**考点**：排序能力，以及排序依据。

**标准回答**：

按"故障时会不会看不见"排序，四个缺口：

**P0：告警。** 现在的动线入口是"用户报障"，而不是"指标异常"。所有这些指标目前的用途是**事后排查**，不是**事前发现**——这中间差的是告警规则。这是最大的缺口，因为它决定了整套设施是主动的还是被动的。

需要两条最基本的：`sum(rate(degrade_total[5m]))` 突增、`max_over_time(circuit_breaker_state[5m]) >= 2`。加上一条 `up == 0`（监控自己挂了）。但阈值需要历史基线，所以实际顺序是：先积累两周数据 → 定基线 → 配规则。**跳过基线直接拍阈值，只会得到一堆被静音的告警**，而被静音的告警比没有告警更糟——它让人以为有覆盖。

**P1：日志聚合。** 现在日志是本地 JSON 文件，`grep` + `jq` 查。单机能用，但两个问题：worker 和 API 在不同进程（可能不同机器），跨进程查 `request_id` 要手工合并；30 天之后日志就没了，而复盘常常发生在几周后。接 Loki 的成本不高（JSON 行已经是结构化的，这是当初选 `serialize=True` 就想好的），收益是 `request_id` 一次查询横跨所有进程。

**P2：故障演练验证链路。** Q28 说的那件事——单测证明不了连通性。切断 Milvus 跑一次完整链路，断言三个数据源都记录正确。这一条不写新代码，是验证已有代码，但它是"我知道这套东西真的能用"和"我以为它能用"的分界。

**P3：OpenTelemetry 迁移。** 只在引入第二个服务、需要跨服务追踪时才做（Q18 的触发条件）。现在做是纯成本。

排序依据：**先补"看不见"的（告警），再补"看得见但不好查"的（聚合），再验证"以为看得见"的（演练），最后才是"更标准"的（OTel）。** 最容易犯的错是反过来——先上 OTel 因为它听起来更专业，而系统连一条告警规则都没有。

**追问链**：

> **追问 1：为什么告警排在日志聚合前面？日志聚合的收益不是更直接吗？**
>
> 因为它们解决的问题不在同一个层级。日志聚合让**已经开始的排查**更快，告警决定**排查什么时候开始**。故障持续 5 分钟被发现和持续 2 小时被发现的差别，比"查日志花 3 分钟还是 30 分钟"的差别大一个数量级。
>
> 一般规则：**缩短 MTTD（发现时间）优先于缩短 MTTR（修复时间）**，因为前者往往是后者的几倍量级，而且它是纯等待——那段时间里没有任何人在做任何有用的事。

> **追问 2：`llm_call_duration_seconds` 只有 `node` 一个 label，不够细吧？**
>
> 是不够。想问"是哪个模型慢"、"是哪个租户的请求慢"，现在答不了。
>
> 但加 label 要过基数关（Q5）。`model` 可以加——取值是配置里的几个模型名，有界。`tenant` 不行——租户数量增长无界，而且 `node × model × tenant` 是乘法关系，序列数会爆。
>
> 我倾向于先加 `model`（因为切换模型是真实会发生的事，届时必须能对比前后耗时），`tenant` 这类维度留给日志——**个体维度进日志，聚合维度进指标**，这条线不该为了方便而模糊。

> **追问 3：span 表会不会太大？要不要清理？**
>
> 会，一次请求 9 条 span，日均一万请求就是九万行。需要保留策略，跟日志一样。
>
> 我倾向于**分级保留**：全部 span 留 7 天，其中 `status != OK` 的留 90 天。理由跟 Q13 的失败样本一样——**降级和错误的 span 单条价值远高于成功的**。成功的 span 主要用于算耗时分布，而那个信息已经聚合进 Histogram 了，原始行的边际价值很低。失败的 span 没有任何聚合替代品，只能看原始记录。
>
> 这条策略现在没实现，属于"知道该做但还没到量"。真到量的时候不做，第一个症状是数据库变慢而不是磁盘满——因为 span 表会被 `trace_id` 查询，表大了索引就慢。

### Q30. 用一句话总结你在可观测性上的收获。

**标准回答**：

**可观测性不是"记录发生了什么"，是"让系统能回答你还没想到要问的问题"。**

这句话的分量在后半句。如果只是"记录发生了什么"，那到处 `logger.info` 就够了——而这恰好是大多数项目的状态，也恰好是最没用的状态：出事的时候翻几十万行日志，发现记下来的全是"进入了某个函数"，唯独没有"为什么这次不一样"。

三层展开，对应这一篇的三组决策：

**第一层，三根支柱各自不可替代，因为它们回答的问题在结构上不同。** 指标答"整体现在什么形状"，日志答"这一次为什么失败"，span 答"时间花在哪、每步产出多少"。日志答不了第一个——那需要遍历几百万行做聚合；指标答不了第二个——它里面没有任何个体信息。所以值班动线必然是**指标发现异常 → 日志定位个体 → span 看瓶颈**，三步各用一样东西，缺一环就断。判断一个信息该进哪里，问它是**聚合维度**还是**个体维度**：前者进指标（必须有界），后者进日志（可以无界）。

**第二层，观测数据的价值取决于设计，不取决于数量。** label 的基数纪律是最硬的一条：每个 label 组合是一条常驻内存的时间序列，把 request_id 加进去就是内存泄漏。而这条纪律顺带就是隐私防线——所有不能当 label 的东西恰好也是不该出现在指标里的用户数据。同理，埋点位置由"**哪里能拿到最完整的信息**"决定而不是"哪里最方便"：`degrade_total` 埋在唯一的降级汇聚点，所以新增节点自动被统计、指标与 span 永远同源；`count_retrieval_failure(code)` 埋在节点里，因为只有那里拿得到 `code`。选错位置的代价不是少一个数，是**两个数据源互相矛盾**——那比没有数据更糟，你不知道该信哪个，只能两边都不信。

**第三层，也是最容易被跳过的：可观测性坏了的表现是"一切正常"。** 错误处理坏了会有人报障，可观测性坏了则是图上一片绿、告警一声不响，而这跟真的没事长得一模一样。所以这套设施的每一处都要按"它自己可能是坏的"来设计：失败的调用也要记耗时（否则得到一个"一切都很快"的假 P99）；`reason=None` 归到 `unknown` 而不是丢弃（否则总数悄悄小于真实值，且无处可查）；日志系统自身用 `setdefault` 防 KeyError（日志抛异常会掩盖真正的错误）；观测失败一律只记日志不抛——"因为记不下耗时所以这次回答失败了"是荒谬的因果。

三层背后是同一个转变：从"**出了事去看日志**"，转到"**在没出事的时候，就把出事时需要的问题想清楚**"。前者是把观测当成事后补救，后者是把它当成设计的一部分。而这两种做法的差别，只会在真出事的那一刻显现出来——那时候已经来不及补了。
