## 一、这天要解决什么问题

想象你要盖房子。动工前必须先做两件事：

1. **画红线**：这块地我盖几层、盖多大，哪些坚决不盖（比如不盖游泳池，因为没预算）。
2. **定图纸分区**：客厅放哪、厨房放哪、卧室放哪，每个房间干一件事。

写软件也一样：

1. **边界冻结**：两周只做「告警首响分析」，坚决不碰「真实命令执行」。
2. **分层架构**：代码分成 4 层，每层只干一件事。

## 二、边界冻结：为什么"不做什么"比"做什么"更重要

### 该看的文件
`docs/adr/000-scope-first-response.md`

### 什么是 ADR

ADR = **Architecture Decision Record（架构决策记录）**。
说人话：**把「我当时为什么这么决定」写下来的一页纸。**

为什么值得写？举个例子对比：

- 普通简历："我做了一个 AIOps 系统。"
- 有 ADR 的你："我在'照搬成熟项目做执行平台'和'用自己的 RAG 长板做首响分析'
  之间选了后者，因为两周内做不出安全的命令执行层，硬做就是安全事故。"

第二种说法，面试官立刻知道你**懂取舍、懂风险**。这就是 ADR 的价值。

### 这篇 ADR 的核心决策

**做**：告警来了 → 查知识库 → 生成带证据的排查报告（只读、只分析）。

**坚决不做**：真实执行命令（SSH 登录服务器、重启服务、删文件……）。

**为什么不做执行**（这是最关键的取舍，一定要理解）：

1. **安全做不起**：真要执行命令，得防「命令注入」（黑客借你的工具搞破坏）、
   得有白名单、沙箱、审计、回滚……两周做不出安全的执行层。
2. **扬长避短**：你的项目强在 RAG 检索（查知识库），那就把这个长板用到极致，
   而不是去补「执行」这个短板。
3. **首响本来就不用执行**：值班工程师半夜被告警吵醒，第一件事是"我该先查什么"，
   这是**动脑**不是**动手**，只读就够了。

> 📌 **记住这个思维**：好的工程师不是什么都做，而是清楚地知道**什么不做、为什么**。

## 三、分层架构：4 层，每层只干一件事

这是整个项目最重要的概念，后面每天的代码都往这 4 层里放。

### 先看一张图

```
用户/告警
   │
   ▼
┌─────────────────────────────────────────┐
│  API 层     (app/api/)                    │  收请求、校验参数、返回 JSON
│  "前台接待"                                │  不写业务逻辑
├─────────────────────────────────────────┤
│  Service 层 (app/services/)               │  业务逻辑、编排流程
│  "业务经理"                                │  "先查这个再算那个"
├─────────────────────────────────────────┤
│  Repository 层 (app/repositories/)        │  只管存取数据库
│  "仓库管理员"                              │  怎么增删改查
├─────────────────────────────────────────┤
│  Model 层   (app/models/)                 │  定义数据长什么样
│  "登记表格式"                              │  表结构、字段类型
└─────────────────────────────────────────┘
   │
   ▼
数据库 / 大模型 / 知识库
```

### 用「餐厅」类比，一次讲透

你去餐厅吃饭：

- **服务员（API 层）**：接待你、记下你点的菜、把菜端给你。
  他**不做菜**，只负责"接单"和"上菜"。
- **厨师长（Service 层）**：决定这道菜怎么做——先切菜、再炒、最后摆盘。
  他负责**流程编排**，但他不自己去仓库搬菜。
- **仓库管理员（Repository 层）**：厨师长说"给我 2 个鸡蛋"，他就去仓库拿。
  他只管**存取**，不管这些鸡蛋要做成什么菜。
- **食材规格（Model 层）**：定义"一个鸡蛋"长什么样、"一份牛排"包含什么。
  它是**数据的格式定义**。

### 为什么要这么分？（面试高频题）

假设不分层，全塞在一个文件里会怎样？

```python
# ❌ 反面教材：全揉在一起
@app.post("/analyze")
def analyze(request):
    # 参数校验
    if not request.get("alert_name"): return {"error": "缺告警名"}
    # 直接连数据库
    conn = psycopg2.connect("...")
    conn.execute("INSERT INTO tasks ...")
    # 直接调大模型
    resp = openai.chat(...)
    # 直接连 Milvus 查知识库
    docs = milvus.search(...)
    # ... 300 行全在一个函数里
```

问题：
1. **改一处牵动全身**：想换个数据库？这个函数里到处是 SQL，改到哭。
2. **没法测试**：想测"业务逻辑对不对"，却被迫连真实数据库、真实大模型。
3. **没法复用**：另一个接口也要建任务？这段 SQL 又得抄一遍。

分层之后：
1. **换数据库** → 只改 Repository 层，其他层无感。
2. **测业务** → 把 Repository 换成"假的"（mock），不连真库也能测。
3. **复用** → 多个 Service 都能调同一个 Repository 方法。

> 📌 这就是 **SOLID 原则里的「单一职责」**：一个模块只有一个改动的理由。
> Repository 只因"存取方式变了"而改，Service 只因"业务规则变了"而改。

### 对照真实代码看这 4 层

以 Day6 做好的"告警分析"为例，一个请求走完 4 层：

| 层 | 文件 | 干了什么 |
|----|------|---------|
| API | `app/api/aiops.py` | 收到 POST，校验 payload，调 service |
| Service | `app/services/alert_diagnosis_orchestrator.py` | 归一化→建任务→检索→生成报告 |
| Repository | `app/repositories/aiops_diagnosis_repository.py` | 把任务 INSERT 进数据库 |
| Model | `app/models/aiops_diagnosis.py` | 定义"诊断任务"这张表的结构 |
