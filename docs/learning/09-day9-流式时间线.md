# 09 · Day9 真实阶段时间线（回调 + 数据库留痕）

> 这篇文档已经按当前代码重写。
>
> 旧版本讲的是 `run_stream()`、AIOps SSE 接口和 `yield`。这些内容不再对应当前项目：现在没有 `run_stream()`，也没有 `/api/aiops/alerts/analyze/stream`。
>
> 当前实现采用的是：**普通 `run()` 完成首响分析；`FirstResponseService.analyze()` 在真实阶段边界触发 `on_phase` 回调；编排层把阶段、耗时和计数原子地写入数据库事件表。**
>
> 因此 Day9 当前的主题应理解为：**让诊断时间线真实、可追溯、可查询，而不是通过 SSE 直接向前端逐条推送。**

---

## 一、这天解决的真实问题

Day6 的诊断入口是：

```text
POST /api/aiops/alerts/analyze
```

它会等待完整报告生成后，一次性返回：

```text
告警
  → 告警归一化
  → 创建诊断任务
  → SOP 检索
  → LLM 生成报告
  → 保存报告
  → HTTP 返回完整结果
```

这条接口不流式返回，但系统仍需要知道：

```text
检索到底花了多久？
模型生成到底花了多久？
SOP 是命中了、为空，还是检索服务失败？
报告是否降级？
某个任务最终失败在哪一步？
```

旧实现的问题是，编排层在真正开始分析之前，就一次性写入：

```text
planning
retrieving
diagnosing
```

三个时间戳几乎一样；之后要等十几秒甚至几十秒才出现 `done`。这样查数据库只能看到：

```text
14:00:00 planning
14:00:00 retrieving
14:00:00 diagnosing
14:00:25 done
```

但看不出那 25 秒到底是：

```text
Milvus 检索慢？
LLM 慢？
还是模型超时？
```

当前方案把事件写在**真实边界**：

```text
真正开始检索时 → retrieving
检索真正结束时 → retrieved（记录耗时、命中数、检索状态）
真正开始调 LLM 时 → diagnosing（记录 prompt token 估算）
生成真正结束时 → diagnosed（记录耗时、是否降级）
报告与任务保存时 → done
```

## 二、当前实现不是 SSE

先划清边界：当前 AIOps API 文件是：

```text
app/api/aiops.py
```

当前 AIOps 路由只有：

```text
POST /api/aiops/alerts/analyze
GET  /api/aiops/tasks
GET  /api/aiops/tasks/{task_id}
```

没有：

```text
POST /api/aiops/alerts/analyze/stream
```

也没有：

```python
EventSourceResponse
async def run_stream(...)
yield {"type": "status", ...}
```

所以前端 AI Ops 当前体验是：

```text
点击 AI Ops
→ 显示“分析中...”
→ 等普通 HTTP JSON 响应
→ 用 report_markdown 整体替换加载态
```

这不是缺陷，而是当前产品选择：先保证结构化报告、证据溯源、任务落库和可审计时间线。

### SSE 在项目哪里仍然存在

项目的普通聊天 RAG V2 仍使用 SSE：

```text
POST /api/chat_v2_stream
```

它用于逐步输出聊天内容与检索状态。但 AIOps 的阶段时间线目前是**数据库时间线**，不是前端 SSE 时间线。

## 三、当前完整链路

```text
POST /api/aiops/alerts/analyze
        │
        ▼
app/api/aiops.py : analyze_alert()
        │
        ▼
AlertDiagnosisOrchestrator.run()
        │
        ├─ normalize_alarm()
        ├─ create_task()                 → NEW
        ├─ record_phase(planning)        → PLANNING + planning 事件
        │
        ▼
FirstResponseService.analyze(alarm, on_phase=...)
        │
        ├─ on_phase(retrieving)          → RETRIEVING + 事件
        ├─ 真正检索 SOP
        ├─ on_phase(retrieved)           → 只记事件 + 检索耗时/命中数
        ├─ on_phase(diagnosing)          → DIAGNOSING + prompt token
        ├─ 真正调用 LLM
        └─ on_phase(diagnosed)           → 只记事件 + LLM 耗时/降级信息
        │
        ▼
repo.save_report()
        → 保存 report
        → DONE
        → done 事件
        │
        ▼
HTTP 201 返回 task_id、report、report_markdown
```

数据库中对应两张核心表：

```text
aiops_diagnosis_tasks   当前任务状态、标准化告警、最终报告
aiops_diagnosis_events  每个阶段的时间线事件
```

## 四、先看状态机：状态和事件不是同一个概念

文件：`app/models/aiops_diagnosis.py`。

任务状态只有六个：

```python
class DiagnosisTaskStatus(StrEnum):
    NEW = "new"
    PLANNING = "planning"
    RETRIEVING = "retrieving"
    DIAGNOSING = "diagnosing"
    DONE = "done"
    FAILED = "failed"
```

状态流转：

```text
NEW → PLANNING → RETRIEVING → DIAGNOSING → DONE
                  │             │              │
                  └─────────────┴──────────────┴──→ FAILED
```

但时间线事件比状态更细：

```text
planning     构造告警上下文
retrieving   开始检索 SOP
retrieved    SOP 检索结束，记录耗时和命中数
diagnosing   开始生成结构化报告
diagnosed    报告生成结束，记录模型耗时和降级信息
done         报告与任务保存成功
failed       任务失败
```

### 为什么 `retrieved` / `diagnosed` 不增加成状态

例如：

```text
retrieving  = 正在做 SOP 检索
retrieved   = SOP 检索已结束
```

检索结束的下一步马上就是生成报告；没有业务逻辑需要判断“任务处在已检索完成但尚未诊断”的长期状态。

因此：

```text
retrieving / diagnosing  → 任务状态
retrieved / diagnosed    → 时间线事件
```

这样状态机保持简单，事件表保留足够的观察细节。

## 五、编排层：`run()` 负责总流程

文件：`app/services/alert_diagnosis_orchestrator.py`。

当前唯一入口：

```python
async def run(
    self,
    db: Session,
    *,
    payload: dict[str, Any],
    source: AlarmSource | str = AlarmSource.MANUAL,
    session_id: str | None = None,
) -> tuple[AiopsDiagnosisTask, FirstResponseReport]:
```

它最终返回两个对象：

```text
task    本次诊断任务，含 ID、状态、事件、报告
report  FirstResponseReport，结构化首响报告
```

### 5.1 归一化和建任务

```python
alarm: AlarmEvent = normalize_alarm(payload, source)
repo = AiopsDiagnosisRepository(db)

task = repo.create_task(
    alarm_event=alarm.model_dump(mode="json"),
    alert_name=alarm.alert_name,
    severity=alarm.severity.value,
    source=alarm.source.value,
    alert_id=str(payload.get("alert_id")) if payload.get("alert_id") else None,
    session_id=session_id,
)
```

这里做了两件事：

```text
不同来源的原始告警 → 统一 AlarmEvent
AlarmEvent → 创建数据库任务（初始 NEW）
```

### 5.2 `planning` 为什么在这里立即写

```python
repo.record_phase(
    task,
    phase="planning",
    status=DiagnosisTaskStatus.PLANNING,
    message="构造告警上下文",
)
```

因为到这里：

```text
告警已归一化
任务已创建
上下文已具备
```

所以 `planning` 已经真实发生，写入时间线是准确的。

### 5.3 不再提前写 retrieving / diagnosing

旧方式会写：

```python
repo.advance_status(task, RETRIEVING)
repo.advance_status(task, DIAGNOSING)
report = await analyze(...)
```

问题是 `analyze()` 还没真正开始检索，状态就先写成 diagnosing，时间线失真。

当前改为：

```python
report = await self._response_service.analyze(
    alarm,
    on_phase=self._make_phase_handler(repo, task),
)
```

意思是：

```text
真正到哪个阶段，由 analyze 在真实开始/结束位置通知。
编排层只负责把通知翻译成任务状态和数据库事件。
```

## 六、回调是什么：不用 `yield` 也能报告进度

回调参数是：

```python
on_phase: PhaseCallback | None = None
```

签名概念上是：

```python
(phase: str, payload: dict) -> None
```

例如首响服务在检索开始前调用：

```python
emit(PHASE_RETRIEVING, {})
```

在检索结束时调用：

```python
emit(
    PHASE_RETRIEVED,
    {
        "duration_ms": retrieve_ms,
        "sop_hit_count": len(sop_evidence),
        "retrieval_status": sop_status.value,
    },
)
```

这里不是“把事件返回给 HTTP 客户端”，而是：

```text
服务内部通知编排器：我开始/完成了某个真实阶段。
```

编排器收到后写进数据库。

## 七、`_make_phase_handler()`：翻译回调为数据库动作

文件：`app/services/alert_diagnosis_orchestrator.py`。

```python
def _make_phase_handler(
    self,
    repo: AiopsDiagnosisRepository,
    task: AiopsDiagnosisTask,
) -> Callable[[str, dict[str, Any]], None]:
```

它返回一个内部函数：

```python
def handle(phase: str, payload: dict[str, Any]) -> None:
    repo.record_phase(
        task,
        phase=phase,
        status=_PHASE_STATUS.get(phase),
        message=_PHASE_MESSAGES.get(phase),
        payload=payload or None,
    )
```

翻译规则来自两个表：

```python
_PHASE_STATUS = {
    PHASE_RETRIEVING: DiagnosisTaskStatus.RETRIEVING,
    PHASE_DIAGNOSING: DiagnosisTaskStatus.DIAGNOSING,
}
```

```python
_PHASE_MESSAGES = {
    PHASE_RETRIEVING: "检索 SOP 与采集证据",
    PHASE_RETRIEVED: "SOP 检索完成",
    PHASE_DIAGNOSING: "生成结构化首响报告",
    PHASE_DIAGNOSED: "报告生成完成",
}
```

结果：

| 回调 phase | 是否变更任务状态 | 写入中文事件 | payload |
|---|---|---|---|
| `retrieving` | 变为 `retrieving` | 检索 SOP 与采集证据 | 空 |
| `retrieved` | 不改变状态 | SOP 检索完成 | 检索耗时、命中数、检索状态 |
| `diagnosing` | 变为 `diagnosing` | 生成结构化首响报告 | Prompt Token 估算 |
| `diagnosed` | 不改变状态 | 报告生成完成 | LLM 耗时、降级信息 |

## 八、首响服务的真实阶段边界

文件：`app/services/first_response_service.py`。

阶段常量：

```python
PHASE_RETRIEVING = "retrieving"
PHASE_RETRIEVED = "retrieved"
PHASE_DIAGNOSING = "diagnosing"
PHASE_DIAGNOSED = "diagnosed"
```

### 8.1 开始 SOP 检索

```python
emit(PHASE_RETRIEVING, {})
retrieve_start = time.perf_counter()
sop_evidence, sop_status = self._sop_service.retrieve_sop_evidence(alarm)
retrieve_ms = _elapsed_ms(retrieve_start)
```

顺序很重要：

```text
先发 retrieving
→ 再开始真正检索
→ 记录真实耗时
```

因此时间线上的 `retrieving` 真正表示“现在开始检索”，而不是事后补写。

### 8.2 检索结束

```python
emit(
    PHASE_RETRIEVED,
    {
        "duration_ms": retrieve_ms,
        "sop_hit_count": len(sop_evidence),
        "retrieval_status": sop_status.value,
    },
)
```

payload 示例：

```json
{
  "duration_ms": 126,
  "sop_hit_count": 2,
  "retrieval_status": "ok"
}
```

`retrieval_status` 需要区分：

| 值 | 含义 |
|---|---|
| `ok` | 成功检索到至少一条 SOP |
| `empty` | 检索服务正常，但知识库没有相关 SOP |
| `failed` | Milvus、Embedding 或检索服务失败；不能理解为“没有 SOP” |

这避免把“向量库挂了”错误写成“知识库没有 SOP”。

### 8.3 开始 LLM 生成

```python
emit(PHASE_DIAGNOSING, {"prompt_tokens": estimate_tokens(user_prompt)})
generate_start = time.perf_counter()
```

`prompt_tokens` 是输入 Prompt 的近似 Token 数；可帮助判断：

```text
模型慢，是上游模型慢？
还是 Prompt 太长导致输入成本和延迟增加？
```

### 8.4 LLM 生成结束

正常路径：

```python
emit(
    PHASE_DIAGNOSED,
    {
        "duration_ms": _elapsed_ms(generate_start),
        "is_degraded": report.is_degraded,
        "answer_length": len(report.raw_text or ""),
    },
)
```

若 LLM 异常：

```python
emit(
    PHASE_DIAGNOSED,
    {
        "duration_ms": _elapsed_ms(generate_start),
        "error_code": wrapped.code,
        "is_degraded": True,
    },
)
```

因此失败也有真实耗时和错误码，不会只留下一个模糊的“失败”。

## 九、为什么回调异常不会破坏诊断

`_make_emitter()` 将可选回调包装为始终可调用的函数：

```python
def _make_emitter(on_phase):
    if on_phase is None:
        return lambda phase, payload: None

    def emit(phase, payload):
        try:
            on_phase(phase, payload)
        except Exception as exc:
            logger.warning(f"阶段回调失败（不影响分析）: {exc}")

    return emit
```

含义：

```text
没有传回调 → emit 是空操作，原有调用仍兼容
数据库事件写失败 → 记录 warning
→ 主分析、SOP 检索、LLM 调用照常继续
```

原因是：时间线属于可观测设施；可观测设施失败不应让首响报告本身失败。

## 十、Repository：状态和事件同一事务写入

文件：`app/repositories/aiops_diagnosis_repository.py`。

核心方法：

```python
def record_phase(
    self,
    task,
    *,
    phase: str,
    status: DiagnosisTaskStatus | None = None,
    message: str | None = None,
    payload: dict | None = None,
):
```

实现核心：

```python
if status is not None:
    self._apply_status(task, status, phase=phase)
event = self._new_event(task.id, phase=phase, message=message, payload=payload)
self.db.commit()
return event
```

这意味着：

```text
状态更新 + 对应时间线事件
→ 同一个数据库事务
→ 一次 commit
```

而不是：

```text
先写状态并提交
→ 再写事件并提交
```

好处：如果进程在两次提交之间崩溃，不会出现：

```text
任务状态已经是 diagnosing
但事件表中没有 diagnosing 记录
```

## 十一、完成与失败如何留痕

### 11.1 成功

编排器在拿到报告后调用：

```python
repo.save_report(
    task,
    report=report.model_dump(mode="json"),
    summary=report.alert_summary,
    event_message="首响报告已生成",
    event_payload={"is_degraded": report.is_degraded},
)
```

`save_report()` 在同一次提交中：

```text
保存结构化 report JSON
设置 task.status = done
设置 current_phase = done
插入 done 事件
```

### 11.2 失败

如果编排层出现未预期异常：

```python
repo.mark_failed(
    task,
    error_message=str(exc),
    event_message=str(exc),
)
```

同一次提交中：

```text
设置 task.status = failed
设置 current_phase = failed
写 error_message
插入 failed 事件
```

所以失败任务不会“状态失败但时间线没有原因”。

## 十四、旧教程与当前实现对比

| 项目 | 旧 Day9 教程 | 当前实现 |
|---|---|---|
| 编排方法 | `run_stream()` | `run()` |

## 十五、为什么当前方案更适合现有代码

当前 AIOps 页面只有一个按钮，点击后发送的是演示告警并等待完整 Markdown 报告。没有独立的时间线 UI，也没有 SSE 消费代码。

此时保留一套：

```text
run_stream
+ SSE endpoint
+ 前端 EventSource/SSE 解析
+ 断线处理
+ 事件去重
+ 时间线组件
```

会增加很多尚未被产品使用的复杂度。

当前方案先解决最重要的事实：

```text
阶段必须在真实边界发生
阶段必须落库
耗时与关键计数必须可查询
失败必须有原因
```

之后若真正要做“页面实时显示时间线”，可以在已有 `aiops_diagnosis_events` 的基础上增加：

```text
轮询 GET /api/aiops/tasks/{task_id}
或 SSE / WebSocket 推送新增事件
```

届时不需要重写诊断业务，只需增加“把已落库事件送到前端”的传输层。

当前 Day9 的核心不再是：

```text
yield + SSE
```

而是：

```text
真实阶段边界
+ on_phase 回调
+ 状态与事件同事务落库
+ 检索/LLM 耗时与状态可审计
+ 任务详情接口可回放时间线
```

一句话：

> AIOps 当前不是把进度实时推给页面，而是先把每一步真实发生了什么、花了多久、是否降级，可靠地保存下来；这份数据库时间线才是后续轮询或 SSE 前端展示的可信基础。
