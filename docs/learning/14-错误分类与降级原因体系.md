# 错误分类与降级原因体系

> 这是「失败降级工程」四批改造的第一篇。它讲的是一件听起来很小、
> 实际决定了后面所有篇章能否成立的事：**当一次调用失败时，
> 我们用什么词来描述这次失败。**

## 1. 为什么要改

先看一个真实的故障场景 —— 这是整个四批改造的起点。

某天凌晨，向量库（Milvus）连接池被打满，SOP 检索开始失败。系统没有崩，
因为 SOP 检索有降级：检索不到证据就返回空列表，让模型基于告警本身去分析。
一份首响报告照样生成出来了，最后一段写着：

```text
建议：知识库中未检索到该告警的相关 SOP 文档，
建议补充 HighCPUUsage 告警的标准处置流程文档。
```

值班同学照做了。他花了一个小时写文档，第二天发现别的告警也在报同样的话。
真正挂掉的是向量库 —— **而系统告诉他的是「知识库里没有这篇文档」。**

这两句话在代码里是同一个分支：

```text
检索返回 0 条  →  "未检索到相关 SOP"
```

但它们是**两个完全相反的结论**：

| 真实情况 | 该做什么 | 系统说的话 |
|---|---|---|
| 知识库里确实没有 | 去写文档 | "未检索到相关 SOP" ✅ |
| 检索服务挂了 | 去修向量库 | "未检索到相关 SOP" ❌ |

第二行是一句**谎话**。它不是 bug 导致的崩溃，而是降级路径**主动编造**出来的
一个错误结论。而且它比崩溃更糟：崩溃会有人来查，谎话会让人照着去干活。

这类问题在项目里有很多个变体，后面每一篇都会讲一个。它们的共同根因是：

> **失败发生时，我们没有一套词汇能准确说出「为什么失败」，
> 于是每个降级点各自编一句话，编出来的话又刚好和别的含义撞车。**

所以第一批要做的事就是：**先建立词汇表**。

## 2. 改之前什么样

改造前项目里没有 `app/core/errors.py` 这个文件。异常处理散在各处，
大致是三种写法。

### 2.1 写法一：捕获后返回一句自由文本

```python
# app/services/first_response_service.py（改造前）
try:
    response = await llm.ainvoke([...])
except Exception as e:
    report = FirstResponseReport(
        alert_summary=f"告警 {alarm.alert_name} 分析失败",
        current_judgment="LLM 调用异常，无法生成分析。",
        raw_text=f"LLM 调用异常: {str(e)}",   # ← 问题在这里
    )
```

`str(e)` 是什么？取决于抛异常的那个库。可能是：

```text
Connection timeout after 60.0 seconds
Error code: 429 - {'error': {'message': 'Rate limit reached...'}}
[Errno 104] Connection reset by peer
```

这三句话对人来说勉强能读，对**程序**来说毫无价值。你没法写一个查询问
「过去一小时超时了多少次」—— 因为「超时」这个概念在数据里不存在，
只存在于一堆各不相同的英文句子里。

而且这三种失败的**修复方向完全不同**：第一个该调超时阈值或扩容，
第二个该去看配额，第三个该查网络。塞进同一个 `raw_text` 字段之后，
它们变成了同一个东西。

### 2.2 写法二：捕获后返回 200

```python
# app/api/chat_v2.py（改造前）
except Exception as e:
    return {"code": 500, "message": "error", "data": {...}}
```

`return` 而不是 `raise` —— FastAPI 看到一个正常返回值，
于是发出 **HTTP 200 OK**，body 里写着 `code: 500`。
这个问题第 18 篇专门讲。

### 2.3 写法三：`except: pass`

```python
except Exception:
    pass
```

失败被完全吞掉，连日志都没有。

### 2.4 三种写法的共同点

它们都在做同一件事的三个版本：**把结构化的失败信息压成非结构化的东西**
（自由文本 / 一个笼统的 500 / 什么都不剩）。

信息一旦压掉就再也拿不回来了。后面三批想做的所有事情 ——
按原因统计降级率、让 HTTP 状态码说真话、给告警分修复方向 ——
全都需要这个信息。所以它必须先被建立起来。

## 3. 改之后什么样

新增 `app/core/errors.py`，它有两个核心产物：一个**异常家族**，一个**枚举**。

### 3.1 DegradeReason：降级原因枚举

```python
# app/core/errors.py:25
class DegradeReason(StrEnum):
    LLM_TIMEOUT = "llm_timeout"                    # 模型超时 → 调阈值/扩容
    LLM_ERROR = "llm_error"                        # 模型报错 → 查配额/鉴权
    PARSE_FAILED = "parse_failed"                  # 输出解析失败 → 改 prompt
    RETRIEVAL_FAILED = "retrieval_failed"          # 检索挂了 → 查向量库
    RETRIEVAL_EMPTY = "retrieval_empty"            # 库里确实没有 → 补文档
    PARTIAL_RETRIEVAL = "partial_retrieval"        # 部分子查询失败 → 看容量
    EVIDENCE_INSUFFICIENT = "evidence_insufficient" # 证据不足 → 补文档
    CIRCUIT_OPEN = "circuit_open"                  # 熔断跳过 → 等恢复/查下游
    TOTAL_BUDGET_EXCEEDED = "total_budget_exceeded" # 总预算耗尽 → 调预算/优化
    FEATURE_DISABLED = "feature_disabled"          # 开关关掉了 → 开开关
```

**这个枚举的划分标准是「修复方向」，不是「哪一层出的错」。**

这一句是整个体系的设计核心，值得展开。你可能会想：为什么不按技术分层分
（网络层错误 / 服务层错误 / 数据层错误）？因为分层对**排障的人**没用。
值班同学半夜被叫起来，他要回答的唯一问题是「我现在该去动哪个东西」。

对照上面表格的右列 —— 每个 reason 都直接指向一个动作。这就是它存在的意义。

顺着这个标准看第一节那个故障，`RETRIEVAL_FAILED` 和 `RETRIEVAL_EMPTY`
必须是两个值，因为一个指向「去修向量库」，另一个指向「去写文档」。
把它们合成一个，那句谎话就会重新长出来。

同理，`FEATURE_DISABLED` 也不能省。开关关掉时如果复用 `RETRIEVAL_FAILED`，
值班同学会去查 Milvus，而 Milvus 一切正常 —— 排障就此卡住。

### 3.2 AppError：自带语义的异常基类

```python
# app/core/errors.py:81
class AppError(Exception):
    code: str = "app_error"                        # 可聚合的错误码
    retryable: bool = False                        # 重试有没有意义
    http_status: int = 500                         # 该返回什么状态码
    degrade_reason: DegradeReason | None = None     # 降级原因
```

四个类属性，每一个都回答一个具体问题：

```text
code           → 「这类错误发生了多少次」（指标聚合用）
retryable      → 「worker 该不该重试这个任务」（第 19 篇用）
http_status    → 「网关和监控该看到什么」（第 18 篇用）
degrade_reason → 「人该去修什么」（本篇的主题）
```

子类只需要覆盖这四个属性，不需要写任何逻辑：

```python
# app/core/errors.py:148
class LLMTimeoutError(LLMError):
    code = "llm_timeout"
    retryable = True          # 超时往往是瞬时的，重试有意义
    http_status = 504         # 让网关能正确统计「网关超时」
    degrade_reason = DegradeReason.LLM_TIMEOUT
```

```python
# app/core/errors.py:205
class InvalidRequestError(AppError):
    code = "invalid_request"
    retryable = False         # 客户端不改参数，重试一万次也一样
    http_status = 400
```

注意 `InvalidRequestError` **没有** `degrade_reason` —— 它不是降级，
是客户端传错了参数。降级的定义是「我方能力下降但仍给出了可用结果」，
参数错误不属于这一类。这个区分在第 18 篇会再用到：
4xx 不该污染错误率告警。

完整家族（括号内是继承关系）：

```text
AppError (errors.py:81)
├── RetrievalError            (127)  retryable=True   502  RETRIEVAL_FAILED
├── LLMError                  (139)  retryable=True   502  LLM_ERROR
│   └── LLMTimeoutError       (148)  retryable=True   504  LLM_TIMEOUT
├── ParseError                (162)  retryable=False  502  PARSE_FAILED
├── UpstreamUnavailableError  (175)  retryable=True   502  （无）
├── CircuitOpenError          (183)  retryable=False  503  CIRCUIT_OPEN
├── TotalBudgetExceededError  (196)  retryable=False  504  TOTAL_BUDGET_EXCEEDED
└── InvalidRequestError       (205)  retryable=False  400  （无）
```

`LLMTimeoutError` 继承 `LLMError` 而不是直接继承 `AppError`，
是为了让 `except LLMError` 能同时接住普通失败和超时 ——
调用点不关心区别时可以只写一个 except。

### 3.3 四个查询函数：给「不是 AppError」的异常兜底

真实世界里大部分异常来自第三方库，它们不可能继承我们的 `AppError`。
所以需要一组函数，把**任意**异常映射到我们的词汇表：

```python
# app/core/errors.py:280
def error_code_of(exc: BaseException) -> str:
    """任意异常 → 可聚合的错误码。"""

# app/core/errors.py:291
def degrade_reason_of(exc: BaseException) -> DegradeReason:
    """任意异常 → 降级原因。"""

# app/core/errors.py:311
def http_status_of(exc: BaseException) -> int:
    """任意异常 → HTTP 状态码。"""

# app/core/errors.py:258
def is_retryable(exc: BaseException) -> bool:
    """任意异常 → 重试有没有意义。"""
```

对 `AppError` 它们直接读类属性；对别的异常，按类名匹配：

```python
# app/core/errors.py:222
_RETRYABLE_EXCEPTION_NAMES = frozenset(
    {
        "TimeoutError",
        "ConnectionError",
        # ...
    }
)
```

**为什么按类名字符串匹配，而不是 `isinstance`？**

因为 `isinstance` 要求 import 那个类，而这些类分布在 pymilvus、httpx、
openai 等库里。全部 import 进来会让 `errors.py` 依赖半个 requirements，
而且某个库没装就直接 ImportError。字符串匹配是**鸭子类型**的思路：
我们只关心「它叫什么」，不关心它从哪来。

代价是类名重复时会误判（两个库都有 `TimeoutError`）——
但这两个恰好都该判为可重试，所以这个代价在本项目里为零。

### 3.4 to_app_error：HTTP 边界的收敛点，且刻意不设降级原因

```python
# app/core/errors.py:328
def to_app_error(exc, *, context=None) -> AppError:
    if isinstance(exc, AppError):
        return exc

    wrapped = AppError(f"{type(exc).__name__}: {exc}", cause=exc, context=context)
    # 实例属性遮蔽类属性：不为每种未知异常都造一个子类（YAGNI）。
    wrapped.code = error_code_of(exc)
    wrapped.retryable = is_retryable(exc)
    wrapped.http_status = http_status_of(exc)
    return wrapped
```

它赋了三个属性，**唯独没有赋 `degrade_reason`** —— 这是有意的，
而且是本篇最容易被写错的一个判断。

降级的定义是「给出一个更差但仍可用的结果，并说明差在哪」。
一个打到 HTTP 边界的未知异常**不是降级，是彻底失败**：没有任何结果可用。

如果这里顺手兜一个 `llm_error`，那么 `degrade_total{reason="llm_error"}`
里就会混进各种真实的代码 bug —— `KeyError`、`AttributeError`、
拼错的字段名。这个指标随即失去意义：看到 `llm_error` 上涨，
值班同学会去查模型配额和上游状态，而实际原因是我们自己代码写错了一行。

所以纪律是：**只有主动抛出的 `AppError` 子类才带 `degrade_reason`**，
因为只有那些地方我们才真的知道降级原因。未知异常只带 `code`，
用于聚合统计「哪类未知错误最多」。

注意这里用的是**实例属性遮蔽类属性**，而不是为每种未知异常造一个子类。
`KeyError`、`AttributeError`、`ZeroDivisionError`……真要一一建类会有几十个，
而它们的处置方式完全一样（都是代码 bug，都不重试，都 500）。YAGNI。

### 3.5 wrap_llm_exception：DRY 的实现

四个 LLM 调用点都需要「把任意异常转成带语义的 AppError」。
这个逻辑只能有一处实现：

```python
# app/core/errors.py:358
def wrap_llm_exception(exc, *, context=None) -> AppError:
    # 已经能自我描述的异常原样放行，不要重新分类。
    if isinstance(exc, AppError) and exc.degrade_reason is not None:
        return exc

    import asyncio
    if isinstance(exc, (asyncio.TimeoutError, TimeoutError)):
        return LLMTimeoutError(f"LLM 调用超时: {exc}", cause=exc, context=context)
    return LLMError(f"LLM 调用失败: {exc}", cause=exc, context=context)
```

调用点只写一行：

```python
except Exception as exc:
    wrapped = wrap_llm_exception(exc)
    logger.error(f"改写失败[{wrapped.code}]: {wrapped.message}")
```

**第一行的判据值得特别说明**，因为它藏着一个真实的 bug。

这行原本写的是 `isinstance(exc, LLMError)` —— 只放行 LLM 家族。
第四批加熔断器时出了问题：`CircuitOpenError` 继承的是 `AppError`
而不是 `LLMError`，于是它走到最后一行被**重新包装**成 `LLMError`，
`degrade_reason` 从 `circuit_open` 变成了 `llm_error`。

后果：值班同学看到 `llm_error` 上涨，去查模型配额和鉴权，
而真实情况是我们自己的熔断器打开了，模型服务可能一直是好的。

这和第一节那句「未检索到相关 SOP」是**完全同一类错误**：
用一个假原因掩盖真原因。只不过这次的受害者是我们自己的监控。

`TotalBudgetExceededError` 同理 —— 它也直接继承 `AppError`，
也会被重包成 `llm_error`。也就是说这个 bug 会同时污染两条降级原因，
而且污染的方向一致：**都把「我方主动放弃」伪装成「上游出错」**。
这个方向很危险，因为它会让人一直往外查。

改成 `exc.degrade_reason is not None` 之后，判据变成了
**「这个异常有没有自带降级原因」**。而「自带降级原因」正是
「它已经说清了自己为什么导致降级」的定义 ——
所以以后新增任何带 `degrade_reason` 的子类都自动正确。
这是开闭原则的一个具体例子：对扩展开放（新子类不用改这里），
对修改关闭（不用维护一张 isinstance 清单）。

## 4. 背后的工程原理

### 4.1 为什么「错误分类」是可观测性的地基

可观测性有三根柱子：日志、指标、追踪。三者都需要一个**共同的词汇表**：

```text
指标：degrade_total{reason="llm_timeout"}     ← reason 从哪来？
日志：SOP 检索失败[circuit_open]              ← 方括号里那个码从哪来？
追踪：span.payload = {"error_code": "..."}    ← 这个码从哪来？
```

三个都来自 `errors.py`。如果没有这一层，每个地方各自编造字符串，
你会得到 `"timeout"` / `"Timeout"` / `"LLM timeout"` / `"llm_timeout"`
四个含义相同的值 —— 在 Prometheus 里是**四条独立的时间序列**，
在日志里是四个搜不到一起的关键词。

所以这一批必须排在最前面。它本身不解决任何用户可见的问题，
但后面三批全都建立在它上面。

### 4.2 为什么用异常携带语义，而不是返回错误码

另一种常见做法是返回 `(result, error_code)` 元组，或者 Go 风格的
`result, err`。Python 里不这么做的原因：

**异常会自动冒泡。** 调用链有五层的时候，返回值风格要求每一层都
显式检查并向上传递错误码 —— 漏掉一层，错误就被静默丢弃。
而异常默认往上抛，你必须**显式**写 `except` 才能拦住它。
默认行为是安全的那一边。

代价是异常的控制流不如返回值直观。项目里用两个纪律来对冲：
降级点必须显式 `except`（不允许让异常穿过一个应该降级的地方），
以及全局兜底处理器（第 18 篇）保证没人漏接。

### 4.3 为什么枚举而不是字符串常量

`DegradeReason` 用 `StrEnum` 而不是一堆 `DEGRADE_LLM_TIMEOUT = "llm_timeout"`：

```python
class DegradeReason(StrEnum):
    LLM_TIMEOUT = "llm_timeout"
```

`StrEnum` 的成员**同时是字符串**，所以 `DegradeReason.LLM_TIMEOUT == "llm_timeout"`
为真，可以直接塞进 JSON、直接当 Prometheus 的 label 值。
但它又是一个封闭集合 —— 拼错 `DegradeReason.LLM_TIMEOT` 会立刻 AttributeError，
而拼错字符串 `"llm_timeot"` 会安静地生成一条新的时间序列。

这就是第 22 篇会讲的 **label 基数纪律**的第一道防线：
label 的取值必须来自封闭枚举，不能是自由字符串。

### 4.4 面试怎么讲这一段

如果被问到「你的项目做了什么错误处理」，不要答「用了 try except」。
答这个结构：

> 我先定义了一套**按修复方向划分**的降级原因枚举。划分标准很关键 ——
> 不是按技术分层，而是按「值班的人该去动哪个东西」。因为我遇到过一个
> 真实故障：向量库挂了，但降级路径说的是「知识库里没有这篇文档」，
> 结果同事花一小时写了一份根本不需要的文档。这两句话在代码里是同一个
> 分支，但修复方向完全相反。
>
> 然后让异常自己携带四个语义属性（错误码、是否可重试、HTTP 状态码、
> 降级原因），这样分类逻辑只有一处实现，而不是散在每个 except 里。
> 后面做指标聚合、HTTP 状态码修正、worker 重试策略，全都复用这一层。

这个回答的价值在于它包含了一个**取舍**和一个**代价**，
而不只是「我做了 X」。

## 5. 怎么验证

错误分类的测试不在单独的 `test_errors.py` 里，而是在
`tests/unit/test_degradation_paths.py` —— 因为分类逻辑本身没什么可测的
（都是类属性），真正需要锁住的是**它在每条降级路径上被用对了**。
测试按「降级场景」而不是按「文件」组织：

```bash
# 错误分类 + 降级路径全部测试
wsl.exe -d Ubuntu -- bash -lc 'cd /home/dong/projects/super_biz_agent_py && \
  .venv/bin/python -m pytest tests/unit/test_degradation_paths.py -v --no-cov'
```

其中直接对应本篇的几个用例：

```bash
wsl.exe -d Ubuntu -- bash -lc 'cd /home/dong/projects/super_biz_agent_py && \
  .venv/bin/python -m pytest tests/unit/test_degradation_paths.py \
  -k "TestLLMFailureClassification or error_code_is_finite_enum or degrade_reason_of_never_returns_none" \
  -v --no-cov'
```

- `test_timeout_maps_to_llm_timeout` —— 超时映射到 `LLM_TIMEOUT`
- `test_generic_error_maps_to_llm_error` —— 其余映射到 `LLM_ERROR`
- `test_already_wrapped_is_returned_as_is` —— 第 3.5 节那个 bug 的回归锁
- `test_error_code_is_finite_enum_not_free_text` —— code 必须是有限集合

## 6. 常见坑

**坑 1：给每个错误都建一个异常类。**

不要为了「分得细」而建二十个异常类。判断标准是：
**如果两个错误的四个属性完全相同，它们就是同一个类。**
`UpstreamUnavailableError` 和 `RetrievalError` 属性不同（前者没有
degrade_reason），所以是两个类；如果哪天发现两个类属性一模一样，
说明其中一个该删。

**坑 2：把 degrade_reason 当成错误码用。**

它们是两个维度。`code` 回答「发生了什么」，`degrade_reason` 回答
「该去修什么」。多个 code 可以映射到同一个 reason ——
比如 `milvus_error` 和 `bm25_error` 都是 `RETRIEVAL_FAILED`。
反过来不行：一个 code 有两个 reason 说明分类有问题。

**坑 3：在 except 里重新分类已经分好的异常。**

```python
# 错的
except Exception as exc:
    raise LLMError(f"失败: {exc}")     # ← 把 CircuitOpenError 也包进来了
```

这就是第 3.5 节那个 bug。正确做法是先判断它是否已经自带语义：

```python
# 对的
except Exception as exc:
    raise wrap_llm_exception(exc)      # ← 内部会放行已分类的异常
```

**坑 4：用 `except BaseException` 或裸 `except:`。**

它们会连 `KeyboardInterrupt` 和 `asyncio.CancelledError` 一起吞掉。
`CancelledError` 在 Python 3.8+ 继承 `BaseException` 而不是 `Exception`，
这个设计正是为了让 `except Exception` **不会**误吞取消信号 ——
吞掉它会导致协程取消失效，总预算超时后请求还在跑。

所以业务代码统一用 `except Exception`。唯一的例外是熔断器的
`guard()`（第 21 篇），它需要看见真正的超时，但那里显式排除了
`CancelledError`，并且原样往上抛。
