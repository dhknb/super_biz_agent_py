# 17 · 检索失败隔离与部分成功降级

> 本篇的主角是两条检索链路：`app/agent/rag_v2/`（多查询并行 RAG）
> 和 `app/services/sop_retrieval_service.py`（AIOps 首响的 SOP 检索）。
>
> 它们改造前有一个共同的病：**把"检索失败"当成了"检索到 0 条"**。
> 前者的后果是整张图崩掉，后者的后果更隐蔽 —— 它会让系统对你撒谎。

---

## 1. 为什么要改

### 1.1 第一个场景：一个分支炸掉，四个分支的活白干

用户问"订单支付失败怎么排查"。rag_v2 把它改写成 4 个子查询并行检索：

```
sub_queries = [
    "订单支付失败的常见原因",
    "支付网关超时排查步骤",
    "支付回调丢失如何补单",
    "支付状态不一致的对账方法",
]
```

前 3 个都成功了，一共召回 11 条文档，证据相当充足。
第 4 个赶上 Milvus 一次连接抖动，`pymilvus` 抛了个 `MilvusException`。

改造前的结果：**用户拿到一个 HTTP 500，什么都没有。**

原因在 LangGraph 的并行语义。`graph.py` 用 `Send` 把 N 个子查询 fan-out
到 `retrieve_each_node` 的 N 个实例，而 LangGraph 的规则是
**任一并行分支抛异常 → 整个 super-step 失败 → 整张图崩**。

那 11 条文档已经从 Milvus 捞出来、已经付过网络往返和 embedding 的钱了，
就因为第 4 个分支不幸，全部丢掉。

这在工程上是双重浪费：算力白烧，用户体验为零。而实际上
"4 个子查询里有 3 个成功"完全足够生成一个好答案 ——
只要我们诚实地告诉模型"证据可能不完整"。

### 1.2 第二个场景：系统对值班同学撒谎

这个更严重，它是整个四批改造的**起因案例**。

AIOps 首响链路：收到告警 → 检索知识库 SOP → 把 SOP 作为证据喂给模型 →
模型输出结构化的首响报告。

`retrieve_sop_evidence` 改造前只返回 `list[Evidence]`。于是：

```
Milvus 挂了           → 返回 []
知识库真的没这篇 SOP  → 返回 []
```

调用方只能写 `if evidence:`，两种情况被压成同一个信号。
零证据时 prompt 里那句话是：

```
（未检索到相关 SOP，请基于告警本身分析）
```

**Milvus 挂掉的时候，这句话是假的。** 我们并没有"未检索到"，
我们是"没检索成功"。模型是个诚实的推理机器，它照着这句假话往下推：

> 这个告警没有对应的 SOP 文档
> → 说明运维知识库有缺口
> → 建议：**补充该告警的 SOP 文档**

值班同学半夜被叫起来，看到报告说"建议补充 SOP"，
于是打开 Confluence 开始写文档。

而真正挂掉的是向量库。它可能已经挂了两个小时，
期间每一份首响报告都在建议"补充 SOP"。
排障方向被系统**主动带反**了。

请注意这和普通的降级不是一回事：

| | 定义 | 例子 |
|---|---|---|
| **降级** | 我少给你一部分能力，**并且告诉你少了什么** | "检索服务不可用，本次分析未使用知识库证据" |
| **撒谎** | 把依赖故障**伪装成一个正常的业务结论** | "未检索到相关 SOP"（实际是检索炸了） |

降级让人做出正确决策，撒谎让人做出错误决策。
**撒谎比直接报错更糟** —— 报错至少会让人去查为什么报错。

而且这个信息是在 `retrieve_sop_evidence` 这一层丢掉的。
一旦在这里把 failed 和 empty 压成同一个 `[]`，
后面无论 prompt 写得多精妙都救不回来 —— 信息已经不在了。

### 2.4 SOP 检索：签名里就没有表达失败的位置

> 注：`app/services/sop_retrieval_service.py` 和 `first_response_service.py`
> 属于 AIOps 模块，在 git 里从未提交过（`git status` 显示 `??`）。
> 所以这里的"改之前"引自当前代码 docstring 里记录的原样，
> 而不是 `git show`。

```python
def retrieve_sop_evidence(self, alarm: AlarmEvent) -> list[Evidence]:
    query = alarm.retrieval_query()
    try:
        docs = self._get_retriever().retrieve_documents(query, top_k=self._top_k)
```

这是一个类型设计问题：`list[Evidence]` 这个返回类型的信息量
不足以承载"成功但为空"和"失败"这两种状态的区别。

## 3. 改之后什么样

### 3.1 retrieve_each_node：把异常收进 state

`app/agent/rag_v2/nodes.py:158-211`：

```python
async def retrieve_each_node(task: RetrieveTask) -> Dict[str, Any]:
    """单条子查询检索。**任何异常都不向上抛**，只记为一条失败明细。"""
    query = task["query"]
    logger.info(f"[rag_v2.retrieve_each] 检索子查询: {query}")

    try:
        # 熔断器包在 to_thread **外面**，而不是塞进线程里。
        # 包在外面，熔断打开时连线程池 worker 都不必占用 —— 这正是熔断器
        # 想省下的那份成本（Milvus 挂了，600 个请求各占一个 worker 白等 60 秒）。
        with retrieval_breaker.guard():
            docs: List[Document] = await asyncio.to_thread(
                vector_search_service.retrieve_documents, query, RETRIEVE_TOP_K
            )
    except Exception as exc:
        # 刻意捕获宽泛的 Exception：下游检索栈会抛什么由 pymilvus /
        # 网络层决定，穷举类型既不可能也没必要 —— 我们要的是
        # 「这个分支没成功」这一个事实，以及足够排障的原因文本。
        #
        # 不吞掉 CancelledError：它在 Python 3.8+ 继承自 BaseException，
        # 不在 Exception 分支里，总预算超时取消协程时能正常向上传播。
        code = error_code_of(exc)
        count_retrieval_failure(code)
        logger.warning(f"[rag_v2.retrieve_each] 子查询 '{query}' 检索失败[{code}]: {exc}")
        return {
            "documents": [],                                    # ← 这一分支没有贡献文档
            "retrieve_failures": [                              # ← 但留下了失败明细
                {"query": query, "error": str(exc), "code": code}
            ],
        }

    for doc in docs:
        doc.metadata = {**(doc.metadata or {}), "_sub_query": query}
    logger.info(f"[rag_v2.retrieve_each] 子查询 '{query}' 召回 {len(docs)} 条")
    return {"documents": docs}
```

关键是 **返回而不是抛出**。语义从此变成：

> 一个分支失败 = 证据少一份，而不是整个请求失败。

三个细节值得单独说：

**`except Exception` 而不是穷举类型。** 这一次宽泛捕获是对的，
因为我们要的信息只有"成没成"这一个 bit。至于是 `MilvusException`
还是 `ConnectionError`，`error_code_of(exc)` 已经把它变成了
一个有限的指标标签（见 [14 篇](14-错误分类与降级原因体系.md)）。

**`CancelledError` 不会被吞。** Python 3.8 起它继承 `BaseException`，
不是 `Exception` 的子类。这很关键：总预算耗尽时
`asyncio.timeout` 靠取消协程来中断，如果这里把 `CancelledError`
当成"一次检索失败"吞掉，取消信号就传不上去，超时机制会失效。

**熔断器在 `to_thread` 外层。** 这是资源保护的先后顺序问题 ——
详见 [21 篇](21-熔断器与运行时降级开关.md)。

### 3.2 state 里的失败通道

`app/agent/rag_v2/state.py:17-34`：

```python
class RAGState(TypedDict, total=False):
    question: str
    conversation_context: str
    sub_queries: List[str]
    documents: Annotated[List[Document], operator.add]
    # 检索失败明细，与 documents 用同一套 fan-in 语义（operator.add 合并各分支）。
    retrieve_failures: Annotated[List[Dict[str, Any]], operator.add]
    deduped_documents: List[Document]
    answer: str
    validation: Dict[str, Any]
    # 本次运行的降级原因（DegradeReason 的字符串值），无降级时不写入。
    # 用列表而非单值：一次运行可能同时命中多个原因
    # （例如部分检索失败 + 证据不足），压成一个会丢信息。
    degrade_reasons: Annotated[List[str], operator.add]
```

`Annotated[List[...], operator.add]` 是 LangGraph 的 **reducer**。
它的含义是"多个并行分支都写这个键时，用 `operator.add` 合并"，
对 list 就是拼接。

没有 reducer 的键（比如 `deduped_documents`）遵循"后写覆盖"，
并行分支同时写就会互相踩。所以 `retrieve_failures` 必须和
`documents` 用**同一套** fan-in 语义 —— 4 个分支各自返回一小段，
LangGraph 自动拼成完整列表。

`degrade_reasons` 用列表而不是单值，是因为一次运行可能同时踩中
多个降级原因（部分检索失败 + 证据不足），压成单值会丢掉一个。

### 3.3 dedup_node：唯一能看到全局的位置

`app/agent/rag_v2/nodes.py`：

```python
    # 在这里判定检索侧的降级原因，而不是在 retrieve_each 里。
    # 原因是单个分支看不到全局：它只知道「我失败了」，判断不了
    # 「是全都失败了，还是只有我失败」—— 而这两者的处置方向完全不同。
    # dedup 是 fan-in 之后的第一个节点，是唯一能看到全部分支结果的位置。
    failures = state.get("retrieve_failures", []) or []
    degrade_reasons: List[str] = []
    if failures:
        if unique_docs:
            # 部分分支失败但仍有证据：结果可用，只是证据不完整。
            degrade_reasons.append(DegradeReason.PARTIAL_RETRIEVAL.value)
            logger.warning(
                f"[rag_v2.dedup] 部分检索失败({len(failures)} 条)，"
                f"在 {len(unique_docs)} 条证据上继续生成"
            )
        else:
            # 全部失败，一条证据都没有：这是基础设施问题，不是知识库缺文档。
            # 必须与 RETRIEVAL_EMPTY 区分开 —— 前者要修 Milvus，后者要补文档。
            degrade_reasons.append(DegradeReason.RETRIEVAL_FAILED.value)
            logger.error(f"[rag_v2.dedup] 全部检索分支失败({len(failures)} 条)，无可用证据")
    elif not unique_docs:
        # 没有失败却也没有结果：知识库里确实没有相关内容。
        degrade_reasons.append(DegradeReason.RETRIEVAL_EMPTY.value)
        logger.warning("[rag_v2.dedup] 检索正常但未命中任何文档")

    result: Dict[str, Any] = {"deduped_documents": unique_docs}
    if degrade_reasons:
        result["degrade_reasons"] = degrade_reasons
    return result
```

**为什么判定必须放在 dedup 而不是 retrieve_each。**
这是本篇最重要的一个结构判断。

单个 `retrieve_each` 实例只知道自己的结果。它无法回答
"是 4 个全挂了，还是只有我挂了"—— 而这两者的处置方向完全相反：

| 状态 | 含义 | 谁该做什么 |
|---|---|---|
| `PARTIAL_RETRIEVAL` | 部分失败，仍有证据 | 答案可用，但要提示不完整；运维看日志找原因 |
| `RETRIEVAL_FAILED` | 全部失败，零证据 | 去修向量库 |
| `RETRIEVAL_EMPTY` | 检索正常，库里没有 | 去补文档 |

三种状态对应三个完全不同的动作。而只有 fan-in 之后的第一个节点
才拿得到全部分支的结果，所以判定只能在这里做。

用 `elif not unique_docs` 而不是独立的 `if`，是因为
"有失败"和"无失败但空"是互斥的两种世界 —— 有失败时
是否为空已经在上面的 `if unique_docs` 里分完了。

### 3.5 SOP 检索：把 status 加进返回类型

`app/services/sop_retrieval_service.py:68-167`。签名变化是核心：

```python
def retrieve_sop_evidence(
    self, alarm: AlarmEvent
) -> tuple[list[Evidence], RetrievalStatus]:     # ← 多返回一个状态
```

三条返回路径，各自如实：

```python
        # 开关关闭 → FAILED（不是 EMPTY）
        if not config.enable_sop_retrieval:
            logger.warning(
                f"SOP 检索已被开关关闭(enable_sop_retrieval=false)，"
                f"本次分析无知识库证据: alert={alarm.alert_name}"
            )
            return [], RetrievalStatus.FAILED

        try:
            with retrieval_breaker.guard():
                docs = self._get_retriever().retrieve_documents(query, top_k=self._top_k)
        except Exception as exc:
            # 检索服务不可用：不抛，但**必须**如实标成 FAILED。
            # 这里升级为 error 级别 —— 它代表依赖故障，不是业务上的「没找到」。
            code = error_code_of(exc)
            count_retrieval_failure(code)
            logger.error(f"SOP 检索失败[{code}]，本次分析无知识库证据: {exc}")
            return [], RetrievalStatus.FAILED

        evidence = [self._doc_to_evidence(doc) for doc in docs or []]

        if not evidence:
            # 检索服务正常，只是知识库里确实没有相关内容。
            # 这是一个**真实的业务结论**，可以放心告诉模型。
            logger.info("SOP 检索完成，知识库中无相关内容")
            return [], RetrievalStatus.EMPTY

        return evidence, RetrievalStatus.OK
```

**开关关闭为什么算 FAILED 而不是 EMPTY。** 这个判断值得停一下。

`EMPTY` 的含义是"知识库里确实没有"—— 那是一个**业务结论**。
开关关着的时候我们根本没去查，说"库里没有"就是
§1.2 那条撒谎链路的翻版，只不过这次撒谎的起因是我们自己关了开关。

`FAILED` 的措辞（"检索本身没成功，这不代表知识库里没有"）
对开关关闭同样成立，所以复用它是准确的。

**为什么不新增一个 `DISABLED` 状态。** 下游对它的处置和 `FAILED`
一模一样：标降级 + 在报告里声明证据链断了。多一个状态会让
每个消费者都多写一条分支，却没有任何行为差异 —— 这是 YAGNI。
真正需要区分"是坏了还是被关了"的场合是排障，而那看日志里
`enable_sop_retrieval=false` 这行字就够了。

```python
            )
        else:
            # 检索服务正常、知识库确实没有相关内容 —— 这是真实结论，可以照实说。
            sop_block = "（未检索到相关 SOP，请基于告警本身分析，并把不确定项放进 pending_confirmations）"
```

注意这段 prompt 不只是"说了实话"，它还**显式禁止**了那个错误推论。
因为模型有很强的倾向去填补空白：只说"检索失败了"，
它仍可能自己推出"所以可能没有 SOP"。所以要把禁令写明。

### 3.7 报告正文里也要有

`app/services/first_response_service.py:319-348`：

```python
    @staticmethod
    def _apply_retrieval_status(
        report: FirstResponseReport,
        sop_status: RetrievalStatus,
    ) -> None:
        """把 SOP 检索状态如实落到报告上（就地修改）。

        只有 FAILED 需要处理：OK 和 EMPTY 都是检索服务正常工作的结果，
        报告本身就是可信的，不该标降级。

        为什么要写进 risk_notes 而不只是设个字段：
        `is_degraded` / `degrade_reason` 是给程序看的（指标聚合、告警），
        risk_notes 是给值班同学看的。人不会去读数据库字段，
        他只会读报告正文 —— 所以「本次没有知识库证据」必须出现在正文里，
        否则他仍然会把一份缺证据的分析当成完整分析来用。
        """
        if sop_status is not RetrievalStatus.FAILED:
            return

        report.is_degraded = True
        # 已有更靠前的降级原因（如 LLM 挂了）时不覆盖：
        # 那个原因是报告不可用的**主因**，检索失败作为附加说明进 risk_notes。
        if report.degrade_reason is None:
            report.degrade_reason = DegradeReason.RETRIEVAL_FAILED

        note = (
            "⚠️ 知识库检索服务本次不可用，这份分析**未使用任何 SOP 证据**。"
            "请勿据此判断「该告警没有 SOP」——需要先确认检索服务（向量库）是否正常。"
        )
        report.risk_notes = f"{note}\n\n{report.risk_notes}".strip() if report.risk_notes else note
```

**降级信息要同时给两类读者。** 这是很容易漏的一点：

- `is_degraded` / `degrade_reason` → 给程序（指标、告警规则、数据库查询）
- `risk_notes` → 给人（值班同学只读报告正文，不会去 select 数据库字段）

只设字段不写正文，那个熬夜的人仍然会把缺证据的分析当完整分析用。

`if report.degrade_reason is None` 这个判断保证不覆盖更靠前的主因：
LLM 挂了是"报告不可用"，检索挂了是"证据不全"，前者更严重。

## 4. 背后的工程原理

### 4.1 舱壁隔离（Bulkhead）

船体分成若干水密舱，一个舱破了不会沉船。软件里对应的是
**把并行的工作单元隔离开，一个失败不拖垮其他**。

改造前 4 个子查询是"共享一个舱"：任一失败全体归零。
改造后每个分支自己是一个舱 —— 失败被封在 `retrieve_failures`
的一条记录里，不外溢。

判断标准很简单：**问"这些工作单元之间有依赖吗"**。
4 个子查询彼此独立，没有任何一个的结果是另一个的输入，
所以它们没有理由共享失败。

反例：如果是"先查用户 → 再用用户 ID 查订单"，
第一步失败第二步必然没意义，那就不该隔离，该直接失败。

### 4.2 部分成功是一种一等状态

很多系统只有二元结果：成功 / 失败。这在分布式场景下不够用。

一次请求扇出到 N 个下游，可能的结果是 N+1 种：
全成功、失败 1 个、失败 2 个、…、全失败。
把中间那些统统归到"失败"是巨大的信息浪费 ——
失败 1 个和失败 N 个的用户体验完全不同。

工业界的对应实践：

- HTTP **207 Multi-Status**：WebDAV 定义的"批量操作，部分成功"
- GraphQL 的响应结构：`data` 和 `errors` **可以同时非空**
- Elasticsearch 搜索响应里的 `_shards: {total, successful, failed}`
- gRPC 的 partial failure 模式（批量接口返回每项的独立状态）

我们的 `PARTIAL_RETRIEVAL` 就是这个思路：结果可用，
但要如实标注"基于不完整证据"。

**关键是标注必须传到最终消费者。** ES 把 `_shards.failed`
放在响应里，我们把 `partial_note` 放进 prompt、
把 `PARTIAL_RETRIEVAL` 放进 span。信息不能停在中间层。

### 4.3 让类型表达全部可能状态

`retrieve_sop_evidence` 改造前的返回类型是 `list[Evidence]`。
这个类型能表达的状态只有"有几条证据"，而实际的业务状态有三种。

**类型的表达力不足，信息就会在这一层丢失** —— 而且是静默丢失，
编译器和类型检查器都不会报警，因为 `return []` 完全合法。

改成 `tuple[list[Evidence], RetrievalStatus]` 之后，
调用方**没法不处理** status（它就在返回值里）。

这是类型驱动设计的基本手法。函数式语言里的同类工具：

```
Result<T, E>        Rust
Either<E, A>        Haskell / Scala
(T, error)          Go
```

它们共同的性质是：**失败不是一个"特殊的空值"，
而是返回类型的一部分**。Python 没有内建的 `Result`，
但一个 tuple 或一个小 dataclass 就能达到同样效果。

顺便说，这也是为什么"用 `None` 表示失败"是个坏习惯 ——
`None` 只有一种，而失败原因有很多种。

### 4.4 为什么"撒谎"比"报错"危害更大

这条值得单独立一节，因为它是这四批改造的思想内核。

一个系统可能给出三种响应：

| 类型 | 用户/运维的反应 | 修复时间 |
|---|---|---|
| **正确结果** | 继续工作 | — |
| **明确失败** | 去查为什么失败 | 短 |
| **看似正常的错误结果** | **按错误结果行动** | 极长，甚至永远发现不了 |

第三种最危险，因为它**消耗了排障者的信任**。
值班同学看到"建议补充 SOP"，他没有理由怀疑这句话 ——
系统一直是这么说话的。他会去写文档，写完发现告警还在，
再回头查，可能已经过了一个小时。

而如果系统直接说"检索服务不可用"，他第一分钟就去看 Milvus 了。

这个模式在这个项目里出现了三次，全部在这四批里修掉：

1. **SOP 撒谎**：检索挂了说成"库里没有"（本篇 §1.2）
2. **HTTP 200 撒谎**：业务失败但 HTTP 状态码是 200，
   错误率监控永远 0%（[18 篇](18-HTTP语义与全局异常处理.md)）
3. **熔断原因撒谎**：`circuit_open` 被重包成 `llm_error`，
   值班同学去查模型配额（[14 篇](14-错误分类与降级原因体系.md) §3.5）

三次都是同一个形状：**用一个假原因掩盖真原因**。
所以判断降级设计好不好，有一个很实用的问题：

> 这条降级路径产生的输出，会让人去做**正确的事**，
> 还是去做**看起来正确但完全无关的事**？

### 4.5 fan-in 节点是全局判定的唯一合法位置

这是并行编程里一条通用结构规律。

分支内部只有**局部视野**。它能回答"我怎么了"，
回答不了"我们整体怎么了"。任何需要全局视野的判定
（多数成功？全部失败？失败率超阈值？）
都必须放在汇聚点。

推论：**如果你发现要在分支里判断全局状态，说明结构错了。**
常见的错误做法是用一个共享计数器 + 锁，那既有竞态风险，
又把顺序依赖引进了本该无序的并行分支。

正确的做法就是我们这里的形状：分支只上报事实
（`retrieve_failures` 里的一条记录），汇聚点做判定。
这也让分支保持纯粹和可测 —— 单测一个分支不需要构造全局状态。

## 6. 常见坑

### 6.1 在分支里判断全局状态

```python
# ❌ 分支内部拿不到全局
async def retrieve_each_node(task):
    try:
        docs = await retrieve(task["query"])
    except Exception:
        if 所有分支都失败了:      # ← 这个条件在这里根本写不出来
            return {"degrade_reasons": ["retrieval_failed"]}
```

判定放 fan-in 节点（§4.5）。想在分支里用共享计数器 + 锁的话，
既有竞态风险，又给本该无序的并行分支引入了顺序依赖。

### 6.2 并行 state 的键忘了加 reducer

```python
# ❌ 4 个分支同时写，最后只剩一个
retrieve_failures: List[Dict[str, Any]]

# ✅ 用 operator.add 合并
retrieve_failures: Annotated[List[Dict[str, Any]], operator.add]
```

这个 bug 特别阴：单分支失败时完全正常（只有一个分支写），
多分支同时失败时才会丢数据 —— 而那正是最需要完整信息的时候。

### 6.3 `except Exception` 吞掉了取消信号

```python
# ❌ 如果 CancelledError 继承 Exception，超时机制就废了
except BaseException as exc:      # ← 千万不要
    return {"retrieve_failures": [...]}
```

Python 3.8+ 里 `asyncio.CancelledError` 继承 `BaseException`，
所以 `except Exception` 天然不会碰它。但如果手滑写成
`except BaseException`，总预算超时（靠取消协程实现）就会被
当成"一次检索失败"吞掉，`asyncio.timeout` 再也中断不了任何东西。

同理，`KeyboardInterrupt` 和 `SystemExit` 也在 `BaseException` 下。

### 6.4 标了降级但没告诉模型

```python
# ❌ state 里标了 partial_retrieval，prompt 里一个字没提
result["degrade_reasons"] = ["partial_retrieval"]
user_prompt = f"根据以下资料回答：{context}"
```

模型不读 state。它看到 8 条证据就当这是全部事实，
用"根据资料，原因是 X"的确定语气回答 ——
而真正的原因可能就在那条失败的子查询里。

必须在 prompt 里显式说明（§3.4 的 `partial_note`）。

### 6.5 标了降级但没告诉人

反过来也是坑：只设 `is_degraded=True` 而不写 `risk_notes`。

程序知道了，人不知道。值班同学不会去 select 数据库字段，
他只读报告正文。降级信息**必须同时给两类读者**（§3.7）。

### 6.6 用 `None` 或 `[]` 表示失败

```python
# ❌ 调用方无法区分「失败」和「成功但为空」
def retrieve() -> list[Evidence]:
    try:
        ...
    except Exception:
        return []
```

这就是 §1.2 那条撒谎链路的根因。**返回类型必须能表达失败。**
tuple、dataclass、枚举状态都可以，重点是让调用方没法不处理它。

### 6.7 为"被关闭"新造一个状态

```python
# ❌ 下游要多写一条分支，行为却和 FAILED 完全一样
class RetrievalStatus(StrEnum):
    OK = "ok"
    EMPTY = "empty"
    FAILED = "failed"
    DISABLED = "disabled"      # ← YAGNI
```

判断标准：**新状态会带来不同的行为吗？** 如果每个消费者
对它的处理都和某个已有状态一致，那它不该存在。
区分"坏了"和"被关了"是排障需求，日志能满足（§3.5）。

## 7. 一句话总结

> 并行分支的失败要**隔离**（不外溢）、**上报**（进 state）、
> **汇总判定**（在 fan-in 节点）、**如实传达**（给模型也给人）。
>
> 而"检索失败"和"检索到 0 条"必须在类型层面就分开 ——
> 一旦压成同一个 `[]`，后面所有的努力都救不回那个信息。
