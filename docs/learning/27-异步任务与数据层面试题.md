## 第一部分 · 队列与任务边界

### Q1. 文档索引为什么要走异步队列？同步做完再返回不行吗？

**考点**

面试官想听的不是「异步快」—— 异步不快，总耗时一分钱都没省。他想确认你知道**同步会在哪一层先崩**。

**标准回答**

同步做不了，卡在三个地方，而且是递进的：

第一层是**连接超时**。索引一个文档要走清洗 → 切分 → 向量化 → 写 Milvus，embedding 是网络调用且按 chunk 数量线性放大。一个几百 KB 的文档切出两三百个 chunk，整条链路轻松过分钟。Nginx 默认 `proxy_read_timeout` 60 秒，前端 fetch 也有超时。同步的结果是**用户侧超时断开，而服务端还在跑** —— 这是最糟的形态，因为客户端认为失败了，服务端认为在成功，两边的认知从此分叉。

第二层是**worker 被长任务占死**。API 进程的 worker 数是有限的（uvicorn 默认几个），一个索引任务占住一个 worker 一分钟，同时上传五个文档就把整个 API 打满 —— 此时聊天接口一起挂掉。**上传功能的故障蔓延成了全站故障**，因为它们共享同一个进程池。

第三层，也是最关键的：**同步路径没有地方记录失败**。同步意味着「失败就把错误返回给用户」，然后请求结束、上下文销毁。用户看到一句 500，然后呢？没有一行记录说明这个文档是什么状态、失败在哪一步、要不要重试。异步强迫你先在库里落一条 `index_jobs` 行，任务的整个生命周期都挂在这条行上 —— **可观测性不是异步的副产品，是异步逼出来的**。

所以异步的收益是「把一个长操作变成一个可查询的实体」，而不是「变快」。

**真实代码**

上传接口做完三件轻活就返回 `202`：落库、建 job、入队。

```python
# app/api/file.py:136-152
job = repo.create_index_job(document.id)

try:
    rq_job = enqueue_index_job(job.id)
    repo.bind_rq_job(job.id, rq_job.id)
except Exception as e:
    logger.exception(f"索引任务入队失败: document_id={document.id}, job_id={job.id}")
    raise HTTPException(
        status_code=503,
        detail=f"文件已保存，但索引任务入队失败，请检查 Redis/RQ: {e}",
    ) from e

return JSONResponse(status_code=202, ...)
```

注意 `503` 那段 detail 的措辞：**「文件已保存，但索引任务入队失败」**。这是刻意的 —— 这个失败点上系统处于一个部分成功的状态，文件在磁盘上、`knowledge_documents` 有行、`index_jobs` 有行，唯独 Redis 里没有任务。如果只回一句「上传失败」，用户会重新上传，而重新上传会命中同名分支去 `update_document_for_reupload`，版本号又 +1。**错误信息说不清系统处于哪个中间态，用户的重试动作就会制造新的中间态。**

状态机本身就是为这个中间态准备的：`DocumentStatus` 有 `PENDING` 这一档（`app/models/knowledge_base.py:18-23`），文档落库后先是 PENDING，worker 接手才转 INDEXING。入队失败的文档停在 PENDING，是一个**可被重建索引接口捞回来**的状态，不是死数据。

**追问链**

> **追问 1：入队失败为什么不把刚才落的库回滚掉，让它彻底干净？**

因为文件已经写到磁盘上了，而磁盘写不在事务里。回滚数据库只能做到「库里干净、磁盘上多一个孤儿文件」—— 这不是干净，是把不一致从「库里有行但没任务」换成「磁盘有文件但库里查不到」。后者更糟：前者能被重建索引接口发现并修复，后者只有磁盘容量告警会发现。

选择保留记录，是因为**留下一条状态为 PENDING 的可见记录，比留下一个不可见的孤儿文件更容易收敛**。

> **追问 2：那 202 之后用户怎么知道索引好了？**

轮询 `index_jobs` 状态。这确实是当前的实现，也确实粗糙 —— 拓展里讲更好的做法。

> **追问 3：如果 embedding 特别快，比如本地模型只要两秒，还需要异步吗？**

需要，但理由变了。两秒的同步是可以接受的用户体验，第一层和第二层理由都不成立了。但第三层还在：**没有任务实体，就没有失败留痕**。而且「现在快」不是稳定属性 —— 换一个大文档、换一个远程 embedding 服务、Milvus 一次选主，两秒立刻变二十秒。异步的边界一旦画在同步上，后面再改要动接口契约（202 → 200，前端要跟着改）。

**拓展**

- **回调 / WebSocket 推进度**：现在是前端轮询。RQ 支持 `on_success` / `on_failure` 回调，可以在任务结束时往一个 Redis pub/sub channel 发消息，API 侧用 SSE 推给前端。改造量不大，但要处理「用户中途关页面」的清理。
- **分片索引**：一个超大文档现在是一个任务。可以按 chunk 批次拆成 N 个子任务并行，用 RQ 的 `Group`（rq 2.x）或者自己维护一个计数器收敛。收益是长尾文档的索引时间从线性降到接近常数，代价是失败语义变复杂（3/10 个分片失败算什么状态）。
- **优先级队列**：现在重建索引和新上传抢同一个队列。人工触发的重建应该比批量导入优先。RQ 支持多队列按顺序消费（`rq worker high default low`），改动只是入队时选队列。

### Q2. 项目里有两个队列（`index_queue` 和 `protocol_pdf_queue`），划分依据是什么？为什么不共用一个？

**考点**

队列划分的依据。答「按业务分」是没答 —— 按业务分是结果，不是理由。面试官想听**共用会出什么具体问题**。

**标准回答**

划分依据是**任务的时长量级和失败特征不同，混在一个队列里会互相饿死或互相误判**。

具体到这两条链路：

| | 知识库索引 | 协议 PDF 入库 |
|---|---|---|
| 单任务耗时 | 秒到分钟（按 chunk 数） | 十秒到十分钟（PDF 解析 + 结构化） |
| `job_timeout` | 30 分钟 | 600 秒 |
| 触发频率 | 高，用户随手上传 | 低，运维人员偶尔导入 |
| 典型失败 | Milvus 抖动、embedding 限流（**多为可重试**） | PDF 损坏、字段抽取不出（**多为不可重试**） |
| 后续动作 | 全自动 | **要人工确认才写入协议库** |

混一个队列的具体后果有两个。

一是**队头阻塞**。worker 是按队列顺序取任务的。一个十分钟的 PDF 任务卡在前面，后面五个用户的文档索引全在排队 —— 而那五个本来每个只要十秒。用户体验上表现为「上传有时候很快有时候要等十分钟」，随机得让人无法信任。

二是**worker 配置无法分化**。这两类任务的资源画像不一样：索引任务是 embedding 密集（网络等待多，可以高并发），PDF 解析是 CPU 密集（PyMuPDF 解析、正则抽取，并发高了只会互相抢 CPU）。分成两个队列后可以给索引队列开 8 个 worker、给 PDF 队列开 2 个。共用一个队列的话，这两个数只能取一个值，而任何一个值对另一类任务都是错的。

**真实代码**

队列定义本身很短，价值在它划分出的边界：

```python
# app/core/task_queue.py:9-11
redis_conn = Redis.from_url(config.redis_url)
index_queue = Queue(config.rq_queue_name, connection=redis_conn)
protocol_pdf_queue = Queue("protocol_pdf_ingest", connection=redis_conn)
```

一个 Redis 连接、两个队列 —— 队列在 RQ 里只是 Redis 里的一个 list，不需要独立连接。

入队参数的差异体现了上面那张表：

```python
# app/services/index_job_queue.py:24-27
    job_timeout="30m",
    failure_ttl=7 * 24 * 60 * 60,
    result_ttl=7 * 24 * 60 * 60,

# app/services/protocol_pdf_job_queue.py:22-24
    job_timeout=600,
    result_ttl=86400,
    failure_ttl=86400,
```

**追问链**

> **追问 1：`index_queue` 用了 `config.rq_queue_name`（可配置），`protocol_pdf_queue` 直接写死字符串。为什么不一致？**

这是真实的不一致，我不打算美化它。索引队列名可配是因为它先做、当时想留一个多环境隔离的钩子（同一个 Redis 跑 dev 和 test，用队列名前缀隔开）。协议 PDF 后做，直接写死了。

要收敛的话正确做法是**两个都拼前缀**：`f"{config.rq_queue_prefix}:index"` / `f"{config.rq_queue_prefix}:protocol_pdf"`。只让一个可配的钩子等于没有钩子 —— 隔离要么全隔要么不隔，隔一半的时候，dev 的 worker 会去消费 test 的 PDF 任务。这个坑没踩到只是因为目前只有一套环境。

> **追问 2：那要不要按队列再分 Redis 实例？**

不用。RQ 的队列就是 Redis list，`LPUSH`/`BRPOP` 的开销和 list 数量无关。分实例要解决的是「一个业务把 Redis 内存打满影响另一个」，而 job 记录很小（一个 job_id 字符串加 meta），`result_ttl` 也压着不让它无限堆。真正需要分实例的信号是内存告警或 `INFO` 里的 `instantaneous_ops_per_sec` 打满，现在离得很远（YAGNI）。

> **追问 3：怎么知道该拆队列了？有量化信号吗？**

有两个：

1. **队列等待时间的分位数**。同一个队列里 P50 和 P99 差一个数量级，说明任务时长分布是双峰的 —— 那就该拆。RQ 的 job 有 `enqueued_at` 和 `started_at`，差值就是等待时间。
2. **worker 利用率与队列深度同时高**。队列在积压但 worker CPU 不满，说明 worker 在等 IO（比如 embedding），该加并发；两者都满说明该加机器。这两个动作对不同任务类型的最优值不同，一旦两类任务的最优动作相反，就是拆队列的时候。

**拓展**

- **死信队列**：现在重试三次耗尽后任务进 RQ 的 `FailedJobRegistry`，靠 `failure_ttl` 自然过期。更规范的做法是失败任务转投一个 `dead_letter` 队列，配一个人工重放接口 —— 尤其对协议 PDF 这种「一个文件对应一批协议数据」的任务，丢了要重新找文件。
- **速率限制**：embedding 服务有 QPS 上限。现在靠 worker 数量间接限流，很脆（改并发就改了限流）。正确做法是入队侧或 worker 侧加令牌桶，把限流从「部署参数」变成「代码里的显式约束」。
- **队列级熔断**：25 篇的熔断器保护的是单次调用。Milvus 整体挂掉时更好的动作是**暂停整个索引队列的消费**，而不是让每个任务各自熔断然后失败 —— 后者会把重试额度白烧掉。

### Q3. `job_timeout`、`result_ttl`、`failure_ttl` 这三个参数分别管什么？你项目里的取值是怎么定的？

**考点**

这三个参数经常被无脑抄默认值。面试官想看你是不是知道它们各自的失效后果 —— 而且这三个后果完全不同：一个是任务被杀，一个是查不到结果，一个是排障没依据。

**标准回答**

**`job_timeout`** 是单个任务的执行上限，超时 worker 会杀掉它并记为失败。定值的原则是**取正常最坏情况的数倍，而不是平均值的数倍**。索引任务给 30 分钟，是因为最坏情况是一个大文档切出上千个 chunk，每个 chunk 一次 embedding 网络调用，还要考虑 embedding 服务限流后的等待。按平均值（十几秒）的三倍去设，结果是大文档永远索引不完 —— **而且失败原因会显示成超时，掩盖了「它其实在正常工作只是慢」这个事实**。

这个参数设小的代价是不对称的：设大了只是让一个卡死的任务多占 worker 一会儿；设小了会让**本来能成功的任务被系统性地杀掉**，而且是按文档大小选择性地杀，形成「小文件能传大文件传不了」这种极难归因的现象。

**`result_ttl`** 是成功任务的记录在 Redis 里保留多久。项目里索引给 7 天、PDF 给 1 天。这个值决定了「任务跑完后还能不能查到它」。给 7 天是因为用户可能周五上传、周一才发现结果不对来问，而 `rq_job_id` 是我们查 RQ 侧信息的唯一凭据（存在 `index_jobs.rq_job_id` 列里）。

**`failure_ttl`** 是失败任务的记录保留多久，也是排障窗口。这个值和 `result_ttl` **本质上不该相等** —— 成功的任务过期了无所谓，失败的任务过期意味着 `job.exc_info` 里的 traceback 没了，只剩数据库里那句 `error_message`。我把索引链路的两个都给了 7 天，是取了「排障窗口要覆盖一个周末」这个下限。

**真实代码**

```python
# app/services/index_job_queue.py:20-28
return enqueue_with_request_id(
    index_queue,
    run_index_job,
    job_id,
    job_timeout="30m",
    failure_ttl=7 * 24 * 60 * 60,
    result_ttl=7 * 24 * 60 * 60,
    retry=default_job_retry(),
)
```

`7 * 24 * 60 * 60` 写成算式而不是 `604800`：后者要按计算器才知道是几天。这类常量的可读性直接影响它会不会被改错。

**追问链**

> **追问 1：协议 PDF 的 `failure_ttl` 只给了 1 天，而它的失败恰恰更需要人工介入。这不矛盾吗？**

矛盾，这是个应该改的取值。

理由链条是这样的：协议 PDF 的失败大多不可重试（PDF 损坏、字段抽不出），意味着**必须有人来看**。而它的触发频率又很低（运维偶尔导入），意味着**可能没人当天就看**。两个特征叠起来，它的排障窗口应该比索引链路**更长**，而不是更短。

现在给 1 天是因为写的时候只想着「PDF 任务少，不占 Redis」—— 用错了决策依据。占用量小是「可以给长」的理由，不是「应该给短」的理由。正确取值应该至少和索引链路对齐到 7 天。

不过要说清楚：这个错的**实际影响有限**，因为失败原因已经通过 `format_failure_message` 落进了 `protocol_pdf_ingestions.error_message`（带 `error_code`）。丢掉的是 RQ 侧的完整 traceback。所以它是「排障时少一层细节」，不是「查不到失败了」。

> **追问 2：`job_timeout` 到了会发生什么？任务函数的 `except` 块会执行吗？**

**不会**，这是个要紧的细节。RQ 默认的 `DeathPenalty` 是靠 `SIGALRM` 实现的，超时会在任务线程里抛 `JobTimeoutException`。这个异常是 `BaseException` 的子类但不是 `Exception` 的子类吗？—— 实际上 RQ 的 `JobTimeoutException` 继承自 `BaseException`，所以 `except Exception` **接不住它**。

后果很实际：超时的任务不会走我们那套「裁决重试 → 落盘失败状态 → raise」的流程。`index_jobs` 行停在 RUNNING，`knowledge_documents` 停在 INDEXING。这和 Q29 里说的 SIGKILL 缺口是同一类问题 —— **有一整类失败模式绕过了我们的 except 块**，而我们的失败留痕机制完全建立在 except 块之上。

要补的话有两条路：一是 `except BaseException` 分开处理超时（要小心别把 `KeyboardInterrupt` 也吞了）；二是走进程外对账（Q29 的 P0）。第二条更根本，因为它同时覆盖了 SIGKILL 和 OOM。

> **追问 3：`job_timeout="30m"` 传字符串，RQ 怎么解析的？**

RQ 支持 `"30m"` / `"2h"` / `"1d"` 这类后缀写法，内部转成秒。传字符串比传 `1800` 可读，代价是拼错后缀（比如写成 `"30min"`）会在入队时抛异常 —— 好在这个异常是立即的、显式的，不是静默降级。项目里 PDF 那条传的是裸数字 `600`，又是一处该统一的不一致。

**拓展**

- **按文档大小动态设 `job_timeout`**：现在是一刀切 30 分钟。可以按 `file_size` 或预估 chunk 数算一个上限（比如 `max(300, chunk_count * 2)`），既不让小文档卡死 30 分钟才被发现，也不让大文档被误杀。
- **超时前预警**：`job_timeout` 到了才知道太晚。可以在任务里按批次上报进度（`job.meta["progress"]`），配一条「进度 30 分钟没动」的告警，比超时告警提前得多。
- **`result_ttl=-1` 的诱惑要抵抗**：设成永久保留看着方便，实际上是让 Redis 内存无上限增长，最后死在一次 OOM 上。要长期留就落库，别留在 Redis。

## 第二部分 · 重试：一个决策劈成两半

### Q4. 讲讲你项目里的重试机制。为什么 `retry` 参数必须在入队时声明？

**考点**

这题是本篇的核心。表面在问 RQ 用法，实际在问**一个逻辑决策被物理边界切开时怎么设计**。答得出「入队声明额度、worker 裁决使用」这个二分，才算真的理解。

**标准回答**

重试这件事在我项目里被**物理地劈成了两半**，中间隔着一次 Redis 序列化：

- **入队侧声明额度**：`retry=default_job_retry()`，也就是「最多 3 次，间隔 10/30/60 秒」。
- **worker 侧裁决使用**：`apply_retry_policy(exc, job_id=...)`，按异常类型决定这次失败要不要真的花掉额度。

为什么必须劈开：因为 RQ 把重试额度**存进 job 记录**（Redis 里那条 hash 的 `retries_left` 字段）。worker 执行时只能**减少**它，不能凭空补上。也就是说，一个入队时没带 `retry=` 的任务，**一次失败就是终局** —— 哪怕失败原因只是 Milvus 正在选主这种几秒钟就自愈的抖动。

这个约束的方向性很重要：额度是**入队时的一次性决定**，worker 是**多次消费**这个决定。所以「要不要给重试机会」这个问题必须在入队那一刻答完，那时候我们还完全不知道会失败在哪 —— 只能给一个宽松的额度。

而「这次失败值不值得花额度」只有 worker 知道，因为只有它手里有异常对象。所以额度给得宽，裁决卡得严。

**真实代码**

入队侧（注释里就写着这个约束）：

```python
# app/services/index_job_queue.py:11-28
```

额度定义：

```python
# app/core/job_failure.py:56-74
# 默认重试策略：最多 3 次，间隔递增。
#
# 为什么间隔要递增而不是固定：瞬时故障（Milvus 选主、网络抖动、LLM 限流）
# 的恢复时间是不确定的。固定 10 秒重试三次，总共只覆盖 30 秒窗口；
# 递增到 60 秒能覆盖到分钟级抖动，而代价只是失败任务晚一点定性。
#
# 为什么是 3 次而不是更多：超过 3 次基本说明不是抖动而是真故障，
# 继续重试只是在推迟暴露问题，同时占着 worker 不干别的活。
_DEFAULT_RETRY_MAX = 3
_DEFAULT_RETRY_INTERVALS = [10, 30, 60]


def default_job_retry() -> Retry:
    """入队侧用的默认重试策略。

    定义成函数而不是模块级常量：`Retry` 实例携带可变状态，
    两个队列共享同一个对象是自找麻烦。
    """
    return Retry(max=_DEFAULT_RETRY_MAX, interval=_DEFAULT_RETRY_INTERVALS)
```

**追问链**

> **追问 1：为什么 `default_job_retry()` 是函数不是模块级常量？这不是多一次对象创建吗？**

因为 `Retry` 实例**携带可变状态**。两个队列共享同一个 `Retry` 对象，一旦 RQ 内部对它做任何原地修改，两条链路的重试行为就纠缠在一起了 —— 而这种纠缠只在并发时暴露，单测跑不出来。

多创建一个小对象的开销可以忽略（入队本身要走一次 Redis 往返），而共享可变状态的调试成本是不可忽略的。这是典型的「用确定的微小代价换掉不确定的大代价」。

这里有个可以泛化的判断准则：**模块级常量只适合不可变值**。看到 `SOME_CONFIG = SomeClass(...)` 就要问一句这个实例可不可变，不可变才能当常量。

> **追问 2：间隔为什么是 10/30/60 而不是标准的指数退避 1/2/4/8？**

因为要覆盖的窗口不一样。指数退避从 1 秒起是为了**高频短抖动**（比如 HTTP 请求遇到瞬时 5xx），第一次重试要快，因为大部分抖动是毫秒级的。

我这里的失败对象是 Milvus 选主、embedding 服务限流、数据库连接池瞬时耗尽 —— 这些的恢复时间是**秒到分钟级**。1 秒后重试几乎必然还是失败，白烧一次额度。所以起点定在 10 秒。

递增到 60 是为了让三次重试的**总覆盖窗口**够宽：10+30+60 = 100 秒，加上任务本身的执行时间，能覆盖到接近两分钟的抖动。固定 10 秒三次只能覆盖 30 秒 —— 一次稍长的 Milvus 选主就穿过去了。

> **追问 3：递增间隔有什么代价？**

有，而且要说清楚：**失败任务的定性被推迟了**。一个必然失败的任务（假如裁决没拦住它）要等 100 秒才最终转 FAILED。这段时间里页面上显示的是 RUNNING 或 QUEUED，用户在等一个不会来的结果。

所以递增间隔和「不可重试的立即否决」是**配套的**，缺一个另一个就变成负担 —— 如果不区分可重试性，递增间隔只是把所有失败都拖长；如果不递增，裁决对了但覆盖窗口不够。这两个设计是一对。

> **追问 4：三次重试都在同一个 worker 上吗？**

不是。RQ 的重试是把任务重新放回队列（走 `ScheduledJobRegistry` 延迟入队），下一次由**任意空闲 worker** 取走。这一点是好事：如果失败原因是这台 worker 的本地问题（磁盘满、本地缓存坏），换一台就好了。

但它带来一个约束：**任务函数必须是可重入的**。我这里靠两件事保证：一是任务参数只有 `job_id`（所有状态都在库里，不在参数里），二是索引流程里先 `vector_store_manager.delete_by_document_id(document.id)` 再写入（`app/workers/index_worker.py:58`）—— 重跑一次不会留下上一次的残留向量。

**拓展**

- **按错误类型给不同额度**：现在所有任务共用 3 次/10-30-60。`429`（限流）值得更多次、更长间隔；Milvus 连接失败值得 3 次；反序列化失败一次都不值。可以让 `default_job_retry()` 接一个 hint 参数。
- **抖动（jitter）**：现在间隔是确定值，意味着同一时刻失败的 N 个任务会在同一时刻一起重试 —— 对刚恢复的下游是一次冲击（惊群）。加一个 ±20% 的随机抖动能把这个尖峰摊平。
- **重试次数上报指标**：现在重试只有日志。应该有一个 `job_retries_total{queue, code}` Counter —— 「重试率突然上升」是下游劣化的**早期信号**，比失败率上升早一个身位（因为重试成功的那些不计入失败）。

### Q5. `apply_retry_policy` 是干什么的？RQ 自己不是有 `Retry(max=3)` 吗，为什么还要自己写一层？

**考点**

RQ 的 `Retry` 是**无条件**的 —— 这一点很多人不知道。面试官想确认你读过行为细节，而不是配了参数就以为万事大吉。

**标准回答**

因为 RQ 的 `Retry(max=N)` 只看「有没有抛异常」，**不看抛的是什么异常**。任务抛异常就重排，不区分「网络抖动」和「PDF 文件损坏」。

后者重试三次的结果是**三次一模一样的失败**：

- 白烧三倍资源（三次完整的 PDF 解析尝试）
- 把最终失败推迟了一百多秒（10+30+60）
- 用户盯着「索引中」多等一轮，然后得到一个从第一次起就已经确定的失败结果

所以 `apply_retry_policy` 做一件事：**按异常类型裁决，不可重试的直接把 `retries_left` 清零**。RQ 在 `handle_job_failure` 里看到 `should_retry` 为 False，就走正常的失败落盘路径，不再重排。

关键是「是否可重试」的判定**不在这里实现** —— 它复用 25 篇的 `app/core/errors.py:is_retryable`。这个函数是分类逻辑的唯一实现点，HTTP 边界、worker、熔断器都读它。在这里重写一遍分类等于给自己埋一个「两处判定慢慢分叉」的雷。

**真实代码**

```python
# app/core/job_failure.py:77-128
def apply_retry_policy(exc: BaseException, *, job_id: str) -> bool:
    """裁决这次失败是否值得让 RQ 重排队，并在不值得时就地否决。

    返回 True 表示 RQ 还会重试，False 表示这次失败是终局。
    ...
    """
    retryable = is_retryable(exc)

    job = None
    with suppress(Exception):  # pragma: no cover - RQ 上下文缺失不该影响任务本身
        job = get_current_job()

    if job is None:
        return retryable

    retries_left = getattr(job, "retries_left", None) or 0

    if not retryable and retries_left > 0:
        # 清零而不是设成 None：`should_retry` 判的是 `is not None and > 0`，
        # 两种写法都能生效，但 0 更能表达「额度用完了」而非「没配过重试」。
        job.retries_left = 0
        logger.warning(
            f"任务失败且不可重试，已取消剩余 {retries_left} 次重试: "
            f"job_id={job_id}, error_code={error_code_of(exc)}"
        )
        return False

    return retryable and retries_left > 0
```

**追问链**

> **追问 1：改一个内存属性就能影响 RQ 的重试决策？这靠得住吗？**

靠得住，而且我照 rq 2.9 源码逐环确认过。docstring 里写着完整的三环链条：

```python
# app/core/job_failure.py:92-102
## 为什么改内存属性是可靠的（照 rq 2.9 源码确认过）

- `Job.perform()` 里 `_job_stack.push(self)`，所以 `get_current_job()`
  拿到的就是 worker 正在执行的**同一个 Job 对象**，不是副本。
- `Worker.perform_job()` 的 except 分支把这个对象直接传给
  `handle_job_failure(job=job, ...)`。
- `handle_job_failure` 里 `retry = job.should_retry and not job_is_stopped`，
  而 `should_retry` 读的是内存属性 `retries_left`，中间没有
  `job.refresh()`，不会从 Redis 重新取值。
```

三个环缺一个这招就不成立：如果 `get_current_job()` 返回副本，改的不是同一个对象；如果 `perform_job` 重新从 Redis 取 job，改动被覆盖；如果 `should_retry` 前面有一次 `job.refresh()`，同样被覆盖。

这里要坦白一个风险：**这是依赖库内部实现的行为，不是公开 API 契约**。rq 升级到 3.x 时这三环任何一环变了，我的裁决就静默失效 —— 而且失效方式是「不可重试的任务开始重试三次」，不报错，只是变慢和浪费。

所以这个依赖必须被测试锁住。`tests/unit/test_job_failure.py:49` 的 `test_non_retryable_error_cancels_remaining_retries` 就是这道锁：**升级 rq 后这个测试红，我立刻知道；没有这个测试，我半年后才从「怎么老是重试三次」里发现。**

> **追问 2：`getattr(job, "retries_left", None) or 0` 为什么这么写？**

两层防御。`getattr(..., None)` 防的是属性不存在（不同 rq 版本可能改字段名），`or 0` 防的是值为 `None`（入队时没配 `retry=` 的任务，`retries_left` 就是 `None`）。

`or 0` 在这里是安全的，因为 `retries_left` 的语义里 `0` 和 `None` 应当同样处理 ——「没有额度了」和「从来没有额度」在裁决上是一回事。要是这个字段的 `0` 有特殊含义（比如「无限重试」），就必须写 `if x is None`，不能用 `or`。

这个区别和 25 篇 `llm_factory.py` 里那个对比正好呼应：那里 `config.llm_timeout_seconds if timeout is None else timeout` **不能**用 `or`，因为 `timeout=0` 是一个有意义的显式值（不等待）。**同一个惯用法，在两处的正确性完全相反 —— 判据是「零值有没有独立语义」。**

> **追问 3：脱离 RQ 上下文时（比如单测直接调函数）会怎样？**

`get_current_job()` 抛异常，被 `suppress` 吞掉，`job` 是 `None`，函数直接返回 `is_retryable(exc)` —— **不做任何副作用**。

这是刻意的：函数在测试里是**纯的**。测试可以直接断言「这个异常应该返回 True/False」，不需要伪造 RQ 上下文。这和 26 篇 `render_metrics()` 返回 `(body, content_type)` 而不是 `Response` 是同一个模式 —— **把判定逻辑做成不依赖运行时环境的纯函数，副作用只在拿得到环境时才发生**。

`tests/unit/test_job_failure.py:67` 的 `test_without_rq_context_is_pure` 锁的就是这条。

**拓展**

- **裁决结果进指标**：现在只有 `logger.warning`。应该有 `job_retry_cancelled_total{code}` —— 「哪类错误最常被否决重试」直接指向该修的地方。
- **可重试性的动态覆盖**：现在 `is_retryable` 是静态分类。某些场景下同一个异常的可重试性取决于上下文（第一次 `ConnectionError` 值得重试，同一个文档连续三次就该停）。可以引入「同一 document_id 的近期失败计数」，但要小心别把简单逻辑复杂化。
- **重试前的健康检查**：不可重试立即否决之外，可重试的也可以在重排前探一下下游（Milvus ping）。下游还没恢复就直接延长间隔，而不是白跑一次完整任务。

### Q6. 一个失败在你系统里可能经过几层重试？会不会叠乘成雪崩？

**考点**

25 篇讨论过这题的一半（LLM 侧）。这里要答**加上 RQ 之后的完整图景**。面试官想看你有没有全局的「最坏情况耗时」意识。

**标准回答**

索引链路上有三层可能的重试，要分清哪些会叠乘、哪些不会：

**第一层：OpenAI SDK 内部重试。** embedding 调用走 SDK，SDK 有 `max_retries` 默认 2。这层在**单次 embedding 调用内部**。

**第二层：无。** 这是关键 —— 索引 worker 里**没有**应用层的循环重试。切分、embedding、写 Milvus 都是一遍过，失败就抛出来。

**第三层：RQ 任务级重试，3 次。** 整个任务从头再跑。

所以最坏情况是 `3 × (任务内所有 embedding 调用 × SDK 2 次)`。**看起来是叠乘的，但实际不是** —— 因为第一层的重试只在**瞬时失败**时发生，而能触发 RQ 重试的失败意味着 SDK 那两次已经全用完了。也就是说这两层是**串行接力**而不是笛卡尔积：SDK 兜不住的才升级到 RQ 层。

真正会叠乘的危险配置是「应用层 for 循环重试 + RQ 重试」—— 那才是 3×3=9 倍。我没有那一层，是因为**任务级重试已经覆盖了应用层重试的全部场景**，而且做得更好：它换 worker、有延迟间隔、有额度记录。在任务函数里再写一层 `for attempt in range(3)` 是纯粹的重复（DRY）。

至于雪崩：叠乘不是雪崩的主因，**并发放大**才是。三层重试最多让一个任务的耗时变成 3 倍，但 50 个任务同时失败同时重试，会在同一时刻给下游 50 倍的压力。压住这个的是 worker 数量（并发上限）和熔断器（下游挂了就快速失败不再压），不是重试层数。

**真实代码**

worker 主流程里没有任何重试循环，失败直接落到 `except`：

```python
# app/workers/index_worker.py:52-58
file_path = Path(document.file_path)
content = file_path.read_text(encoding="utf-8")
content = text_cleaner.clean(content)
docs = document_splitter_service.split_document(content, document.file_path)
docs = metadata_enricher.enrich_documents(docs, document.file_path)

vector_store_manager.delete_by_document_id(document.id)
```

一条直线，没有 try 包在里面 —— 任何一步失败都由外层统一处置。

**追问链**

> **追问 1：整个任务从头重跑，前面的工作不是白做了吗？大文档重跑三次很贵。**

是白做，而且确实贵。这是我为了**幂等性简单**付的代价。

任务从头跑的好处是不需要维护「跑到哪了」的检查点，而检查点的复杂度很高：要记录已完成的 chunk 区间、要保证检查点写入本身是原子的、要处理检查点和 Milvus 实际状态不一致（写了向量但检查点没落）。

现在的做法把这些全免掉了：`delete_by_document_id` 先清干净，再全量写。**幂等靠「重来一遍」而不是「记住上次」实现。**

代价可以量化：一个 1000 chunk 的文档在第 900 个 chunk 失败，重试要重跑 900 次已经成功的 embedding。所以这个选择的合理性取决于「文档有多大」和「失败率有多高」—— 当前文档规模下（多为几百 KB 的技术文档）成立，真要处理大文件就得上分片。

> **追问 2：那 embedding 的钱不是白花了？**

对，重跑的 embedding 要重新付费。缓解办法是**按 chunk 内容 hash 做 embedding 缓存**：`sha256(chunk_content) → vector`，存 Redis。重跑时 900 个已算过的 chunk 直接命中缓存。

值得说的是我已经在算这个 hash 了：

```python
# app/workers/index_worker.py:62
chunk_hash = hashlib.sha256(doc.page_content.encode("utf-8")).hexdigest()
```

它现在的用途是存进 `knowledge_chunks.content_hash` 做内容追溯，但**同一个 hash 直接就能当 embedding 缓存的 key**。也就是说这个优化的前置条件已经具备了，缺的只是缓存层本身。

> **追问 3：怎么验证三层没有叠乘？**

看 `job.exc_info` 里的时间戳和日志。三层串行接力的话，一次 RQ 尝试的耗时里包含 SDK 的两次重试等待；如果是笛卡尔积，会看到同一个 chunk 的 embedding 请求在日志里出现 6 次。

更严格的验证是在测试里注入一个计数 mock，断言「任务重试 3 次时，某个下游 mock 被调用的总次数」。目前没写这个测试 —— 值得补，因为「不小心在某个 service 里加了一层重试」是很容易发生的回归，而它的表现只是「偶尔特别慢」。

**拓展**

- **总预算而非层级计数**：更好的模型是给整个任务一个 deadline（比如「20 分钟内做完，否则不管重试几次都停」），而不是数层数。25 篇的 `chat_total_budget_seconds` 是对话侧的同类设计，任务侧还没有。
- **重试链路可视化**：`job.meta` 里记下每次尝试的 `(attempt, started_at, error_code)`，排障时一眼看到「三次都是同一个错」还是「三个不同的错」—— 后者说明系统在多点劣化，是更严重的信号。
- **失败归因到 chunk**：现在任务失败只知道哪个文档。记下「失败在第几个 chunk」既能支持断点续传，也能定位「是不是某个特定 chunk 的内容有问题」。

### Q7. `format_failure_message` 为什么要把「会不会重试」写进错误信息里？

**考点**

小函数，但体现的是「错误信息是给谁看的」这个意识。答得出「不写会导致值班同学排查一个自愈中的问题」就到位了。

**标准回答**

因为**状态列写着 FAILED，但后台其实还排着两次重试**。

不说清楚的后果很具体：值班同学看到页面上一个 FAILED 的文档，立刻开始排查 —— 看日志、连 Milvus、检查 embedding 服务。而这个任务可能十秒后自己就好了。**他排查的是一个正在自愈的问题**，花掉的时间全是浪费，而且期间可能做出干扰性操作（重启 worker，反而打断了重试）。

这是「中间态被显示成终态」的典型问题。RQ 侧的真实状态是「本次尝试失败，等待重排」，但我们数据库的枚举里没有这一档 —— `IndexJobStatus` 只有 QUEUED / RUNNING / SUCCEEDED / FAILED（`app/models/knowledge_base.py:26-30`）。缺一档「RETRYING」，只能用文案补。

同时带上 `error_code` 是为了**可聚合**。自由文本没法统计「同一类失败出现了多少次」，而 `error_code` 是有限枚举 —— 这一点和 26 篇讲的 label 基数是同一个道理：要被聚合的维度必须是有界的。

**真实代码**

```python
# app/core/job_failure.py:131-143
def format_failure_message(exc: BaseException, *, will_retry: bool) -> str:
    """拼装落库用的失败原因。

    带上 `error_code` 是为了可聚合 —— 自由文本没法做「同一类失败出现了多少次」
    的统计，而 `error_code` 是有限枚举。

    带上重试状态是为了**不误导看页面的人**：状态列写着 FAILED，但后台其实
    还排着两次重试。不说清楚的话，值班同学会立刻开始手工排查一个
    十秒后可能自己就好了的问题。
    """
    code = error_code_of(exc)
    suffix = "，RQ 将自动重试" if will_retry else ""
    return f"[{code}] {exc}{suffix}"
```

顺带解释了 Q9 里 worker 的 `except` 块为什么是「先裁决、再落盘」这个顺序：`will_retry` 必须先算出来才能拼这条 message。**那个顺序不是风格偏好，是数据依赖强制的** —— 想不通为什么裁决要排在落盘前面，看一眼这个函数的签名就明白了。

**追问链**

> **追问 1：为什么不干脆加一个 `RETRYING` 状态，而要靠拼文案？**

因为加状态会**破坏状态机的单调性**。现在 `IndexJobStatus` 是单向推进的：QUEUED → RUNNING → SUCCEEDED/FAILED，终态不再变。加 RETRYING 之后会出现 RUNNING → RETRYING → RUNNING → FAILED 这种往复，而所有读这个状态的地方（前端、监控、重建索引接口的前置判断）都要理解这个环。

更麻烦的是**谁负责把 RETRYING 改回去**。worker 在失败时写 RETRYING，然后重排；下一次 worker 取到任务时写 RUNNING。中间如果 worker 被 SIGKILL，状态永远停在 RETRYING —— 又多了一个卡死态要对账。

拼文案的代价是「机器读不到这个信息」（只能人看），收益是状态机不变复杂。当前只需要人看，所以够了。真要机器读，正确做法是**加一列** `retry_count` 而不是加一个状态 —— 计数是幂等可覆盖的，状态是有跃迁约束的。

> **追问 2：`f"[{code}] {exc}"` 直接把异常 str 进去，会不会带出敏感信息？**

会，这是个真实风险。`str(exc)` 里可能有文件路径、数据库连接串片段（`OperationalError` 常带 host/port）、甚至 SQL 语句。这个字符串落进 `error_message` 列，而 `error_message` 会通过状态查询接口返回给前端。

当前项目是内网工具，风险可接受。要收紧的话有两条路：一是给 `AppError` 加一个 `safe_message` 属性，对外只返回它；二是在拼装时按错误类型选择性脱敏。第一条更彻底，因为它把「哪些信息可以对外」变成了异常类型的一部分，而不是散落在每个拼装点的判断。

> **追问 3：这个函数有测试吗？**

有三个，锁住三条语义：

```
tests/unit/test_job_failure.py:75  test_message_carries_error_code
tests/unit/test_job_failure.py:82  test_message_states_pending_retry
tests/unit/test_job_failure.py:88  test_message_omits_retry_hint_when_final
```

第三个（终局时**不带**重试提示）容易被漏掉，但它和第二个一样重要：多余的「将自动重试」比缺失的更糟 —— 值班同学会等一个不会来的重试，从而**延迟**介入。

**拓展**

- **结构化 `error_message`**：现在是拼字符串，读的时候还得解析。改成 JSON 列（`{"code": ..., "message": ..., "will_retry": ...}`）就能被直接查询和聚合。代价是列类型变更要迁移。
- **失败原因的用户友好翻译**：`[llm_timeout] Request timed out` 对用户没意义。可以按 code 映射一句人话（「模型服务响应超时，稍后会自动重试」），原始信息留给日志。
- **`retry_count` 列**：如追问 1 所说，加计数列比加状态安全。有了它就能做「重试两次以上的任务」告警。

### Q8. 假如让你从零设计这套重试，你会怎么划分职责？

**考点**

这是回过头看自己设计的开放题。面试官想看你能不能**跳出现有实现讲原则**，而不是复述代码。

**标准回答**

我会按「**谁掌握做这个决定所需的信息**」来切，而不是按代码模块切。三个问题各自问的信息不同：

| 问题 | 需要的信息 | 只有谁有 | 落在哪 |
|---|---|---|---|
| 这类任务**允许**重试几次？ | 任务的业务性质、SLA | 入队方（知道自己在提交什么任务） | `enqueue_*` 的 `retry=` |
| 这次失败**值得**重试吗？ | 异常对象 | worker（catch 到异常的人） | `apply_retry_policy` |
| 这个异常**算不算**可重试？ | 错误分类体系 | 全局唯一 | `errors.is_retryable` |

现在的实现正好是这个划分，但我要说清楚它不是设计出来的，是**被 RQ 的约束逼出来的**：额度必须在入队时进 job 记录，这一点没有选择。

如果从零设计一个队列框架，我会让 worker 能**追加**额度（而不只是减少）—— 那样「限流类错误多给两次机会」就能在 worker 侧一次决定完，不需要入队侧预留一个宽松额度。现在的形态是「入队给宽、worker 卡严」，本质上是在用一个宽额度模拟「worker 可以决定给多少」。

第三行是最重要的一行：**分类逻辑必须全局唯一**。这是 25 篇的核心结论。同一个 `ConnectionError`，HTTP 边界要判 503、worker 要判可重试、熔断器要判计不计失败 —— 三处判断必须来自同一个函数。分开写的话，某天有人在 worker 里加了一个新的可重试异常，HTTP 边界不知道，于是同一个故障在 API 上返回 500（不可重试）而在 worker 上重试三次。**两边对同一个世界有不同的认知，这种 bug 极难定位，因为每一处单独看都是对的。**

**真实代码**

三层的连接点就一行：

```python
# app/core/job_failure.py:54
from app.core.errors import error_code_of, is_retryable
```

`job_failure.py` 不定义任何分类规则，只消费。docstring 里写明了这个纪律：

```python
# app/core/job_failure.py:40-41
3. 重试裁决与「是否可重试」的判定复用 `app/core/errors.py` 的
   `is_retryable`，不在这里重写一遍分类逻辑（DRY）。
```

**追问链**

> **追问 1：入队侧要不要能针对不同任务给不同额度？**

要，而且现在做不到 —— 两条链路都调 `default_job_retry()`，拿的是同一套 3 次/10-30-60。

真实需求是存在的：协议 PDF 的失败大多不可重试（PDF 损坏），给 3 次额度基本用不上；而它偶尔的 LLM 限流失败又值得更长的间隔（限流窗口常是分钟级）。这两个特征说明它应该是「次数少、间隔长」，和索引链路的「次数中、间隔中」不一样。

改起来很轻：`default_job_retry(max=2, intervals=[30, 120])`。没改是因为**当前失败量小到看不出差异** —— 这是个诚实的 YAGNI，不是遗漏。判断该改的信号是：如果 `job_retries_total` 里协议 PDF 的重试大多是白烧的（重试后仍失败），就该调。

> **追问 2：worker 侧的裁决会不会和入队侧的意图冲突？**

会，而且现在的冲突方向是**安全的**：worker 只能否决，不能追加。所以 worker 最多让重试少发生，不会让它超出入队方授权的次数。

反过来（worker 能追加）就危险了：入队方明确说「这个任务只给一次机会」，worker 却因为异常看着像瞬时故障而重试五次。这是越权。

所以「只能减不能加」这个约束虽然是 RQ 强加的，但它恰好是**正确的权限方向**：额度是授权，裁决是在授权范围内的自由裁量。要能追加，就必须让入队方能表达「上限是多少」—— 那又变回了同一个模型。

> **追问 3：如果换掉 RQ（比如上 Celery），这套划分能平移吗？**

第三层（`is_retryable`）完全平移，它不依赖任何队列概念。第二层的**判据**能平移，**实现方式**不行 —— Celery 的重试是任务里 `self.retry(...)` 主动触发，语义上更接近「worker 决定」，反而更贴近我理想中的模型。第一层在 Celery 里是 `@task(max_retries=3)` 装饰器上的声明，从「入队时」挪到了「任务定义时」。

值得注意的是这个平移会**变好**：Celery 的模型允许 worker 用 `countdown` 动态指定下次间隔，也允许在异常类型基础上决定重试与否。我现在为了绕开 RQ 的限制写的那段「改内存属性」的取巧代码，在 Celery 下就不需要了。

**拓展**

- **重试策略配置化**：把 `(max, intervals)` 按队列名放进 config，运维能在不改代码的情况下调。风险是配置和代码的认知分叉，需要在启动时打印生效值。
- **`Retryable` 协议**：让业务异常自己声明重试参数（`exc.retry_after`），比外部按类型查表更贴合「限流响应头里带了 Retry-After」这种场景。
- **重试预算的全局视角**：现在每个任务独立算额度。下游整体挂掉时，正确动作是**全局停止重试**（熔断）而不是每个任务各自烧三次。这是 Q2 拓展里说的队列级熔断。

## 第三部分 · 失败留痕

### Q9. 讲一个你在这个项目里修过的、最隐蔽的 bug。

**考点**

这是本篇的压轴题，也是整个系列里最值钱的一道。面试官要的不是「我修了个 bug」，而是**你能不能描述一个在正常运行下完全看不见、只在真故障时才致命的缺陷**。能讲清这个，等级判定会直接上一档。

**标准回答**

改之前两个 worker 的 `except` 块是同一个形状：

```python
except Exception as exc:
    db.rollback()
    job = repo.get_index_job(job_id)
    if job is not None:
        job.status = FAILED
        job.error_message = str(exc)
        db.commit()          # ← 问题就在这一行
    raise
```

问题是 **`except` 块里又 `commit()` 了一次**。

如果这次 commit 也失败，抛出的新异常会顺着 `except` 块往外走，把原始异常**顶掉**。Python 的 traceback 里确实会留一句 "During handling of the above exception, another exception occurred"，但 RQ 落到 `job.exc_info` 的、告警里弹出来的、你排障第一眼看到的，全是后面那个 `OperationalError: server closed the connection`。真正的原因（比如「PDF 第 3 页解析失败」）沉在下面。

而这不是罕见情况，恰恰是**最常见**的组合：原始异常本身就是数据库连接断开或网络故障时，同一个 session 上的 commit **必然**也失败。也就是说 —— **越是基础设施故障，越会丢失真实原因，而那正是最需要看清原因的时候。**

第二个后果同样致命：失败状态没写进去，`index_jobs` 行永远停在 RUNNING，`knowledge_documents` 永远停在 INDEXING。用户在页面上看着「索引中」转了三天，没有任何人知道它其实早就死了。**而所有监控都在盯 FAILED 状态，于是永远不告警。**

这个 bug 的隐蔽性在于：单测会过（测试里数据库是好的，第二次 commit 成功），本地会过，压测也会过 —— 它只在数据库真挂的时候现形，而那正是你最需要日志说真话的时刻。

**真实代码**

处置分三条，都写在 `app/core/job_failure.py:1-42` 的模块 docstring 里：

```python
# app/core/job_failure.py:34-41
## 处置

1. 用一个**独立的短生命周期 session** 写失败状态。原 session 的连接可能
   已经废了（连 rollback 都可能抛），在同一个连接上抢救等于在漏水的船上补漏。
2. 整段抢救逻辑包在 try 里，**任何二次失败只记日志，绝不外抛**。
   原始异常必须原样 raise 出去 —— 那才是要修的东西。
3. 重试裁决与「是否可重试」的判定复用 app/core/errors.py 的
   is_retryable，不在这里重写一遍分类逻辑（DRY）。
```

落地后的 `except` 块（`app/workers/protocol_pdf_worker.py:46-93`）：

```python
except Exception as exc:
    will_retry = apply_retry_policy(exc, job_id=job_id)          # ① 裁决
    message = format_failure_message(exc, will_retry=will_retry)

    with suppress(Exception):                                    # ② 尽力释放
        db.rollback()

    def _write_failed(session: Session) -> None:                 # ③ 新 session 落盘
        failure_repo = ProtocolIngestionRepository(session)
        failed_job = failure_repo.get_job(job_id)
        if failed_job is None:
            return
        failed_job.status = ProtocolIngestionJobStatus.FAILED
        failed_job.error_message = message
        failed_job.finished_at = datetime.now(UTC).replace(tzinfo=None)

        ingestion = failure_repo.get_ingestion(failed_job.ingestion_id)
        if ingestion is not None:
            ingestion.status = ProtocolIngestionStatus.FAILED
            ingestion.error_message = message

    record_job_failure(_write_failed, job_id=job_id)

    logger.opt(exception=exc).error(...)
    raise                                                        # ④ 原样抛
finally:
    with suppress(Exception):
        db.close()
```

**追问链**

**追问 1：`raise` 换成 `raise RuntimeError(...) from exc` 行不行？信息更全。**

不行，会破坏两件事。第一，RQ 靠这个异常对象判定失败并决定是否重排队（`app/workers/protocol_pdf_worker.py:89` 的注释就是这句），换成新异常类型后，`job.exc_info` 里记的是 `RuntimeError`，而所有按 `error_code` 聚合的统计全部失效 —— 因为 `error_code_of` 拿到的是包装后的类型。第二，`from exc` 保留的是 `__cause__` 链，但告警系统和 RQ 页面通常只展示最外层类型和 message，链里的东西要点开才看得到。**这个 bug 的本质就是「真实原因被包在下一层」，用 `raise ... from` 修它等于换个姿势重犯。**

**追问 2：`finally` 里的 `db.close()` 为什么也要 suppress？close 还能抛？**

能。连接已断时 `close()` 要走一趟归还连接池的逻辑，底层 socket 已经废了就会抛。而 `finally` 里逃出去的异常会**覆盖** `except` 块里正在往外抛的原始异常 —— Python 的语义是 `finally` 的异常优先。所以这里不 suppress，就等于在出口处又埋了一遍同样的 bug。`app/core/job_failure.py:179-183` 里对 `session.close()` 做了同样处理，注释写得很直接：「若让它从 finally 里逃出去，就又变成了『二次异常顶掉原始异常』—— 正是本模块要消灭的那个 bug」。

**追问 3：那 `record_job_failure` 内部如果连 `SessionLocal()` 都建不出来呢？**

那就只能认了，但要留下痕迹。`app/core/job_failure.py:160-166` 单独捕获了这一档：

```python
try:
    session = SessionLocal()
except Exception as exc:
    logger.error(f"任务失败状态落盘失败（无法建立 session）: job_id={job_id}: {exc}")
    return
```

这种情况是连接池耗尽或数据库彻底不可达。此时数据库里那行永远停在 RUNNING，只有日志能说明发生了什么 —— 这也正是 Q30 里 P0 那条「RUNNING 状态需要进程外对账」的由来：**只要抢救动作本身依赖数据库，就一定存在一个数据库不可用因而抢救不了的窗口。** 靠进程内代码补不完，必须有个外部对账任务。

**拓展**

现在还缺的是**抢救失败本身的可观测性**。`record_job_failure` 二次失败只打了一行 `logger.error`，没有指标。应该加一个 `job_failure_record_errors_total` Counter —— 这个指标平时恒为 0，一旦不为 0 就说明「有任务的失败状态没落进数据库」，是需要立刻人工介入对账的信号。它比大多数业务指标都值钱，因为它监控的是**监控本身的失效**。

### Q10. `record_job_failure` 为什么要接受一个回调，而不是直接接受「要改哪些字段」？

**考点**

考接口设计。参数选回调还是选数据，取决于「谁知道该写什么」。

**标准回答**

因为两个 worker 要写的东西完全不同：索引 worker 要改 `index_jobs` 和 `knowledge_documents` 两张表，协议 PDF worker 要改 `protocol_pdf_ingestion_jobs` 和 `protocol_pdf_ingestions` 两张表，字段名、状态枚举、外键路径全不一样。

如果接口设计成接受数据（比如 `record_job_failure(table="index_jobs", job_id=..., status=...)`），这个函数就得知道所有表的结构，每加一种任务类型就要改它一次 —— 违反开闭原则，而且它会慢慢长成一个装着所有表名的 if-else。

设计成回调，职责就干净地切开了：

- `record_job_failure` 负责**会话生命周期与异常吞咽**（建 session、commit、二次失败只记日志、close 也 suppress）——这部分对所有 worker 完全一样，是真正值得复用的东西。
- 回调负责**写什么**（哪张表、哪些字段）—— 这部分每个 worker 都不同，本来就该留在 worker 里。

分界线是：**「怎么安全地写」是通用的，「写什么」是特定的。** 通用的那半抽出来，特定的那半用回调注入。

**真实代码**

```python
# app/core/job_failure.py:146-159
def record_job_failure(
    write_status: Callable[[Session], None],
    *,
    job_id: str,
) -> None:
    """用独立 session 写入任务失败状态；二次失败只记日志，绝不外抛。

    `write_status` 拿到的是一个全新的 Session，需要在里面用这个 session
    重新构造 repository 并重新取行 —— 原 session 里那些 ORM 对象属于
    一个可能已经废掉的连接，不能跨 session 复用。

    这个函数的全部价值在于「绝不 raise」：抢救失败是坏消息，
    但让抢救过程中的异常顶掉原始异常，是更坏的消息。
    """
```

注意签名里 `write_status` 接收的是 `Session` 而不是 repository —— 因为两个 worker 用的 repository 类型不同，传 Session 才能让回调自己决定构造哪个。

**追问链**

**追问 1：回调是个闭包，捕获了外层的 `message`、`job_id`。这有什么风险？**

风险是**它也可能捕获到外层那些绑在坏连接上的 ORM 对象**。`app/workers/protocol_pdf_worker.py:67-69` 的注释专门防这一点：

```python
def _write_failed(session: Session) -> None:
    # 必须用新 session 重新构造 repo、重新取行：原 session 里的
    # ORM 对象绑在那个可能已经断掉的连接上，跨 session 复用会在 flush 时炸。
    failure_repo = ProtocolIngestionRepository(session)
    failed_job = failure_repo.get_job(job_id)
```

闭包里只捕获了 `job_id`（一个字符串）和 `message`（一个字符串），**没有捕获外层的 `job` 对象**。这是刻意的：如果图省事写 `job.status = FAILED`（用外层那个已加载的对象），新 session 一 flush 就会因为对象属于别的 session 而报 `InvalidRequestError`，或者更糟 —— 它会尝试用旧连接刷，直接抛 `OperationalError`。**抢救代码里绝不能出现旧 session 的对象，只能出现纯值。**

**追问 2：为什么不干脆让回调自己拿 Session？把 `SessionLocal()` 也放进 worker？**

那样每个 worker 都要重写一遍「建 session / try / except 只记日志 / finally suppress close」这四层结构，一共十几行。两个 worker 抄两遍，第三个 worker 抄第三遍，其中一遍漏掉 `suppress` 就重新引入了那个 bug。**这段代码的特点是「写错了不会立刻发现」，所以它必须只有一处实现。**

**拓展**

现在两个 worker 的 `except` 块结构完全一致（裁决 → rollback → 定义回调 → record → 日志 → raise），大约 25 行几乎逐字重复。可以再抽一层装饰器 `@handle_job_failure(write_status_factory)`，让 worker 函数体只剩 happy path。没做是因为回调的构造依赖 worker 内部的局部变量（`job_id` 从参数来，但表和字段各不同），抽装饰器需要引入一层工厂函数，**代码总量不减、间接层 +1**。等第三个 worker 出现时再抽，那时才有三个样本能看出真正的公共形状。

### Q11. 这段代码里有七处 `with suppress(Exception)`。这不就是吞异常吗？你凭什么判断哪里能吞、哪里不能？

**考点**

`suppress(Exception)` 是 code review 里最容易被打回的写法之一，而这里连着写了七处。面试官要看的是**你有没有一条可复述的判据**，还是单纯图省事。答得出「suppress 的合法性取决于此刻是否已有一个更有信息量的异常在飞」就到位了。

**标准回答**

先给判据，三条全成立才 suppress：

1. **这个动作是 best-effort 的** —— 做不成不影响正确性。`db.rollback()` 和 `db.close()` 都属于「尽力释放资源」，失败了最坏结果是连接被池子回收时超时清理，不会算错任何数据。
2. **它抛出的异常严格不如在飞的那个有信息量。** `close()` 在断连时抛的是一个 socket 层错误，而正在往外抛的是「PDF 第 3 页解析失败」。留哪个不用想。
3. **吞掉之后仍然留有痕迹。** `record_job_failure` 里 suppress 的两处，外层已经 `logger.error` 记过二次异常的类型和消息了（`app/core/job_failure.py:172-176`），suppress 只是防止它继续往上飞。

关键在第二条：**suppress 的正当性不是这个异常本身不重要，而是此刻有一个更重要的异常正在往外抛。** 同一句 `db.close()` 出现在 happy path 上就绝不能 suppress —— 那时没有别的异常在飞，吞掉等于静默丢数据。

所以这七处全部落在同一种处境：**失败路径上，异常已经在飞了。** Q9 那个 bug 的本质就是「第二个异常顶掉了第一个」，而 `finally` 里逃出去的异常按 Python 语义**优先于** `except` 正在抛的那个 —— 出口处不 suppress，等于在同一个地方又埋一次同样的 bug。

有一处是例外，理由完全不同：

```python
# app/core/job_failure.py:109-111
job = None
with suppress(Exception):  # pragma: no cover - RQ 上下文缺失不该影响任务本身
    job = get_current_job()
```

这里不在失败路径上，suppress 表达的是**「这个能力是可选的」** —— 单测直接调函数时拿不到 RQ 上下文，此时函数应该退化成纯判定而不是崩掉。判据换成了另一条：*缺了它功能降级但不出错，那就允许缺*。这两种 suppress 长得一样，含义完全不同，混在一起读会误判。

**真实代码**

七处按用途分成三类：

| 位置 | 动作 | 属于哪类 |
|---|---|---|
| `job_failure.py:110` | `get_current_job()` | 能力可选（退化成纯函数） |
| `job_failure.py:177` | `session.rollback()` | 失败路径 best-effort |
| `job_failure.py:182` | `session.close()` | 失败路径出口，防覆盖原异常 |
| `index_worker.py:116` | `db.rollback()` | 失败路径 best-effort |
| `index_worker.py:146` | `db.close()` | `finally` 出口，防覆盖原异常 |
| `protocol_pdf_worker.py:64` | `db.rollback()` | 失败路径 best-effort |
| `protocol_pdf_worker.py:92` | `db.close()` | `finally` 出口，防覆盖原异常 |

出口那三处的注释写得最直接：

```python
# app/core/job_failure.py:179-183
finally:
    # close 在连接已断时同样可能抛。若让它从 finally 里逃出去，
    # 就又变成了「二次异常顶掉原始异常」—— 正是本模块要消灭的那个 bug。
    with suppress(Exception):
        session.close()
```

注意 `index_worker.py:115` 那行注释区分了 rollback 和 close 的理由：**「它只是尽力释放事务，失败不该影响后面的抢救。」** rollback 挡的是「别让它打断抢救流程」，close 挡的是「别让它覆盖原异常」—— 一个在中间，一个在出口，防的不是一回事。

**追问链**

**追问 1：`with suppress(Exception)` 和 `try: ... except Exception: pass` 有区别吗？**

运行语义上没有区别，可读性上有，而且这个差别在这类代码上恰好重要。

`suppress` 把「我是故意吞的」写在了**块的第一行**，读代码的人一眼看到意图。`try/except pass` 要读到最后一行才知道结局 —— 而这类代码天生长得像 bug，让 reviewer 多读两行就多一次误判机会。

还有个更实在的好处：`suppress` **没法在捕获后做别的事**。这个限制是特性不是缺陷 —— 它保证了块里只有「尝试」没有「处理」。用 `except Exception: pass` 的话，后来的人很容易在 `pass` 那里加一行别的逻辑，于是这个块悄悄从「best-effort 尝试」变成了「异常处理分支」，而它外面那个 `raise` 还在等着抛原始异常。

**追问 2：为什么不写 `suppress(OperationalError)` 更精确？宽泛地捕 `Exception` 显得很懒。**

因为这里要防的不是某个具体异常，而是**「任何来自一条已损坏连接的意外」**。这个集合比想象的宽：SQLAlchemy 的 `OperationalError` / `InterfaceError`、驱动层（psycopg）自己的异常、连接对象已被置空导致的 `AttributeError`、池子已关闭导致的 `RuntimeError`。

精确捕获在这个位置是**错误的方向**：漏掉任何一个类型就重新引入了 Q9 那个 bug，而它换来的收益（避免误吞无关异常）在这里恰好为零 —— 这几行里除了一次 `close()` 调用什么都没有，不存在「无关异常」。

一般原则是「捕获尽量窄」，但这条原则的前提是「窄捕获漏掉的异常应该往上抛」。这里的前提不成立：这个位置任何异常都不该往上抛。**原则的适用要看它的前提在不在，而不是把它当口号。**

**追问 3：这七处都有测试覆盖吗？**

四处有专门的用例，三处没有：

```
tests/unit/test_job_failure.py:107  test_commit_failure_never_masks_original_exception
tests/unit/test_job_failure.py:119  test_session_construction_failure_is_swallowed
tests/unit/test_job_failure.py:127  test_close_failure_never_escapes
tests/unit/test_job_failure.py:135  test_write_status_failure_rolls_back_and_is_swallowed
```

覆盖的是 `job_failure.py` 里那三处（加上 commit 失败这条主线）。两个 worker 里的 `rollback` / `close` 那四处没有独立用例 —— 是真实欠账，因为它们和被测的那三处是**同构但独立**的代码，复制粘贴出来的东西天然会漏改。这也正好印证了 Q10 里说的：这种「写错了不会立刻发现」的逻辑应该只有一处实现，而 worker 里这四处正是没抽干净的残留。

**拓展**

- **`suppress` 应该留一行 debug 日志。** 现在是完全静默的，代价是丢掉一个真实信号：`close()` 连续失败通常意味着连接池状态有问题（比如池子被耗尽后连接对象错乱），而现在这件事一点痕迹都没有。做法是包一个 `suppress_and_log(*excs, hint=...)` 上下文管理器，行为不变，只多打一条 `logger.debug`。日志级别必须是 debug —— 这是正常失败路径上的预期噪音，用 warning 会污染告警。
- **让判据可执行。** ruff 的 `S110`（try-except-pass）和 `BLE001`（blind except）能拦住裸写法，但对 `suppress(Exception)` 默认不管。可以加一条自定义检查：`suppress(Exception)` 必须紧邻一行注释说明理由。当前七处都写了注释，但那是靠自觉 —— 而自觉不会被 CI 检查。
- **区分开两种 suppress 的命名。** 「失败路径 best-effort」和「能力可选」用同一个写法表达，读者要靠上下文分辨。如果把后者显式写成 `optional_rq_job()` 这样的小函数，两种意图在代码里就是两个不同的名字，不必靠注释区分。

### Q12. 你怎么测试这些「失败路径上的失败」？

**考点**

考测试意识。这类代码的默认状态是「从未执行过」—— 25 篇 Q28 的主题在这里有具体落点。

**标准回答**

核心手法是**注入二次失败**：让 mock 的 session 在 `commit()` 时抛异常，然后断言原始异常仍然原样传出。

`tests/unit/test_job_failure.py` 一共 157 行 13 个用例，其中五个专门打失败路径的失败：

| 用例 | 注入的故障 | 断言 |
|---|---|---|
| `test_commit_failure_never_masks_original_exception` | `session.commit()` 抛 | 原始异常保留、不外抛 |
| `test_session_construction_failure_is_swallowed` | `SessionLocal()` 抛 | 不外抛 |
| `test_close_failure_never_escapes` | `session.close()` 抛 | 不外抛 |
| `test_write_status_failure_rolls_back_and_is_swallowed` | 回调本身抛 | rollback 被调用、不外抛 |
| `test_writes_through_independent_session` | — | 用的是新 session，不是传入的 |

这五个用例锁住的不是「功能对不对」，而是**四个「绝不 raise」的承诺**。每一个都对应 `job_failure.py` 里一处 `suppress` 或 `except`。删掉任何一处 `suppress`，就有一个用例变红。

`apply_retry_policy` 那边还有一个特别的用例 —— `test_without_rq_context_is_pure`：脱离 RQ 上下文时函数只返回判定结果、不做副作用。这个用例锁的是**可测试性本身**，它保证了这个函数能在没有 Redis 的环境里被直接调用。

**真实代码**

用例清单（`tests/unit/test_job_failure.py`）：

```
40:  test_retryable_error_keeps_remaining_retries
49:  test_non_retryable_error_cancels_remaining_retries
59:  test_exhausted_retries_reports_no_retry
67:  test_without_rq_context_is_pure
75:  test_message_carries_error_code
82:  test_message_states_pending_retry
88:  test_message_omits_retry_hint_when_final
95:  test_writes_through_independent_session
107: test_commit_failure_never_masks_original_exception
119: test_session_construction_failure_is_swallowed
127: test_close_failure_never_escapes
135: test_write_status_failure_rolls_back_and_is_swallowed
151: test_returns_fresh_instance_each_call
```

最后一个 `test_returns_fresh_instance_each_call` 测的是 Q6 里 `default_job_retry()` 为什么是函数：断言两次调用返回不同实例。**一个只有两行的用例，锁住的是一个「共享可变状态」类型的隐患。**

**追问链**

**追问 1：这些用例都是 mock 出来的失败。真实的数据库断连和 mock 抛异常，行为一样吗？**

不完全一样，这是这套测试的边界，得说清楚。mock 抛的是我们指定的异常类型，而真实断连时 SQLAlchemy 可能在**不同的时机**抛不同的东西：可能在 `commit()` 抛，也可能在更早的 `flush()` 抛，甚至可能在 `get()` 时就抛。mock 只覆盖了「在 commit 抛」这一种时机。

不过对这段代码来说够了 —— 因为处置逻辑是「无论在哪抛、无论抛什么，都只记日志不外抛」，`suppress(Exception)` 和 `except Exception` 对时机不敏感。真正需要真实断连才能验证的是**连接池的恢复行为**（断连后新建的 session 能不能拿到可用连接），那属于 `pool_pre_ping` 的职责，见 Q17。

**追问 2：怎么保证以后有人加了新的 `except` 分支，测试还能跟上？**

保证不了，这是测试的固有局限 —— 测试只能锁住已知的承诺。能做的是把承诺写在**代码注释里**而不只是测试里，让改代码的人在原地就看到理由。`job_failure.py:179-183` 那段 `close` 的注释就是这么写的（「若让它从 finally 里逃出去，就又变成了……正是本模块要消灭的那个 bug」）。**注释解释为什么，测试锁住是什么，两者缺一不可。**

**拓展**

缺一个**混沌测试**：在集成测试里真的把 PostgreSQL 停掉，跑一批任务，然后重启数据库，断言所有任务最终都不在 RUNNING 状态。这个测试会直接暴露 Q30 P0 那个缺口 —— 因为在数据库全程不可用的窗口里，进程内代码确实救不回来，测试必然失败。**一个必然失败的测试比一个跳过的测试有价值：它把「已知缺口」变成了 CI 里持续可见的红灯，而不是文档里一句会被遗忘的话。**

### Q13. worker 被 `kill -9` 了会怎样？

**考点**

考边界意识。前面所有的失败处置都建立在「`except` 块能执行」这个前提上，这题问的是前提不成立时会怎样。

**标准回答**

`except` 一行都不会执行。`SIGKILL` 不可捕获，进程立即消失。于是：

- `index_jobs` 行停在 RUNNING，`error_message` 是空的
- `knowledge_documents` 停在 INDEXING
- Redis 里的 job 会被 RQ 的看门狗（另一个 worker 或 `rq` 的 maintenance 逻辑）在 `job_timeout` 到期后标记失败，但**数据库那两行没人改**

结果是：数据库说「正在索引」，Redis 说「失败了」，两边不一致，而**用户看的是数据库**。文档在页面上「索引中」转到世界末日。

更要紧的是监控盲区：所有告警规则都在盯 FAILED 状态和错误率。RUNNING 状态永远不触发告警 —— 它看起来是个正常的中间态。**这个故障形态的特征是「完全静默」**，只有用户来投诉才会被发现。

`kill -9` 不是罕见场景：容器 OOM 被 kubelet 杀、节点驱逐、`docker stop` 超时后升级成 SIGKILL、运维手动清进程，都会走到这条路。

**真实代码**

现在能兜住的只有一层：入队时声明的 `job_timeout`。

```python
# app/services/index_job_queue.py:24
job_timeout="30m",
```

RQ 会在超时后把 Redis 侧的 job 标为失败并（如果有额度）重排队。重排队后新的执行会重新走 `run_index_job`，把 `job.status` 改回 RUNNING、`started_at` 更新 —— 数据库那行因此被"救活"了。

**但这只在有重试额度且重排队成功的情况下成立。** 额度耗尽（三次都被 kill，比如文档太大每次都 OOM）之后，数据库那行就永久停在 RUNNING。而 `apply_retry_policy` 也帮不上忙 —— 它是在 `except` 里跑的，`kill -9` 下根本不执行。

**追问链**

**追问 1：那能不能在 worker 启动时扫一遍 RUNNING 的行，把它们标成失败？**

不能直接这么做，会误杀。多 worker 部署下，A worker 启动时看到的 RUNNING 行可能正是 B worker 正在跑的任务 —— 标成 FAILED 会让一个健康任务的状态被踩掉，而它十分钟后还会成功，于是状态又从 FAILED 跳回 SUCCEEDED，中间那段时间用户看到的是错的。

正确做法要靠**心跳 + 超时**两个条件同时成立：给 `index_jobs` 加一列 `heartbeat_at`，worker 在长任务里定期更新；对账任务只处理「状态是 RUNNING 且 `heartbeat_at` 超过阈值」的行。没有心跳列的话，唯一可用的近似条件是 `started_at` 加上 `job_timeout` —— 但那个判据对「刚启动的长任务」不成立。

**追问 2：为什么这个对账不能做成 worker 里的一个定时任务？**

因为它要救的正是「worker 进程死了」这件事。放在 worker 里，worker 全挂时对账也停了 —— 而 worker 全挂恰恰是最需要对账的时刻。这跟 Q9 追问 3 里那个「抢救依赖数据库、数据库挂了就救不了」是同构的问题：**兜底逻辑不能和它要兜的东西同生共死。**

正确的位置是一个独立的调度器（RQ Scheduler / K8s CronJob），它的失败与 API 和 worker 都不相关。

**追问 3：RQ 本身不是有 `StartedJobRegistry` 吗？为什么还要自己对账？**

RQ 的 registry 只管 **Redis 侧**的一致性 —— 它能把超时的 job 从 started 挪到 failed。但它对我们的业务表一无所知，`index_jobs` 和 `knowledge_documents` 那两行它不会碰。这是 Q4 讲的「一个决策劈成两半」的另一个面：**任务状态在 Redis 和 PostgreSQL 里各存了一份，RQ 只维护它那份。** 两份状态的对齐是我们的责任，不是框架的。

**拓展**

这是 Q30 里唯一的 P0。完整方案三步：

1. 给两张 job 表加 `heartbeat_at` 列，worker 在主循环里定期更新（索引任务按 chunk 批次更新，天然有循环）
2. 一个独立的 CronJob，扫「RUNNING 且 heartbeat 超时」的行，标为 FAILED，`error_message` 写「worker 异常终止（无心跳），请重试」
3. 加一个 `jobs_stuck_running` Gauge，让这个数字本身可告警 —— 不是等对账去修，而是让「有多少任务卡住了」变成一个能看见的量

第 3 步单独拿出来说：**先让问题可见，再让问题自动修复。** 顺序反了的话，自动修复逻辑本身出 bug 时没人知道。

## 第四部分 · 跨进程上下文

### Q14. `request_id` 是怎么传到 worker 进程里的？

**考点**

考对 ContextVar 边界的理解。很多人知道用 ContextVar 存 request_id，但没想过它到不了另一个进程。

**标准回答**

必须显式地序列化进去、反序列化出来 —— 因为 **ContextVar 只在同一个进程的同一个执行上下文里有效**。

入队时是 HTTP 请求进程持有 rid，而真正干活的是另一台机器上的 worker 进程。两者之间唯一的通道是 Redis 里的那条 job 记录。所以链路是这样的：

```
中间件 → ContextVar → 日志 → trace → RQ meta → worker 日志
```

最后那一跳是断的，必须手工缝上：入队时把 rid 写进 `job.meta`，worker 执行时读回来重新绑定到自己进程的 ContextVar。

不这么做的后果很具体：上传一个文档触发索引任务，**API 侧日志有 rid、worker 侧日志全是 `-`**。文档索引失败时，你手里握着用户给的 rid，却没法把它和 worker 的报错日志连起来 —— 而失败恰恰都发生在 worker 侧。**rid 断在了它最有用的那一段。**

**真实代码**

模块 docstring 把这条链和断点讲得很直接：

```python
# app/core/job_context.py:1-15
"""RQ 任务的 request_id 传递。

这是 request_id 全链路的最后一段：
    中间件 → ContextVar → 日志 → trace → **RQ meta → worker 日志**

为什么这一段单独存在：
ContextVar 只在**同一个进程的同一个执行上下文**里有效。
入队时 HTTP 请求进程持有 rid，而真正干活的是另一台机器上的 worker 进程 ——
两者之间唯一的通道是 Redis 里的那条 job 记录。
所以必须显式地「序列化进去、反序列化出来」：
入队时写进 `job.meta`，worker 执行时读回来重新绑定到自己的 ContextVar。

不这么做的后果：上传一个文档触发索引任务，API 侧日志有 rid、
worker 侧日志全是 "-"。文档索引失败时，你手里有 API 的 rid，
却没法把它和 worker 的报错日志连起来 —— 而失败恰恰都发生在 worker 侧。
"""
```

入队侧和 worker 侧各一半：

```python
# app/core/job_context.py:42-53
def enqueue_with_request_id(queue, func, *args, **kwargs) -> Job:
    meta: dict[str, Any] = dict(kwargs.pop("meta", None) or {})
    meta.setdefault(JOB_META_REQUEST_ID, get_request_id_or_none())
    return queue.enqueue(func, *args, meta=meta, **kwargs)

# app/core/job_context.py:56-73
@contextmanager
def job_request_id_scope() -> Iterator[str]:
    request_id: str | None = None
    try:
        job = get_current_job()
    except Exception:
        job = None
    if job is not None:
        request_id = (job.meta or {}).get(JOB_META_REQUEST_ID)

    with request_id_scope(request_id) as bound:
        yield bound
```

键名是常量而不是字面量，理由写在 `app/core/job_context.py:34-37`：

```python
# job.meta 里存放 request_id 的键名。定义成常量而非字面量：
# 入队侧和 worker 侧必须用同一个键，写错一个字母就会静默失效
# —— 没有任何报错，只是 rid 永远取不到。
JOB_META_REQUEST_ID = "request_id"
```

**「静默失效」是这里的关键词**：拼错常量名是 `NameError`，拼错字符串字面量什么都不会发生。同一个错误，一种形态在启动时就炸，另一种形态在三个月后排障时才被发现。

**追问链**

**追问 1：`meta.setdefault(...)` 为什么不是直接赋值？**

为了保留调用方显式传入的 meta。这个函数的签名跟 `queue.enqueue` 完全兼容（`app/core/job_context.py:45-47` 的注释说明这是刻意的），调用方可能自己带了 `meta={"trace_id": ...}`；直接赋值会把整个 meta 覆盖掉，`setdefault` 只在缺 `request_id` 键时补上。

这跟 26 篇里 logger patcher 用 `setdefault` 是同一个考虑：**切面注入的东西不能踩掉调用方显式表达的意图。**

**追问 2：worker 侧取不到 rid（比如任务是脚本直接触发的）怎么办？留空还是新生成？**

新生成。`request_id_scope(None)` 会生成一个新的，理由在 `app/core/job_context.py:61-63`：「后台任务哪怕是独立触发的，也该有自己的追踪标识，否则它那一段日志等于没有 id」。

留空的话，一批脚本触发的任务的日志全是 `-`，彼此之间也没法区分 —— 十个并发任务的日志交织在一起，连"哪几行属于同一个任务"都分不出来。**没有关联 id 的日志在并发下等于没有日志。**

**追问 3：`get_current_job()` 为什么要包在 try 里？它还能抛？**

能。脱离 RQ 上下文时（单测里直接把 worker 函数当普通函数调）RQ 内部可能抛，取决于版本。注释里标了 `# pragma: no cover - RQ 上下文缺失时不该影响任务本身` —— **这是整个模块的一条原则：追踪机制自身的失败绝不能影响业务任务。** 跟 26 篇里 logger patcher 用 `setdefault` 防 `KeyError` 是同一条原则的两处落点：可观测性设施坏掉的正确表现是"少了点信息"，不是"任务挂了"。

**拓展**

rid 现在只到日志。更有价值的一步是让它**在数据里也可查**，这一步已经做了一半：`chat_run_traces` 和 `aiops_diagnosis_tasks` 都有 `request_id` 列并带索引（迁移 `migrations/versions/20260823_0008_add_request_id_columns.py`），而两张 job 表还没有。

那个迁移的 docstring 把理由写得很清楚：

```python
# migrations/versions/20260823_0008_add_request_id_columns.py:7-14
为什么要加这两列：
落库的 trace 只有自己的主键 id，而 id 是**请求跑完才生成**的。
一个请求执行 30 秒，这 30 秒里的日志没有任何字段能关联回这条记录。
加上 request_id 之后，「用户报障给的 id」→「日志」→「trace 记录」三者可互查。

为什么建索引：
这两列的唯一用途就是按 request_id 精确查一条/一组记录（排障场景）。
不建索引就是全表扫描，表一大排障就变慢 —— 而排障恰恰是最不能慢的场景。
```

给 `index_jobs` 和 `protocol_pdf_ingestion_jobs` 补上同样的列，就能从一个 rid 直接查到「这次上传触发的任务现在什么状态」，不必先翻日志找 job_id。列进 Q30 的 P1。

### Q15. `with_job_request_id` 用了 `functools.wraps`。上一篇里 `instrument_node` 却刻意不用 —— 同一个项目里两个装饰器，为什么一个必须用、一个必须不用？

**考点**

这是全篇最能区分层次的一题。`functools.wraps` 大家都会背「保留元信息」，但**它在什么情况下是必需的、什么情况下是有害的**，需要理解框架怎么用这些元信息。

**标准回答**

因为两个框架读取元信息的目的完全相反。

**RQ 必须用 wraps**：RQ 通过「模块路径 + 函数名」序列化和反序列化任务函数。入队时它记下 `app.workers.index_worker.run_index_job` 这个字符串存进 Redis，worker 取出来后靠这个字符串 import 并调用。如果装饰器不保留 `__name__` / `__qualname__` / `__module__`，RQ 记下的就是 `app.core.job_context.wrapper` —— worker 侧 import 到的是那个泛用的 wrapper，**根本不是要跑的任务**。任务函数身份是 RQ 的寻址依据，所以 wraps 是硬性要求。

**LangGraph 必须不用 wraps**：`functools.wraps` 会顺手设置 `__wrapped__` 属性指向原函数。LangGraph（以及很多做内省的库）会顺着 `__wrapped__` 去拿"真正的"函数 —— 一旦它这么做，**插桩就被静默绕过了**：节点照常执行，span 一条都不产生。所以 26 篇里的 `_copy_identity` 只手工复制 `__name__` 和 `__doc__`，绝不设 `__wrapped__`。

一句话总结这个对比：**RQ 用元信息来找到函数，LangGraph 用元信息来绕过包装。同一个属性，一个是寻址依据，一个是逃生通道。**

**真实代码**

```python
# app/core/job_context.py:76-93
def with_job_request_id(func: F) -> F:
    """装饰 RQ 任务函数，让函数体内所有日志自动带上原始请求的 rid。

    为什么用装饰器而不是在每个 worker 函数里手写 `with`：
    worker 函数体都是「try 一大段 / except 落库失败状态」的结构，
    手写 with 会让整块代码再缩进一层，diff 噪音大且容易漏。
    装饰器是零侵入的切面（DRY）。

    RQ 通过「模块路径 + 函数名」反序列化任务函数，functools.wraps
    保留了 __name__ / __qualname__ / __module__，所以入队与执行都能正确解析。
    """

    @functools.wraps(func)
    def wrapper(*args: Any, **kwargs: Any) -> Any:
        with job_request_id_scope():
            return func(*args, **kwargs)

    return wrapper
```

用法（`app/workers/index_worker.py:28-29`）：

```python
@with_job_request_id
def run_index_job(job_id: str) -> None:
```

入队侧传的就是这个被装饰后的函数对象（`app/services/index_job_queue.py:22`），RQ 从它身上读出 `app.workers.index_worker.run_index_job`。

**追问链**

**追问 1：怎么验证 wraps 真的是必需的？**

去掉它就能看到失败，而且失败的形态很有意思：**入队会成功**，`queue.enqueue(run_index_job, job_id)` 一路顺畅返回一个 job 对象，接口照常回 202。失败发生在几秒后的 worker 侧 —— worker 拿到 `app.core.job_context.wrapper` 去 import，然后调用它、传进 `job_id`。`wrapper` 的签名是 `(*args, **kwargs)`，所以调用不会因签名不符而报错，它会进入 `job_request_id_scope()` 然后调 `func(job_id)` —— 而 `func` 是闭包捕获的**上一次装饰的那个函数**，具体是谁取决于 import 顺序。

也就是说：不是干净的报错，而是**可能跑错任务**。这比报错糟糕得多。

**追问 2：那两个 worker 都用了这个装饰器，去掉 wraps 后两个任务会不会互相串？**

会，而且这就是上一问那个"取决于 import 顺序"的具体后果。`app.core.job_context.wrapper` 这个路径在模块里只对应一个名字，但它被用来装饰了两个不同的函数 —— 反序列化时得到的是模块里那个名字当前绑定的对象，两个任务的寻址会指向同一处。协议 PDF 的任务可能跑成索引任务，参数还是 PDF 的 job_id，于是 `repo.get_index_job(job_id)` 返回 None，日志打一句「索引任务不存在」，然后**任务标记为成功结束**（`app/workers/index_worker.py:33-36` 是 `return` 而不是 raise）。

于是：PDF 入库任务显示成功，而 PDF 一个字都没解析。**这是本篇里最恶劣的一种失败形态 —— 静默的、跨任务的、报告成功的。** 一个 `functools.wraps` 挡住了它。

**追问 3：`return wrapper  # type: ignore[return-value]` 那个 ignore 是在掩盖类型问题吗？**

不是掩盖，是承认一个类型系统表达不了的事实。`F = TypeVar("F", bound=Callable[..., Any])` 声明了"进去什么类型出来还是什么类型"，但 `wrapper` 的实际类型是 `(*args, **kwargs) -> Any`，mypy 无法证明它等于 `F`。运行时行为是对的（wraps 之后它在各方面都表现得像原函数），但静态类型系统看不到 `functools.wraps` 的语义。

正确的做法是用 `ParamSpec`：

```python
P = ParamSpec("P")
R = TypeVar("R")

def with_job_request_id(func: Callable[P, R]) -> Callable[P, R]:
```

这样 mypy 能验证参数和返回类型都对上，`ignore` 就不需要了。这是个小欠账，值得清 —— **`type: ignore` 每多一处，类型检查的信号就弱一分**。

**拓展**

这两个装饰器的对比可以再抽象一层：**装饰器是否应该伪装成原函数，取决于是否有第三方靠身份做决策。**

- RQ 靠身份寻址 → 必须完全伪装
- LangGraph 靠身份逃逸 → 必须只伪装表面（名字给日志用，`__wrapped__` 绝不给）
- 纯粹给人看的装饰器（比如计时日志）→ 用不用都行

写装饰器时该问的不是"要不要 wraps"，而是"**谁会读这个函数的元信息，读来干什么**"。

### Q16. `job_context.py` 为什么不放进 `task_queue.py`？两个文件加起来才一百行。

**考点**

考模块边界的判断依据。合并的诱惑是"文件少"，拒绝的理由要具体。

**标准回答**

因为 `task_queue.py` 在**导入时**就构造 Redis 连接和 Queue 单例：

```python
# app/core/task_queue.py:9-11
redis_conn = Redis.from_url(config.redis_url)
index_queue = Queue(config.rq_queue_name, connection=redis_conn)
protocol_pdf_queue = Queue("protocol_pdf_ingest", connection=redis_conn)
```

这是模块级代码，`import` 一下就执行。而 worker 模块只需要「读回 rid」这一个能力，不该为此被迫拉起队列单例 —— 那会让 worker 的单测**必须先准备好 redis 配置**。

`job_context.py` 只依赖 rq 的类型（`Queue`、`Job`）和 `get_current_job`，这些都是纯导入，不建连接。所以 worker 侧 `from app.core.job_context import with_job_request_id` 是零副作用的。

判断依据不是"文件大小"，而是「**这个模块被导入时会发生什么**」。有副作用的模块和纯函数模块混在一起，纯函数那部分就丧失了可独立测试的性质。

**真实代码**

理由写在模块 docstring 里：

```python
# app/core/job_context.py:17-20
为什么放在独立模块而不是 task_queue.py：
task_queue.py 在导入时会构造 Redis 连接与 Queue 单例。worker 模块只需要
「读回 rid」这一个能力，不该为此被迫拉起队列单例 —— 那会让 worker 的单测
必须先准备好 redis 配置。这里只依赖 rq 的类型与 get_current_job。
```

注意这个划分和依赖方向是一致的：`enqueue_with_request_id(queue, ...)` 把 queue 作为**参数**接收，而不是 import 一个具体的 queue。所以 `job_context` 不依赖 `task_queue`，两个 `*_job_queue.py` 才是把两者组装起来的地方（`app/services/index_job_queue.py:5-7` 同时 import 了两边）。

**追问链**

**追问 1：`Redis.from_url()` 在模块级执行，如果 Redis 不可用，import 会失败吗？**

不会。`Redis.from_url()` 是懒连接 —— 它只解析 URL 构造客户端对象，第一次真正发命令时才建 TCP 连接。所以 Redis 挂着的时候 import 照常成功，失败发生在 `queue.enqueue(...)` 那一刻，被上传接口的 `except` 接住转成 503（`app/api/file.py:141-146`）。

这个行为是对的：**import 期的失败最难诊断**（栈里全是框架，还可能触发级联的 import 错误），把失败推迟到实际调用点，错误信息才有上下文。反过来说，如果这里用的是立即建连的客户端，Redis 短暂抖动会导致整个 API 进程起不来。

**追问 2：模块级单例还有别的坑吗？**

有一个：**它把 fork 语义带进来了**。RQ worker 默认用 fork 执行任务，如果父进程已经建立了 Redis 连接，fork 出的子进程会继承那个 socket fd —— 两个进程共用一个连接，命令会互相错乱。RQ 内部对自己的连接处理了这个问题，但如果我们在任务函数里用 `app.core.task_queue.redis_conn` 做别的事（比如从任务里再入队一个任务），就要留意。

当前没踩到，因为任务函数里没有直接用 `redis_conn`。但这是个隐患，正确做法是 worker 侧要用 Redis 时通过 `get_current_job().connection` 拿 RQ 自己管理的那个。

**拓展**

`task_queue.py` 现在是硬编码的模块级单例，测试里想换掉只能 monkeypatch 模块属性。更干净的形态是一个 `get_queue(name)` 工厂加上 lru_cache —— 既保留单例语义，又让测试能清缓存。没做是因为当前只有两个队列、两个调用点，工厂函数带来的间接层大于收益（YAGNI）。等队列数量到五个以上、或者需要按环境切换连接参数时再改。

## 第五部分 · 会话与事务边界

### Q17. `create_engine(..., pool_pre_ping=True)` 解决什么问题？不开会怎样？

**考点**

考对连接池生命周期的理解。这个参数几乎是所有长驻 Python 服务的必选项，但很多人只知道"加上就对了"。

**标准回答**

解决**连接池里躺着死连接**的问题。

连接池的工作方式是：用完的连接不关，还回池里等下次复用。问题在于连接对面是数据库和中间的网络设备，它们有自己的超时策略：

- PostgreSQL 的 `idle_in_transaction_session_timeout`、`tcp_keepalives_idle`
- 云上的负载均衡器通常 350 秒或 5 分钟空闲就断
- 数据库重启、主从切换、容器重调度

这些都会让连接在服务端死掉，而**客户端毫不知情** —— TCP 的半开状态就是这样：对端发了 FIN 或者干脆没发，本地的 socket 依然是 ESTABLISHED。于是下一个请求取到这条连接，发出第一条 SQL，然后拿到 `OperationalError: server closed the connection unexpectedly`。

这个失败有两个恶劣特征：

1. **它是随机的**。取到哪条连接看运气，所以现象是"偶发 500"，重试一次往往就好了 —— 最难查的那种。
2. **它集中在低峰之后**。夜里没人用，连接闲置超时集体死掉；早上第一批请求全部撞上。所以症状常常是"每天早上有几个 500"，看起来像业务问题，其实是连接池。

`pool_pre_ping=True` 让 SQLAlchemy 在把连接交出去之前先发一个轻量探测（PostgreSQL 上是 `SELECT 1`）。探测失败就丢弃这条连接、重建一条，对上层完全透明。

代价是**每次取连接多一次往返**。同机房内是零点几毫秒，相对于任何真实查询都可以忽略。这是个几乎无脑该开的开关 —— 收益是消除一整类偶发故障，成本是可测量但无关紧要的延迟。

**真实代码**

```python
# app/core/database.py:15-18
engine = create_engine(
    config.database_url,
    pool_pre_ping=True,
)
```

**追问链**

**追问 1：`pool_recycle` 和 `pool_pre_ping` 是什么关系？该用哪个？**

两个思路：`pool_recycle=N` 是**预防式**的 —— 连接活过 N 秒就主动丢弃，不管它是否还好。`pool_pre_ping` 是**检测式**的 —— 不猜寿命，用之前问一句。

预防式要求你知道链路上最短的那个超时是多少，而这个值往往不在你手里（云 LB 的配置可能随时被平台调整，你不会收到通知）。猜大了照样撞死连接，猜小了白扔可用连接。检测式不需要知道任何超时值。

所以：**pre_ping 是通用解，recycle 是优化**。两个可以一起开 —— recycle 设一个保守值（比如 1800 秒）减少 pre_ping 探测到死连接的次数，pre_ping 兜住 recycle 猜错的情况。当前只开了 pre_ping，因为还没有到需要为一次探测往返做优化的量级。

**追问 2：pre_ping 之后是不是就不会遇到连接错误了？**

不是，它只覆盖「取连接的那一刻」。连接**在事务执行中途**断掉，pre_ping 帮不上 —— 探测通过之后、SQL 执行期间数据库重启，照样抛 `OperationalError`。

这正是第三部分那套失败抢救逻辑存在的原因：`record_job_failure` 用**独立的新 session** 写失败状态（`app/core/job_failure.py:160-161`），就是假设"当前这条连接已经废了"。pre_ping 减少了这种情况的发生率，但消除不了，所以失败路径必须能在连接已死的前提下工作。

**两层防御的分工：pre_ping 管「别拿到一开始就是坏的连接」，job_failure 管「用着的连接中途坏了怎么留痕」。**

**追问 3：worker 进程和 API 进程共用这个 engine 吗？连接数怎么算？**

不共用实例，但共用配置。`app/core/database.py` 是模块级的 engine，每个进程 import 时各自构造一个 —— API 进程一个池，每个 worker 进程一个池。

所以总连接数是「进程数 × 池大小」。SQLAlchemy 默认 `pool_size=5, max_overflow=10`，即每个进程最多 15 条。四个 uvicorn worker 加四个 RQ worker 就是 8 × 15 = 120 条，很容易撞上 PostgreSQL 默认的 `max_connections=100`。

当前没配显式的池大小，是个该关注的点：worker 是串行执行任务的，一个 worker 进程同时只需要 1–2 条连接（主 session + 抢救 session），给它 15 条纯属浪费。给 worker 侧配 `pool_size=2, max_overflow=3` 能省下大量连接额度。列进 Q30。

**拓展**

再往前一步是 **PgBouncer**：把连接池从应用侧移到数据库前面，应用连 PgBouncer，PgBouncer 复用少量真实连接。这样进程数增长不再线性推高数据库连接数。

代价是 transaction pooling 模式下不能用 session 级特性（prepared statement、`SET LOCAL`、advisory lock），需要检查代码里有没有依赖。当前架构（少量进程、简单查询）还用不上，但这是水平扩容 worker 时会先撞到的墙 —— **worker 数量的上限往往不是 CPU，是数据库连接数**。

### Q18. `sessionmaker(expire_on_commit=False)` 改变了什么？为什么要关掉这个默认行为？

**考点**

这题考对 SQLAlchemy 身份映射和过期机制的理解，同时考「关掉一个安全默认值」的判断能力。

**标准回答**

默认的 `expire_on_commit=True` 会在每次 `commit()` 后把 session 里所有对象标记为过期。下一次访问任何属性都会触发一次 `SELECT` 重新加载。

关掉它换来两件事：

**第一，commit 之后对象还能用。** 这在这个项目里是刚需，因为 repository 的方法普遍是「改属性 → commit → 返回对象」，调用方拿到对象要继续读属性。如果开着过期，`return document` 之后调用方每读一个字段就是一次数据库往返 —— 上传接口的响应体里读了 `document.id`、`status.value`、`version`、`content_hash` 四个字段，那就是四次 SELECT。

更糟的是 **worker 的失败路径**：`except` 块里如果要读原 session 中对象的属性来拼错误消息，而那条连接已经死了，过期机制会去 SELECT，然后抛出第二个异常 —— 又回到第三部分那个「二次异常顶掉原始异常」的坑。**关掉过期让失败路径少一个雷。**

**第二，省掉 `refresh()`。** 有了它，commit 之后的 `db.refresh(obj)` 在大多数情况下变成纯浪费 —— 一次白跑的 SELECT。

代价要说清楚：**session 里的对象可能是脏的**。别的进程改了同一行，本 session 里的对象不会自动看到。对这个项目是可接受的，因为对象生命周期都很短（一个请求或一个任务内），而且没有"长期持有一个对象并期待它跟数据库同步"的场景。

**真实代码**

```python
# app/core/database.py:20-25
SessionLocal = sessionmaker(
    bind=engine,
    autoflush=False,
    autocommit=False,
    expire_on_commit=False,
)
```

有一处代码直接用到了这个性质，注释写得很明确：

```python
# app/repositories/aiops_diagnosis_repository.py:166-169
        self.db.commit()
        # 不 refresh：SessionLocal 配了 expire_on_commit=False，
        # 提交后对象属性依然可读，refresh 只是白跑一次 SELECT。
        return event
```

**追问链**

**追问 1：那为什么别的方法还在 `commit()` 后调 `refresh()`？**

这是个真实的不一致。`create_task`（`app/repositories/aiops_diagnosis_repository.py:57-58`）、`advance_status`（`134`）、`create_ingestion`（`app/repositories/protocol_ingestion_repository.py:45-46`）都是 commit 完再 refresh，而 `record_phase` 明确指出了 refresh 是多余的。

要分两种情况看：

- **纯粹多余的**：对象所有字段都是应用层赋的值，refresh 只是把刚写进去的值再读回来。`advance_status` 属于这类。
- **有理由的**：对象有**数据库端生成**的字段，比如 `server_default` 的时间戳、自增序列、触发器算出来的列。这些值在 `INSERT` 之后才存在于数据库，Python 对象里是空的 —— 这时 refresh 是必需的。

这个项目里主键是 Python 侧 `uuid4()` 生成（`app/models/knowledge_base.py:36`），时间戳是 Python 侧 `default=_utcnow_naive` 生成（`51`），**没有任何数据库端生成的字段**。所以所有 refresh 都属于第一类，都可以删。

没删的原因诚实说是历史遗留 —— 早期按"commit 后 refresh"的通用范式写的，后来发现 `expire_on_commit=False` 让它没必要了，只在新写的 `record_phase` 里改了。这是个该统一的小欠账，收益是每次写操作省一次往返。

**追问 2：`expire_on_commit=False` 加上长生命周期 session，会出什么问题？**

会读到过期数据，而且**不报错**。假设一个 session 活了十分钟，期间别的进程把某行的 status 从 RUNNING 改成 FAILED，本 session 里那个对象仍然显示 RUNNING。基于它做判断就会错。

这就是为什么 session 的生命周期必须短且明确：API 侧是一个请求（`get_db` 的 `finally: db.close()`），worker 侧是一个任务（`finally` 里 close）。**`expire_on_commit=False` 是安全的，前提是没有人长期持有 session** —— 这两个设定是配套的，不能只抄一个。

**追问 3：如果确实需要一个对象的最新值怎么办？**

显式 `db.refresh(obj)`，或者 `db.expire(obj)` 让它下次访问时重新加载。关掉自动过期不等于失去了过期能力，只是把它从"每次 commit 全量过期"变成"需要时手工点名"。**默认行为该服务于常见情况，特殊情况用显式调用表达** —— 反过来（默认全量过期，然后到处想办法避免）会让性能敏感的代码充满 workaround。

**拓展**

`autoflush=False` 是同一批配置里另一个值得说的。默认的 autoflush 会在每次查询前自动把 pending 的改动 flush 到数据库，好处是查询能看到未提交的改动，坏处是**flush 的时机变得不可预测** —— 一个看起来只读的 `select` 可能触发写入并因约束冲突抛异常，栈里指向查询语句而不是那个有问题的赋值。

关掉之后 flush 只发生在显式调用 `flush()` 或 `commit()` 时。项目里有三处显式 flush，都是为了拿到自增/外键依赖的中间状态：

```python
# app/repositories/chat_run_trace_repository.py:78-82
    def _ensure_session(self, session_id: str) -> None:
        session = self.db.get(ConversationSession, session_id)
        if session is None:
            self.db.add(ConversationSession(id=session_id))
            self.db.flush()
```

这里必须 flush 而不能等 commit：紧接着要插入的 `ChatRunTrace` 有指向 `conversation_sessions` 的外键（`app/models/chat_run_trace.py:31-36`），父行不先落到数据库，子行插入就撞外键约束。**flush 而非 commit，是因为两者要在同一个事务里** —— 如果 trace 插入失败，补出来的那条空 session 行也该一起回滚。

### Q19. Repository 层每个方法内部都 `commit()`。这样设计有什么问题？

**考点**

这是本篇最该主动暴露的设计缺陷。面试官问 repository 模式，八成会问到事务边界。

**标准回答**

问题很明确：**事务边界被固定在了错误的层级上，导致跨 repository 无法共享事务。**

现在每个 repository 方法都是「改 → commit」的完整单元。这意味着服务层无法把两个 repository 的写操作组合成一个原子操作。举个具体的：协议 PDF 确认入库时要写 `protocol_records` / `protocol_equipment_mappings` / `protocol_detection_points` / `protocol_threshold_rules` 四张表，然后把 ingestion 状态改成 COMPLETED。如果这五件事分散在两个 repository 里各自 commit，中间任何一步失败就留下一个**协议库写了一半、ingestion 还是 WRITING** 的状态。

这个项目里没炸，是因为 `write_protocol_catalog` 刻意只用 `flush()` 不 commit（`app/repositories/protocol_ingestion_repository.py:141` 和 `156`），把提交权留给了调用链末尾的 `confirm_with_state_trace`。也就是说：**这个方法违反了本层的惯例，专门为了拿到事务组合能力。** 一个惯例需要被违反才能写对，说明惯例本身有问题。

正确的形态是 **Unit of Work**：repository 只负责 `add` / 改属性 / `flush`，事务的开始和提交由服务层或一个 UoW 上下文管理器控制：

```python
with unit_of_work() as uow:
    protocol_repo(uow).write_catalog(...)
    ingestion_repo(uow).mark_completed(...)
# 退出时统一 commit，异常时统一 rollback
```

这样事务边界跟**业务边界**对齐，而不是跟方法边界对齐。

**真实代码**

现在的形态，`knowledge_repository.py` 里每个写方法都自带 commit：

```python
# app/repositories/knowledge_repository.py:102-110
    def replace_chunks(self, document_id: str, chunks: list[KnowledgeChunk]) -> None:
        old_chunks = self.db.scalars(
            select(KnowledgeChunk).where(KnowledgeChunk.document_id == document_id)
        ).all()
        for chunk in old_chunks:
            self.db.delete(chunk)
        for chunk in chunks:
            self.db.add(chunk)
        self.db.commit()
```

而 `aiops_diagnosis_repository` 已经在往正确方向挪了 —— 它把「不提交的私有方法」和「提交的公开方法」分开，让前者可组合：

```python
# app/repositories/aiops_diagnosis_repository.py:86-98
    def _apply_status(self, task, status, *, phase=None) -> None:
        """就地推进状态，**不提交**。非法跃迁抛 ValueError。

        抽成不提交的私有方法，是为了让「推进状态」和「落一条事件」
        能被组合进同一个事务（见 record_phase）。
        状态跃迁的合法性校验只有这一处实现（DRY）。
        """
```

**追问链**

**追问 1：`record_phase` 具体解决了什么？收益能量化吗？**

能，而且这个 docstring 是全项目写得最清楚的一处：

```python
# app/repositories/aiops_diagnosis_repository.py:146-161
    """一次事务内完成「推进状态 + 追加时间线事件」。

    **为什么要有这个方法**

    原来编排层每个阶段都要写两行：`advance_status(...)` 再 `add_event(...)`，
    两个方法各自 `commit()`。一次告警诊断因此产生 9 次提交，
    而真正的业务边界只有 5 个。多出来的往返除了拖慢链路，
    还制造了一个可观测的不一致窗口：状态已经是 RETRIEVING，
    但时间线上还没有对应的事件 —— 此刻查详情接口会看到一个
    「正在检索但没人记录它开始了」的任务。

    状态与事件是同一件事的两个面（一个给程序判断，一个给人阅读），
    本就该原子地一起落库。

    `status=None` 表示只记事件不改状态 —— 用于阶段**结束**时补记耗时，
    那不是一次新的状态跃迁。
    """
```

**9 次提交 → 5 次**，减少的不只是往返：每次多余的提交都开了一个**不一致窗口**。状态已经改了、事件还没落，这个窗口里查详情接口会看到「任务在 RETRIEVING 但时间线最后一条是 planning」。窗口很短，但它是真实可观测的 —— 而且并发查询下必然有人撞上。

**追问 2：失败路径上这个窗口的危害更大吗？**

大得多，`mark_failed` 的 docstring 点出了这一点：

```python
# app/repositories/aiops_diagnosis_repository.py:181-184
    `event_message` 非空时，顺手在**同一个事务**里落一条 `failed` 事件。
    失败路径上这一点尤其重要：原来是 mark_failed 提交完、再 add_event 提交，
    中间那一瞬如果进程被 kill，任务已经是 FAILED 但时间线上找不到原因 ——
    排障时最需要的那条记录，恰好是最容易丢的一条。
```

「排障时最需要的那条记录，恰好是最容易丢的一条」—— 这跟第三部分那个 bug 是同一个模式的两个实例：**失败处理路径上的每一次额外提交，都是一次丢失失败原因的机会。**

`save_report` 也是同样的处理（`app/repositories/aiops_diagnosis_repository.py:210-212`）：「报告已存但时间线停在 diagnosing 的任务，看起来像是『卡住了』，而它其实早就跑完了」。

**追问 3：那 `add_event` 为什么还留着？**

因为确实有「只记一条事件、不伴随状态变化、也不和别的写操作同批」的场景。docstring 里给了明确的使用边界：

```python
# app/repositories/aiops_diagnosis_repository.py:242-246
        """向任务追加一条时间线事件（独立事务）。

        当「记事件」不伴随任何状态变化、也不和别的写操作同批时用它；
        否则优先用 record_phase / save_report / mark_failed 的内联事件参数，
        少一次提交，也少一个不一致窗口。
        """
```

**留着一个次优的 API，但在文档里标明什么时候该用另一个** —— 比强行删掉逼所有调用点绕路要好。前提是这个"什么时候"写得足够具体。

**拓展**

引入 UoW 的成本要算清楚：它会改动所有 repository 的方法签名（`__init__(self, db)` 变成接收 UoW 或 Session）和所有调用点。当前有 5 个 repository、几十个调用点。

我会分两步做，而不是一次性重构：

1. **先给需要组合的地方补「不提交的私有方法 + 提交的公开方法」这一对**，就像 `_apply_status` / `advance_status` 那样。零破坏性，收益立刻可见。
2. 等到出现**第三个**跨 repository 的原子需求时再上 UoW —— 两个还能用 flush 硬扛，三个就说明这是常态而非例外。

现在只有协议 PDF 确认那一处，用 flush 扛住了。**没到那个点就上 UoW 是过度设计，到了那个点还不上就是技术债** —— 判断标准是需求出现的频次，不是模式的优雅程度。

### Q20. API 侧用 `get_db()` 依赖注入拿 session，worker 侧直接 `SessionLocal()`。为什么不统一？

**考点**

考对「依赖注入的适用边界」的理解。统一是好事，但统一到不适合的地方就是教条。

**标准回答**

因为两边的**生命周期管理者不同**。

`get_db()` 是个生成器依赖，FastAPI 在请求结束时负责走到 `finally` 关掉它：

```python
# app/core/database.py:28-33
def get_db() -> Generator[Session, None, None]:
    db = SessionLocal()
    try:
        yield db
    finally:
        db.close()
```

这套机制依赖 FastAPI 的请求生命周期。worker 里没有请求、没有 FastAPI，`Depends(get_db)` 无从注入 —— 硬要用就得手工驱动生成器（`next(gen)` 然后手工 `gen.close()`），比直接 `SessionLocal()` 加 `try/finally` 更绕、更容易漏。

worker 侧就直接写清楚：

```python
# app/workers/index_worker.py:30
    db = SessionLocal()

# app/workers/index_worker.py:145-147
    finally:
        with suppress(Exception):
            db.close()
```

注意 worker 的 `close()` 包在 `suppress` 里，而 `get_db` 的没有 —— 这个差别是有理由的。API 侧 close 失败会被 FastAPI 的异常处理接住转成 500，是可接受的；worker 侧 close 抛异常会从 `finally` 逃出去，**顶掉正在往外传的原始异常**，正是第三部分要消灭的那个 bug。`finally` 里的异常优先级高于正在传播的异常，这是 Python 的语言规则，所以 worker 的 finally 必须是绝对安全的。

**共用的是 `SessionLocal` 这个工厂（配置统一），不共用生命周期管理方式（因为管理者不同）。** 该统一的是配置，不是调用形式。

**追问链**

**追问 1：worker 里为什么不用 `with SessionLocal() as db:`？SQLAlchemy 的 Session 支持上下文管理器。**

支持，而且 `with` 退出时会自动 close。但这里的 `try/except/finally` 结构中，`except` 块要做的事很多（裁决重试、拼消息、rollback、用新 session 抢救、打日志、raise），用 `with` 包起来之后这些还是得写在 `with` 内部的 try 里 —— 嵌套一层却没省掉任何东西。

真正的理由是 **close 必须被 suppress 包住**。`with` 语句的 `__exit__` 里那个 close 是 SQLAlchemy 控制的，我没法给它套 suppress。连接已断时 close 会抛，那个异常会顶掉原始异常。所以这里必须手写 finally。

**这是个「语言糖在失败路径上不够用」的例子** —— `with` 的清理动作不可干预，而失败路径恰恰需要"清理动作自己失败时也不能出声"。

**追问 2：`get_db()` 里为什么没有 `commit()` 或 `rollback()`？很多项目会在这里统一处理。**

因为提交责任在 repository 层（见 Q19）。`get_db` 只管创建和关闭，不碰事务语义。

这个划分有个好处：**session 的所有权和事务的所有权分开了。** 如果 `get_db` 在 finally 里 commit，那么请求处理到一半抛异常时，未完成的改动可能被提交上去 —— 要避免就得判断"有没有异常"，于是 `get_db` 开始理解业务语义，职责就糊了。

不 commit 的代价是：忘记 commit 的改动会在 close 时被静默丢弃。SQLAlchemy 的 `close()` 会 rollback 未提交的事务，没有任何警告。这个代价靠"repository 方法必然 commit"的惯例兜住 —— 而这个惯例正是 Q19 里说的那个双刃剑。

**追问 3：一个请求里如果有两个 repository，它们拿到的是同一个 session 吗？**

是。`Depends(get_db)` 在单次请求内是缓存的，两次 `Depends(get_db)` 返回同一个 Session 对象。所以 `KnowledgeRepository(db)` 和别的 repository 拿到的 db 是同一个。

这也是为什么 Q19 那个问题**有解的可能** —— 底层 session 本来就是共享的，缺的只是"谁来决定 commit 时机"。UoW 要做的不是让它们共享 session（已经共享了），而是把 commit 的调用点从 repository 挪到上层。**这让重构的难度比听起来小：不需要改变对象的传递路径，只需要移动 commit 语句。**

**拓展**

worker 侧现在每个任务函数开头一句 `SessionLocal()`、finally 一句 close，两个 worker 各写一遍。可以抽成和 `with_job_request_id` 平级的装饰器：

```python
@with_job_request_id
@with_job_session          # 注入 session，finally 里安全 close
def run_index_job(job_id: str, db: Session) -> None:
```

### Q21. `sessionmaker` 里关掉了 `autoflush`，可 repository 里又有五处手动 `flush()`。这不矛盾吗？

**考点**

这题能筛掉一大半人。很多人用了几年 SQLAlchemy 都说不清 `flush` 和 `commit` 的区别，更说不清 `autoflush` 关掉之后**多出来的责任是什么**。

**标准回答**

不矛盾，因为关掉的是**自动时机**，不是这个能力本身。

`flush()` 是把内存里的挂起变更翻译成 SQL 发给数据库，但**不提交**；`commit()` 是先 flush 再提交事务。两者的区别是「数据库看得见了」和「别的连接看得见了」。

`autoflush=True`（默认）的含义是：每次执行查询前，SQLAlchemy 先偷偷 flush 一遍挂起的对象，好让这次查询能看到它们。听起来很贴心，代价是**异常出现的位置和真正的错误位置不一致**。

具体的坑长这样：你 `add()` 了一个还没填完必填字段的对象，接着写了一行 `select` 去查别的东西。autoflush 在这个 `select` 之前把半成品刷进数据库，于是 `NOT NULL violation` 从那行 `select` 抛出来。你盯着一句纯读的语句看半小时，而真正的问题在上面二十行的 `add()` 那里。**这类 bug 的调试成本远高于「我忘了 flush」。**

关掉之后，flush 的时机变成显式的，我在两种情况下必须手动调：

**第一种：需要拿主键。** 项目的主键是 Python 侧默认值 `default=lambda: str(uuid4())`（`app/models/protocol_catalog.py`、`knowledge_base.py:36` 等都是这个形状）。关键在于 —— SQLAlchemy 的 Python 侧 `default` 是在 **INSERT 时**求值的，不是在构造对象时。也就是说 `add()` 之后 `obj.id` 还是 `None`，必须 flush 一次才有值。

**第二种：让同一事务里的后续操作看见这一行。** 比如插一条消息前要保证会话行存在（外键），或者写协议明细前要先有协议主记录。

**真实代码**

配置：

```python

    bind=engine,
    autoflush=False,
    autocommit=False,
    expire_on_commit=False,
)
```

第一种情况 —— 拿主键。`app/repositories/protocol_ingestion_repository.py:253-263`：

```python

    self.db.flush()          # ← 没这一行，下面的 mapping.id 是 None
```

第二种情况 —— 外键可见性。`app/repositories/chat_run_trace_repository.py:78-82`：

**追问链**

**追问 1：既然要手动 flush，那 `autoflush=True` 让它自动做不是更省事？漏掉 flush 的风险不就没了吗？**

省事，但换来的是**错误位置的错乱**，这个代价更大。而且 autoflush 有个更阴的行为：它会在你**只是想读一下**的时候写库。举个真实会踩的例子 —— 一个方法里 `add()` 了对象但决定回滚（业务校验没过），在 `rollback()` 之前如果有任何一句 `select`，autoflush 已经把那个对象 INSERT 进去了。虽然 rollback 会撤销，但如果这个 INSERT 撞了唯一键，异常会从 `select` 抛出，整段逻辑崩在一个和它无关的地方。

更根本的理由：**关掉 autoflush 之后，"数据库在什么时刻被写入"这件事变成代码里可读的**。看到 `flush()` 就知道这里发生了一次往返；没看到就知道没有。autoflush 打开时，任何一句 `select` 都可能是隐藏的写点，读代码没法判断。

**追问 2：`flush()` 之后如果事务回滚了，那些 flush 出去的数据怎么办？**

一起回滚，flush 不是提交。flush 只是把 SQL 发出去让数据库执行，数据停在事务内 —— 别的连接看不到（默认隔离级别下），rollback 一样能撤销。

这一点正是 `_ensure_session` 用 flush 而不是 commit 的依据：会话行和 trace 行在同一个事务里，`create_trace` 最后那次 `commit()`（第 59 行）一起提交。中间任何一步失败，两行都不留 —— 不会有孤立的空会话。

**追问 3：`autoflush=False` 有没有反过来咬人的时候？**

有，而且形态是「查不到刚写的东西」。同一个 session 里 `add()` 之后用 `select` 去查它，查不到（因为 INSERT 还没发出去）。

但 `db.get(主键)` 是个例外 —— 它先查 identity map，能拿到内存里那个挂起的对象。所以 `_ensure_session` 里 `self.db.get(...)` 在同一请求内第二次调用时能命中，不会重复 add。**这个区别（`get` 走 identity map、`select` 走数据库）是关掉 autoflush 之后必须知道的细节**，否则会写出「明明 add 过却又 add 一遍」的重复插入。

**拓展**

- **`flush()` 的显式性可以更进一步**：现在 flush 散落在五处，靠注释和惯例维持。更强的做法是给需要 id 的地方封一个 `add_and_flush(obj)` 辅助函数，把「add 完必须 flush 才有 id」这个知识编码进函数名，而不是留给每个调用点记住。
- **`autoflush=False` 应该有测试锁住**：现在这是个配置项，谁改成 True 都不会有测试失败，但会引入上面说的错乱。可以加一个断言 `SessionLocal.kw["autoflush"] is False` 的用例 —— 一行代码，锁住一个容易被"顺手优化"掉的决定。这跟 26 篇里用测试锁住设计承诺是同一个手法。

## 第六部分 · 状态机与幂等

### Q22. AIOps 诊断任务有个状态跃迁表。为什么要显式维护它？直接赋值 `task.status = X` 不行吗？

**考点**

考「非法状态是不是一种 bug」。很多人觉得状态字段就是个 enum 列，赋值就完事；能说清「非法跃迁必须在写入时就拦住」的人，理解的是**数据库里的脏状态修不回来**。

**标准回答**

不行，因为**状态字段的合法值集合和合法跃迁集合是两件事**。

Enum 类型只能保证「值在六个之内」，保证不了「从 DONE 不能回到 PLANNING」。而后者被破坏的后果是持久的：一条已经产出报告的任务被改回 PLANNING，报告还在 `report` 列里，状态却说它还在计划阶段。**页面上这条任务永远转圈，而它其实早就跑完了** —— 和 25 篇讲的「停在 RUNNING 的僵尸任务」是同一种脏数据，只是成因是代码写反了而不是进程死了。

更麻烦的是这种脏状态**没有自愈路径**。跑完的任务不会再跑一次，没有任何代码会把它推回 DONE。要修只能人工写 UPDATE。

所以校验必须放在**写入路径上**，而且只有一处实现。放在 service 层不行 —— service 有五六个调用点，每个都得记得校验，漏一个就是缺口。放在 repository 层，就是所有写入的必经关口。

至于 `src == dst` 视为合法，是为了**幂等**：重试或重复调用时把 RETRIEVING 再写一遍 RETRIEVING，语义上什么都没发生，不该报错。异步任务和重试机制是同时存在的，不允许幂等重入等于给自己埋雷。

**真实代码**

跃迁表和判定函数放在 model 层（`app/models/aiops_diagnosis.py:53-76`）：

```python
_ALLOWED_TRANSITIONS: dict[DiagnosisTaskStatus, set[DiagnosisTaskStatus]] = {
    DiagnosisTaskStatus.NEW: {DiagnosisTaskStatus.PLANNING, DiagnosisTaskStatus.FAILED},
    DiagnosisTaskStatus.PLANNING: {
        DiagnosisTaskStatus.RETRIEVING,
        DiagnosisTaskStatus.FAILED,
    },
    DiagnosisTaskStatus.RETRIEVING: {
        DiagnosisTaskStatus.DIAGNOSING,
        DiagnosisTaskStatus.FAILED,
    },
    DiagnosisTaskStatus.DIAGNOSING: {
        DiagnosisTaskStatus.DONE,
        DiagnosisTaskStatus.FAILED,
    },
    DiagnosisTaskStatus.DONE: set(),
    DiagnosisTaskStatus.FAILED: set(),
}


def can_transition(src: DiagnosisTaskStatus, dst: DiagnosisTaskStatus) -> bool:
    """判断状态跃迁是否合法。相同状态视为幂等允许。"""
    if src == dst:
        return True
    return dst in _ALLOWED_TRANSITIONS.get(src, set())
```

三处结构值得注意：

1. **每个中间态都能转 FAILED**，因为任何阶段都可能出异常。这不是网开一面，是必需的 —— 失败路径必须永远走得通，否则异常发生时连状态都落不下去，又回到 25 篇那个「监控盯着 FAILED 却永不告警」的困境。
2. **DONE 和 FAILED 的出边是空集**，明确表达「终态不可再变」。用空 `set()` 而不是把它们从字典里省掉，是为了让「终态」这件事在表里**看得见**；省掉的话 `.get(src, set())` 也能返回空集，但读表的人不知道那是刻意的还是漏了。
3. **表放在 model 层而不是 repository 层**。状态机是领域知识（这个任务能怎么流转），不是存储细节。放在 model 层，未来加个「导出状态机图」的工具或在 API 层做前置校验都能直接复用。

repository 层是唯一的执行点（`app/repositories/aiops_diagnosis_repository.py:86-104`）：

```python
def _apply_status(self, task, status, *, phase=None) -> None:
    """就地推进状态，**不提交**。非法跃迁抛 ValueError。

    抽成不提交的私有方法，是为了让「推进状态」和「落一条事件」
    能被组合进同一个事务（见 record_phase）。
    状态跃迁的合法性校验只有这一处实现（DRY）。
    """
    if not can_transition(task.status, status):
        raise ValueError(f"非法状态跃迁: {task.status.value} → {status.value}")
    task.status = status
    task.current_phase = phase or status.value
```

**追问链**

**追问 1：非法跃迁抛 `ValueError`。这是编程错误还是运行时错误？异常类型选得对吗？**

选得不算好，这是个真实的可改进点。

非法跃迁本质是**编程错误** —— 编排逻辑写反了顺序，或者对状态机理解有误。它不该发生在正确的代码里，跟「LLM 超时」这种运行时故障是完全不同的东西。用 `ValueError` 的问题是：它会被 worker 的 `except Exception` 捕获，然后走完整套「裁决重试 → 落盘 FAILED」的流程。而按 25 篇那套分类，未知异常默认**不可重试**，所以行为上没错 —— 重试一个写反了的编排三次确实毫无意义。

但它会被记成一次业务失败，混在「Milvus 挂了」「PDF 坏了」这些真故障里。更合适的做法是定义一个 `IllegalStateTransition(AppError)`，`code="illegal_state_transition"`、`retryable=False`。这样它在 `error_code` 维度上就和真故障分开了 —— 这类错误的正确处置是**改代码**，不是修环境，混在一起会污染故障统计。列进 Q30 的 P2。

**追问 2：`can_transition` 里 `src == dst` 返回 True。会不会掩盖真正的重复执行 bug？**

会，这是这个设计明确接受的代价。

比如编排逻辑因为写错循环，把 RETRIEVING 连写了三遍 —— 幂等允许下这三次都静默通过，没有任何信号。想发现它得靠别的手段：事件时间线上会出现三条同 phase 的事件（`record_phase` 每次都追加事件），看详情接口能看出异常。

选择幂等而不是严格拦截的理由是**权衡后果的不对称**：拦截重复写入的收益是「早点发现一个编排 bug」，代价是「重试机制下正常的重入被判成错误，任务白白失败」。后者会伤到用户，前者只是少一个调试便利。而且重试是异步任务的常态，不是异常情况 —— 为了抓罕见 bug 让常态路径变脆，方向反了。

**追问 3：这个跃迁表有测试吗？怎么测才算测到位？**

有 `tests/unit/test_aiops_diagnosis_repository.py`。测到位的标准是**两个方向都测**：合法跃迁能过、非法跃迁抛异常。只测前者的话，把 `can_transition` 改成 `return True` 测试全绿 —— 这个测试等于没测。

更彻底的做法是**穷举**：六个状态两两组合 36 对，断言只有表里那 8 条加 6 条自反的能过。跃迁表就 20 行，穷举测试的代价很低，而收益是**任何人往表里加一条边都必须同步改测试** —— 强迫他明确表达「我知道我在放开一条新路径」。这跟 26 篇里用测试锁住 label 集合是同一个手法：**把有限枚举穷举掉，比抽样测几个典型值可靠得多。**

**拓展**

- **状态机图自动生成**：`_ALLOWED_TRANSITIONS` 是纯数据，能直接渲染成 Mermaid 或 DOT 图贴进文档。现在 `DiagnosisTaskStatus` 的 docstring 里手画了一张 ASCII 图（`app/models/aiops_diagnosis.py:31-34`），它和表是两份需要同步维护的真相 —— 图从表生成才是对的。
- **其他状态机也该有跃迁表**：`DocumentStatus`、`IndexJobStatus`、`ProtocolIngestionStatus` 目前都只有 enum，没有跃迁约束。`ProtocolIngestionStatus` 有九个值、状态流转最长（PENDING → EXTRACTING → STRUCTURING → VALIDATING → AWAITING_CONFIRMATION → WRITING → COMPLETED，另有 FAILED / REJECTED 两个终态），最需要这层保护，却恰恰没有 —— 它的状态推进散落在 `set_status` / `save_dry_run` / `confirm_with_state_trace` / `reject` 四个方法里各自直接赋值。这是本篇里最该补的一处。

### Q23. `record_phase` 把「推进状态」和「记一条事件」合进了一个事务。为什么？拆成两次调用不是更清晰吗？

**考点**

考事务边界的划分依据。这是个有真实收益数字的改动（9 次提交降到 5 次），但更值钱的答案是**那个不一致窗口**。

**标准回答**

拆开有两个问题，第二个才是主要的。

**第一个是往返次数。** 原来编排层每个阶段写两行：`advance_status(...)` 然后 `add_event(...)`，两个方法各自 `commit()`。一次告警诊断因此产生 9 次提交，而真正的业务边界只有 5 个 —— 多出来的 4 次纯属浪费，每次都是一个网络往返加一次 WAL 落盘。

**第二个是可观测的不一致窗口。** 两次 commit 之间存在一个真实的时间片，此时数据库的状态是：`task.status` 已经是 RETRIEVING，但时间线上还没有对应的事件。这个瞬间去查详情接口，会看到一个**「正在检索，但没有任何记录说它开始检索了」的任务**。

单看这个窗口很短（几毫秒），但它有两个放大器：一是查详情是个高频操作（前端轮询进度），二是进程可能在这个窗口里死掉 —— 那样不一致就从「几毫秒」变成「永久」。

判断依据是：**状态与事件是同一件事的两个面** —— 一个给程序判断（status 列驱动前端渲染和后续流转），一个给人阅读（时间线告诉人发生了什么）。它们描述的是同一个事实，本就该原子地一起落库。拆成两个事务等于允许「同一个事实的两个面互相矛盾」。

**真实代码**

`app/repositories/aiops_diagnosis_repository.py:137-169`：

```python
def record_phase(self, task, *, phase, status=None, message=None, payload=None):
    """一次事务内完成「推进状态 + 追加时间线事件」。
    ...
    `status=None` 表示只记事件不改状态 —— 用于阶段**结束**时补记耗时，
    那不是一次新的状态跃迁。
    """
    if status is not None:
        self._apply_status(task, status, phase=phase)
    event = self._new_event(task.id, phase=phase, message=message, payload=payload)
    self.db.commit()
    # 不 refresh：SessionLocal 配了 expire_on_commit=False，
    # 提交后对象属性依然可读，refresh 只是白跑一次 SELECT。
    return event
```

能这样组合的前提，是 `_apply_status` 和 `_new_event` 两个私有方法**都不提交**（第 86-122 行）。这是个刻意的设计：把「改内存对象」和「提交事务」分开，提交的时机才能由调用方决定。如果 `_apply_status` 内部就 commit，就不可能有 `record_phase` 这个方法。

同样的模式在失败路径和成功路径上都用了（`mark_failed:171-197`、`save_report:199-231`），而且失败路径上的理由更硬：

```python
"""把任务标记为 FAILED，记录错误原因。任何状态都可转 FAILED。

`event_message` 非空时，顺手在**同一个事务**里落一条 `failed` 事件。
失败路径上这一点尤其重要：原来是 mark_failed 提交完、再 add_event 提交，
中间那一瞬如果进程被 kill，任务已经是 FAILED 但时间线上找不到原因 ——
排障时最需要的那条记录，恰好是最容易丢的一条。
"""
```

**「排障时最需要的那条记录，恰好是最容易丢的一条」** —— 这跟 25 篇那个「越是基础设施故障，越会丢失真实原因」是同一个结构：**失败路径上的薄弱环节，专门在你最需要它的时候断掉。**

`save_report` 的版本也一样（第 210-213 行）：报告已存但时间线停在 diagnosing 的任务，「看起来像是卡住了，而它其实早就跑完了」。

`add_event` 保留下来作为独立事务的版本（第 234-255 行），docstring 明确划了适用边界：

```python
"""向任务追加一条时间线事件（独立事务）。

当「记事件」不伴随任何状态变化、也不和别的写操作同批时用它；
否则优先用 record_phase / save_report / mark_failed 的内联事件参数，
少一次提交，也少一个不一致窗口。
"""
```

**追问链**

**追问 1：`record_phase` 里 `status=None` 表示只记事件不改状态。这个可选参数会不会让接口语义变含糊？**

有这个风险，但这里的区分是有实际含义的：**阶段开始**是一次状态跃迁（PLANNING → RETRIEVING），**阶段结束**只是补记一条耗时事件，状态不动（它还在 RETRIEVING，直到下一个阶段开始）。

如果不允许 `status=None`，阶段结束就只能调 `add_event`，那又变回两个方法、两次提交。所以这个可选参数换来的是「一个方法覆盖时间线上的所有写入点」。

代价是 `record_phase(task, phase="x")` 这种调用读起来不明显 —— 光看调用点不知道状态会不会变。改进方向是拆成两个名字明确的方法：`enter_phase(task, status, phase)` 和 `note_phase(task, phase, message)`，共用底层的不提交私有方法。**同一个实现、两个语义清晰的入口**，比一个带可选开关的方法好读。这是个纯命名改进，没做只是因为调用点不多。

**追问 2：`record_phase` 里不 `refresh` 而 `create_task` 里 refresh 了。标准不一致吧？**

不一致，而且这个不一致是有理由的，但理由没写在代码里 —— 算个可读性欠账。

`create_task`（第 58 行）refresh 是因为**新建对象需要拿数据库生成的值**。虽然主键是 Python 侧 uuid，但 `created_at` 这类 `default=_utcnow_naive` 也是 Python 侧的… 严格说这次 refresh 确实可以省。它更多是「新建后返回一个确定同步的对象」这个习惯。

`record_phase` 明确不 refresh，注释写了依据：`expire_on_commit=False`（见 Q18），提交后对象属性依然可读，refresh 只是白跑一次 SELECT。

一致的标准应该是：**只有确实需要读取数据库生成值（`server_default`、触发器、自增主键）时才 refresh**。按这个标准，项目里现有的 refresh 大部分都可以去掉 —— 因为所有默认值都是 Python 侧的。这是个成体系的小优化，收益是每次写操作少一次 SELECT 往返。列进 Q30 的 P3。

**追问 3：这个「9 次提交降到 5 次」的数字是实测的还是估的？**

是数出来的：诊断流程有 5 个阶段，改之前每个阶段两次提交（状态 + 事件）本该是 10 次，但第一个阶段的状态是建任务时一起写的，所以实际 9 次。改之后每阶段一次，5 次。

诚实地说，**这个数字本身不是主要收益**。5 次网络往返对一个总耗时几十秒的诊断流程来说微不足道。真正的收益是那个不一致窗口，往返次数只是顺带的。面试时把次数当主要理由讲反而会被追问「你测过这 4 次往返占多少耗时吗」—— 答不出来就显得是在拿听起来像优化的东西凑数。

**拓展**

- **事件表的写入可以异步化**：时间线事件是纯追加的观测数据，理论上可以攒批或异步写。但那会重新引入不一致窗口，方向和本题相反。真要优化，先测量事件写入到底占多少耗时 —— 大概率是 0.1% 以下，属于 26 篇讲的「没测量就不该优化」。
- **`state_trace` 与事件表的重复**：协议 PDF 那条链路把状态历史存在 `protocol_pdf_ingestions.state_trace` 这个 JSON 列里（`app/models/protocol_ingestion.py:63`），而 AIOps 用的是独立的 `aiops_diagnosis_events` 表。两套机制解决同一个问题。JSON 列的好处是随主记录一起读、无需 join；坏处是没法跨任务聚合（「所有任务的 validating 阶段平均耗时」这种查询做不了）。哪种对取决于要不要聚合 —— 而这正是 26 篇 span 表选独立表的理由。**同一个项目里两种选择并存不算错，但应该有一份文档说清各自的适用边界**，否则下一个人加功能时只能靠猜。

### Q24. 同一个文件重复上传两次会怎样？你的去重是怎么做的？

**考点**

考幂等的实现层次。八成的人会答「算 hash 去重」—— 但这只回答了「怎么判断重复」，没回答「判断出重复之后做什么」。真正的分水岭是：**能不能说清哪种重复该跳过、哪种重复必须重做、以及两次上传撞在一起时会发生什么**。

**标准回答**

去重是三分支的，键是 **sanitize 后的文件名**，`content_hash` 只用来在同名的前提下判断内容有没有变：

1. **没查到同名文档** → 全新创建，入队索引。
2. **同名 + hash 相同 + 状态是 `INDEXED`** → 复用，**不入队**，返回 200 `reused`。
3. **其它情况**（同名但内容变了 / 上次失败了 / 还停在 pending）→ 原地更新，`version + 1`，状态重置回 `PENDING`，清掉旧的 `error_message`，重新入队。

分支 2 的三个条件必须同时成立，缺一个都不能跳过索引。`hash` 相同但状态是 `FAILED`，说明上次索引没做完，向量库里可能什么都没有 —— 这时候「内容没变」不是跳过的理由，反而是**必须重试**的理由。这一条是最容易写错的地方：只比 hash 就跳过，等于把上次的失败永久固化了，用户重传多少次都不会好。

分支 2 的价值是省 embedding 调用。重传一份没变的文档跳过索引，省的是最贵的那一步（一次 embedding 是网络往返 + 计费）。

**真实代码**

`app/api/file.py:84-134`：

```python
# 去重:按 sanitize 后的 filename 查同名(未软删)文档
existing = repo.get_document_by_filename(safe_filename)

if existing is None:
    document = repo.create_document(...)
    reused = False
elif (
    existing.content_hash == content_hash
    and existing.status == DocumentStatus.INDEXED
):
    # 同名+内容没变+已索引完成 → 复用,跳过索引(省 embedding)
    return JSONResponse(status_code=200, content={..., "reused": True})
else:
    # 同名但内容变了 / 之前失败 / pending → 更新现有记录,版本号 +1
    document = repo.update_document_for_reupload(...)
```

查询侧刻意排掉了软删的记录（`app/repositories/knowledge_repository.py:60-68`），所以删掉之后同名再传会走分支 1、拿到一个新 id：

```python
stmt = (
    select(KnowledgeDocument)
    .where(KnowledgeDocument.filename == filename)
    .where(KnowledgeDocument.status != DocumentStatus.DELETED)
    .order_by(KnowledgeDocument.created_at.desc())
)
return self.db.scalars(stmt).first()
```

**追问链**

**追问 1：两个人同时传同一个文件名会怎样？**

会出问题，而且这是这段代码目前最大的漏洞：**并发重传没有任何互斥**。

具体过程：请求 A 和 B 同时传 `report.md`。两边都查到同一条 `existing`（状态 `INDEXING`），都走分支 3，都 `version + 1`（结果是 2 而不是 3，一次更新被覆盖），都 `create_index_job`，两个 job 都进队列。

两个 job 跑起来之后，各自都会执行 `vector_store_manager.delete_by_document_id(document.id)`（`app/workers/index_worker.py:58`）再插入。交错的顺序决定结果：
- A 删 → B 删 → A 插 → B 插：向量库里同一份内容存了两遍，检索会返回重复片段。
- A 删 → A 插 → B 删 → B 插：侥幸正确。

chunk 表同理。`replace_chunks` 是「删旧的 + 插新的」一个事务（`app/repositories/knowledge_repository.py:102-110`），但 `(document_id, chunk_index)` **没有唯一约束**（见 `app/models/knowledge_base.py:65-81`），所以两轮插入可以并存，同一个 `chunk_index` 出现两行。

修法有三档，代价递增：
1. **加唯一约束** `(document_id, chunk_index)` —— 不解决竞争，但让它**响亮地失败**而不是静默产生重复数据。一行迁移，应该立刻做。
2. **状态守卫**：分支 3 里如果 `existing.status == INDEXING`,直接返回 409「上一次索引还在进行」。简单、够用，代价是用户偶尔要重试。
3. **PostgreSQL advisory lock**：`pg_advisory_xact_lock(hashtext(filename))`，把「查 + 判分支 + 写」整段串行化。彻底，但引入了一个跨请求的锁，要考虑 API 进程被卡住的情况。

我会选 1 + 2。3 属于「并发上传真成为常态之后」才值得付的成本。

**追问 2：为什么去重键是文件名而不是 `content_hash`？用 hash 做键不是更准吗？**

用 hash 做键会得到不同的语义，而且不是我要的那个。

hash 做键意味着「同内容不同名视为同一份」。但知识库里 `filename` 是**用户看得见的标识** —— 用户在文档列表里看到的是名字，删除按钮删的是名字对应的那条。如果 `SOP-v1.md` 和 `SOP-copy.md` 内容相同被合并成一条，用户删掉「SOP-copy」的时候会发现「SOP-v1」也消失了。**去重键必须和用户心里的身份认同一致**，否则删除和更新的行为都会显得诡异。

代价是同内容不同名会重复 embedding 一遍。这个代价我认，因为它只多花钱，不产生用户困惑。

真正的问题在另一头：**文件名做键，意味着不同内容同名会覆盖**。而这个覆盖是**物理不可逆**的 —— `app/api/file.py:65-67` 在写新文件之前先 `unlink()` 了旧文件：

```python
if file_path.exists():
    logger.info(f"文件已存在，将覆盖: {file_path}")
    file_path.unlink()
```

所以 `version` 列虽然一直在加，但**只有最新一版的内容真实存在**。`version = 5` 给人一种「有五个历史版本」的印象，实际上前四版的字节已经没了。这是个诚实说必须承认的设计缺口：版本号在计数一件没有被保存的东西。真要版本化，落盘路径得带上版本或 hash（`uploads/{document_id}/{version}.md`），存储成本换可回溯性。

**追问 3：这段代码里还有别的问题吗？**

有两个，都在去重之前：

一是**大小校验发生在读完之后**（`app/api/file.py:70-74`）：

```python
content = await file.read()      # 整个文件进内存
if len(content) > MAX_FILE_SIZE:  # 然后才检查
    raise HTTPException(status_code=400, ...)
```

一个 2GB 的请求会被完整缓冲进 API 进程的内存才被拒绝。`MAX_FILE_SIZE = 10MB` 这个限制在这个写法下**只限制入库，不限制内存占用**。正确做法是流式读 + 累加字节数,超了立刻中断；或者在网关层用 `client_max_body_size` 挡在前面 —— 后者更好，因为它让恶意请求根本到不了应用。这个接口没有认证，所以这不只是健壮性问题。

二是**先删旧文件再写新文件**，中间没有原子性。`unlink()` 成功、`write_bytes()` 失败（磁盘满）的话，旧文件没了、数据库里那条记录还指着这个路径、状态还是 `INDEXED`、向量还在库里。检索会命中一份**文件已经不存在**的文档。修法很标准：写临时文件再 `os.replace()` 原子改名，同文件系统内是原子的。

**拓展**

- **旧 job 没有被取消**：分支 3 每次都 `create_index_job` 建一条新的 job 行，上一条如果还在队列里，照样会跑。RQ 支持 `job.cancel()`，配合 `document.rq_job_id`（`app/models/knowledge_base.py:94` 存了它）可以在重传时先撤销上一个。没做的原因是「撤销一个可能已经开跑的任务」本身有竞争 —— 要做就得配合追问 1 里的状态守卫一起做。
- **`reused` 这个返回字段值得保留**：客户端能据此区分「真的索引了」和「跳过了」。很多 API 会把这两种情况都返回 200 让客户端猜。**幂等接口应该告诉调用方「你这次是不是空操作」**，否则调用方没法判断自己的重试逻辑是否正确。
- **分支 2 返回 200 而分支 1/3 返回 202** 是刻意的：202 的语义是「已接受，稍后完成」，配套一个要轮询的 `job_id`；分支 2 没有任何后续动作，`job_id` 是 `None`，用 202 会让客户端去轮询一个不存在的任务。**状态码要和「有没有后续动作」对齐**，这是最容易被忽略的一致性。

### Q25. 你项目里有软删也有硬删。怎么决定用哪种？

**考点**

考「删除」这个动作的边界意识。软删是个被过度推荐的模式 —— 很多项目全表软删，然后每个查询都得记着加 `WHERE deleted_at IS NULL`，漏一个就泄露数据。能说清**软删换来了什么、代价在哪、哪些数据软删是自欺欺人**的人，才算真理解。

**标准回答**

项目里三种删除并存，判断依据是**这份数据是原始的还是派生的，以及删错了能不能恢复**：

| 数据 | 删法 | 依据 |
|---|---|---|
| 知识文档 | 软删（`status = DELETED`） | 原始数据，误删代价高 |
| 对话消息 | 软删（`deleted_at` 时间戳） | 原始数据，且要留审计痕迹 |
| 会话记忆摘要 | **硬删**（`db.delete`） | 派生数据，可从消息重算 |
| 向量 | **硬删**（Milvus 里真删） | 派生数据，且留着会被检索命中 |

关键的判断是**派生数据不该软删**。摘要是消息压缩出来的，留着一份「已清理会话的摘要」不但没用，还危险 —— 用户点了「清空会话」，摘要里却还浓缩着那些内容，等于没清。向量同理：软删一条向量对检索没有意义，因为**检索查的是 Milvus，不是数据库**。向量只要还在，被删掉的文档就还会出现在回答里。

**真实代码**

`clear_session` 是这套判断最集中的地方（`app/repositories/conversation_repository.py:134-156`）—— 消息软删、摘要硬删、一个事务提交：

```python
def clear_session(self, session_id: str) -> bool:
    now = datetime.now(UTC).replace(tzinfo=None)
    session = self.db.get(ConversationSession, session_id)
    ...
    session.cleared_at = now

    for message in self.db.scalars(stmt).all():
        message.deleted_at = now          # 消息:软删

    snapshot = self.get_memory_snapshot(session_id)
    if snapshot is not None:
        self.db.delete(snapshot)          # 摘要:硬删

    self.db.commit()                      # 一次提交,原子
```

文档删除则是软删 + 外部硬删（`app/api/file.py:234-240`）：

```python
document = repo.mark_document_deleted(document_id)   # 内部 commit
if document is None:
    raise HTTPException(status_code=404, detail="文档不存在")

deleted_vectors = vector_store_manager.delete_by_document_id(document.id)
```

**追问链**

**追问 1：`mark_document_deleted` 先提交了数据库，然后才删向量。这个顺序有问题吗？**

有，而且是这一题里最值得说的缺陷。

`mark_document_deleted` 内部 `commit()`（`app/repositories/knowledge_repository.py:112-119`），提交完才轮到删向量。如果删向量抛异常，接口返回 500，但**数据库那边已经落地了** —— 文档状态是 `DELETED`，向量还在 Milvus 里。

后果不是「数据不一致」这么抽象。后果是：**这份文档从列表里消失了，但用户提问时它还会被检索到、还会被引用进回答**。用户以为删了，实际上只是看不见了。这比不删更糟，因为它剥夺了用户再删一次的机会 —— 列表里已经没有这一条,点不到删除按钮了。

顺序应该反过来：**先删向量，再提交数据库状态**。因为要比的是「哪种残留是可自愈的」：
- 现在的顺序，残留物是**幽灵向量**，没有任何路径能清掉它（除非直接连 Milvus）。
- 反过来的顺序，残留物是**还显示在列表里的文档**，用户看到没删成功，再点一次删除就好了 —— 而且第二次删除天然幂等（向量已经没了，`delete_by_document_id` 返回 0；状态改成 `DELETED` 也是幂等的）。

**跨两个存储的写操作没有事务，那就把不可回滚的那一步放前面，让失败留下一个用户能自己修的状态。** 这个原则比「用分布式事务」实用得多，也是这个规模的项目唯一负担得起的做法。

**追问 2：`status = DELETED` 这种软删和 `deleted_at` 时间戳，哪种更好？**

`deleted_at` 更好，而项目里文档用的是前者 —— 这是个已知欠账。

`status = DELETED` 的问题是它**占用了状态列**：一条文档被删之前是 `INDEXED` 还是 `FAILED`，删完就看不出来了；删除时间也没记。而状态列还有别的职责（驱动索引流程），把「生命周期是否结束」和「索引进行到哪一步」挤进同一个字段，是两个正交的维度共用一列。

对话消息就做对了 —— 独立的 `deleted_at`（`app/repositories/conversation_repository.py:149`），时间点留着，原本的角色和内容都不受影响。

同一个项目里两种约定并存，纯粹是因为文档表写得早、消息表写得晚。正确的收敛方向是给 `KnowledgeDocument` 加 `deleted_at`，`status` 只表示索引状态，查询条件从 `status != DELETED` 改成 `deleted_at IS NULL`。这是个带迁移的改动（要把现存的 `DELETED` 行回填 `deleted_at`，而回填时间只能取一个近似值 —— **这就是软删约定不统一的真实代价：修的时候已经丢了信息**）。

**追问 3：软删之后，chunk 行和 `KnowledgeChunk` 里的内容都还在。这算不算数据泄露？**

算，取决于删除请求的含义。

如果用户点删除的意思是「我不想再用它」，留着无妨。如果意思是「这份文档不该存在了」（比如误传了含敏感信息的文件），那么 chunk 表里逐段存着**全文**（`app/models/knowledge_base.py:76` 是 `Text` 列，存的是切分后的原文），磁盘上的原始文件也还在 `uploads/` 下 —— 只删了向量和一个状态字段，原文一点没动。

所以严格说，现在这个删除**不是删除，是隐藏**。要做真删除需要三步：删 chunk 行、删磁盘文件、删向量，而且这三步都不可逆。合理的产品形态是把两种意图分开：列表里的「删除」是隐藏（当前行为），另有一个「彻底删除」走真删并要求二次确认。

**明确区分「隐藏」和「销毁」比默认软删更负责** —— 默认软删的项目最常见的失败模式，就是用户以为销毁了、法务以为销毁了，而数据一直在。

**拓展**

- **`replace_chunks` 的删法可以优化**：现在是把旧 chunk 全部 `select` 进内存再逐行 `db.delete()`（`app/repositories/knowledge_repository.py:102-110`），一份 500 段的文档要构造 500 个 ORM 对象、发 500 条 DELETE。改成 `delete(KnowledgeChunk).where(KnowledgeChunk.document_id == ...)` 一条语句就够。ORM 逐行删只在需要触发级联或 ORM 事件时才必要 —— chunk 底下没有子表、没有事件钩子，所以批量删是安全的。没改是因为单文档 chunk 数一般在几十量级，还没到痛的时候。
- **`cascade="all, delete-orphan"`（`app/models/knowledge_base.py:58-61`）目前是死配置**：它只在硬删 `KnowledgeDocument` 时生效，而项目里没有任何代码硬删文档。留着不是错（将来加「彻底删除」时它就派上用场），但要知道它现在不提供任何保护。
- **软删让唯一约束失效**：`filename` 上如果加唯一索引，软删的行会一直占着这个名字。项目里之所以没这个问题，是因为压根没加唯一索引 —— 去重靠 `get_document_by_filename` 的应用层查询（Q24）。这也是为什么 Q24 追问 1 里的并发问题存在：**没有数据库约束兜底的去重，在并发下必然漏**。软删和唯一约束天然冲突,标准解法是部分索引：`CREATE UNIQUE INDEX ... WHERE deleted_at IS NULL`,PostgreSQL 支持。这条和上一题的修复方案 1 是配套的。

## 第七部分 · 迁移

### Q26. 你项目里有 9 个迁移，`down_revision` 串成一条直线。这是刻意设计的吗？两个人同时加迁移会怎样？

**考点**

考对 alembic 修订图的理解。很多人以为迁移是一个「按文件名排序的列表」——能说清它是**有向图**、多 head 是协作的正常产物而不是错误的人，才真正维护过多人项目的迁移。

**标准回答**

严格线性不是刻意设计，是单人开发的自然结果。alembic 的修订**本来就是有向图**：`down_revision` 指向父节点，两个修订指向同一个父就是分叉，`down_revision` 写成元组就是合并。

多人协作时必然出现多 head：A 和 B 都从 `20260824_0009` 拉分支各加一个迁移，两人的 `down_revision` 都是 `20260824_0009`，合并到 master 后 `alembic upgrade head` 直接报错 `Multiple head revisions are present`。

处理方式有两种，**选哪种取决于有没有人已经跑过那个迁移**：

- **还没跑过**（只在功能分支里存在）：后合的人把自己的 `down_revision` 改成指向对方，历史保持线性。
- **已经在共享环境跑过**：必须用 `alembic merge heads` 生成一个空的合并修订。不能再改 `down_revision`，因为数据库的 `alembic_version` 表里存的是已应用的 revision id，改掉一个别人已应用的修订的 id，那个环境会永远认为自己停在一个不存在的版本上，之后再也升不上去。

这个判断标准值得记住：**迁移文件一旦在任何共享环境执行过，它的 id 和 down_revision 就是不可变的**，和「已 push 的 commit 不 rebase」是同一条纪律。

还有一个我这个项目埋着的协作隐患：我用了 `20260824_0009` 这种「日期 + 手写序号」的命名。alembic 默认生成随机 hex（`ae1027a6acf`）恰恰是为了避免撞号 —— 两个人同时写都会得到 `0010`。我选了可读性（一眼看出顺序和日期），代价是并发下需要人工协调序号。单人项目这笔交易是划算的，团队里就该换回随机 id 或者用 `alembic branch_labels` 按模块分段。

**真实代码**

`migrations/versions/` 下 9 个文件构成一条链，每个文件顶部两行声明它在图里的位置：

```python
# migrations/versions/20260612_0001_create_knowledge_base_tables.py:13-14
revision: str = "20260612_0001"
down_revision: Union[str, None] = None          # 链的起点

# migrations/versions/20260824_0009_create_chat_run_spans.py:40-41
revision: str = "20260824_0009"
down_revision: Union[str, None] = "20260823_0008"
```

完整链：`0001`(None) → `0002` → `0003` → `0004` → `0005` → `0006` → `0007` → `0008` → `0009`。

执行入口在 `Makefile:383-385`：

```makefile
migrate:
	.venv/bin/alembic upgrade head
```

**追问链**

**追问 1：每个迁移都写了 `downgrade()`。你敢在生产用 `alembic downgrade` 吗？**

不敢，而且我认为生产环境的 downgrade 基本是个伪需求。

原因是 **downgrade 的语义假设「数据还是升级前那样」**，而这个假设在生产上从升级完成的那一秒起就不成立了。`0008` 加了 `request_id` 列，跑了一天，几万行都填上了值；downgrade 一句 `op.drop_column` 把这些数据直接删掉 —— 它是可逆的 DDL，不是可逆的操作。

生产回滚的正确姿势是**向前修复**：写一个新迁移撤销上一个迁移的效果，把「怎么处理这一天里产生的数据」显式写在里面。多一个迁移文件，换一份可审计的数据处置决定。

那 `downgrade()` 还写它干什么？两个真实用途：**本地开发**（改错了退回去重来）和 **CI 里验证可逆性**（见追问 2 和 Q28）。它是开发工具，不是运维工具。

**追问 2：`0001` 的 `downgrade()` 最后两行为什么要单独 drop 两个 Enum？`drop_table` 不是连着删掉了吗？**

```python
# migrations/versions/20260612_0001_create_knowledge_base_tables.py:107-108
index_job_status.drop(op.get_bind(), checkfirst=True)
document_status.drop(op.get_bind(), checkfirst=True)
```

不会。**PostgreSQL 的 ENUM 是独立的 schema 对象**，不属于任何表。`DROP TABLE knowledge_documents` 删掉表，`documentstatus` 这个类型还在库里。

不删的后果不是立刻报错，而是**可逆性在第二轮断掉**：downgrade 到 base，再 upgrade 一次，`CREATE TYPE documentstatus` 报 `type "documentstatus" already exists`。第一次 downgrade→upgrade 看起来是好的，第二次才炸 —— 这种「跑一遍没问题、跑两遍才出错」的缺陷最容易漏。

关键在于这是 **PostgreSQL 特有的**。MySQL 的 enum 是列的一部分，SQLite 干脆就是 VARCHAR。而我的测试全跑在 SQLite 上，**这两行代码在测试里既不需要也测不出来** —— 它们纯靠写迁移时想到了。这正好引出 Q28 那个更大的问题。

**追问 3：`alembic.ini:4` 那行明文数据库 URL 是干什么的？**

```ini
sqlalchemy.url = postgresql+psycopg://postgres:postgres@localhost:5432/super_biz_agent
```

它是**死配置**。`migrations/env.py:39` 会覆盖掉：

```python
configuration["sqlalchemy.url"] = get_url()      # get_url() 返回 app_config.database_url
```

但「不生效」不等于「无害」，它有两个实际问题：

1. **明文口令进了 git**。虽然是本地默认口令，但这个模式一旦被复制到别的项目就会带上真口令。
2. **它会误导人**。新人要改迁移目标库，第一反应是改 `alembic.ini` 里这行 —— 改完发现没生效，得读 `env.py` 才明白。**配置文件里存在一个不生效的配置项，比没有这个配置项更糟。**

正确做法是删掉这行，或者写成 `sqlalchemy.url =` 空值加一行注释「实际 URL 由 env.py 从 app.config 读取」。这是个一行的改动，列进 Q29 的 P3。

**拓展**

- **CI 里应该有个「迁移三连」**：`alembic upgrade head` → `alembic downgrade base` → `alembic upgrade head`。它一次性守住了追问 2 那个 Enum 坑（第二轮 upgrade 会炸）和所有 downgrade 的语法错误。成本是 CI 里起一个 PostgreSQL 容器。
- **`alembic check`（1.9+）几乎是免费的守卫**：它比对 `target_metadata` 和数据库实际 schema，有差异就退出码非零。加进 CI 一行的事 —— 但在本项目现在跑它会立刻变红，原因就是下一题。

### Q27. 你现在在这个项目上跑一次 `alembic revision --autogenerate`，会发生什么？

**考点**

压轴题，考「autogenerate 的输入到底是什么」。绝大多数人答「它会对比 model 和数据库，生成差异」—— 对，但没答到点上。真正的考点是：**左边那个「model」不是自动扫描来的，它靠 import 副作用填充，因此它的完整性是一个没人守卫的隐式契约。**

**标准回答**

会生成**四条 `op.drop_table()`**，删掉全部链路追踪和 AIOps 诊断历史。

推导链是四步：

1. autogenerate 做的是双向 diff：左边是 `target_metadata` 里声明的表，右边是数据库里实际存在的表。
2. **`Base.metadata` 不会自动发现 model**。它是 `DeclarativeBase` 的类注册表，一个 model 类被定义时（也就是它所在模块被 import 时）才注册进去。模块不被 import，那张表在 metadata 里就不存在。
3. `migrations/env.py` 只 import 了 4 个 model 模块。
4. 于是有 4 张表处于「数据库里有、metadata 里没有」的状态。autogenerate 对这种情况的判定是**「这张表被删掉了」**，生成 `drop_table`。

这不是推测，是实测出来的：

```
env.py 导入后 metadata 有 14 张表
全部导入后 18 张表
env.py 看不到的表:
   - aiops_diagnosis_events
   - aiops_diagnosis_tasks
   - chat_run_spans
   - chat_run_traces
```

14 张能一张一张对上：`knowledge_base` 3 张 + `conversation` 5 张 + `protocol_ingestion` 2 张 + `protocol_catalog` 4 张。少的 4 张分布在 3 个没被 import 的模块里：`chat_run_trace.py`、`chat_run_span.py`、`aiops_diagnosis.py`（这个模块自己定义了 2 张表）。

**它现在没炸，只因为 9 个迁移全是手写的** —— 每个文件都带着手写的中文 docstring（`0009` 那个写了 26 行解释为什么不上 OpenTelemetry）。也就是说这个缺陷**不是被防住了，只是没被触发**。`Makefile` 里有 `make migrate`（跑 upgrade），没有 `make revision`，所以生成迁移得手敲那条命令，而敲的人恰好一次都没敲过。

**真实代码**

缺陷就在这四行的「少了三行」：

```python
# migrations/env.py:6-11
from app.config import config as app_config
from app.core.database import Base
from app.models import conversation  # noqa: F401
from app.models import knowledge_base  # noqa: F401
from app.models import protocol_catalog  # noqa: F401
from app.models import protocol_ingestion  # noqa: F401
# ↑ 缺 chat_run_trace / chat_run_span / aiops_diagnosis

# migrations/env.py:18
target_metadata = Base.metadata      # ← 这里拿到的是一个不完整的世界模型
```

那 4 张表确实在数据库里，因为迁移建过它们：

- `20260629_0004_create_chat_run_traces.py` → `chat_run_traces`
- `20260723_0006_create_aiops_diagnosis_tables.py` → `aiops_diagnosis_tasks` + `aiops_diagnosis_events`
- `20260824_0009_create_chat_run_spans.py` → `chat_run_spans`

而这四张表存的东西恰好是**最不该丢的那类数据**：26 篇讲的 span 时间线、trace 质检记录、诊断任务的完整时间线 —— 全是历史观测数据，删了不能重建（业务数据能从源头重跑，观测数据的源头就是那次已经过去的请求）。

**追问链**

**追问 1：为什么不直接 `import app.models` 一句了事？**

因为不管用。`app/models/__init__.py` 只有一行 docstring：

```python
"""数据模型模块"""
```

import 一个包不会 import 它的子模块。真正的选项是三个：

| 方案 | 做法 | 代价 |
|---|---|---|
| 在 env.py 补三行 | 最直接 | 每加一个 model 都要记得改 `migrations/env.py` |
| 在 `app/models/__init__.py` 里显式 re-export | env.py 一行 `import app.models` | 还是要改一个文件，但改的是「更容易想到的那个文件」 |
| env.py 里 `pkgutil.iter_modules` 动态遍历 | 一劳永逸 | 显式性差；会连带 import `document.py`/`request.py`/`response.py` 这些 Pydantic 模块（无害但语义混乱）；出错时报错点很远 |

我选第二个。理由是**它把「本项目有哪些 ORM 模块」这份清单收敛到唯一一处，而且那一处是最自然的位置**。加新 model 的人正在编辑 `app/models/` 目录，改同目录下的 `__init__.py` 有可能想到；让他记得去改 `migrations/env.py` 基本不可能 —— 缺陷复发的概率取决于「要改的文件离正在改的文件有多远」。

第三个方案看起来最彻底，但它把一个明确的清单换成了一个隐式的目录扫描规则。**Q26 追问 3 刚说过「不生效的配置比没有更糟」，这里是同一类判断：一个看不见的自动机制出错时，比一个看得见的清单漏项更难查。**

**追问 2：怎么防止它再犯一次？**

只有测试能防。这类缺陷**靠代码审查发现不了** —— 因为缺陷是「少了一行」，而审查看的是「加了哪些行」。diff 里没有的东西，评审看不见。

三个层次的守卫，从便宜到贵：

1. **一个单元测试**：断言 `len(Base.metadata.tables) == 18`，或者更好 —— 遍历 `app/models/` 下所有定义了 `__tablename__` 的模块，和 `env.py` 的 import 集合比对。缺点是数字要手工维护。
2. **CI 里跑 `alembic check`**：它就是「metadata 与数据库有无差异」这个检查本身，语义完全对得上。需要一个真的库。
3. **纪律**：autogenerate 的产物永远人工过一遍。alembic 官方文档自己就写了它的输出「不能盲信，必须审查」。

第 1 条是现在就该加的 —— 一个用例，锁住一个「一行代码就能毁掉的东西」。

**追问 3：假如真有人生成了那个迁移并且跑了呢？**

数据没了。`drop_table` 之后没有任何应用层手段能救回来，只能靠库级别的备份或 PITR。

所以缓解得靠三道更前置的闸门，按性价比排：

1. **迁移文件必须走 code review**（最便宜，最有效）。四条 `drop_table` 在 diff 里是极其醒目的。
2. **生产库的应用账号不给 DDL 权限**，迁移用独立账号手动跑。这样即便代码里有 drop，应用自己也执行不了。
3. **生产迁移前打快照**。最贵，但是唯一一道真正的兜底。

第 1 条是关键：这个缺陷的可怕之处在于**生成阶段完全静默**（alembic 不会警告「你的 metadata 好像不完整」，它没法知道），唯一会说话的地方就是生成出来的那个文件本身。所以「人必须看那个文件」不是流程洁癖，是这条链路上仅存的一次告警机会。

**拓展**

- **这个缺陷的形态值得单独记住**：它不是逻辑写错，是**「声明的世界模型」和「真实世界」不同步，而且不同步本身不产生任何信号**。同一类形态还有：`__all__` 漏名字导致 `from x import *` 少东西、Pydantic 响应模型少一个字段导致返回值被静默截断、DI 容器忘记注册某个实现直到运行时才 KeyError。共同点都是**「少写了」而不是「写错了」** —— 写错了有报错，少写了只有沉默。对付它们的唯一办法是让「完整性」变成一个可被机器断言的命题。
- **迁移与 model 的双写是 alembic 的固有代价**。另一条路是 SQLModel / Django ORM 那种「model 即 schema」加自动迁移，从根上消灭这个不同步。代价是失去对 DDL 的精细控制 —— 比如 `0008` 那个「刻意不用 `postgresql_concurrently=True`」的决定，在自动迁移的世界里没有地方表达。这是「消除一类 bug」和「保留控制力」之间的交换，没有普适答案；数据量小、schema 变更频繁的项目该选前者。

### Q28. 测试里有 9 处 `Base.metadata.create_all(engine)` 配内存 SQLite，完全绕过了迁移。这样有什么问题？

**考点**

考「测试环境与生产环境的差异会掩盖什么」。答「不够真实」是空话，能具体点出**哪几处方言差异会让测试变成假绿**的人，是真被这类问题坑过。

**标准回答**

两类盲区，第二类更危险。

**第一类：迁移文件本身从没被执行过。**

9 个迁移的 `upgrade()` / `downgrade()` 一次都没在 CI 里跑过。列名写错、索引名重复、`downgrade` 漏删一个索引 —— 全都要等到有人手动 `make migrate` 才暴露。而 `create_all` 是从 model 定义直接建表，它跑通只能证明「model 定义合法」，**证明不了迁移文件和 model 描述的是同一个 schema**。Q27 那个缺陷就是这两条路径分叉的直接后果：测试相信 model，生产相信迁移，没有任何一个环节同时看两边。

**第二类：SQLite 和 PostgreSQL 的行为差异。**

这个项目里至少有四处：

| 差异点 | PostgreSQL | SQLite | 掩盖了什么 |
|---|---|---|---|
| ENUM | 独立 schema 对象 | 就是 VARCHAR | Q26 追问 2 那个「跑两遍才炸」的坑；以及非法枚举值在 SQLite 上能写进去 |
| JSON 列 | JSONB + `->`/`@>` 操作符 | 文本存储 | `state_trace`、`structured_data` 上的任何 JSON 查询在测试里测的不是真实行为 |
| 外键约束 | 默认强制 | **默认不强制**（需 `PRAGMA foreign_keys=ON`） | `ondelete="CASCADE"` 在测试里根本不级联 |
| DDL 事务性 | DDL 在事务内，失败回滚 | 部分支持 | 迁移中途失败后的库状态 |

**第三行是最要紧的**：`chat_run_spans` 靠 `ondelete="CASCADE"` 保证 trace 删了 span 不留孤儿（`0009` 的 docstring 专门写了「不指望应用层记得先删 span —— 应用层总会有人忘」）。而这个承诺在 SQLite 测试里是**假绿的** —— 不是没测，是测了并且通过了，但通过的原因是约束压根没生效。

**当初为什么这么选：快。** 内存 SQLite 建 18 张表是毫秒级，跑完 9 个迁移要几百毫秒，而且需要一个真的 PostgreSQL 实例。9 个 fixture 每个都建一次库，换成 PG 之后本地跑一次单测的体验会明显变差 —— 而单测跑得慢，人就不跑了。这个取舍本身是对的。

**正确的分层是两条腿，而不是二选一**：单元测试继续用 SQLite + `create_all`（它们测的是 repository 的逻辑分支和状态机，不是 SQL 方言）；**另加一个跑真 PostgreSQL + 完整迁移的集成测试**，哪怕只有一个用例。

**追问链**

**追问 1：为什么只有集成测试用了 `StaticPool`，8 个单测都不用？**

因为 **`sqlite:///:memory:` 的数据库是 per-connection 的** —— 每条新连接得到一个全新的空库。

默认连接池在连接归还后可能关闭它、下次请求时新建一条 → 新连接看到空库，刚建的 18 张表全不见了。`StaticPool` 强制整个 engine 只维护一条连接、所有请求复用它，库才活着。`check_same_thread=False` 是配套的：TestClient 在别的线程里跑，SQLite 默认禁止跨线程用同一连接。

单测不需要，是因为**它们在一个测试函数里用同一个 session、只借一次连接**。API 测试跨请求（TestClient 每个请求走一遍 `get_db()`，各借各的连接），所以必须。

值得注意的是：**这两个参数是「内存 SQLite」这个测试专属选择带来的专属复杂度** —— 用真 PG 时它们完全不存在。这是 Q28 的隐性成本之一，「测试环境更简单」这个直觉不总是成立，有时只是把复杂度换了个形状。

**追问 2：怎么在 CI 里跑真 PostgreSQL？成本多大？**

GitHub Actions 的 `services:` 起一个 postgres 容器，或者用 `testcontainers` 库在测试里拉起来。成本是 CI 时间几十秒 + 一份 fixture。

**最小可行版本就一个用例**：

```
alembic upgrade head        → 断言 18 张表都在
alembic downgrade base      → 断言表都没了
alembic upgrade head        → 再跑一遍，不许报错
```

这一个用例同时守住了三件事：Q26 追问 2 的 Enum 可逆性（第三步会炸）、Q27 的 metadata 完整性（表数量对不上）、以及所有 9 个迁移的语法。**投入产出比高得离谱** —— 一个用例，覆盖三个已知缺陷类别。

**追问 3：`create_all` 和迁移都能建表，到底谁是权威？**

生产上迁移是唯一权威 —— `create_all` 从没在生产跑过。但测试用 `create_all` 就意味着**系统里有两个 schema 权威源：测试相信 model，生产相信迁移**。

这正是 Q27 那个 bug 能藏住的结构性原因，不是巧合：没有任何一个环节**同时看这两边**。加追问 2 那个集成测试，本质作用就是造出这样一个环节。

顺带说明一件事：这个问题在「用 SQLModel 那种 model 即 schema 的方案」里天然不存在（只有一个权威源）。所以 Q27 拓展里那个交换在这里又出现了一次 —— **双写带来的不只是 Q27 一个缺陷，是一整类「两个权威源可能分叉」的缺陷**。选择 alembic 就是接受了要自己维护这两边的一致性。

**拓展**

- **比「跑两遍建表」更精确的做法是 schema diff**：alembic 的 `compare_metadata(context, metadata)` API 能返回 metadata 和实际库的结构差异列表。在 CI 里跑完迁移之后调它，断言返回空列表 —— 不只告诉你「不一致」，还告诉你**差在哪一张表的哪一列**。这实际上就是 `alembic check` 的底层实现，手写一遍的好处是可以自定义忽略规则（比如忽略掉那些故意不进 metadata 的历史表）。
- **SQLite 的外键可以打开**：加一个 autouse fixture 在每条连接上执行 `PRAGMA foreign_keys=ON`（用 SQLAlchemy 的 `connect` 事件钩子）。这能让上表第三行那个假绿变成真测试，成本是几行 conftest 代码。**这是四处方言差异里唯一一处能低成本消除的**，另外三处只能靠真 PG。

## 第八部分 · 演进优先级与总结

### Q29. 如果给你两周时间专门改这块，优先级怎么排？

**考点**

考排序依据。列一堆待办事项谁都会，考点是**依据是什么** —— 而且面试官会盯着那些「听起来很架构、但被你排到最后」的项目问为什么。

**标准回答**

排序依据是两条，按顺序应用：**先看能不能自愈，再看出事了能不能被发现。**

**P0 —— 会丢数据 / 会永久卡住，且不可自愈**

1. **补 `migrations/env.py` 的三行 import，CI 里加 `alembic check`**（Q27）。改动 3 行代码 + 1 行 CI 配置，消除的是本篇唯一一个「一条命令毁掉全部历史观测数据」的缺陷。性价比没有任何一项能比。
2. **RUNNING 状态的进程外对账**（Q13）。worker 被 `kill -9` 的任务永久停在 RUNNING，页面上永远转圈。做法是一个定时任务扫「`status=RUNNING` 且 `started_at` 超过 `job_timeout` 两倍」的行，标 FAILED 并写明「worker 失联」。**必须是进程外的** —— 这是这条的全部要点，任何写在 worker 进程里的补偿代码在 SIGKILL 下都不会执行。

**P1 —— 出了事看不见**

3. **`index_jobs` / `protocol_pdf_ingestion_jobs` 加 `request_id` 列**。`0008` 只给 `chat_run_traces` 和 `aiops_diagnosis_tasks` 加了，这两张任务表和日志之间现在没有关联键 —— Q14 那套跨进程传递做了一半，日志里有 rid，库里没有落点。
4. **`job_failure_record_errors_total` Counter**。Q11 里那七处 `suppress` 掉的二次失败现在只进日志，不可告警。「失败留痕失败了」这件事本身必须可监控，否则 Q9 那个 bug 的同类问题下次还是只能靠人读日志发现。

**P2 —— 设计欠账，但当前不出事**

5. **`retry_count` 列**（Q7）。让「正在重试中」变成可查询状态，而不是只存在于日志里。注意不是加 `IndexJobStatus.RETRYING` —— 那会破坏状态机单调性。
6. **worker 侧连接池收紧到 `pool_size=2, max_overflow=3`**（Q17 追问）。worker 是单线程串行的，最多用 1 条连接，默认的 5+10 只是白占 PG 的 `max_connections`。
7. **一个真 PG + 完整迁移的集成测试**（Q28 追问 2）。

**P3 —— 一致性与可读性**

8. UoW 化 commit 边界（Q19）。
9. 去掉不必要的 `refresh()`（Q23 追问 2）。
10. `record_phase` 拆成 `enter_phase` / `note_phase`（Q23 追问 1）。
11. `with_job_session` 装饰器（Q20 拓展）。
12. 删掉 `alembic.ini:4` 那行不生效的明文 URL（Q26 追问 3）。

**追问链**

**追问 1：UoW 听起来是架构问题，你把它排到 P3？**

对，而且这是我认为**最值得辩护的一条排序**。

理由是它现在**没造成任何一个 bug**。9 次提交已经落在 5 个真实业务边界上（Q23），那个「状态已推进但时间线还没事件」的不一致窗口已经在 `record_phase` 里关掉了。而 UoW 真正解决的问题 —— 跨 repository 的原子事务 —— **需求还没出现**：现在没有任何一个用例需要在同一个事务里同时改 knowledge 和 conversation。

这是 YAGNI 的一个正例：**架构上不优雅，但优雅本身不是收益**。真出现跨 repo 需求那天再改，而且那天的改动量不大 —— Q19 已经论证过，底层 session 本来就共享，缺的只是把 commit 的调用点从 repository 挪到上层，不需要改对象的传递路径。

反过来说，如果我发现现在已经有人在业务代码里写「先调 repoA 再调 repoB，中间失败就手动补偿」，那 UoW 立刻升到 P1 —— 因为那意味着不一致已经在发生了，只是被手写补偿掩盖着。**判断标准不是「这个设计是否正确」，是「不做它现在有没有人在流血」。**

**追问 2：P0 那两条一个是 3 行代码，一个要新起一个定时任务。工作量差这么多，凭什么同级？**

因为 P0 的定义是「不可自愈的损害」，不是「改起来快」。

两条的损害形态确实不同：Q27 是**低概率、高损害、瞬时**（一条命令，四张表没了）；Q13 是**高概率、中损害、持续**（每次 worker 重启/OOM 都发生，页面上留一条永远转圈的任务）。它们的共同点是**过了那个时刻就没有任何自动机制能修回来** —— 表删了只能靠备份，卡死的行只能靠人工 UPDATE。

至于工作量差异，它影响的是**做的顺序**而不是优先级：先花半小时做完 Q27（3 行），再花两天做 Q13。**「同级」的意思是两周之内两条都必须做完，不是两条要同时开工。**

**追问 3：那你怎么保证 P3 那些事永远不会被做？排到 P3 基本等于不做吧。**

诚实地说，是的，P3 里的大部分永远不会作为独立任务被做，我不打算假装它们会。

但它们仍然有价值，价值在于**它们是「顺路要做」的清单**。下次因为别的原因动到 `aiops_diagnosis_repository.py` 时，顺手把 `refresh` 去掉、顺手把方法拆开；下次动 `alembic.ini` 时顺手删掉那行死配置。这类改动的合理成本模型不是「专门排一个任务」，是「附加在一次已经付出了阅读成本的改动上」。

所以 P3 真正需要的不是排期，是**记录在一个下次动到相关代码时会被看到的地方** —— 写在这份文档里比写在待办列表里更可能被看到，因为改代码的人会来查设计理由。

### Q30. 一句话总结这块设计。

**「异步的核心难点不是把任务扔出去，是任务在另一个进程里失败之后，你还能不能说清它为什么失败。」**

展开讲三层。

**第一层：本篇有分量的代码全在失败路径上。**

正常路径简单到几乎不用讲 —— 入队一行、worker 里读库、跑逻辑、写库。而 `apply_retry_policy` 的裁决逻辑、`record_job_failure` 的三步抢救、七处 `suppress` 的边界划分、`request_id` 的跨进程传递，全是为了「失败之后还能说清原因」而存在的。**这个比例本身就是异步系统的特征**：同步调用失败了，异常直接抛给调用方，调用方自己知道；跨进程之后，「让人知道发生了什么」变成一件必须显式编码的事。

**第二层：失败路径的代码有一个别处没有的性质 —— 它运行时系统已经不正常了。**

Q9 那个 bug 是本篇最贵的教训：`except` 块里的第二次 `commit()` 顶掉了原始异常，而且**专挑基础设施故障的时候顶** —— 数据库连不上的时候，抢救动作自己也连不上，于是真实原因被替换成了抢救失败的原因。越是需要看清原因的时候，越看不清。

这个教训能推广成一条规则：**正常路径可以假设依赖可用，失败路径不能假设任何东西还能用**。session 能不能建、commit 能不能成、`close()` 会不会抛，全都要当成可能失败来写。这就是那七处 `suppress` 的合法性来源 —— 它们不是在偷懒吞异常，是在拒绝让抢救代码的失败盖住被抢救的信息。

**第三层：数据层那个缺陷和 Q9 是同一类东西。**

Q27 的漏导入和 Q9 的异常覆盖，表面上一个在数据层一个在任务层，本质完全一样：**「你以为在做的事」和「实际发生的事」不一致，而且不一致本身不发出任何信号。**

两者的区别只在于沉默的程度。Q9 好一点 —— 日志里留了痕迹（错误信息的类型不对，仔细看能看出来）。Q27 连痕迹都没有，一直沉默到有人敲下那条 autogenerate 命令的瞬间。

对付这一类缺陷，靠的不是「写得更仔细」。这两个 bug 都是很有经验的写法下出现的（一个是标准的 try/except 抢救，一个是标准的 alembic 配置）。靠的是**把不一致变成一个机器可以断言的命题**：一个测试锁住「commit 失败不许覆盖原异常」，一行 CI 命令锁住「metadata 必须等于数据库」。

**所以如果把这一篇压成一句实操建议**：异步和持久化这两块，**代码审查能覆盖的部分远小于你以为的**，因为最贵的缺陷都是「少写了什么」而不是「写错了什么」。剩下那部分只能交给测试和 CI。
