## 一、错误分类体系

### Q1. 你项目里的异常体系是怎么设计的？为什么不直接用 Python 内置异常？

**考点**：能不能说出「异常需要携带什么信息才能被程序消费」，而不是只说「自定义异常更清晰」。

**标准回答**：

我定义了一个 `AppError` 基类，它和普通异常的区别是带了**四个类属性**，每个属性对应一个下游消费者：

| 属性 | 类型 | 谁消费它 | 不带会怎样 |
|---|---|---|---|
| `code` | `str` | 监控指标的 label、日志聚合 | 只能按 message 文本聚合，同一个故障因为 message 里带了不同的 ID 被算成几百种错误 |
| `retryable` | `bool` | RQ worker、熔断器 | 重试策略只能「一律重试 3 次」或「一律不重试」 |
| `http_status` | `int` | 全局异常处理器 → 网关/LB/APM | 全部返回 200 或全部返回 500，两种都是错的 |
| `degrade_reason` | `DegradeReason \| None` | 降级埋点、值班定位 | 只知道「降级了」，不知道往哪个方向修 |

关键在于**这四个属性回答的是四个不同的问题**：这是什么错（`code`）、能不能再试一次（`retryable`）、外部该看到什么（`http_status`）、人该去修哪里（`degrade_reason`）。内置异常一个都答不了 —— `ConnectionError` 只告诉你「连接出问题了」，它不知道自己该不该重试，也不知道自己对应哪个 HTTP 状态。

改造前的代码是这样的：到处 `except Exception as e` 然后 `error_message = str(e)`。`str(e)` 是给人看的自由文本，它有三个不可修复的问题：

1. **不能聚合**：`"连接 Milvus 失败: [Errno 111] Connection refused to 10.0.1.7:19530"` 和同一个故障在另一个节点上产生的文本不相等，Prometheus 里就是两个 series。
2. **不能判断可重试性**：靠 `if "timeout" in str(e)` 这种字符串匹配，上游改一个字文案就失效，而且没有任何测试能发现它失效了。
3. **不能决定 HTTP 语义**：文本里没有「这是客户端参数错还是服务端故障」的信息。

**真实代码**（`app/core/errors.py:1`）：

```python
class AppError(Exception):
    """应用异常基类。

    子类只覆盖类属性,不重写 __init__ —— 构造逻辑只有一份(DRY)。
    """

    code: str = "internal_error"
    retryable: bool = False
    http_status: int = 500
    degrade_reason: DegradeReason | None = None

    def __init__(
        self,
        message: str,
        *,
        cause: BaseException | None = None,
        context: dict[str, Any] | None = None,
    ) -> None:
        super().__init__(message)
        self.message = message
        self.cause = cause
        self.context = context or {}
```

子类的全貌（`app/core/errors.py`）：

| 子类 | `code` | `retryable` | `http_status` | `degrade_reason` |
|---|---|---|---|---|
| `RetrievalError` | `retrieval_error` | ✅ | 502 | `RETRIEVAL_FAILED` |
| `LLMError` | `llm_error` | ✅ | 502 | `LLM_ERROR` |
| `LLMTimeoutError` | `llm_timeout` | ✅ | **504** | `LLM_TIMEOUT` |
| `ParseError` | `parse_error` | **❌** | 502 | `PARSE_FAILED` |
| `UpstreamUnavailableError` | `upstream_unavailable` | ✅ | 502 | **None** |
| `CircuitOpenError` | `circuit_open` | ❌ | **503** | `CIRCUIT_OPEN` |
| `TotalBudgetExceededError` | `total_budget_exceeded` | ❌ | 504 | `TOTAL_BUDGET_EXCEEDED` |
| `InvalidRequestError` | `invalid_request` | ❌ | **400** | None |

**追问链**：

**Q：为什么子类只覆盖类属性、不重写 `__init__`？**

因为 `__init__` 里的逻辑（保存 message、cause、context）对所有子类完全一样。如果每个子类都写一遍 `__init__`，八个子类就是八份相同代码，以后要给异常加一个字段（比如 `occurred_at`）得改八处，改漏一处就是运行时 `AttributeError`。类属性覆盖是 Python 里表达「只有默认值不同」最省的方式 —— 子类体里就三行赋值，一眼能看完差异。

这也让**新增异常类型的成本接近零**，而成本低是它能真正被用起来的前提。如果加一个异常要写 20 行，人就会偷懒复用一个语义不对的现成异常，分类体系就烂掉了。

**Q：`ParseError` 为什么不可重试？它明明是 LLM 相关的错误。**

因为它的失败原因**不在时间维度上**。`LLMError` 是「这次调用没成功」—— 网络抖动、限流、服务重启，等 10 秒再试很可能就好了。`ParseError` 是「调用成功了，但返回的内容不符合我要的 JSON 结构」。重试的前提是「同样的输入下一次可能得到不同的结果」，而这里下一次极可能拿到同样格式错误的输出 —— 尤其当我用 `temperature=0` 调的时候。

所以判断可重试性的标准不是「错误发生在哪个组件」，而是**「重新执行一次，成功概率是否显著上升」**。这个标准还解释了 `CircuitOpenError` 为什么不可重试：熔断器开着的时候，立刻重试 100% 还是被拒 —— 重试甚至是有害的，它把本该冷却的下游继续压着。

**Q：`UpstreamUnavailableError` 为什么 `degrade_reason` 是 None，但 `LLMError` 有？**

这是我最初写错、后来改的地方。`degrade_reason` 的语义是**「这次请求降级了，原因是 X」**，它的前提是「请求还是返回了结果，只是质量下降」。`UpstreamUnavailableError` 用在没有降级路径的地方 —— 上游没了，我给不出任何结果，这是**彻底失败**，不是降级。

如果给它填一个 `degrade_reason`，`degrade_total{reason=...}` 这个指标就会把「降级了但用户拿到了东西」和「彻底 500 了」混在一起。这两者的处理优先级完全不同：前者可以第二天再看，后者要立刻起来。**指标一旦混了语义，它的告警阈值就没法设了。**

**拓展**：

还没做但清楚该怎么做的三件：

1. **`AppError` 的 `context` 目前是自由 dict，没有 schema**。它进日志是安全的，但如果哪天要进指标就危险了 —— 有人塞了 `context={"query": user_input}` 就是一次 label 基数爆炸。正确做法是给 `context` 分两层：`labels`（受限枚举，可进指标）和 `detail`（自由文本，只进日志）。
2. **缺少 `error_chain` 的结构化输出**。现在 `cause` 只存了一层，多层包裹（`RetrievalError(cause=CircuitOpenError(cause=TimeoutError))`）时只有最外层进了 `error_code`。应该在日志里输出完整链路的 code 列表 `["retrieval_error", "circuit_open", "timeout"]`，值班一眼能看到根因而不是表象。
3. **没有「异常预算」概念**。更成熟的做法是给每类 `code` 配 SLO：`llm_timeout` 允许 0.1%，`parse_error` 允许 0.5%，超了才告警。现在是绝对阈值告警，业务量涨了就会误报。

### Q2. `code` 和 `message` 有什么区别？为什么需要两个字段？

**考点**：能不能区分「给机器的标识」和「给人的描述」，这是可观测性设计的基本功。

**标准回答**：

一句话：**`code` 给机器聚合，`message` 给人定位，两者的稳定性要求正好相反。**

- `code` 必须**跨版本稳定**。它会出现在 Prometheus 的 label 里、告警规则里、值班手册里。改一个 `code` 等于让所有历史告警规则失效，所以它是准 API。
- `message` 必须**尽可能具体**，最好带上这一次的上下文（哪个 collection、哪个 job_id、哪个字段解析失败）。它每次都不一样，这正是它的价值。

把两者合成一个字段会两头不讨好：够具体就不能聚合，够稳定就不能定位。

**真实代码** —— 这个区分在 span 的失败记录里最能看出来（`app/agent/rag_v2/state.py`，检索失败结构）：

```python
# retrieve_failures 里同时存了两个字段:
#   error: 人读的单条描述,进日志
#   code:  机器读的分类,可聚合、可做指标 label
```

而 span 上传的 payload 里只放 `sorted(set(codes))` —— 去重是因为四个检索分支通常因为同一个原因失败，排序是为了两个 span 的 payload 可以直接 diff。这个细节体现的就是「机器读的字段要为可比较性做设计」。

指标侧的用法（`app/core/metrics.py`）：

```python
count_retrieval_failure(code)   # label 用 code,绝不用 message
```

**追问链**：

**Q：为什么不把 `message` 也做成模板，比如 `"连接 {host} 失败"`，这样既具体又能聚合？**

这就是 `code` 加 `context` 的组合，只是换了个写法 —— 而且是更差的写法。模板化 message 的问题是**模板本身没有约束**：谁都能写一个新模板，写的时候不会想到「这会不会和已有模板撞」。而 `code` 是枚举，加一个值要动 `errors.py`，改动可见。

另一个实际问题：模板渲染后你就拿不回模板了。日志里躺着的是渲染结果，要聚合就得反向解析 —— 又回到字符串匹配。

**Q：那 `code` 应该做多细？每个异常一个，还是几个异常共享一个？**

划分标准和 `degrade_reason` 一样：**看有没有人会因为这个区分而采取不同行动**。`llm_timeout` 和 `llm_error` 分开，因为一个指向「上游慢了/我的超时设太紧了」，另一个指向「上游报错了」，值班的第一步动作不同。而「Milvus 连接失败」和「Milvus 查询失败」我合成了一个 `retrieval_error`，因为值班的动作都是「看 Milvus 健康状况」—— 分开只会让告警规则多一条，不会让任何人更快修好。

我的标准是：**如果两个 code 的处置手册第一步是同一句话，它们应该合并。**

**拓展**：

- 现在 `code` 是字符串常量，没有集中的注册表。理想做法是像 `DegradeReason` 一样做成 `StrEnum`，这样 IDE 能补全、拼错会在测试里挂掉。之所以还没做，是因为 `code` 有一部分来自 `error_code_of()` 对第三方异常的映射，那部分本质上是动态的 —— 要做成枚举得先想清楚「未知第三方异常映射到哪个枚举值」，`unknown` 是个诚实但没什么用的答案。
- 还缺一份**从 `code` 到处置动作的映射文档**。现在这个知识在我脑子里，值班的人拿到 `error_code: retrieval_error` 得来问我。这是纯运维债，不是技术债，但它在故障时的代价是分钟级的。

### Q3. 异常分类的逻辑放在哪里？为什么不写在各个 `except` 块里？

**考点**：单一实现点意识。这题能直接看出候选人有没有维护过跨模块的错误处理。

**标准回答**：

我把分类逻辑收敛成了**四个纯函数**，放在 `app/core/errors.py`：

```python
is_retryable(exc)      -> bool              # 能不能重试
error_code_of(exc)     -> str               # 归到哪个 code
degrade_reason_of(exc) -> DegradeReason|None # 降级原因
http_status_of(exc)    -> int               # 对外 HTTP 状态
```

所有调用点（API 层、worker、graph 节点、熔断器）都调这四个函数，**没有任何地方自己判断异常类型**。

为什么不写在 `except` 块里：因为分类规则会变，而 `except` 块有几十处。举个真实的例子 —— 我要把 `httpx.ReadTimeout` 归成可重试。写在 `except` 里的话，我得找出所有捕获过它的地方，然后判断哪些需要改。找不全的后果不是报错，而是**同一个异常在系统的不同位置得到不同的裁决** —— API 层认为该重试，worker 认为不该，这种不一致极难发现，因为两条路径的测试是分开写的。

收敛到一处之后，改一个 `frozenset` 里的字符串，全系统的裁决同时更新。

**真实代码**（`app/core/errors.py`，`is_retryable`）：

```python
def is_retryable(exc: BaseException) -> bool:
    if isinstance(exc, AppError):
        return exc.retryable

    for klass in type(exc).__mro__:
        name = klass.__name__
        if name in _NON_RETRYABLE_EXCEPTION_NAMES:
            return False
        if name in _RETRYABLE_EXCEPTION_NAMES:
            return True

    return False
```

三个设计点，每个都有具体理由：

1. **`AppError` 优先**。自家异常已经明确声明了 `retryable`，不该再被名字匹配覆盖。这也保证了「显式声明 > 启发式推断」的优先级。

2. **遍历 `__mro__` 而不是只看 `type(exc).__name__`**。第三方库经常继承自己的基类（`httpx.ReadTimeout` → `httpx.TimeoutException` → …），只匹配叶子类名意味着每加一个子类都要更新集合。走 MRO 就能靠基类名一次覆盖整个家族。

3. **同一轮循环里先查「不可重试」再查「可重试」**。因为存在「基类可重试但某个子类不可」的情况，把两个判断放在同一轮遍历里、不可重试优先，语义就是「MRO 上最近的那个裁决胜出」。如果写成两个独立循环，就变成「所有不可重试规则都优先于所有可重试规则」，跨越继承距离，会误判。

**Q：为什么用类名字符串匹配，而不是 `isinstance` 加真实的类？**

因为 `isinstance` 需要 `import httpx`、`import pymilvus`、`import redis`。这会让 `app/core/errors.py` —— 项目最底层、被所有模块 import 的文件 —— 依赖一堆第三方包。后果有三个：

- 循环 import 风险大幅上升；
- 单元测试跑 errors.py 得装齐所有可选依赖；
- 任何一个包在某个环境没装，整个错误体系直接 import 失败 —— **错误处理模块自己因为错误而挂掉**，这是最不能接受的失败模式。

字符串匹配的代价是拼错不会报错。我用测试补这个洞：`tests/unit/test_errors.py` 里对每个集合里的名字都断言一次分类结果。

**追问链**：

**Q：`is_retryable` 默认返回 `False`，为什么不默认 `True`？「不确定就再试一次」听起来更宽容。**

因为两个方向的错误代价不对称。

默认 `True` 的坏情况：一个损坏的 PDF 进了入库队列，解析必然失败。默认可重试 → RQ 按 `[10, 30, 60]` 重试三次 → 这个 job 占着 worker 100 秒，四次失败写四条一样的错误日志。如果同时进来 50 个坏文件，队列被完全堵死，正常文件也进不去。**确定性失败被反复重试，等于自己对自己发起了 DoS。**

默认 `False` 的坏情况：一个真的瞬时故障没被重试，用户看到一次失败，重新提交一次就好了。

第二种明显更轻。而且默认 `False` 有个额外好处：**它让「需要重试」变成一个必须显式声明的决定**。加一个名字进 `_RETRYABLE_EXCEPTION_NAMES` 的时候，人会想一下「这个错误真的是瞬时的吗」。默认 `True` 则相反 —— 什么都不做就获得了重试，没人会去想。

**Q：那怎么保证真正需要重试的异常没被漏掉？**

靠指标，不靠想。`job_failed_total{code=...,retried=false}` 这个维度能直接看出「哪些 code 从来没被重试过」。如果某个 code 量大、失败后用户重新提交一次就好了，那它就是被漏掉的可重试异常。这比在代码里穷举第三方库的异常树可靠得多 —— **让线上数据告诉我该加哪个名字。**

**拓展**：

- 四个函数目前**都是纯函数**（无 IO、无状态），所以测试成本极低，这是刻意的。以后如果要支持「按配置调整可重试集合」，必须保持纯函数形态 —— 配置读取放到调用方，不要让 `is_retryable` 自己去读 config，否则它就没法在单元测试里被穷举了。
- 缺一个 `classify(exc)` 一次返回全部四个结果的入口。现在四个函数各自遍历一遍 MRO，同一个异常在 API 层会被走四次。性能上无所谓（异常路径本来就不是热路径），但语义上四次遍历是有可能不一致的 —— 如果哪天有人只改了其中一个集合。合并成一次分类返回一个 `ErrorFacts` 对象会更安全。

### Q4. `to_app_error` 是干什么的？它为什么故意不设置 `degrade_reason`？

**考点**：这题问的是「未知异常和已知降级的边界」。答得好说明你想清楚了降级的定义。

**标准回答**：

`to_app_error(exc)` 把任意异常规整成 `AppError`，用在 HTTP 边界上 —— 全局异常处理器需要一个统一的对象来取 `http_status` 和 `code`，不能对着裸 `KeyError` 做判断。

它**故意不设置 `degrade_reason`**，理由是：

一个到了 HTTP 边界还没被处理的未知异常，意味着**没有任何降级路径接住它**。这是彻底失败，不是降级。降级的定义是「主路径不可用，走了备用路径，用户拿到了打折的结果」；而这里用户拿到的是 500，什么都没拿到。

更要紧的是指标污染。假如我给未知异常填个 `degrade_reason=LLM_ERROR`，那 `degrade_total{reason="llm_error"}` 里就会混进真正的代码 bug —— `KeyError`、`AttributeError`、`TypeError`。值班看到这个指标涨了，会去查模型服务的配额和状态，而真实原因是我某个字段名写错了。**用一个假原因掩盖真原因，比没有原因更糟**，因为它会主动把人引向错误的方向。

**真实代码**（`app/core/errors.py`）：

```python
def to_app_error(exc: BaseException, *, context=None) -> AppError:
    """把任意异常规整为 AppError,用于 HTTP 边界统一处理。

    注意:这里**不设置 degrade_reason**。
    走到这里说明没有降级路径接住它 —— 那是彻底失败,不是降级。
    给它填一个 degrade_reason 会污染 degrade_total 指标,
    让真正的代码 bug(KeyError/AttributeError)伪装成 LLM 故障。
    """
    if isinstance(exc, AppError):
        return exc
    return AppError(
        str(exc) or type(exc).__name__,
        cause=exc,
        context=context,
    )
```

`str(exc) or type(exc).__name__` 这个兜底也有实际来由：一部分异常 `str()` 出来是空字符串（典型的是 `KeyError` 之外的一些自定义异常和 `StopIteration`），空 message 会让日志里出现一条什么信息都没有的错误记录。退到类名至少还有「是什么类型的错」。

**追问链**：

**Q：那彻底失败的情况怎么在监控上体现？**

走 HTTP 状态码和错误日志，不走 `degrade_total`。三条不同的路：

| 情况 | HTTP | 指标 | 日志级别 |
|---|---|---|---|
| 降级成功（拿到打折结果） | 200 | `degrade_total{reason=...}` | warning |
| 已分类的失败 | 502/503/504 | `http_requests_total{status="5xx"}` | error |
| 未知异常 | 500 | `http_requests_total{status="5xx"}` | error + 完整 traceback |

这三条路的告警阈值完全不同，这正是它们必须分开的原因。降级率 5% 可以接受，5xx 率 5% 是重大故障。

**Q：`to_app_error` 返回的 `AppError` 基类实例，`retryable` 是 `False`，这对不对？**

对，而且理由和 Q3 是同一个：未知异常默认不重试。但这里有个细节 —— `to_app_error` 用在 HTTP 边界，HTTP 边界本来就不重试（重试是客户端的事）。所以这个 `retryable=False` 实际上没有消费者，它只是继承来的默认值。

我提这个是因为面试里如果被问到「这个字段在这条路径上有意义吗」，诚实的答案是「没有」。它不是设计，是默认值恰好合理。

**拓展**：

- 缺一层「**未知异常的收敛监控**」。理想状态是 `to_app_error` 每次被调用都记一个 `unknown_exception_total{type="KeyError"}`，因为**走到这个函数就是一次「我没预料到」的证据**。这个指标涨了应该去补分类，而不是去修业务。现在这个信号只存在于日志里，得靠人翻。
- `context` 参数目前调用方基本没传。它本来的用途是「补充异常发生时的关键上下文」，但因为异常处理器拿不到业务上下文，实际传的机会很少。要用起来，得在业务层主动 `raise ... from` 时带上，那是另一轮改造。

### Q5. 讲一个你在这套错误体系里踩过的 bug。

**考点**：这题是送分题也是照妖镜。答不出具体 bug，说明这套体系可能是抄的模板而不是自己调出来的。

**标准回答**：

`wrap_llm_exception` 的判据写错了，导致**熔断器的错误被伪装成了模型服务的错误**。

原来的写法是：

```python
if isinstance(exc, LLMError):     # ← 错的
    return exc
```

意图是「已经是 LLM 类异常了就不用再包一层」。问题在于 `CircuitOpenError` 继承自 `AppError`，**不是** `LLMError` 的子类。于是当 LLM 熔断器打开、`guard()` 抛出 `CircuitOpenError` 时：

1. `isinstance(exc, LLMError)` 为 `False`；
2. 它不是 `TimeoutError`；
3. 落到最后一行，被包成 `LLMError`；
4. `degrade_reason` 从 `circuit_open` **变成了** `llm_error`。

后果是值班拿到 `degrade_reason: llm_error`，第一反应去查 DashScope 的配额和状态页 —— 而真实原因是**我自己的熔断器把请求拒了**。上游完全健康。这个误导方向特别恶劣，因为查上游会查出「一切正常」，然后人会开始怀疑监控本身。

修复后的判据：

```python
def wrap_llm_exception(exc, *, context=None) -> AppError:
    # 判据用 degrade_reason 是否为 None,而不是列一串 isinstance:
    # 以后新增任何带 degrade_reason 的子类都自动正确(开闭原则)。
    if isinstance(exc, AppError) and exc.degrade_reason is not None:
        return exc
    if isinstance(exc, (asyncio.TimeoutError, TimeoutError)):
        return LLMTimeoutError(f"LLM 调用超时: {exc}", cause=exc, context=context)
    return LLMError(f"LLM 调用失败: {exc}", cause=exc, context=context)
```

**为什么这个修复比「多加一个 isinstance」好**：

最直接的修法是 `isinstance(exc, (LLMError, CircuitOpenError))`。它能修好这个 bug，但**下一个带 `degrade_reason` 的新异常还会犯同样的错** —— 而且犯错的方式一样隐蔽：不报错，只是原因标错了。

改成判 `degrade_reason is not None` 之后，判据从「它是哪个类」变成了「**它是否已经自带了降级原因**」，这正好就是这个 if 真正想问的问题。以后新增任何带 `degrade_reason` 的子类，不改这个函数就自动正确 —— 开闭原则在这里不是教条，它是「让下一个人不必知道这段历史」。

**追问链**：

**Q：这个 bug 是怎么被发现的？**

写熔断器的测试时发现的 —— 断言「熔断打开后降级原因应为 `circuit_open`」，实际拿到 `llm_error`。

值得说的是**它在生产里几乎不可能被发现**：请求正常降级、正常返回、状态码正常、没有任何异常日志。唯一的症状是一个 label 的值不对。这类 bug 只能靠「对降级原因本身写断言」抓到，而大部分项目的测试只断言「降级了」不断言「原因是什么」。

这件事之后我加了一条测试规则：**凡是产生 `degrade_reason` 的路径，测试必须断言具体的 reason 值，不能只断言 `is not None`。**

**Q：`asyncio.TimeoutError` 和 `TimeoutError` 为什么都要写？**

Python 3.11 起 `asyncio.TimeoutError` 已经是 `TimeoutError` 的别名，理论上写一个就够。两个都写是为了让代码在读的时候不需要读者知道这个版本细节 —— 而且如果哪天回退到旧版本或者引入了别的 timeout 类型，这行不会静默漏掉。这是有意的冗余，成本是一个元组多一个元素。

**Q：为什么把 `TimeoutError` 单独拎出来，而不是统一包成 `LLMError`？**

因为 `http_status` 不一样：`LLMTimeoutError` 是 **504 Gateway Timeout**，`LLMError` 是 502 Bad Gateway。这个区分对网关和 APM 有实际意义 —— 504 通常会触发「上游慢」这一类的排查路径，502 触发「上游错」。合成一个就丢掉了这个信号。

**拓展**：

同类的判据错误在这套体系里还有潜在的一处：`degrade_reason_of()` 对第三方异常的映射依赖名字集合，如果一个第三方库把超时异常命名成 `DeadlineExceeded`（gRPC 风格）而我的集合里只有 `Timeout*`，就会归到 `unknown`。这不是 bug，是覆盖不全 —— 修法是前面说的 `unknown_exception_total` 指标，让漏的部分自己暴露出来，而不是我去猜第三方库的命名习惯。

## 二、降级原因体系

### Q6. 你说「降级必须带原因」，这套原因是怎么划分出来的？凭什么是十个而不是三个或三十个？

**考点**：枚举设计的划分依据。绝大多数候选人会说「按错误类型分」——那是同义反复，等于没有依据。面试官想听的是你有没有一个**能判定新值该不该加**的标准。

**标准回答**：

我的划分依据只有一条：**修复方向**。两个原因如果对应同一个修复动作，就合并；对应不同动作，就必须拆开。

判定一个新值该不该加，问一句话就够了：**值班的人看到这个原因，会去做的事，和现有任何一个原因导致的动作，是不是同一件？** 不是，才加。

之所以选「修复方向」而不是「错误类型」，是因为这个枚举的唯一消费者是**人**——具体说是凌晨三点被叫起来的那个人。他需要的不是「发生了什么」，而是「我该去动哪个东西」。按错误类型分会得到一堆技术上正确、运维上没用的值。

十个不是设计出来的，是这条标准套下来剩下的：

| 原因 | 修复方向 |
|---|---|
| `llm_timeout` | 看模型服务延迟、调超时阈值 |
| `llm_error` | 看模型服务状态、配额、密钥 |
| `parse_failed` | 改提示词或改解析代码 |
| `retrieval_failed` | 看 Milvus/BM25 是否存活 |
| `retrieval_empty` | 补文档、看切分质量 |
| `partial_retrieval` | 看是哪个子查询挂了，通常是散发放大 |
| `evidence_insufficient` | 补文档 or 调阈值，先看证据分布 |
| `circuit_open` | **看我们自己的熔断器**，不是看下游 |
| `total_budget_exceeded` | 看整条链路耗时分布，调预算 |
| `feature_disabled` | 看配置开关，什么都不用修 |

```python
class DegradeReason(StrEnum):
    """降级原因 —— 划分依据是「修复方向」,不是「错误类型」。"""

    LLM_TIMEOUT = "llm_timeout"
    LLM_ERROR = "llm_error"
    PARSE_FAILED = "parse_failed"
    RETRIEVAL_FAILED = "retrieval_failed"
    RETRIEVAL_EMPTY = "retrieval_empty"
    PARTIAL_RETRIEVAL = "partial_retrieval"
    EVIDENCE_INSUFFICIENT = "evidence_insufficient"
    CIRCUIT_OPEN = "circuit_open"
    TOTAL_BUDGET_EXCEEDED = "total_budget_exceeded"
    FEATURE_DISABLED = "feature_disabled"
```

真实代码：`app/core/errors.py`

**追问链**：

*「用 StrEnum 而不是 Enum，有什么讲究？」*

`StrEnum` 的成员本身就是 `str`，`DegradeReason.LLM_TIMEOUT == "llm_timeout"` 为真，直接 `json.dumps` 得到字符串而不是 `"DegradeReason.LLM_TIMEOUT"`，塞进 Prometheus label 也不用 `.value`。这个枚举要穿过三层边界——响应体 JSON、日志字段、指标 label，每一层都要求字符串。用普通 `Enum` 就得在每个边界写 `.value`，漏一个就是 label 里出现 `DegradeReason.LLM_ERROR` 这种脏数据，而且它和正常值不聚合，图表上直接分裂成两条线。

*「那为什么不干脆用字符串常量？」*

枚举给我三样字符串给不了的东西：拼错会被静态检查抓住（`DegradeReason.LLM_TIMEOU` 报错，`"llm_timeou"` 不报）、能被穷举（写测试遍历 `for r in DegradeReason` 保证每个值都有对应的处理分支）、能被 IDE 找到全部引用。降级原因这种要在文档、告警规则、看板里到处对齐的东西，必须有单一定义处。

**拓展**：

现在缺的是**枚举与告警规则的联动检查**。`degrade_reason` 加了新值，Grafana 看板和告警规则不会自动知道，于是新原因触发时图上没有它、告警不响。想做的是把这个枚举导出成一份 JSON，CI 里拿它和告警规则文件做 diff，有未覆盖的值就让流水线红。

再往后是**原因的分级**。十个原因里 `feature_disabled` 根本不需要人管，`circuit_open` 需要立刻看，`retrieval_empty` 可以第二天处理。现在它们在指标里权重相同，导致 `degrade_total` 这个总量指标失去意义——一次配置关闭和一次 Milvus 宕机贡献一样的计数。应该给每个原因加一个 severity 属性，告警只对高等级求和。

### Q7. `retrieval_failed` 和 `retrieval_empty` 为什么不合并？都是「检索没给出结果」。

**考点**：这题是 Q6 那条标准的实战检验。合并看起来更简洁，而这正是陷阱——它测的是你能不能顶住「简洁」的诱惑，因为这两个值的分离恰恰是整套体系里价值最高的一次拆分。

**标准回答**：

因为它们的修复方向完全相反，合并之后值班的人一定会做错事。

- `retrieval_empty`：Milvus **活着**，查询正常执行，返回了 0 条。原因是知识库里确实没有相关文档，或者切分把答案切碎了。修复动作是**写文档、调切分**。
- `retrieval_failed`：Milvus **死了**，或者连接超时、BM25 语料加载失败。查询根本没执行成功。修复动作是**去运维那个服务**。

合并成一个 `retrieval_no_result` 会发生什么：Milvus 宕机，告警说「检索没有结果」，值班的人打开知识库开始补文档——写了半小时，指标一点没动，因为库根本连不上。这就是「用一个假原因掩盖真原因」的具体形态，代价是故障期间最宝贵的那几十分钟。

反过来的错误同样有害：知识库缺文档被报成 `retrieval_failed`，值班的人去查 Milvus 状态，一切正常，于是判定为误报，把告警静音了。下一次真的宕机就没人看。

**真实代码**：

这两个原因在代码里是两个独立入口，不是同一个函数按条件分支：

```python
class RetrievalStatus(StrEnum):
    """检索结果的三态。

    这个枚举存在的唯一目的是消灭「静默返回空列表」这种撒谎式降级。
    """

    OK = "ok"
    EMPTY = "empty"
    FAILED = "failed"
```

`RetrievalError` 的类属性直接钉死了 `degrade_reason`：

```python
class RetrievalError(AppError):
    code = "retrieval_error"
    retryable = True
    http_status = 502
    degrade_reason = DegradeReason.RETRIEVAL_FAILED
```

`RETRIEVAL_EMPTY` 则不来自任何异常——它来自一次**成功**的调用。这是关键区别：空结果不是异常路径，它是正常返回值的一种取值，所以必须由返回值携带状态，而不是由异常携带。这就是 `RetrievalStatus` 存在的理由。

真实代码：`app/core/errors.py`

**追问链**：

*「返回空列表就是空列表，为什么叫「撒谎式降级」？」*

因为 `[]` 有两个含义，而调用方无法区分。上游拿到 `[]`，它既可能是「查过了，库里没有」，也可能是「查挂了，我吞了异常给你个空的」。这两种情况调用方的正确行为不同：前者应该告诉用户「知识库暂无相关内容」，后者应该告诉用户「检索服务异常，答案可能不准」并且上报故障。返回 `[]` 而不带状态，等于用一个值编码了两个不兼容的事实，接收方只能猜——猜的那一刻，可靠性设计就已经失效了。

更实际的后果：我们的 `coverage_score`（证据覆盖度）会因为空结果而降低，进而触发 `evidence_insufficient`。于是一次 Milvus 宕机会在指标上表现为「证据不足」，值班的人第三次被引向补文档。**一次错误的降级原因会沿着链路继续污染下游的降级原因。**

*「三态是不是不够？为什么没有 PARTIAL？」*

散发场景确实有部分成功，但它没进 `RetrievalStatus`，而是作为 `DegradeReason.PARTIAL_RETRIEVAL` 存在。原因是这两个枚举的作用域不同：`RetrievalStatus` 描述**单次检索调用**的结果，一次调用不存在「部分成功」；`PARTIAL_RETRIEVAL` 描述**扇入之后的整体状态**，那是四个分支聚合后才成立的判断。把它塞进 `RetrievalStatus` 会让单分支节点面对一个自己永远不该产生的值——而能产生但不该产生的值，早晚会有人产生。

**拓展**：

`retrieval_empty` 现在还不够细。真实原因至少有三种：查询词与语料完全无交集、有交集但相似度低于阈值、被域过滤器挡掉了。三种的修复方向也不同（补文档 / 调阈值 / 修过滤规则），按我自己的标准就该拆。没拆是因为现在还分不出来——需要检索层把「召回前候选数」和「阈值过滤后数量」一起上报，才有依据判定。这是**先埋点，后拆枚举**，反过来会拆出一堆填不上的值。

### Q8. `FEATURE_DISABLED` 看起来根本不是错误，为什么要放进降级原因里？

**考点**：这题看你有没有把「降级」和「错误」区分清楚。会答的人少，因为大部分人心里降级就是错误的委婉说法。

**标准回答**：

因为降级的定义是「返回的结果比正常情况差」，跟有没有出错无关。功能被配置关闭时，用户拿到的答案确实少了一环（比如没做证据质检），这就是降级；只是它的成因是我们主动的选择，不是故障。

放进去的实际理由是：**如果不放，它就会借用一个假原因。** rerank 关掉时，代码要往 `degrade_reason` 里填什么？只有两个选择——填 `None`（那么指标上这次降级不存在，看板显示一切正常，而用户确实拿到了降级结果），或者随便挑一个已有值。挑 `llm_error` 或 `retrieval_failed` 的后果是灾难性的：看板上 `degrade_total{reason="retrieval_failed"}` 突然升高，值班的人去查 Milvus，Milvus 好得很，查半小时才发现是三个月前某人关了个开关。

所以 `FEATURE_DISABLED` 的价值不在它自己，在于它**吸走了本来会污染其他原因的那部分流量**。这是枚举设计里很常见的一类值：不是因为它重要才加，是因为不加它别的值会变脏。

**追问链**：

*「那『主动关闭』和『故障』混在一个指标里，指标不就没意义了吗？」*

对，这是这个设计的真实代价，我承认。`degrade_total` 的总量因此包含了一部分恒定的、无需处理的计数——rerank 关着，每次请求都 +1。我的应对是：告警规则里**排除** `feature_disabled`，看板里单独列一条线。也就是说，我用 label 把它隔离，而不是用「不上报」把它隐藏。

这两种做法的区别在可发现性。不上报的话，将来有人误关了一个本该开的开关，线上静默降级，没有任何信号；上报并隔离的话，那条线会从 0 变成 QPS，一眼就能看见。**我宁愿指标里多一条要手动排除的线，也不要一个能静默生效的开关。**

*「如果一个功能长期关着，那条线一直是满的，不就等于噪声吗？」*

那说明我们该做的是删代码，不是删指标。一个开关关了三个月还在，要么该开，要么该删——那条一直满的线正好逼我们做这个决定。这也是 YAGNI 在运维层面的样子。

**拓展**：

现在这个值太粗，只说「有功能被关了」，没说是哪个。rerank、子查询扩展、证据质检都可以独立关闭，指标上却是同一个值。应该加一个 `feature` 维度（`degrade_total{reason="feature_disabled", feature="rerank"}`）。没做是因为 label 维度增加会乘进时间序列基数，而现在只有一个开关真的常关（rerank）——先观察，再加维度。

### Q9. `PARTIAL_RETRIEVAL` 这个原因，是谁负责判定的？为什么？

**考点**：这题连着 LangGraph 那篇的扇入设计，考的是你有没有意识到「有些判断只能在特定位置做」。

**标准回答**：

由**扇入节点**（`dedup`）判定，不能由任何一个检索分支自己判定。

原因是信息不完整：一个分支只知道自己成功还是失败，它无法区分「只有我失败了」（→ `partial_retrieval`，还有三个分支的证据可用，答案基本可信）和「四个都失败了」（→ `retrieval_failed`，完全没有证据，这是一次实质性的失败）。这两种情况的严重程度差一个数量级，而判定它们所需的信息只存在于扇入点。

所以四个分支只做一件事：**记录自己的失败，不下结论**。结论由能看到全部四份记录的那个节点下。

```python
# 检索分支只写事实,不写判断
{"retrieve_failures": [{"error": str(exc), "code": error_code_of(exc)}]}
```

扇入节点拿到四条记录后做三态判定：全成功 → 无降级；部分失败 → `PARTIAL_RETRIEVAL`；全失败 → `RETRIEVAL_FAILED`。

**追问链**：

*「让每个分支都读一下全局 state，不就能知道别人的情况了吗？」*

不能。超步（superstep）模型下四个分支是并行的，同一个超步内彼此的写入互不可见——分支 A 执行时，分支 B 可能还没跑完，也可能刚跑完但 reducer 还没合并。读到什么完全取决于调度顺序，这意味着同一次输入可能得到不同的降级原因。**结论依赖于调度时序，就等于结论不可复现，而不可复现的降级原因比没有原因更糟**——它会让你在排障时怀疑自己的记忆。

栅栏（barrier）之后才有「全部四份记录」这个稳定事实，所以判定必须在栅栏之后。

*「那如果以后检索不是四路扇出，而是动态宽度呢？判定逻辑要改吗？」*

不用，因为判定用的是比例而不是绝对数：失败数等于总分支数才算全失败。总分支数从 `state` 里的任务数拿，不是硬编码的 4。这也是为什么这个判定必须在扇入点——只有那里同时知道**分母**（发出了几个任务）和**分子**（收到了几条失败记录）。分支自己连分母都不知道。

**拓展**：

缺的是**降级原因的层级关系**。`partial_retrieval` 和 `evidence_insufficient` 经常同时成立：三路成功一路失败，剩下的证据覆盖度也不够。现在只能填一个，填哪个都丢信息。合理的做法是 `degrade_reason` 保持单值（给告警用），另加一个 `degrade_reasons: list` 记录全部成立的原因（给排障用）。没做的原因是响应体已经有向后兼容约束，加数组字段要和前端对齐，成本大于当前收益。

### Q10. 降级发生时，除了记原因，你还做了什么？

**考点**：考「降级」是不是只做了一半。只记原因不告诉用户，是很常见的半成品。

**标准回答**：

三件事，分别面向三个不同的消费者：

1. **给用户**：`generate` 节点把降级情况写进 `partial_note`，拼到答案里。用户会看到「部分检索失败，以下答案基于不完整的资料」这类提示。这一步的意义是**不让用户把降级结果当成正常结果用**——AIOps 场景下，用户可能照着答案去动生产环境。
2. **给指标**：`degrade_total{reason=...}` 计数，在 span 收敛点 `_apply` 里统一发出。
3. **给排障**：span 状态标成 `DEGRADED`，payload 里带上 `sorted(set(codes))`。

三个消费者的需求完全不同：用户要的是自然语言且不能有技术细节；指标要的是低基数的枚举值；排障要的是尽可能多的原始信息。用一份数据同时喂三个会必然导致某一方拿到不合适的东西——最常见的失败形态是把异常的 `str(exc)` 直接给用户看。

**真实代码**：

`degrade_total` 只在一个地方发出：

```python
# 埋点位置由「哪里能拿到最完整的信息」决定,不是由「哪里最方便」决定。
```

`degrade_total` 在 `_apply`（span 收敛点）发，因为那里是所有节点必经的唯一出口；而 `count_retrieval_failure(code)` 留在检索节点里发，因为只有那里拿得到 `code`。同一个原则推出两个不同的位置，不矛盾。

**追问链**：

*「span 状态为什么需要一个 DEGRADED，成功失败两态不够吗？」*

因为我的节点**故意不抛异常**——降级路径上，节点是正常返回的。如果 span 只有 OK/ERROR 两态，降级会被记成 OK，于是可观测性完全看不到降级，而降级恰恰是这个系统最需要被看到的状态。

这里有个更一般的结论：**降级设计和可观测性设计是耦合的，不能只做一半。** 你一旦决定「节点吞掉异常并降级」，就同时欠下了「必须新增一个 span 状态」这笔债。只做前半部分，得到的是一个看起来永远健康的系统——所有 span 都是 OK，错误率 0%，而用户在收降级答案。

*「那 CANCELLED 呢？超时取消算什么状态？」*

现在算 ERROR，这是个已知缺陷。总预算超时会取消掉正在跑的节点，`asyncio.CancelledError` 被计成节点错误，于是「generate 花了 85 秒把预算吃光」表现为「validate 节点报错」。真实的锅在 generate，报出来的是 validate。应该加 `CANCELLED` 状态，把取消和自身失败分开——取消是**被连带的**，不该计入该节点的失败率，否则一个慢节点会污染它后面所有节点的健康度。

**拓展**：

`partial_note` 现在是代码拼的固定句式，好处是绝对可控（不会有模型幻觉），坏处是生硬，且不随场景变化。想做的是把降级原因作为结构化输入交给生成节点，让它在答案开头自然地说明局限——但这要求模型绝不能夸大或缩小局限程度，需要专门的评测集来验证，成本不低。**在「生硬但准确」和「自然但可能失真」之间，可靠性文档选前者。**

### Q11. 你怎么保证每个降级路径都真的填了原因，而不是漏填？

**考点**：从设计跳到执行。前面十题讲的都是「应该怎样」，这题问「你凭什么相信代码真的是这样」。

**标准回答**：

三层保障，从强到弱：

**第一层，让原因跟着异常走，不靠调用方填。** `degrade_reason` 是异常的**类属性**，不是构造参数。抛 `RetrievalError` 的人不需要知道降级原因是什么，原因已经钉在类上了。这是最强的保障，因为它把「记得填」变成了「不可能不填」。

```python
class RetrievalError(AppError):
    code = "retrieval_error"
    retryable = True
    http_status = 502
    degrade_reason = DegradeReason.RETRIEVAL_FAILED
```

子类只覆盖类属性，从不重写 `__init__`——重写了就会出现「有的子类支持传 degrade_reason，有的不支持」这种不一致，而不一致的接口最终一定会被用错。

**第二层，分类函数兜底。** 第三方异常没有类属性，走 `degrade_reason_of(exc)` 集中映射。集中的意义是：新增映射只改一处，而不是在二十个 `except` 块里各写一遍。

**第三层，测试遍历枚举。** 测试里 `for reason in DegradeReason` 断言每个值都有产生路径。这层最弱——它能发现「定义了但没人用」的死值，发现不了「用了但用错了」。

**追问链**：

*「第三层既然最弱，为什么还留着？」*

因为它防的是一类很隐蔽的腐化：某次重构把产生 `parse_failed` 的分支删了，枚举值还在，文档还在，告警规则还在，看板上那条线永远是 0。没人会去查一条一直为 0 的线——大家会默认「这类问题没发生过」，实际上是「这类问题不再被上报」。**指标为零有两种含义，而看板不会告诉你是哪一种。** 这个测试的作用就是把这两种含义区分开。

*「你前面说 `wrap_llm_exception` 曾经把 `circuit_open` 覆盖成 `llm_error`，那不就是第一层失效了吗？」*

是，那正好说明第一层保障的是「有没有填」，不保障「填得对不对」。当时的判据是 `isinstance(exc, LLMError)`，而 `CircuitOpenError` 是 `AppError` 的子类但不是 `LLMError` 的子类，于是它没被识别成「已经带了原因的异常」，被当作裸异常重新包装了一遍，原因从 `circuit_open` 翻成了 `llm_error`。后果是值班的人去查模型服务配额，而真凶是我们自己的熔断器。

修法是把判据换成 `exc.degrade_reason is not None`——问「你带原因了吗」，而不是问「你是哪个类」。这样以后新增任何带 `degrade_reason` 的子类都自动正确，不需要回来改这个 `if`。这是开闭原则在异常体系里最实际的一次应用，具体见 Q5。

**拓展**：

想加的是**静态检查**：用 AST 扫描所有 `except` 块，凡是捕获后没有 raise、没有调分类函数、也没有写 `degrade_reason` 的，标记出来。这类「静默吞异常」的代码是可靠性的头号杀手，而它在 review 里极难看出来——一个 `except Exception: pass` 只有两行，混在三百行 diff 里根本不显眼。这个检查不需要多聪明，能抓住 80% 就已经比人工 review 强。

## 三、HTTP 边界与错误响应

### Q12. 讲一个你改过的、影响面最大的可靠性问题。

**考点**：这题看你能不能识别「表面上能跑、实际上把整个监控体系废掉」的那类问题。它们不产生报错，所以最难被发现，也最值钱。

**标准回答**：

改造前，所有异常都返回 **HTTP 200**，业务错误码放在响应体里：

```json
HTTP/1.1 200 OK
{"code": 500, "message": "检索服务异常", "data": {"success": false}}
```

这个写法在国内后端很常见，前端读 `body.code` 也能正常工作。问题是：**HTTP 层面的一切自动监控都失效了。**

具体失效的东西，一个一个数：

| 组件 | 它看到的 | 真实情况 |
|---|---|---|
| Nginx `$status` 日志 | 200 | 500 |
| 负载均衡健康检查 | 健康 | 服务在报错 |
| APM（错误率） | 0% | 可能 30% |
| `http_requests_total{status="5xx"}` | 0 | 应该有值 |
| 云厂商监控大盘 | 全绿 | 有故障 |
| 网关重试策略 | 不触发（200 不重试） | 该重试 |

也就是说：**我们的错误率永远是 0%。** 不是「统计不准」，是恒等于零，无论线上烧成什么样。

最讽刺的地方在于这个项目本身是干什么的——它是个 AIOps 系统，做的是帮别人发现故障。而它自己的故障对所有标准监控完全隐身。这不是配置疏漏，是一个把自己排除在自己所解决的问题之外的架构缺陷。

修法是加全局异常处理器，让 HTTP 状态码回归语义，同时**响应体保持完全向后兼容**。

**真实代码**：

```python
def build_error_body(...)-> dict:
    """构造错误响应体。

    保持与现有 ApiResponse 兼容:code / message / data.success / data.errorMessage
    三个新增字段都是**追加**的,不改动任何既有字段的含义 ——
    前端不改代码也能正常工作,改了代码能拿到更多信息。
    """
```

新增的三个字段全是追加：`error_code`（机器可读分类）、`degrade_reason`（降级原因）、`request_id`（串日志用）。旧字段一个没动。

真实代码：`app/core/exception_handlers.py`

**追问链**：

*「响应体里已经有 code 了，为什么还要 HTTP 状态码？信息不是重复了吗？」*

因为消费者不同。响应体的 `code` 只有**我们的前端**读得懂；HTTP 状态码是**所有中间设施**读得懂的通用语言——网关、LB、CDN、APM、Service Mesh、云监控，它们都不会去解析你的 JSON body，也不该去解析。可靠性设施的价值在于「不需要业务配合就能工作」，用 200 包裹错误恰好废掉了这个价值。

信息确实重复，但这是**故意的冗余**：同一个事实要用两种语言各说一遍，因为有两类听众。

*「那为什么不干脆把响应体的 code 删掉，只留 HTTP 状态码？」*

因为前端已经在读它了，删掉是破坏性变更。可靠性改造有个自己的原则：**修可靠性的改动，本身必须是低风险的。** 如果我为了让监控正确而引入一次前端故障，净收益是负的。所以我选择只加不改——HTTP 状态码修正给设施用，响应体维持原样给前端用，两边同时正确。等前端有余量再收敛。

*「4xx 和 5xx 你怎么分？」*

按「谁该改代码」分。`InvalidRequestError` → 400，客户端传错了参数；`RetrievalError`/`LLMError` → 502，我们的下游挂了；`LLMTimeoutError`/`TotalBudgetExceededError` → 504，超时；`CircuitOpenError` → 503，我们主动拒绝且带 Retry-After 语义。这四个映射写在异常类的 `http_status` 类属性上，不在处理器里做 if-else——理由和 Q11 一样，让状态码跟着异常走。

**拓展**：

现在缺的是**对这个修复本身的回归保护**。将来有人为了「统一返回格式」再把状态码改回 200，测试不会拦——因为响应体没变。应该加一组契约测试：对每类异常断言 HTTP 状态码，而不只断言 body。**这次修复的价值全在状态码上，那么测试就必须断言状态码。**

### Q13. 为什么用全局异常处理器，而不是在每个路由里 try/except？

**考点**：横切关注点的识别。会答「更简洁」的人很多，能说清「为什么这件事本质上不属于路由」的人少。

**标准回答**：

因为「异常 → HTTP 状态码」是一个**横切关注点**：它跟具体哪个接口无关，规则完全一致，且必须一致。

放在每个路由里会有三个必然后果：

1. **不一致**。八个接口写八遍映射，早晚有一个漏了某个异常类型，或者把 502 写成 500。而不一致的错误响应比统一的错误响应更难排查——你会怀疑是不是两个接口走了不同的代码路径。
2. **漏网**。`try/except` 只能捕获你想到的异常。真正拖垮服务的往往是没想到的那个（`KeyError`、`AttributeError`），它会穿透所有 `except AppError` 直达 Starlette 默认处理器。
3. **业务代码被淹没**。一个二十行的路由函数配三十行异常映射，读代码的人得先跳过异常处理才能看到业务逻辑。

全局处理器把这件事收敛到一处，路由函数里一个 `try` 都不需要——**该抛就抛，边界统一处理**。这和检索层「低层抛、高层捕」是同一个原则的不同层级应用。

**真实代码**：

```python
def register_exception_handlers(app) -> None:
    app.add_exception_handler(AppError, app_error_handler)
    app.add_exception_handler(Exception, unhandled_exception_handler)
```

两个处理器分工明确：`AppError` 是**已分类**的异常，走结构化响应；`Exception` 是**未分类**的，兜底，防止用户看到 Starlette 的纯文本 `Internal Server Error`。

真实代码：`app/core/exception_handlers.py`

**追问链**：

*「兜底那个处理器如果不加，会怎样？」*

Starlette 会返回纯文本 `Internal Server Error`，`Content-Type: text/plain`。前端拿 `response.json()` 去解析会直接抛 JSON 解析错误，然后大概率走进一个没写好的 catch，最终表现是**白屏**——用户什么都看不到，连「服务异常」都看不到。

所以这个兜底处理器的价值不在于错误信息更详细，而在于**错误的形态是可预期的**。前端只需要处理一种格式，无论后端出了什么问题。这类「保证输出形态统一」的兜底，是可靠性里性价比最高的一类代码——十几行，覆盖所有未知情况。

*「为什么不接管 `HTTPException`？」*

因为 FastAPI 自己的 `HTTPException` 已经有正确的状态码和 JSON 响应了，接管它只会引入两个风险：一是我可能把 FastAPI 内部依赖的行为改坏（比如 `422` 的校验错误详情结构，前端和文档都在依赖），二是我得重新实现一遍它已经做对的事。

判断标准是：**只接管当前行为有问题的部分。** `HTTPException` 没问题，那就不动。可靠性改造最容易犯的错就是趁机把周边一起重写——每一处重写都是一次新的风险敞口，而这些风险没有任何一条来自你要修的那个问题。

*「两个处理器的日志级别一样吗？」*

不一样，这里有个细节：`AppError` 按状态码分级，**5xx 记 error，4xx 记 warning**。原因是 4xx 是客户端传错参数，不是我们的故障，它不该进错误率告警——不然一个刷接口的脚本传一堆非法参数就能把我们的错误率告警打爆，值班的人被叫起来看一堆「用户传了个空字符串」。

同时 `AppError` 是**预期内**的失败，不打 traceback（打了也没信息量，栈都一样）；兜底处理器用 `logger.opt(exception=exc)` 打完整栈，因为未分类异常的价值全在栈上。

**拓展**：

现在的日志分级只看状态码，不看频率。一次 502 是 error，一分钟一千次 502 也是一千条 error——日志被同一个故障刷满，真正有信息量的那几条被埋掉。想做的是在处理器里加采样：同一个 `error_code` 在窗口内超过 N 次就降级为聚合日志（「过去 60s 内 retrieval_error × 843」）。这个改动要小心，因为采样本身也可能藏掉唯一一次关键错误，所以第一条和最后一条必须完整保留。

### Q14. `_resolve_request_id` 为什么要先读 ASGI scope，再读 ContextVar？直接读 ContextVar 不行吗？

**考点**：这题技术密度很高。它要求你真的理解 Starlette 的中间件是怎么套的，而不只是「知道有中间件」。答不出来不丢人，答出来会很加分。

**标准回答**：

不行，直接读 ContextVar 会导致**未分类异常的 `request_id` 永远是 null**——恰好是最需要它的那一次。

原因在中间件的嵌套顺序。Starlette 把 `Exception` 的处理器挂在 `ServerErrorMiddleware`，那是**最外层**；而我们的 `RequestIdMiddleware` 在里面，它的 `finally` 里会 `reset_request_id(token)`：

```
ServerErrorMiddleware        ← Exception 处理器在这里(最外层)
  └── RequestIdMiddleware    ← 设置 ContextVar,finally 里 reset
        └── ExceptionMiddleware  ← AppError 处理器在这里
              └── 路由
```

于是两条路径的表现完全不同：

- **`AppError`**：在内层 `ExceptionMiddleware` 被捕获，此时 `RequestIdMiddleware` 的 `finally` 还没执行，ContextVar 里有值 → 正常。
- **未分类异常**：穿透到最外层 `ServerErrorMiddleware`，路上经过 `RequestIdMiddleware` 的 `finally`，ContextVar 已经被 reset → 读到 `None`。

所以未分类异常——也就是我们最不了解、最需要靠 `request_id` 去日志里翻上下文的那类——反而拿不到 `request_id`。这是典型的「防护措施在最需要它的场景下失效」。

修法是从 ASGI `scope` 里读。`scope` 是一个普通 dict，跟着请求走，不受 ContextVar 的生命周期影响，中间件 reset 不掉它。

**真实代码**：

```python
def _resolve_request_id(request) -> str | None:
    """优先从 ASGI scope 取,其次从 ContextVar 取。

    顺序不能反 —— 见上面的中间件嵌套说明。
    """
```

同一个原因还导致另一件事：错误响应必须**自己重写响应头**。正常响应的 `X-Request-ID` 是 `send_with_request_id` 包装器加的，但异常走到外层时那个包装器已经不在调用链里了，所以 `_json_error_response` 得自己把头塞回去。

真实代码：`app/core/exception_handlers.py`

**追问链**：

*「那为什么还留着 ContextVar 这条路？既然 scope 总是有值。」*

因为不是所有异常处理都发生在有 `Request` 对象的地方。RQ worker 里没有 ASGI scope，那边只有 ContextVar；而日志模块也要读 `request_id`，它拿不到 `request`。两条路径覆盖两类调用者，读取顺序保证在都有值时用更可靠的那个。

*「把 reset 去掉，让 ContextVar 一直留着，不就没这个问题了？」*

不能。ContextVar 不 reset 会有两个后果：一是嵌套场景下内层结束后外层读到内层的值（`reset(token)` 的存在就是为了支持嵌套）；二是在线程池复用的场景下，上一个请求的 `request_id` 可能被下一个请求读到——**日志里出现张冠李戴的 request_id，比没有 request_id 危险得多**，因为你会顺着错的那条线索排查很久。

所以 reset 是对的，需要修的是读取方，不是写入方。这个判断很关键：出问题时优先怀疑「我读的位置不对」，而不是急着放宽写入方的约束——放宽约束通常会换来一个更隐蔽的问题。

*「`X-Request-ID` 从客户端传进来的话，你信不信？」*

信，但只用于串联，不用于任何安全或幂等判断。透传客户端的 `request_id` 是分布式追踪的常规做法，能把前端日志和后端日志串起来。但它是**不可信输入**：可能重复、可能超长、可能带注入字符。所以要做长度截断和字符白名单，且绝不能拿它当数据库主键或幂等键——那样客户端就能通过重复的 id 影响我们的写入行为。

**拓展**：

现在只有 `request_id`，没有 `trace_id` / `span_id` 的标准传播。想做的是接 OpenTelemetry 的 W3C Trace Context（`traceparent` 头），这样跨服务调用能自动串联，而不是靠我们自己约定一个头。没做是因为现在只有一个服务，跨服务传播的收益为零，而引入 OTel SDK 的成本不小——**追踪基础设施的价值随服务数量超线性增长，单服务时几乎为零。**

### Q15. 你的错误响应体里既有 `code` 又有 `error_code`，这不是冗余吗？

**考点**：向后兼容的具体手法。这题小，但能看出你有没有真的在生产环境改过响应格式。

**标准回答**：

是冗余，而且是必要的冗余。两个字段服务两个时期的消费者：

- `code`：整数，改造前就有，前端在用。值是 `500`/`400` 这类，语义上和 HTTP 状态码重复。
- `error_code`：字符串，新增，值是 `retrieval_error`/`llm_timeout` 这类**细粒度分类**。

关键区别在**粒度**。`code: 500` 告诉你「服务端出错」，这个信息量太低——检索挂了、模型超时、解析失败，全都是 500，前端无法据此做差异化处理，监控也无法据此聚合。`error_code` 才是能做 label、能分组、能写告警规则的那个。

之所以不改 `code` 而是新增，理由和 Q12 一样：**只加不改。** 前端不动代码，行为完全不变；前端想升级，读新字段就行。这让可靠性改造可以在不协调发布的情况下上线，而需要协调发布的改造往往会被无限期推迟。

**追问链**：

*「那 `code` 什么时候能删？」*

等到能证明没有调用方在读它的时候。具体做法是给 `code` 加一个访问统计——但响应字段是被动读取的，服务端看不到前端读了哪个字段。所以实际路径只能是：前端埋点上报自己读的是哪个字段，或者干脆约定一个废弃窗口（比如两个大版本）。

我倾向于**先不删**。一个整数字段的维护成本几乎为零，而删除它的风险是真实的。可靠性工作里，删除比新增更需要证据。

*「`degrade_reason` 也在响应体里，用户能看到降级原因，这合适吗？」*

对内合适，对外需要区分。`degrade_reason` 的值是 `retrieval_failed` 这类内部枚举，暴露给最终用户意义不大（他不知道 Milvus 是什么），但对**调用我们接口的其他团队**很有价值——他们能据此决定要不要重试、要不要走备用逻辑。

需要注意的是它绝不能携带具体的错误细节。`degrade_reason` 是枚举值，基数固定、不含任何内部路径、栈、SQL 或主机名。真正需要防的是把 `str(exc)` 直接塞进 `message` 给用户——那里面可能有连接串、文件路径、内部 IP。这条边界在 `errors.py` 里靠 `context` 字段隔开：详细上下文进日志，不进响应体。

**拓展**：

现在 `message` 字段还是中文自然语言，前端如果要做国际化就只能靠字符串匹配，很脆。合理做法是响应体给 `error_code` + 结构化参数，文案由前端按 `error_code` 查表生成。没做是因为当前只有一个中文前端，收益为零。但这个设计债要记着：**一旦有第二个客户端，文案就必须移出后端**。

### Q16. 分类函数 `is_retryable` 为什么默认返回 `False`？默认重试不是更安全吗？

**考点**：默认值的选择。这题看你能不能算清「重试一个不该重试的东西」的成本——很多人默认重试更安全，那是没被伤过。

**标准回答**：

因为默认重试的代价比默认不重试大得多，而且是**放大式**的。

默认 `True` 会发生什么：一个损坏的 PDF 进来，解析抛异常，被当成可重试，跑三遍——每遍都要重新下载、重新解析、重新占用 worker 和内存。三次全失败，最终结果和一次失败一样，只是多花了三倍资源、多占了几分钟 worker、日志里多了三条一模一样的错误。如果队列里有一批这样的坏文件，worker 会被完全占满，**正常任务全部排队**。也就是说，默认重试会把「几个坏文件」放大成「整条流水线停摆」。

默认 `False` 的代价：某个我没登记的瞬时异常不被重试，任务失败一次，需要人手动重跑。代价是有限的、局部的、可见的。

两者的差别在**失败模式**：默认不重试是「漏掉一次自动恢复」，默认重试是「用尽资源去做注定失败的事」。可靠性设计里，前者可以接受，后者不行。

**真实代码**：

```python
def is_retryable(exc: BaseException) -> bool:
    if isinstance(exc, AppError):
        return exc.retryable
    for klass in type(exc).__mro__:
        name = klass.__name__
        if name in _NON_RETRYABLE_EXCEPTION_NAMES:
            return False
        if name in _RETRYABLE_EXCEPTION_NAMES:
            return True
    return False
```

三段判定，顺序有讲究：

1. **自己的异常**优先——它自带 `retryable` 类属性，最可信。
2. **显式不可重试**在前，**已知瞬时**在后。顺序反了会出问题：某个异常同时匹配两个集合时，「不可重试」必须胜出。保守方向优先。
3. 遍历 `__mro__` 而不是只看 `type(exc).__name__`，这样子类能继承父类的判定。

真实代码：`app/core/errors.py`

**追问链**：

*「为什么用类名字符串匹配，而不是 `isinstance`？」*

为了避免对第三方包的硬依赖。要用 `isinstance` 判断 `pymilvus.MilvusException`，就得 `import pymilvus`——而 `errors.py` 是整个项目最底层的模块，被所有地方 import。让它依赖 pymilvus、httpx、openai 三个包，会导致：任何一个包没装，整个项目连异常定义都 import 不了；而这个模块恰恰是**出问题时最需要能用**的那个。

按名字匹配的代价是不精确（两个不同包的同名异常会被混淆）和拼错不报错。我认为可接受，因为这个集合很小、集中在一处、有测试覆盖。这是「底层模块保持零依赖」和「判定精确」之间的取舍，我选前者。

*「那怎么防拼错？」*

测试里对每个登记的名字构造一个同名异常类，断言分类结果。这只能验证「这个名字确实会被匹配」，验证不了「这个名字对应的第三方异常真的存在」。后者需要在有第三方包的环境里做一次导入检查，属于集成测试的范围。

*「`AppError` 分支为什么不放最后？」*

因为它最精确，而且 `AppError` 的 `retryable` 是我自己定的，不该被名字匹配覆盖。举个具体的：`ParseError` 是 `AppError` 子类且 `retryable = False`，但如果名字匹配先跑，而 `_RETRYABLE_EXCEPTION_NAMES` 里恰好有个泛化的名字命中了它的某个基类，就会得到 `True` —— **我的显式声明被启发式规则推翻了**。所有分类逻辑都该遵循这个顺序：显式声明 > 启发式匹配 > 默认值。

**拓展**：

现在的 `retryable` 是布尔，表达不了「可重试但要等更久」。数据库连接池耗尽和网络抖动都是可重试的，但前者应该等几十秒（等连接释放），后者一秒就够。合理的做法是把 `retryable: bool` 升级成 `retry_policy`，带上建议间隔。没做是因为当前只有三类重试场景，用一套 `[10, 30, 60]` 间隔覆盖够了——**在两三个场景时引入策略对象是过度设计，到五六个时就是欠债了**。

## 四、超时与重试语义

### Q17. 你项目里的超时是怎么设计的？为什么需要两层？

**考点**：能不能区分「单次调用超时」和「一次用户请求的总预算」。只答一层的人，通常没经历过链路变长之后超时失效的场景。

**标准回答**：

两层，管的是两件不同的事：

| 层级 | 参数 | 值 | 语义 |
|---|---|---|---|
| 单次调用 | `llm_timeout_seconds` | 60s | **这一次** LLM 调用最多等多久 |
| 整体预算 | `chat_total_budget_seconds` | 90s | **这一个用户**最多等多久 |

为什么缺一不可：chat_v2 一次请求串行调三次 LLM（rewrite → generate → validate）。只有单次超时时，最坏情况是 3 × 60s = 180s，再加检索耗时，用户等 185s+ 才拿到一个失败——**每一次调用都"没超时"，但整个请求早就该被放弃了**。

反过来只有总预算也不行：总预算是外层 `asyncio.timeout`，它只能在 90s 到点时取消，中间那次挂死的调用会一直占着连接池的位置到 90s。单次超时的价值是**尽早释放资源**，总预算的价值是**兜住用户体验上限**。

**真实代码**：

```python
# app/config.py:70
llm_timeout_seconds: float = 60.0
# app/config.py:81
chat_total_budget_seconds: float = 90.0
```

```python
# app/agent/rag_v2/service.py:61
async with asyncio.timeout(config.chat_total_budget_seconds):
    async for state in self.graph.astream(inputs, stream_mode="values"):
        ...
```

参数收敛在 `LLMFactory`（`app/core/llm_factory.py:84`）：

```python
timeout = config.llm_timeout_seconds if timeout is None else timeout
max_retries = config.llm_max_retries if max_retries is None else max_retries
```

**追问链**：

> **追问 1：这个 60s 是怎么定出来的？**
>
> 不是拍的，是倒推的：总预算 90s ÷ 串行 3 次 ≈ 30s。但 generate 节点要生成长答案，实测 p99 在 20s 上下，30s 太紧会误杀正常请求。所以选了一个"单次不误杀、靠外层总预算兜住整体"的分工：单次给 60s 只负责挡住**挂死**（分钟级别的异常），正常慢请求由总预算统一裁决。

> **追问 2：那两层参数不一致（60 × 3 > 90）算配置错误吗？**
>
> 不算，是有意的。如果要求 `单次 × 次数 ≤ 总预算`，单次就得压到 30s，那就是用单次超时去做整体预算该做的事。让单次超时宽松、总预算收紧，是因为**取消一次挂死的调用**和**放弃这次回答**是两个决策，不该由一个参数同时表达。

> **追问 3：为什么用 `is None` 判断，不用 `timeout or config.x`？**
>
> 因为 `or` 会把 `timeout=0` 静默替换成默认值。`0` 在超时语义里是"立刻超时"，是一个合法且有用的值（测试里要构造超时场景）。用 `or` 会让显式传 0 的调用方拿到 60s，而且不报错——这是一类很难查的 bug：参数传了、行为没变。这个坑在 `llm_factory.py:76-79` 的 docstring 里写着。

**拓展**：

现在缺一层：**下游各自的超时**。Milvus 有 `milvus_timeout`，但 BM25 语料加载、embedding 调用没有独立超时，它们只被总预算覆盖。真正完整的超时体系应该是「每个 IO 边界都有自己的超时，且内层严格小于外层」，这叫超时预算的**层级递减**。补法是把预算作为参数往下传（`deadline` 而不是 `timeout`——传绝对时间点，下游自己算还剩多少），这也是 Go 的 `context.WithDeadline` 解决的问题。

### Q18. 你项目里一共有几层重试？它们会不会叠加？

**考点**：重试是最容易叠加成灾的机制。能不能把项目里所有重试点数清楚，是「有没有真正对生产负责」的分水岭。

**标准回答**：

四层，我数过：

| 层 | 位置 | 次数 | 谁触发 |
|---|---|---|---|
| SDK | openai SDK `max_retries` | 2 | LLM HTTP 层自动 |
| MCP | `retry_interceptor` | 3 | 工具调用失败 |
| RQ | `default_job_retry()` | 3，间隔 10/30/60s | 异步任务失败 |
| 熔断器 | HALF_OPEN 探测 | 1 | 冷却期结束 |

**会叠加，而且我算过最坏情况**：LLM 一次调用 = 1 + 2 次重试 = 3 次 HTTP 请求，每次 60s 超时 = 180s。这已经超过 90s 总预算了——也就是说 **SDK 重试在总预算下是不完整生效的**，第三次重试还没发出去就被外层取消。

这不是 bug，但是一个必须知道的事实：单次超时 60s + 重试 2 次这组参数，实际起作用的只有前一次半。要么把 `llm_timeout_seconds` 降到 25s 让三次都能跑完，要么承认重试主要靠 SDK 自己的快速失败场景（连接被拒、429）生效。我选了后者并写进注释，因为**慢**故障重试没意义（上游都慢了，重试只是加倍施压），**快**故障重试才有意义，而快故障不吃满 60s。

**真实代码**：

```python
# app/config.py:75
llm_max_retries: int = 2
```

```python
# app/core/job_failure.py
_DEFAULT_RETRY_MAX = 3
_DEFAULT_RETRY_INTERVALS = [10, 30, 60]
```

**追问链**：

> **追问 1：MCP 那层重试为什么不返回异常，而是返回 `isError=True`？**
>
> 因为 MCP 工具跑在 ReAct 循环里，**模型是调度器**。抛异常会中断整个 agent 循环；返回 `isError=True` 让模型看到"这个工具失败了"，它可以换个工具、换个参数、或者直接告诉用户。一般规律：**固定流程里的失败交给代码处理，ReAct 里的失败交给模型处理**。

> **追问 2：这四层重试有没有统一的退避策略？**
>
> 没有，这是现存缺陷。MCP 用 1/2/4s 指数退避但**没有 jitter**——多个客户端同时失败会在同一时刻同时重试，把刚恢复的下游再打挂一次（thundering herd）。RQ 用固定表 [10,30,60]。SDK 用 openai 自己的策略。三套退避互不知情。正确做法是抽一个 `backoff(attempt) -> float` 带 full jitter，四处共用。

> **追问 3：重试和熔断器是什么关系？会不会互相打架？**
>
> 会，顺序很重要。熔断器必须在**重试之外**：先过熔断器，再进重试。反过来的话，下游挂了时每个请求还要先重试 3 次才被计一次失败，熔断器的灵敏度被除以 3，而且每次熔断判定前都白等 3 × timeout。这就是 `guard()` 包在最外层的原因。

**拓展**：

缺一个**重试预算**（retry budget）的概念：Google SRE 的做法是限制"重试请求数 / 正常请求数 ≤ 10%"，超了就不再重试。这比"每个请求重试 N 次"健壮，因为它约束的是**给下游的总压力**，而不是单个请求的固执程度。实现上是一个滑动窗口计数器，和熔断器共用同一个 registry 就行。

### Q19. 总预算 90s 耗尽的时候，用户看到什么？

**考点**：超时之后的行为，比超时本身更能体现设计水平。答"返回 504"的人没想过"已经生成的内容怎么办"。

**标准回答**：

看到**已经产出的部分内容 + 一句明确的中断说明**，不是一个空的错误页。

关键实现是用 `astream` 而不是 `ainvoke`。`asyncio.timeout` 触发时会取消里面的任务，`ainvoke` 被取消就什么都没有了——中间已经检索到的文档、已经生成的一半答案全部丢失。`astream(stream_mode="values")` 每个超步结束吐一个**完整快照**，我把它存进 `last_state`，超时后从最后一个快照里拼结果。

**真实代码**：

```python
# app/agent/rag_v2/service.py:57
last_state: Dict[str, Any] = {}
try:
    async with asyncio.timeout(config.chat_total_budget_seconds):
        async for state in self.graph.astream(inputs, stream_mode="values"):
            if state:
                last_state = state
except asyncio.TimeoutError:
    logger.warning(
        f"[rag_v2:{session_id}] 总预算 {config.chat_total_budget_seconds}s 耗尽，"
        f"返回部分结果; 已有字段={sorted(last_state.keys())}"
    )

result = _build_query_result(last_state)
if ...:
    result["answer"] = result["answer"] or _budget_exceeded_answer(last_state)
```

日志里打 `已有字段=sorted(last_state.keys())` 是刻意的：超时排查的第一个问题永远是"卡在哪一步"，字段列表直接回答了这个问题——有 `documents` 没 `answer` 就是卡在 generate。

**追问链**：

> **追问 1：SSE 流式那条路怎么处理超时？HTTP 200 已经发出去了。**
>
> 这是流式的根本约束：**响应头已发出，状态码改不了**。所以只能在事件体里传递失败信号（`service.py:124-128` 发一个说明预算耗尽的事件），而且**不能抛异常**——抛异常会直接断连接，客户端连"为什么断的"都不知道，还会丢掉已经推送的内容。这是流式接口和普通接口在错误处理上最大的差异，也是为什么流式接口必须自己定义一套业务层的错误事件协议。

> **追问 2：返回部分结果算不算撒谎？用户可能以为这就是完整答案。**
>
> 只要**明说**就不算。`_budget_exceeded_answer` 生成的文案里明确写了"本次回答超出 N 秒预算，已中断"。撒谎式降级是"静默返回一个看起来正常的结果"，带原因的降级是"给出能给的 + 说清缺了什么"。整个降级体系的判据都是这一条。

> **追问 3：为什么用 `result["answer"] or ...` 而不是直接覆盖？**
>
> 因为超时可能发生在 validate 阶段——那时 answer 已经生成好了，只是没来得及质检。这种情况下把答案覆盖成"超时了"是**主动丢弃已完成的工作**。`or` 表达的是"只有确实没答案时才用兜底文案"。

**拓展**：

现在少一个 span 状态：`CANCELLED`。被总预算取消的节点，在观测上和成功节点长得一样（因为取消是通过异常传播的，而节点内部 `except Exception` 会吞掉）。缺了它就没法回答"超时的请求里，最常被取消的是哪个节点"——而这恰好是优化超时配置最需要的数据。补法是在 `instrument_node` 里单独 `except asyncio.CancelledError` 打 CANCELLED 再 `raise`，和熔断器里那段处理是同一个道理。

### Q20. `apply_retry_policy` 干什么？为什么要覆盖 RQ 自己的重试次数？

**考点**：这题考的是「读过依赖库源码」这件事本身。RQ 的 `Retry(max=N)` 是无条件的，要做到"按异常类型决定是否重试"，必须知道 RQ 内部怎么读这个值。

**标准回答**：

RQ 的 `Retry(max=3)` 是**无条件重试 3 次**——它不看异常是什么。但重试对不同异常的价值完全不同：

- Milvus 连接超时：值得重试，10 秒后可能就好了
- PDF 文件本身损坏：重试 3 次就是把同一个错误犯 3 遍，白占 worker

所以我在失败处理里读异常分类，非可重试异常直接把 `job.retries_left` 清零。

**真实代码**（`app/core/job_failure.py`）：

```python
def apply_retry_policy(exc: BaseException) -> bool:
    retryable = is_retryable(exc)
    job = get_current_job()
    if job is None:
        return retryable          # 不在 RQ 上下文里就只返回判断,不做副作用
    if not retryable:
        job.retries_left = 0
    return retryable
```

这段能work的依据是我翻了 rq 2.9 的源码：`worker.py` 里 `_job_stack.push(self)` 说明 `get_current_job()` 拿到的是**同一个对象**，而 `handle_job_failure` 读的是内存里的 `retries_left`，中间**没有 `job.refresh()`**。所以在 except 块里改这个属性，RQ 随后就会读到改后的值。

`job is None` 时只返回判断、不产生副作用——这样它在单元测试里是个纯函数，不需要造 RQ 上下文。

**追问链**：

> **追问 1：依赖库内部实现改了怎么办？这算不算脆弱耦合？**
>
> 算，我承认。缓解手段是两条：一是 `job is None` 的分支保证了行为退化是"按 RQ 默认重试"而不是崩溃；二是这个行为应该有测试锁住——构造一个非可重试异常，断言 `retries_left == 0`。更干净的方案是用 RQ 的 `Callback`/自定义 `Worker.handle_job_failure`，但那是更大的改造，当前收益不值。**知道自己踩在什么上面**，比假装没踩要好。

> **追问 2：`[10, 30, 60]` 为什么递增？固定 10s 三次不行吗？**
>
> 固定 10s × 3 只覆盖 30 秒的故障窗口。而瞬时故障的恢复时间是**未知**的：数据库主从切换要几十秒，容器重启要一两分钟。递增间隔用同样的 3 次重试覆盖了 100 秒窗口，代价只是"最坏情况下慢一点"——而这是异步任务，慢一点没人在意。这就是指数退避的本质：**用时间换覆盖面**。

> **追问 3：为什么是 3 次？为什么不多试几次？**
>
> 因为重试次数超过 3 之后，边际收益急剧下降而成本线性上升：占着 worker 槽位、推迟真实故障的暴露时间。100 秒还没好的故障，大概不是瞬时故障，该让它进 FAILED 让人看见。**重试的目的是吞掉抖动，不是掩盖故障。**

**拓展**：

`format_failure_message` 里有一个容易被忽略的细节——它在消息末尾追加"，RQ 将自动重试"。这行字的作用是防止有人看到 FAILED 就开始手工排查一个十秒后会自愈的问题。可靠性设计里有一类工作是**给人看的**：状态里必须包含"接下来会发生什么"，否则运维只能靠猜。同理，消息开头的 `[code]` 前缀是给日志聚合用的，一条消息同时服务人和机器两个读者。

## 五、Worker 失败留痕

### Q21. 异步任务失败时，你怎么保证失败原因不丢？讲一个你实际踩到的坑。

**考点**：这是可靠性问题里最阴险的一类——**错误处理代码本身出错**。面试官想看你有没有在真实故障中被"日志里什么都没有"折磨过。

**标准回答**：

我踩到的坑是：**错误处理代码里的二次提交，把原始异常顶掉了。**

改造前 worker 的失败分支长这样（简化）：

```python
try:
    ...业务逻辑...
except Exception as e:
    job.status = "FAILED"
    job.error_message = str(e)
    db.commit()          # ← 问题在这一行
    raise
```

正常情况下没问题。但当**原始异常本身就是数据库/连接故障**时——比如连接被中间件掐断、连接池耗尽、事务已经处于失败状态——这个 `db.commit()` 自己也会抛异常。于是：

1. `except` 块内抛出新异常，Python 用新异常替换了正在传播的异常；
2. RQ 抓到的、写进 `job.exc_info` 的，是那个 `commit` 失败的 `OperationalError`；
3. 真正的原始原因（比如"Milvus 连接超时"）**彻底消失**。

这个 bug 的恶劣之处在于它的触发条件：**越是基础设施故障，越会丢失真实原因，而那正是最需要看清原因的时候。** 平时（业务逻辑 bug）它工作得很好，你不会发现它坏了；等到真出大事故，它准时失灵。

第二个后果同样致命：因为 commit 失败，`FAILED` 状态**根本没落库**。任务停在 `RUNNING`、文档停在 `INDEXING`，一直挂着。我们真实遇到过任务在 RUNNING 里躺了好几天没人发现——因为监控看的是"有没有 FAILED"，而它永远不会变成 FAILED。**失败留痕失效的表现不是"看到错误的原因"，而是"什么都看不到"。**

**真实代码**（`app/core/job_failure.py`）：

```python
def record_job_failure(
    job_id: str,
    exc: BaseException,
    *,
    document_id: int | None = None,
) -> None:
    """把失败落库。这个函数的全部价值在于「绝不 raise」。"""
    session = None
    try:
        # 关键:新开一个 Session,不复用出错的那个连接
        session = SessionLocal()
        code = error_code_of(exc)
        message = format_failure_message(exc, code=code)
        ...更新 job / document 状态...
        session.commit()
    except Exception as rescue_exc:
        # 抢救失败只记日志,绝不向上抛 —— 否则又会顶掉原始异常
        logger.error(f"[job_failure] 记录失败状态时出错: {rescue_exc}")
    finally:
        if session is not None:
            try:
                session.close()
            except Exception:
                pass
```

三层防护对应三个具体的失败模式：新开 Session 应对"原连接已死"；整体 `try` 应对"抢救也失败"；连 `close()` 都包住，是因为 `finally` 里抛出的异常会**再一次**顶掉原始异常——那就等于把刚修掉的 bug 原地复活。

**追问链**：

> **追问 1：为什么必须新开 Session？回滚一下复用不行吗？**
>
> 因为出错时连接可能已经**物理上不可用**了：TCP 被 RST、连接被服务端关闭、连接池已经把它标记为失效。这时候 `rollback()` 本身就会抛。在同一个连接上抢救，等于在漏水的船上补漏。新开 Session 会从池里拿一个（或新建）健康连接，是唯一有机会成功的做法。
>
> 代价是这个操作**不在原事务里**，所以它只做一件独立的事——写状态，不夹带任何业务数据。职责单一在这里不是审美，是可行性前提。

> **追问 2：抢救也失败了，那不就还是没留痕？**
>
> 是。但差别在于：现在**原始异常完整地向上传播了**，RQ 的 `job.exc_info` 里是真实原因，日志里还额外有一条 `[job_failure]` 说明抢救为什么失败。而改造前的版本是原始原因被替换、状态没落库、两头都黑。
>
> 可靠性设计里没有"保证不失败"，只有"失败时的表现足够好"。这里的目标不是"一定能写进数据库"，而是"**任何情况下都不比什么都不做更糟**"。

> **追问 3：Python 3 有异常链（`raise ... from`），原始异常不是保留在 `__context__` 里吗？**
>
> 语言层面确实保留了，`traceback` 打印时会有 "During handling of the above exception, another exception occurred"。但**下游消费者不一定会读**：RQ 写 `exc_info` 时用的是格式化后的字符串，能看到；而我们的 `job.error_message` 字段只有一个，`str(e)` 拿到的是新异常。指标聚合、告警规则、前端展示读的全是这个字段。语言帮你留了证据，但**留在了没人看的地方**。

**拓展**：

这个模式可以抽象成一条通用规则：**错误处理路径必须比正常路径更保守。** 具体三条——不做可能失败的 IO（做不到就包住）、不依赖出错时的任何资源、不向上抛新异常。

再往下一步是给 RUNNING 状态加**兜底扫描**：定期查 `status = RUNNING AND updated_at < now() - 30min` 的任务，标成 FAILED 并附上 `stale_timeout` 原因。因为无论错误处理写得多小心，都有一类失败是它绝对抓不到的——**worker 进程被 SIGKILL / OOM killer 干掉**，没有任何代码有机会执行。防御性编程的边界就在这里：进程内的代码防不住进程本身的死亡，那必须靠**进程外的对账**。这条我还没做，但它是这个模块最明显的缺口。

### Q22. `default_job_retry()` 为什么写成函数，而不是一个模块级常量？

**考点**：可变对象共享。这是个小细节，但答不上来说明对"实例状态"没有敏感度。

**标准回答**：

因为 `rq.Retry` 对象**携带可变状态**。RQ 在调度重试时会读写它内部的字段，如果所有入队调用共用同一个 `Retry` 实例，两个任务的重试计数就可能互相干扰。

```python
_DEFAULT_RETRY_MAX = 3
_DEFAULT_RETRY_INTERVALS = [10, 30, 60]


def default_job_retry() -> Retry:
    """每次调用返回**新**实例。

    不写成 DEFAULT_RETRY = Retry(...) 模块级常量,是因为 Retry
    携带可变状态,多个 job 共用一个实例存在互相干扰的风险。
    """
    return Retry(max=_DEFAULT_RETRY_MAX, interval=list(_DEFAULT_RETRY_INTERVALS))
```

注意 `interval=list(...)`——同理，传的是**拷贝**而不是模块级列表本身。如果直接传 `_DEFAULT_RETRY_INTERVALS`，任何一个持有它的对象做了原地修改（`pop`、`append`），全局默认值就被改了，而且是**永久的、影响后续所有任务的**改动。这类 bug 排查起来极其痛苦，因为现场看起来像"配置突然变了"。

**追问链**：

> **追问 1：`Retry` 真的会被 RQ 修改吗？你验证过吗？**
>
> 我没有逐行验证 RQ 内部对 `Retry` 的写操作。这里用的是**默认不共享可变对象**的原则——判断依据不是"它现在会不会改"，而是"如果它改了，后果是什么、我能不能提前发现"。后果是跨任务串扰、几乎不可能复现，成本是每次多创建一个极小的对象。这个性价比不需要犹豫。
>
> Python 的 `def f(x=[])` 是同一类问题的教科书版本，区别只是这里的共享发生在模块级而不是默认参数。

> **追问 2：那配置里的重试次数为什么写成模块私有常量，而不是进 `config`？**
>
> 因为它现在没有调整需求。放进 `config` 意味着多一个环境变量、多一处文档、多一个"生产和测试值不一致"的可能。等真的需要按队列区分重试策略了再提上去——那时候它的形态大概也不是一个全局值，而是队列级配置。**提前抽象成配置项，等于提前把一个还没定型的东西固定下来。**

**拓展**：

更完整的做法是让重试策略**按错误类型分级**：网络抖动重试 3 次、限流重试 5 次且间隔更长、解析失败 0 次。现在的实现是"一个默认策略 + `apply_retry_policy` 把非可重试的降到 0"，本质上是两档。分级需要先有数据支撑——各类失败的实际恢复时间分布。没有这份数据就分级，只是把猜测写成了配置。

### Q23. 异步 worker 里怎么做请求追踪？`request_id` 从哪里来？

**考点**：跨进程上下文传递。HTTP 请求里 `request_id` 靠中间件生成，但 RQ worker 是**另一个进程**，中间件根本不存在。

**标准回答**：

分两种情况，靠同一个工具处理：

```python
@contextmanager
def request_id_scope(request_id: str | None = None) -> Iterator[str]:
    """给非 HTTP 入口(RQ worker、脚本、定时任务)用的上下文管理器。

    传 None 时生成一个新的 —— 这样后台任务的日志不会全挤在 "-" 下面。
    """
    rid = request_id or new_request_id()
    token = set_request_id(rid)
    try:
        yield rid
    finally:
        reset_request_id(token)
```

- **入队时带上了 `request_id`**（HTTP 请求触发的任务）：worker 用 `request_id_scope(job.meta["request_id"])`，于是同一个 `request_id` 串起 API 侧和 worker 侧的全部日志——用户报"我上传的文档没进去"，一个 ID 就能拉出完整链路，横跨两个进程。
- **没有来源**（定时任务、手工重跑）：`request_id_scope()` 不传参，**生成一个新的**。

第二种情况的设计是关键。最省事的写法是没有来源就用 `NO_REQUEST_ID`（`"-"`），但那样所有后台任务的日志会**全部挤在同一个 `"-"` 下面**，`request_id` 这个字段对 worker 日志直接失去筛选能力——而 worker 恰恰是最难排查的地方，因为它没有用户在旁边描述现象。生成新 ID 的成本是一次 `uuid4()`，收益是每一次后台执行都可独立追踪。

**真实代码**（`app/core/request_context.py`）：

```python
REQUEST_ID_HEADER = "X-Request-ID"
NO_REQUEST_ID = "-"


def new_request_id() -> str:
    # 16 位十六进制:够唯一,又比完整 uuid 短一半,日志里好读
    return uuid4().hex[:16]


def get_request_id_or_none() -> str | None:
    """给数据库用。日志用 "-",数据库用 NULL —— 见下面的追问。"""
    rid = _request_id_var.get()
    return None if rid == NO_REQUEST_ID else rid
```

**追问链**：

> **追问 1：为什么日志里用 `"-"`，数据库里用 `NULL`？统一成一个不是更简单？**
>
> 因为两个消费者对"没有值"的处理方式完全不同。
>
> 日志是**给人按列读的文本**。用 `NULL` 或空串会让这一列时宽时窄，`grep`/`awk` 按列切分也会错位。`"-"` 是日志领域约定俗成的占位符（Nginx access log 就这么干），宽度稳定、肉眼可辨。
>
> 数据库里 `"-"` 会变成一个**真实的值**。`GROUP BY request_id` 时，所有无上下文的行会被聚成一个虚假的"请求 `-`"分桶，看起来像有一个请求发起了几万次操作。`NULL` 在 SQL 语义里就是"未知"，聚合函数默认跳过，`WHERE request_id IS NULL` 是明确的查询。**"没有值"在文本里是一个字符，在关系模型里是一种状态**，混用就会污染统计。
>
> 所以有了 `get_request_id_or_none()`——这个转换判断只写一次，两个 repository 共用。否则它会以 `rid if rid != "-" else None` 的形式散落在各个写库点，而漏掉一处的表现是"某张表里混着 `-` 和 `NULL`"，等你发现时数据已经脏了。

> **追问 2：为什么用 `reset(token)` 而不是 `set(NO_REQUEST_ID)`？**
>
> 因为要支持**嵌套**。`reset(token)` 恢复的是"进入这个作用域之前的值"，而 `set(默认值)` 是无条件覆盖。如果一个 worker 任务内部又用 `request_id_scope` 起了子作用域，用 `set` 的话子作用域退出后外层的 ID 就没了，后面的日志全部错标。`ContextVar` 提供 token 机制正是为了这个，不该绕过它。

> **追问 3：`uuid4().hex[:16]` 截断会不会碰撞？**
>
> 64 bit 随机值。按生日界，碰撞概率到 1% 需要约 6 亿个 ID。而 `request_id` 的作用域是"一段时间内的日志检索"，不是全局唯一主键——它不做外键、不做去重依据。即使真撞了，两条链路混在一起最多让一次排查多花几分钟。用完整 32 位 uuid 换这点概率，代价是每行日志长 16 个字符、人眼对比时更容易看错。**唯一性要求由用途决定，不是越强越好。**

**拓展**：

下一步是把 `request_id` 换成 W3C Trace Context 标准的 `traceparent`（`trace_id` + `span_id` + 采样标记）。收益是能直接接入 OpenTelemetry 生态，和上游网关、下游中间件的链路自动打通，不用自己维护 ID 传递。现在没做是因为链路只有两跳（API → worker），自己传的成本比引入 OTel SDK 低。**触发信号是跳数变多**——比如中间加了消息队列或者拆出独立服务，手工传递开始漏的时候，就该换了。

## 六、熔断器

### Q24. 你为什么要加熔断器？降级已经能兜住失败了，熔断解决什么额外的问题？

**考点**：区分"单次失败的处理"和"持续失败的处理"。很多人以为熔断是降级的加强版，其实它解决的是完全不同的问题——**成本**。

**标准回答**：

降级解决"这一次失败怎么办"，熔断解决"**已经知道它坏了，还要不要接着白等**"。

算一下就很清楚。Milvus 挂了，QPS 10，`llm_timeout` / 检索超时 60s：

- 没有熔断：每个请求都老老实实连一次 Milvus，等 60 秒超时，然后降级。一分钟里 **600 个请求，每个都白等 60 秒**才拿到一个早就能预知的结果。用户侧体验是"页面转一分钟然后告诉我检索不可用"。
- 有熔断：前 5 个请求正常失败，第 6 个开始 `guard()` 直接抛 `CircuitOpenError`，**耗时接近 0**。降级逻辑一字不改，只是提前触发。

所以熔断的价值不在"避免失败"——失败照样发生，降级照样走。它的价值是**把失败的代价从 60 秒压到 0 秒**。

还有个额外好处：不再往一个已经出问题的下游打 10 QPS。下游经常是因为过载才挂的，这时候持续施压会让它更难恢复；熔断顺带做了**上游侧的流量卸载**。这是熔断和纯客户端超时的本质区别——超时只保护自己，熔断同时保护对方。

**真实代码**（`app/core/circuit_breaker.py` 模块文档里就是这段推算）：

```python
# app/config.py:93
circuit_breaker_failure_threshold: int = 5
# app/config.py:97
circuit_breaker_cooldown_seconds: float = 30.0
```

**追问链**：

> **追问 1：为什么不用 pybreaker / circuitbreaker 这些现成库？**
>
> 因为我需要的部分很小，而不需要的部分不小。我要的是：连续 N 次失败后打开、冷却后半开探测、注册表能列出所有实例（`/metrics` 要用）、以及**异常分类要接我自己的 `is_retryable`/`CircuitOpenError` 语义**。现成库给的是通用统计窗口、装饰器语法、各种监听器钩子。
>
> 关键在最后一条：熔断器必须知道"哪些异常算失败"。`CancelledError` 不算、`CircuitOpenError` 自己不算、`ParseError` 算不算取决于业务。这套判断在我这儿已经是 `app/core/errors.py` 的一部分了，接进第三方库要么写适配层，要么被它的分类方式牵着走。自己写 275 行，全是我需要的语义。
>
> **YAGNI 不只是"别写用不到的代码"，也包括"别引用用不到的库"。** 一个依赖的成本不只是安装，还有升级、CVE 跟踪、和自己抽象的冲突。

> **追问 2：熔断器打开期间，用户体验是什么样的？**
>
> 和降级一样，只是更快：拿到一个带 `degrade_reason=circuit_open` 的降级回答。这个原因值很重要——它告诉排查的人"**不是下游告诉我们它坏了，是我们自己决定不问了**"。如果这里复用 `retrieval_failed`，值班的人会去查 Milvus 日志，而那段时间我们压根没发请求过去，Milvus 日志里干干净净，人就懵了。
>
> 这是 Q6 那套"按修复方向划分原因"的一个具体例子：`circuit_open` 的修复动作是"确认下游恢复后等冷却结束，或手工 reset"，和 `retrieval_failed` 的"去修 Milvus"完全不同。

**拓展**：

现在的实现有个明确缺口：**熔断状态是进程内的**。多副本部署时,每个副本各自数失败次数、各自决定开合。后果是同一个故障要被发现 N 次（N = 副本数），而且副本间状态不一致——有的在拒绝、有的在放行。

要做成集群级需要共享状态（Redis 存计数和状态机），但那会引入新问题：熔断器自己依赖了一个下游，Redis 挂了怎么办？答案通常是"退化成本地判断"，于是两套逻辑都要维护。所以业界主流（Hystrix、resilience4j）都是**本地熔断**——接受"每副本各判一次"的重复成本，换实现简单和无额外依赖。我沿用这个选择，但会在文档里写清楚它是选择而不是遗漏。

### Q25. 熔断阈值为什么用「连续 N 次失败」，而不是「失败率超过 X%」？失败率不是更科学吗？

**考点**：这是熔断器设计里最容易答错的一题。教科书和主流框架（Hystrix）都用滑动窗口失败率，敢选另一条路要能说出理由。

**标准回答**：

失败率在我这个场景下有三个具体问题，而连续计数恰好都没有。

**第一，失败率需要最小样本量，连续计数自带这个保证。** 失败率是 `失败/总数`，1 次请求失败就是 100%——所以所有实现都要配一个 `minimumNumberOfCalls`，样本不足时不判断。于是你有了两个耦合的参数（窗口大小 + 最小样本），还得回答"低 QPS 时段窗口永远填不满怎么办"。而"连续 5 次失败"这句话**本身就包含了 5 个样本**，一个参数说完。

**第二，失败率对偶发失败敏感，连续计数天然免疫。** 一个健康系统的失败率不是 0，是 0.5% 左右的抖动。窗口取小了，几个抖动挤在一起就误熔断；取大了，反应变慢。而连续 5 次失败要求这 5 次**中间不能有任何一次成功**——偶发抖动只要不是密集连发，计数就被下一次成功清零了。

```python
def record_success(self) -> None:
    with self._lock:
        self._consecutive_failures = 0   # ← 一次成功就归零
        ...
```

**第三，也是最关键的：失败率对"半死状态"敏感，而这恰恰不该熔断。** 假设 Milvus 有一半分片挂了，成功率 50%。失败率策略会毫不犹豫地打开熔断——于是那本来能成功的 50% 请求也全被拒绝了，我们**主动把一个半可用的系统变成完全不可用**。而连续计数在这种情况下几乎不会触发：成功和失败交替出现，计数一直被清零。

这不是缺陷，是我想要的行为。**判断依据是"降级能不能兜住"**：能兜住的时候，让请求去试永远比不试好，因为试了有一半会成功。只有下游**完全**不可用（连续失败）时，去试才是纯粹的浪费。所以我要的判据是"它是不是彻底死了"，而不是"它有多不健康"。

**追问链**：

> **追问 1：那如果下游一直保持"失败 5 次成功 1 次"的病态节奏呢？熔断器永远不开。**
>
> 对，这是这个策略的真实盲区，我不否认。但代价是可控的：83% 的请求走降级（有原因、有指标、会告警），17% 正常返回。用户体验差，但比"100% 被拒"好。而且这种状态**能被观测到**——`degrade_total{reason="retrieval_failed"}` 会持续高位，这是告警规则该覆盖的场景，不是熔断器该覆盖的。
>
> 更完整的做法是两个判据并存：连续 N 次（快速识别彻底死亡）+ 长窗口失败率（识别慢性病态），任一触发即熔断。这是 resilience4j 的做法。我没做是因为需要先有失败率的历史数据来定阈值，而现在 `degrade_total` 才刚开始积累。**没有数据就定阈值，只是把猜测写成了配置。**

> **追问 2：`failure_threshold=5` 和 `cooldown=30s` 这两个数是怎么定的？**
>
> 坦白说是估的，但估的方式有依据。
>
> 阈值 5：要大到不被抖动误触发，小到故障后能快速生效。QPS 10 时 5 次失败大约 0.5 秒内攒够——快得足够；而连续 5 次抖动的概率是 `0.005^5`，可以忽略。
>
> 冷却 30s：这是"下游恢复后我们多久能感知"和"探测请求给下游多大压力"的折中。下游重启一般在几十秒级，30s 意味着最多多等一个周期。更重要的是它**必须大于单次超时**（60s）……这里其实有个问题：冷却 30s 小于超时 60s，意味着一次探测请求本身耗时就可能超过冷却期。这不会导致错误（`_probe_in_flight` 保证只有一个探测在飞），但会让"半开→打开"的节奏比配置看起来的更慢。我知道这个不一致，暂时没改是因为它的影响是"恢复稍慢"而不是"行为错误"。
>
> **这两个数应该由线上数据校准，而不是想出来的。** 现在能说的是它们的量级合理、方向明确，以及我知道该看哪个指标来调整。

### Q26. `guard()` 里那串 `except` 的顺序是有讲究的吗？

**考点**：异常捕获顺序不只是语法问题，每一个分支都对应一个真实的误判场景。

**标准回答**：

有，而且每一个分支都是为了防止一类**具体的误判**。

```python
async def guard(self, coro_factory):
    self._maybe_half_open()
    if self._state is _State.OPEN:
        raise CircuitOpenError(f"熔断器 {self.name} 已打开")
    try:
        result = await coro_factory()
    except CircuitOpenError:
        raise                      # ① 自己抛的不算自己的失败
    except asyncio.CancelledError:
        raise                      # ② 取消不算下游的错
    except BaseException:
        self.record_failure()      # ③ 其他一切都算
        raise
    else:
        self.record_success()
        return result
```

**① `CircuitOpenError: raise`——防止自锁。** 如果被守护的代码内部又调了另一个（或同一个）熔断器并抛出 `CircuitOpenError`，不排除它就会被当成本熔断器的一次失败。后果是"熔断器 A 打开导致熔断器 B 也累积失败并打开"，故障沿调用链**扩散**。熔断器的存在是为了隔离故障，自己成为传播路径就是本末倒置。

**② `CancelledError: raise`——防止归错因。** 这是最微妙的一条，来自一个具体场景：外层总预算 90s 耗尽时，`asyncio.timeout` 会取消所有在跑的任务。假设 generate 节点已经烧掉 85 秒，validate 节点刚起来 5 秒就被取消——如果把这次取消记成 LLM 熔断器的失败，就是**把 generate 的慢账记到 validate 的下游头上**。几次预算超时之后，一个完全健康的模型服务被熔断了。
>
取消是**我们自己的决定**，不是下游的表现。它必须原样抛出，不进统计。

**③ `except BaseException`——不是笔误。** 这里故意不用 `Exception`，因为真正的 `TimeoutError`（Python 3.11 起 `asyncio.TimeoutError` 就是内置 `TimeoutError`，属于 `Exception`）以及某些库的 `BaseException` 子类，都是**下游确实不可用**的证据，应该计入。用 `Exception` 会漏掉一部分真实失败。顺序上它在 ①② 之后，所以那两类已经被摘走了——`except BaseException` 兜住的是"排除误判之后的一切"。

**追问链**：

> **追问 1：`record_failure` 之后为什么还要 `raise`？**
>
> 因为熔断器**不改变业务语义**。它只负责统计和拒绝，异常该怎么传就怎么传。这条约束带来一个很实际的好处：接入熔断器时，现有的 `except Exception → 降级` 分支**一行都不用改**。`CircuitOpenError` 是 `Exception` 的子类，会被同一个分支抓住，走同一套降级逻辑，只是变快了。
>
> 这是我把 `CircuitOpenError` 设计成异常而不是返回值的原因——**它要能被已有的错误处理路径无感接住**。如果设计成 `guard()` 返回 `None` 表示被拒，每个调用点都得加一段 `if result is None` 判断，那才是侵入式改造。

> **追问 2：为什么用 `threading.Lock` 而不是 `asyncio.Lock`？`guard` 是个 async 函数。**
>
> 因为调用点**同时跨线程和协程**。检索路径是 `await asyncio.to_thread(sync_retrieve)`——真正的检索在工作线程里跑，而熔断器的 `record_failure` 可能在那个线程里被调；LLM 路径是纯协程。`asyncio.Lock` 只在单个事件循环内有效，工作线程里用它无意义（甚至报错）。`threading.Lock` 两种场景都正确。
>
> 代价是它会阻塞事件循环。但临界区里只有几个整数赋值和一次 `time.monotonic()`，纳秒级，比 `await` 一次的调度开销还小。**这是"用一把重锁保护一个极短临界区"的正确取舍。**

> **追问 3：`time.monotonic()` 而不是 `time.time()`，为什么？**
>
> 因为 `time.time()` 是墙上时钟，**会被 NTP 校准往回拨**。如果冷却期开始后系统时间被调回 1 分钟，`now - opened_at` 会变成负数，永远小于 `cooldown_seconds`——熔断器**永久卡在 OPEN**，再也不会半开探测。这种故障极难排查：代码逻辑完全正确，只是时间倒流了。
>
> `monotonic()` 保证单调递增，专门用于测量间隔。规则很简单：**测"过了多久"用 monotonic，记"什么时候"用 time。** 这个 bug 我没实际踩到，是写的时候就避开的——它属于"看一眼就知道要出事，但出事后极难定位"的那一类。

### Q27. 半开状态怎么实现的？多个请求同时到达半开状态会发生什么？

**考点**：半开是熔断器唯一有并发风险的状态。答不出"惊群"说明只看了状态图没想过实现。

**标准回答**：

半开的目的是**用最少的代价试探下游是否恢复**。冷却期结束后放**一个**请求过去：成功就立刻关闭，失败就重新打开并重新计时。

风险在"一个"上。冷却期一到，正在排队的所有请求会**同时**发现状态可以半开，如果不加控制，几十个请求会一起打向那个可能还没恢复的下游——这就是惊群（thundering herd）。而且这批请求会一起失败、一起 `record_failure`，把刚建立的判断搅乱。

```python
def _maybe_half_open(self) -> None:
    with self._lock:
        if self._state is not _State.OPEN:
            return
        if time.monotonic() - self._opened_at < self.cooldown_seconds:
            return
        if self._probe_in_flight:      # ← 已经有探测在飞,继续拒绝
            return
        self._probe_in_flight = True
        self._state = _State.HALF_OPEN
```

`_probe_in_flight` 在锁内检查并置位（检查和置位必须原子，否则两个请求都能通过），所以**同一时刻只有一个探测请求**在飞，其他请求继续按 OPEN 处理、被快速拒绝。探测有结果后（成功关闭 / 失败重开）才清掉这个标记。

探测**成功就立即关闭**，不像有些实现要求连续成功 M 次。理由是：如果下游其实已经好了，我们还在拒绝那些本来会成功的请求——那是**自己制造的故障**，和熔断器要解决的问题正好相反。代价是可能被一次幸运的成功骗过去（下游只是偶尔能响应），但那样下一批请求会很快再把它打开，损失只是一个探测周期。**在"多拒一会儿"和"早点放行"之间，我选后者**，因为前者的成本是确定的，后者的成本是概率性的。

**追问链**：

> **追问 1：探测请求恰好是个慢请求，60 秒才返回，这期间怎么办？**
>
> 这 60 秒里所有请求都被 `_probe_in_flight` 挡在外面，全部快速降级。这是我接受的行为——不确定下游状态时，**拒绝比放行安全**，因为放行的代价是每个请求 60 秒。
>
> 但它暴露了 Q25 追问里提到的那个参数问题：冷却 30s < 超时 60s，意味着探测请求的耗时能跨过一整个冷却周期，恢复感知会比配置看起来的慢。更合理的配置是让冷却期大于单次超时，或者给探测请求配一个更短的专用超时（它的目的只是"看看还活着吗"，不需要拿到完整结果）。后者是更好的方向，还没做。

> **追问 2：`_REGISTRY` 和 `reset_all_breakers()` 是干什么的？**
>
> `_REGISTRY` 是全局注册表，每个 `CircuitBreaker` 构造时自动登记。两个用途：`all_breakers()` 供 `/metrics` 导出每个熔断器的状态（`circuit_breaker_state{name="retrieval"} 1`），这样能在监控上直接看到"什么时候开的、开了多久"；`reset_all_breakers()` 主要给**测试**用。
>
> 测试那个用途不是附带的。熔断器是**有状态的全局对象**，一个测试把它打开了，后面所有测试都会拿到 `CircuitOpenError`——而且失败顺序取决于测试执行顺序，表现为"单独跑能过，一起跑就挂"。所以有个 autouse fixture 在每个测试前重置全部熔断器。**全局状态一旦引入，就必须同时提供清理入口**，否则测试隔离性无法保证。

**拓展**：

半开阶段可以做得更细：不是放 1 个请求，而是**按比例放行**（比如 10% 流量），根据这批的成功率决定关闭还是重开。这样恢复更平滑，避免"刚关闭就被全量流量再次打挂"——下游刚重启时容量往往还没热起来（连接池空、缓存冷、JIT 未预热），全量涌入可能直接把它再打死。

按比例放行本质上是把熔断器和**限流**结合起来，形成一个渐进恢复的斜坡。这是 Netflix 的 adaptive concurrency 那一类做法。当前实现选最简单的"1 个探测"，因为我们的下游（Milvus、模型服务）都不是自建的、也不存在冷启动容量问题。**判断依据是下游的恢复特性，不是熔断器本身能做到多复杂。**

## 七、可靠性的验证

### Q28. 这些降级和熔断逻辑，你怎么测？总不能真把 Milvus 关掉。

**考点**：可靠性代码的最大特点是**正常路径永远测不到它**。不主动测，就只能在生产环境第一次运行——而那时候它已经在处理真实故障了。

**标准回答**：

核心认知是：**错误处理代码的默认状态是"从未执行过"**。业务代码写错了，第一次跑就会暴露；错误处理写错了，可能上线半年都风平浪静，直到真出故障那天才发现它自己也是坏的。Q21 那个"二次提交顶掉原始异常"的 bug 就是活例子——它在所有非基础设施故障下都工作正常。

所以测法是**注入**，不是等待：

1. **异常分类是纯函数，直接断言。** `is_retryable` / `error_code_of` / `degrade_reason_of` / `http_status_of` 不碰任何 IO，喂一个异常实例进去断言输出。这也是把分类集中到四个函数最实际的好处——**它们本来就是最该测、也最容易测的部分**。Q5 那个 `wrap_llm_exception` 把 `circuit_open` 翻成 `llm_error` 的 bug，一条 `assert wrap_llm_exception(CircuitOpenError("x")).degrade_reason == DegradeReason.CIRCUIT_OPEN` 就能锁住。

2. **降级路径用 mock 抛异常。** 让检索函数 `side_effect = RetrievalError(...)`，然后断言的**不是"没崩"**，而是三件事：`degrade_reason` 等于预期值、答案里带了 `partial_note`、`degrade_total` 指标涨了。"没崩"是最弱的断言——静默吞掉异常也能让测试过，而那正是我要防的东西。

3. **熔断器状态机直接驱动。** 它不依赖真实下游，构造一个必然抛异常的 `coro_factory`，调 N 次断言 OPEN，然后**把 `_opened_at` 往前拨**（不用真 sleep 30 秒）断言进入 HALF_OPEN。这是 `time.monotonic()` 的另一个好处——它是可控的数字，测试里改状态就行。

4. **worker 失败留痕要模拟"抢救也失败"。** 这是最容易漏的一类：让 `SessionLocal` 本身抛异常，断言 `record_job_failure` **不抛**、并且日志里有记录。这个测试直接对应 Q21 里"抢救失败时也不能比什么都不做更糟"那条设计承诺——**承诺必须有测试锁住，否则它只是注释。**

**追问链**：

> **追问 1：那有没有测过"两个降级同时发生"？**
>
> 测得不够。目前测的基本都是单点注入：检索失败、LLM 超时、熔断打开各测一遍。组合场景（检索部分失败 + validate 又超时）只覆盖了少数几个。
>
> 组合爆炸是真实的：10 个降级原因、几个节点，组合数上百，全测不现实。可行的收敛方式是按**降级原因的写入点**测，而不是按组合测——保证每个原因都有一条路径能写进 state、且 `generate` 对"任意原因组合"都能生成 `partial_note`（后者用 property-based 测试更合适：随机生成原因集合，断言输出非空且包含所有原因）。这个我还没做。

> **追问 2：你怎么知道生产上这些降级路径真的被走到过？**
>
> 看 `degrade_total{reason=...}` 的分布。这个指标的作用不只是告警，还是**降级代码的覆盖率报告**：一个原因如果几个月都是 0，说明它要么永远不会发生（该删），要么写入点有 bug（该修）。两种情况都需要处理，而不知道自己有一段代码从未执行过是更糟的状态。
>
> 反过来，某个原因突然从 0 变成高位，通常比错误率上升更早暴露问题——因为降级意味着"我们兜住了"，用户还没投诉，但指标已经在说下游不对了。**降级指标是比错误率更灵敏的健康信号。**

> **追问 3：混沌工程做了吗？**
>
> 没有。当前规模下（单机部署、依赖只有 Milvus 和模型服务）投入产出不划算：搭一套故障注入平台的成本，超过我用 mock 覆盖这几条路径的成本。
>
> 但我知道 mock 测不到什么：**真实故障的形态比 mock 丰富得多**。mock 抛的是干净的 `ConnectionError`；真实的 Milvus 故障可能是连接建立成功但读取半天不返回、返回格式异常、只有部分分片失败。这类"半死"形态是 mock 很难模拟的，也正是 Q25 里讨论的那个盲区。所以我的说法是"单元测试覆盖了分类和状态机的正确性，没有覆盖真实故障的形态多样性"——**说清楚测了什么、没测什么，比宣称测过了更有用。**

**拓展**：

再往前一步是**故障演练常态化**：在预发环境定期切断 Milvus / 把模型服务的 base_url 指向黑洞，跑一遍完整链路，断言"服务仍然返回 200 且带正确的 `degrade_reason`"。这比单元测试值钱的地方在于它验证的是**整条链路的组合行为**——中间件顺序、`request_id` 是否还在、指标是否上报、SSE 是否正常结束。这些都是单元测试按定义测不到的东西（每个组件单独都对，串起来不对）。

再往上是把可靠性变成**可度量的目标**：定义 SLI（比如"非降级成功率"），设 SLO，用错误预算决定"这个季度该做新功能还是补稳定性"。现在缺的不是工具，是历史数据——`degrade_total` 才刚开始积累。**没有基线的 SLO 是拍脑袋，而拍出来的目标只会被当成摆设。**

## 八、演进与总结

### Q29. 这套可靠性设计，你觉得最大的缺口在哪？下一步做什么？

**考点**：能不能给自己的系统排优先级，以及排序的依据是什么。

**标准回答**：

按"故障发生时会不会看不见/救不回来"排序，四个缺口：

**P0：RUNNING 状态的进程外对账。** 这是唯一一个**当前会导致任务永久卡死**的缺口。Q21 里那套 `record_job_failure` 防住了所有"代码有机会执行"的失败，但防不住 worker 被 OOM killer / SIGKILL 干掉——那时候没有任何 `except` 会运行。表现是任务停在 RUNNING、文档停在 INDEXING，而监控看的是"有没有 FAILED"，所以**永远不会告警**。修法是定时扫 `RUNNING AND updated_at < now() - 30min` 标成 FAILED。成本一个定时任务，收益是补上唯一的"救不回来"场景。

**P1：冷却期与超时的参数对齐。** 冷却 30s < 单次超时 60s，探测请求的耗时能跨过整个冷却周期（Q27）。它不产生错误，只是让恢复比配置看起来的慢。修法是给探测请求配独立的短超时——探测只要回答"还活着吗"，不需要完整结果。

**P2：降级原因的指标基线。** 十个原因现在只有计数，没有历史分布，所以既不知道哪个原因从未触发过（可能是死代码，也可能写入点有 bug），也没法给熔断阈值和 SLO 定合理的值。这一条不写代码，只是让积累的数据能被看见——但它是 P1/P3 调参的前提。

**P3：集群级熔断 / 组合降级测试。** 前者要引入 Redis 依赖并处理"熔断器自己的下游挂了"，业界主流也都是本地熔断，所以不急；后者需要 property-based 测试来对付组合爆炸。

排序依据只有一条：**先补"故障时看不见或救不回来"的，再补"看得见但不够准"的，最后才是"更完善"的。** 可靠性投入最容易犯的错是反过来——去做那些看起来更高级的（集群熔断、混沌平台），而放着一个会让任务卡死好几天的缺口不管。

### Q30. 用一句话总结你在可靠性上的收获。

**标准回答**：

**可靠性不是"不出错"，是"出错时系统的行为仍然是设计过的"。**

这句话有三层，每一层都对应这篇里的一组具体决策：

**第一层，失败必须留下可操作的痕迹。** 一个异常光有 message 不够，它得携带 `code`（能聚合）、`retryable`（能决策）、`http_status`（能被网关和 APM 读懂）、`degrade_reason`（能指向修复方向）。把这四个属性放进异常基类，是这套设计的起点。反面例子就在项目自己的历史里：HTTP 200 配 `{"code": 500}`，所有标准监控看到的错误率永远是 0%——**我们做的是帮别人发现故障的系统，自己的故障却对所有监控隐身。**

**第二层，降级必须带原因，而原因要按修复方向划分。** `retrieval_failed` 和 `retrieval_empty` 都是"检索没结果"，但一个要去修 Milvus、一个要去补文档。合并它们等于让值班的人在下游宕机时去写文档。同理 `circuit_open` 不能复用 `retrieval_failed`——"下游告诉我们它坏了"和"我们自己决定不问了"是两回事，后者的日志里下游干干净净。**分类的标准从来不是"看起来像不像"，而是"处理动作是否相同"。**

**第三层，错误处理路径必须比正常路径更保守。** 因为它的默认状态是从未执行过。二次提交顶掉原始异常那个 bug 最能说明问题：它在所有业务 bug 下都工作正常，只在基础设施故障时失灵——**越是大事故，越会丢失真实原因。** 所以这条路径上不做可能失败的 IO、不依赖出错时的任何资源、不抛新异常，连 `finally` 里的 `close()` 都要包住。

这三层背后是同一个转变：从"**加上 try/except 就算处理了错误**"，转到"**每一个失败都要能回答四个问题**"——怎么聚合、要不要重试、外部怎么看、人该去修什么。想清楚这四个问题，try/except 里该写什么自然就定了；想不清楚，写多少 `except` 都是在把问题藏起来。
