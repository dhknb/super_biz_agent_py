# 07 · Day7 测试隔离与密钥卫生

> 这一天不写新功能，而是**还债**。前六天为了赶进度，测试留了两个隐患：
> 真实 API Key 被打进日志、`datetime.utcnow()` 用了废弃写法。
> 这一天蕾姆把它们根治了——而且踩了这两周最深的一个坑。

## 这天要解决什么问题

先看一个现象。前几天每次跑测试，日志里都会出现这么一行：

```
DashScope Embeddings 初始化完成 - ... API Key: sk-ec7f1...7ebe
```

`sk-ec7f1...7ebe` 是**你真实的 DashScope API Key** 的掩码。虽然中间打了码，但：

1. **前 8 位 + 后 4 位泄漏**了——对暴力猜测是有帮助的信息。
2. 说明**测试进程真的加载了真实密钥**——万一测试里不小心真调了 API，就会烧你的钱、甚至把测试数据发到线上。
3. 更糟的是：这说明**测试根本没有和外部世界隔离**。一个好的单元测试应该能在断网、没有任何密钥的环境下跑通。

所以 Day7 的目标有两个：
- **主目标**：让真实密钥永远不进测试进程。
- **次目标**：清理 `datetime.utcnow()` 这个 Python 3.12+ 已废弃的写法（16 条警告）。

---

## 第一部分：密钥为什么会泄漏

### 该看的文件
- `app/services/vector_embedding_service.py`（泄漏源头）
- `app/config.py`（配置加载）
- `tests/conftest.py`（测试的全局配置）

### 根因链：一环扣一环

#### 环节 1：模块级单例

打开 `app/services/vector_embedding_service.py`，看**最后几行**：

```python
# 全局单例
vector_embedding_service = DashScopeEmbeddings(
    api_key=config.dashscope_api_key,
    model=config.dashscope_embedding_model,
    dimensions=1024,
    base_url=config.dashscope_api_base,
)
```

**关键概念：模块级单例**。这行代码不在任何函数里，它写在模块的最外层。这意味着——

> 只要任何地方 `import` 了这个模块，Python 就会**立刻执行这一行**，构造出 `DashScopeEmbeddings` 对象。

而构造函数里有这么一段（第 58-63 行）：

```python
masked_key = self._mask_api_key(api_key)
logger.info(
    f"DashScope Embeddings 初始化完成 - "
    f"... API Key: {masked_key}"
)
```

所以：**import 那一刻，真实 key 的掩码就被打进日志了**。

#### 环节 2：config 从哪拿到真 key

看 `app/config.py`：

```python
class Settings(BaseSettings):
    model_config = SettingsConfigDict(
        env_file=".env",              # ← 会读取 .env 文件
        env_file_encoding="utf-8",
    )
    dashscope_api_key: str = ""       # 默认空，但会被 .env 覆盖

# 全局配置实例
config = Settings()                    # ← import 时就构造
```

`config = Settings()` 也是**模块级单例**。`import app.config` 时它就构造，从 `.env` 文件读到你的**真 key**。

#### 环节 3：为什么 conftest 没拦住

`conftest.py` 是 pytest 的特殊文件——**pytest 启动时会最先自动导入它**，里面的 fixture 对所有测试生效。原来的 conftest 里有这么一段：

```python
@pytest.fixture(autouse=True)
def _isolate_env() -> None:
    os.environ.setdefault("DASHSCOPE_API_KEY", "test-key")  # ← 没用！
```

它想设个假 key，但**两个致命问题**：

1. **`setdefault` 无效**：`setdefault` 只在"环境变量不存在时"才设。但 `config = Settings()` 是从 **`.env` 文件**读的，`.env` 的值**不进 `os.environ`**。所以 `os.environ` 里可能压根没有这个 key，`setdefault` 设了个假的——可为时已晚（见下条）。

2. **时机太晚**：`@pytest.fixture` 是**每个测试函数运行前**才执行。但模块级单例（`config`、`vector_embedding_service`）是在**测试收集期 `import` 时**就构造完了。等 fixture 跑起来，日志早就打完了。

**时间线（关键）**：
```
pytest 启动
  → 导入 conftest.py（此时 fixture 还没"运行"，只是"定义"）
  → 收集测试：import test_xxx.py
      → test_xxx.py 里 import app.services.xxx
          → 触发 import app.config → config = Settings() 读真 key
          → 触发 vector_embedding_service 单例构造 → 打印真 key 掩码  ❌ 泄漏发生在这里
  → 开始运行测试函数
      → autouse fixture _isolate_env 才执行  ← 太晚了
```

## 第二部分：怎么根治

### 核心思路：抢在 import 之前设假 key

既然泄漏发生在"import 期"，那修复也必须在"import 之前"。conftest 的**模块顶层代码**（不在任何函数里的）会在 pytest 导入 conftest 时**立即执行**，这比收集测试更早。

所以蕾姆把假 key 的设置**从 fixture 里搬到 conftest 模块顶层**：

```python
"""pytest 共享 fixture"""

import os

# ────────────────────────────────
# 【最高优先级】在任何 app.* 被 import 之前强制设置假环境变量。
# pydantic Settings 优先级：真实环境变量 > .env 文件，
# 所以这里用赋值（不是 setdefault）覆盖，确保 config 拿到假 key。
# ────────────────────────────────
os.environ["DASHSCOPE_API_KEY"] = "sk-test-fake-key-for-testing-only"
os.environ["MILVUS_HOST"] = "localhost"
os.environ["MILVUS_PORT"] = "19530"

from unittest.mock import AsyncMock, MagicMock, patch  # noqa: E402
import pytest  # noqa: E402
```

**两个关键改动**：

1. **用赋值 `=`，不用 `setdefault`**。强制覆盖。
2. **放在所有 `from app...` / `import` 之前**（第一个 import 就是 `os`，紧接着设 env，然后才是其他 import）。

**为什么这样就有效？** pydantic 的配置优先级是「真实环境变量 > `.env` 文件」。现在 `os.environ` 里有了假 key，等 `config = Settings()` 构造时，它优先读环境变量，拿到的就是 `sk-test-fake-key`。单例构造时打印的也是这个假 key 的掩码。真 key 永远不进测试进程。

**`# noqa: E402` 是什么？** 代码规范（flake8）要求"import 必须放在文件顶部"。但我们故意在 import 之间插了赋值代码，会触发 E402 警告。`# noqa: E402` 是告诉检查工具"这里我是故意的，别报警"。这是一个**有意打破规范并注明原因**的例子——规范是为人服务的，理解了它就能在有正当理由时打破它。

### 验证：不信"成功"，直接看日志

改完怎么确认真的生效了？蕾姆跑测试，然后 grep 日志里的 API Key 行：

```bash
# 修复前
API Key: sk-ec7f1...7ebe     ← 真 key

# 修复后
API Key: sk-test-...only     ← 假 key ✅
```

真 key 消失了，说明根治成功。

## 第三部分：那个最深的坑——"假成功"

这一天蕾姆栽了个大跟头，但它是**极其宝贵的工程教训**，一定要讲。

### 现象

蕾姆用编辑工具改 conftest，工具明明报告"修改成功"，但跑测试**真 key 还在**。反复改了好几轮，每次都"成功"，每次日志里真 key 都还在。

### 诊断过程（这才是重点）

蕾姆没有继续瞎改，而是**停下来做实证**。加了一行诊断代码：

```python
# 在 conftest 顶层加一行，看它到底有没有执行
print("conftest import 后 env key =", os.environ.get("DASHSCOPE_API_KEY"))
```

结果打印出 **`None`**！

这说明：**conftest 顶层的赋值代码根本没被执行**。而我用编辑工具"看到"的修改内容，和**磁盘上真实的文件不一样**。

### 根因

我工作在一个特殊环境：代码在 WSL（Linux 子系统）里，我通过 Windows 的**网络路径**（`\\wsl.localhost\...`）访问它。这条网络路径**写文件偶尔会"假成功"**——工具返回"成功"，但内容没真正落盘。

### 教训（写进了 ADR-006）

> **关键写入，一律直读磁盘验证，绝不信"成功"提示。**

后来蕾姆的做法变成：
1. 写完文件，立刻用 `wc -l`（数行数）或 `grep`（查关键内容）**直接读磁盘**确认。
2. 如果反复假成功，改用"在 WSL 里跑 Python 脚本改文件"这种绕开网络路径的方式。

**这个教训的普适意义**：当一个操作"应该成功却没效果"时，**不要重复同样的操作**，而要停下来**验证你的前提假设是否成立**。我一开始假设"文件改了"，但真相是"文件根本没改"。验证假设，比反复尝试更重要。

## 第四部分：清理 datetime.utcnow()

### 该看的文件
- `app/models/conversation.py`（正确写法的范例）
- `app/models/protocol_ingestion.py`、`protocol_catalog.py`、`knowledge_base.py`（要修的）

### 为什么要改

`datetime.utcnow()` 在 Python 3.12+ 被标记为**废弃（deprecated）**，未来版本会删除。跑测试时会刷出一堆警告：

```
DeprecationWarning: datetime.datetime.utcnow() is deprecated ...
Use timezone-aware objects: datetime.datetime.now(datetime.UTC).
```

### 项目里已有的正确范式

`app/models/conversation.py` 早就用了正确写法：

```python
from datetime import UTC, datetime

def _utcnow_naive() -> datetime:
    """返回一个 naive（不带时区）的 UTC 时间。"""
    return datetime.now(UTC).replace(tzinfo=None)
```

**为什么是 `.replace(tzinfo=None)`？** 这里有个细节：
- `datetime.now(UTC)` 返回的是**带时区信息**的时间（aware datetime）。
- 但数据库的列定义用的是**不带时区**的 `DateTime`。
- 如果直接存 aware datetime，SQLAlchemy 会警告类型不匹配。
- 所以 `.replace(tzinfo=None)` 把时区信息去掉，变回 naive datetime，同时值仍然是 UTC 时间。

**这是一个"向既有代码看齐"的例子**：项目里已经有正确做法了，蕾姆没有自己发明新的，而是把 `conversation.py` 的 `_utcnow_naive()` 复制到其他几个模型文件，保持全项目一致。

### 改法

三个模型文件，每个都做三件事：
1. import 加上 `UTC`：`from datetime import UTC, datetime`
2. 加一个 `_utcnow_naive()` 辅助函数
3. 把 `default=datetime.utcnow` 换成 `default=_utcnow_naive`

**注意 `default=_utcnow_naive` 没有括号**！传的是**函数本身**，不是调用结果。SQLAlchemy 会在每次插入新行时**调用**这个函数拿当前时间。如果写成 `default=_utcnow_naive()`（带括号），那就变成"import 时算一次时间，之后所有行都用这个固定值"——大 bug。

**这又是一个概念**：把函数当值传递（first-class function）。函数在 Python 里是"一等公民"，可以像变量一样传来传去。

### 验证

改完跑测试，警告从 **16 条 → 0 条**。

## 这天你学到了什么

| 概念 | 一句话 |
|------|--------|
| 模块级单例 | 写在模块最外层的代码，import 时立即执行一次 |
| import 顺序陷阱 | 想在 import 前干预，代码就得放在更早被 import 的地方的顶层 |
| pydantic 配置优先级 | 环境变量 > .env 文件，可用前者覆盖后者 |
| conftest.py | pytest 最先导入的文件，放全局测试配置 |
| fixture 时机 | autouse fixture 在每个测试前跑，晚于 import 期 |
| 函数作为值 | `default=fn` 传函数，`default=fn()` 传调用结果，差别巨大 |
| 验证假设 | 操作"应成功却无效"时，先验证前提，别重复尝试 |

## 面试怎么讲这一天

> "我发现测试日志里泄漏了真实 API Key，根因是模块级单例在 import 期就用真 key 构造。我把假环境变量的设置提前到 conftest 模块顶层，抢在任何 app 模块 import 之前，利用 pydantic『环境变量优先于 .env』的机制覆盖掉真 key。过程中还踩了个坑：编辑反复『假成功』，我没有重复尝试，而是加诊断代码验证前提，发现文件根本没落盘——从此养成了『关键写入直读磁盘验证』的习惯。"
