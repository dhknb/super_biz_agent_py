## 1. 这天要解决什么问题

Day2 我们有了 `AlarmEvent`，但它只是**内存里的一个对象**——请求处理完就没了。

现实需求是：一次诊断要**能查、能追踪、能审计**。值班同学问「上午那条 CPU 告警诊断到哪一步了？」，系统得答得出来。这就需要把诊断**存进数据库**，变成一条有生命周期的「任务」。

Day3 做三件事：
1. **ORM 模型**：定义两张表（诊断任务 + 事件时间线）在 Python 里长什么样。
2. **状态机**：任务有 `new→planning→retrieving→diagnosing→done/failed` 的合法流转，非法跳转要拦住。
3. **Alembic 迁移**：把表结构变更**版本化**，能升级能回滚。

---

## 2. 先补概念：什么是 ORM

ORM = Object-Relational Mapping（对象关系映射）。

数据库里是**表和行**（像 Excel）：

```
表 aiops_diagnosis_tasks
| id    | alert_name    | status   | ...
| abc.. | HighCPUUsage  | done     | ...
```

Python 里是**对象**：

```python
task = AiopsDiagnosisTask(alert_name="HighCPUUsage", status="done")
task.alert_name   # "HighCPUUsage"
```

ORM 就是这两者之间的翻译层：你在 Python 里操作对象，ORM 帮你翻译成 SQL（`INSERT`/`SELECT`/`UPDATE`）。本项目用的 ORM 是 **SQLAlchemy**。

好处：不用手写 SQL 字符串（易错、易被注入），用 Python 类型安全地操作数据。

## 3. 逐段讲 ORM 模型（`aiops_diagnosis.py`）

### 3.1 时间戳辅助函数

```python
from datetime import UTC, datetime

def _utcnow_naive() -> datetime:
    """与项目其余模型保持一致：存 naive UTC 时间。"""
    return datetime.now(UTC).replace(tzinfo=None)
```

- `datetime.now(UTC)`：取当前 UTC 时间（带时区信息，叫 "aware"）。
- `.replace(tzinfo=None)`：去掉时区标记，变成 "naive"（朴素）时间。
- **为什么要去掉时区**？因为这个项目其它表（`conversation.py`）都存 naive UTC，为了**统一**。数据库列类型是 `DateTime`（不带时区），存 aware 时间会出警告。
- **为什么不用 `datetime.utcnow()`**？它在 Python 3.12+ 被废弃了（Day7 我们专门清理过）。新写法是 `datetime.now(UTC)`。

### 3.2 状态枚举 + 状态机

```python
class DiagnosisTaskStatus(StrEnum):
    NEW = "new"
    PLANNING = "planning"
    RETRIEVING = "retrieving"
    DIAGNOSING = "diagnosing"
    DONE = "done"
    FAILED = "failed"
```

这是任务的六种状态。用 `StrEnum` 的原因和 Day2 一样：既是枚举又是字符串，存数据库直接存 `"new"` 这种值。

**关键设计——状态机**。不是任意状态都能互相跳转。比如 `NEW` 不能直接跳到 `DONE`（没经过分析怎么能完成？）。用一张「允许跳转表」来约束：

```python
_ALLOWED_TRANSITIONS: dict[DiagnosisTaskStatus, set[DiagnosisTaskStatus]] = {
    DiagnosisTaskStatus.NEW: {DiagnosisTaskStatus.PLANNING, DiagnosisTaskStatus.FAILED},
    DiagnosisTaskStatus.PLANNING: {DiagnosisTaskStatus.RETRIEVING, DiagnosisTaskStatus.FAILED},
    DiagnosisTaskStatus.RETRIEVING: {DiagnosisTaskStatus.DIAGNOSING, DiagnosisTaskStatus.FAILED},
    DiagnosisTaskStatus.DIAGNOSING: {DiagnosisTaskStatus.DONE, DiagnosisTaskStatus.FAILED},
    DiagnosisTaskStatus.DONE: set(),      # 终态，不能再跳
    DiagnosisTaskStatus.FAILED: set(),    # 终态
}
```

怎么读这张表：`NEW` 这行的值是 `{PLANNING, FAILED}`，意思是「从 NEW 只能去 PLANNING 或 FAILED」。`DONE` 和 `FAILED` 的值是空集合 `set()`，意思是「到了就出不来了」（终态）。

判断函数：

```python
def can_transition(src: DiagnosisTaskStatus, dst: DiagnosisTaskStatus) -> bool:
    if src == dst:
        return True                    # 相同状态视为幂等允许
    return dst in _ALLOWED_TRANSITIONS.get(src, set())
```

- `src == dst` 时返回 True：允许「原地不动」（幂等，重复设置同一状态不报错）。
- 否则查表：目标状态 `dst` 在不在 `src` 的允许集合里。

**为什么要状态机**？防止程序 bug 或并发导致的非法状态。比如某段代码不小心想把一个 `NEW` 任务直接标成 `DONE`，状态机会拦住并抛错，让 bug 早暴露。这是**防御式编程**。

> 💡 面试点：状态机是后端常见模式（订单、工单、审批流都用）。能说清「为什么用状态机、非法跳转怎么拦」是加分项。

### 3.3 主表：诊断任务

```python
class AiopsDiagnosisTask(Base):
    __tablename__ = "aiops_diagnosis_tasks"

    id: Mapped[str] = mapped_column(
        String(64), primary_key=True, default=lambda: str(uuid4())
    )
```

逐个拆：
- `class ...(Base)`：继承 `Base`（SQLAlchemy 的声明基类），这样 SQLAlchemy 才知道这是一张表。
- `__tablename__`：这张表在数据库里的名字。
- `Mapped[str]`：类型注解，告诉 SQLAlchemy 这一列是字符串。
- `mapped_column(...)`：定义列的细节。
- `String(64)`：数据库里是最长 64 字符的字符串。
- `primary_key=True`：这是主键（唯一标识每一行）。
- `default=lambda: str(uuid4())`：不传 id 时，自动生成一个 UUID（像 `"a3f2...c1"` 的全局唯一串）。用 `lambda` 是因为要**每次调用都生成新的**，不能写 `default=str(uuid4())`（那样所有行会共用同一个 id）。

继续看关键列：

```python
    alert_id: Mapped[str | None] = mapped_column(String(128), nullable=True, index=True)
    alert_name: Mapped[str] = mapped_column(String(255), nullable=False)
    severity: Mapped[str] = mapped_column(String(32), nullable=False, default="unknown")
    source: Mapped[str] = mapped_column(String(32), nullable=False, default="manual")
```

- `str | None` + `nullable=True`：这列可以为空（比如手工触发的告警没有外部 `alert_id`）。
- `nullable=False`：这列必填（`alert_name` 必须有）。
- `index=True`：给这列建**索引**。索引像书的目录——按 `alert_id` 查任务时会很快。代价是占空间、写入稍慢。经验：经常用来查询/过滤的列才建索引。

```python
    session_id: Mapped[str | None] = mapped_column(
        String(64),
        ForeignKey("conversation_sessions.id"),
        nullable=True,
        index=True,
    )
```

`ForeignKey("conversation_sessions.id")`：**外键**。表示这个 `session_id` 指向 `conversation_sessions` 表的 `id`。作用是关联——这次诊断属于哪个会话。数据库会保证你填的 `session_id` 必须真实存在（引用完整性）。

```python
    status: Mapped[DiagnosisTaskStatus] = mapped_column(
        Enum(DiagnosisTaskStatus, values_callable=lambda items: [item.value for item in items]),
        nullable=False,
        default=DiagnosisTaskStatus.NEW,
        index=True,
    )
```

- `Enum(...)`：数据库层面也用枚举类型，只允许那六个值。
- `values_callable=lambda items: [item.value for item in items]`：告诉 SQLAlchemy 存**枚举的值**（`"new"`）而不是**名字**（`"NEW"`）。这行不写的话，SQLAlchemy 默认存名字，容易踩坑。这是项目里所有枚举列的统一写法。
- `default=DiagnosisTaskStatus.NEW`：新任务默认 `new` 状态。

```python
    alarm_event: Mapped[dict[str, Any]] = mapped_column(JSON, nullable=False, default=dict)
    report: Mapped[dict[str, Any] | None] = mapped_column(JSON, nullable=True)
```

`JSON` 列：直接存一个 JSON 对象。`alarm_event` 把整个告警原始数据塞进去（审计留档），`report` 存 Day4 的结构化报告。用 JSON 列的好处是灵活——不用为报告的每个字段单独建列。

### 3.4 关系（relationship）

```python
    events: Mapped[list["AiopsDiagnosisEvent"]] = relationship(
        back_populates="task",
        cascade="all, delete-orphan",
        order_by="AiopsDiagnosisEvent.created_at",
    )
```

- `relationship(...)`：定义**表之间的关联**。一个任务有多条事件（一对多）。
- `back_populates="task"`：双向关联——事件那边有个 `task` 属性指回来。
- `cascade="all, delete-orphan"`：级联删除。删任务时，它的事件也一起删（不留孤儿数据）。
- `order_by=...`：查出来的事件按创建时间排序。

有了它，你能直接 `task.events` 拿到这个任务的所有事件，不用手写 SQL join。

### 3.5 事件表（时间线留痕）

```python
class AiopsDiagnosisEvent(Base):
    __tablename__ = "aiops_diagnosis_events"

    id: Mapped[str] = mapped_column(String(64), primary_key=True, default=lambda: str(uuid4()))
    task_id: Mapped[str] = mapped_column(
        String(64), ForeignKey("aiops_diagnosis_tasks.id"), nullable=False, index=True
    )
    phase: Mapped[str] = mapped_column(String(64), nullable=False)
    message: Mapped[str | None] = mapped_column(Text, nullable=True)
    payload: Mapped[dict[str, Any] | None] = mapped_column(JSON, nullable=True)
    created_at: Mapped[datetime] = mapped_column(DateTime, default=_utcnow_naive, index=True)

    task: Mapped[AiopsDiagnosisTask] = relationship(back_populates="events")
```

这张表记录诊断过程中的每一步（「开始制定计划」「检索 SOP」…）。Day9 的 SSE 时间线就是读这些事件。现在先把「留痕」的地基打好。

## 4. 逐段讲 Repository（`aiops_diagnosis_repository.py`）

### 4.1 什么是 Repository

Repository（仓储）= **专门负责数据库读写的一层**。它不含业务逻辑，只干「怎么存、怎么取」。

好处（呼应 Day1 的分层）：
- 业务代码（service）不用关心 SQL 细节。
- 换数据库、改查询方式，只动这一层。
- 测试时容易 mock。

### 4.2 构造函数

```python
class AiopsDiagnosisRepository:
    def __init__(self, db: Session):
        self.db = db
```

`db: Session` 是 SQLAlchemy 的**会话对象**——代表一次数据库连接/事务。所有增删改查都通过它。注意 repository **不自己创建** `db`，而是外部传进来（这也是依赖注入，见 Day5/7）。

### 4.3 创建任务

```python
def create_task(
    self,
    *,
    alarm_event: dict[str, Any],
    alert_name: str,
    severity: str = "unknown",
    source: str = "manual",
    alert_id: str | None = None,
    session_id: str | None = None,
) -> AiopsDiagnosisTask:
    if session_id:
        self._ensure_session(session_id)
    task = AiopsDiagnosisTask(
        alert_id=alert_id,
        alert_name=alert_name,
        severity=severity,
        source=source,
        session_id=session_id,
        alarm_event=alarm_event,
        status=DiagnosisTaskStatus.NEW,
    )
    self.db.add(task)      # 把对象加入会话（还没写库）
    self.db.commit()       # 提交事务（真正写库）
    self.db.refresh(task)  # 从库里刷新，拿到自动生成的 id/时间戳
    return task
```

- `*,`：后面所有参数都必须用「关键字」传（`create_task(alert_name="x")`，不能 `create_task("x")`）。好处是调用处一目了然，不会传错位置。
- `add → commit → refresh` 是 SQLAlchemy 的标准三步：
  - `add`：把对象放进会话的「待写入」区。
  - `commit`：真正执行 SQL、写入数据库。
  - `refresh`：把数据库里的最新状态（比如自动生成的 id、`created_at`）读回对象。

### 4.4 状态推进（用上状态机）

```python
def advance_status(
    self,
    task: AiopsDiagnosisTask,
    status: DiagnosisTaskStatus,
    *,
    phase: str | None = None,
) -> AiopsDiagnosisTask:
    if not can_transition(task.status, status):
        raise ValueError(f"非法状态跃迁: {task.status.value} → {status.value}")
    task.status = status
    task.current_phase = phase or status.value
    self.db.commit()
    self.db.refresh(task)
    return task
```

关键：**推进前先用 `can_transition` 检查**。非法跳转直接抛 `ValueError`，不写库。这就是状态机的落地——把「合法流转」这条业务规则强制在数据层。

### 4.5 保存报告 + 置为完成

```python
def save_report(
    self,
    task: AiopsDiagnosisTask,
    *,
    report: dict[str, Any],
    summary: str | None = None,
) -> AiopsDiagnosisTask:
    if not can_transition(task.status, DiagnosisTaskStatus.DONE):
        raise ValueError(f"非法状态跃迁: {task.status.value} → done")
    task.report = report
    task.summary = summary
    task.status = DiagnosisTaskStatus.DONE
    task.current_phase = "done"
    task.error_message = None
    self.db.commit()
    self.db.refresh(task)
    return task
```

存报告和「置为 DONE」是一个原子操作——要么都成功，要么都失败（靠 `commit` 的事务性）。同样先检查状态机（只有 `DIAGNOSING` 能到 `DONE`）。

### 4.6 失败处理

```python
def mark_failed(self, task, *, error_message: str) -> AiopsDiagnosisTask:
    task.status = DiagnosisTaskStatus.FAILED
    task.current_phase = "failed"
    task.error_message = error_message
    self.db.commit()
    self.db.refresh(task)
    return task
```

注意：`mark_failed` **不检查状态机**——因为任何状态都应该能转 FAILED（随时可能出错）。这跟状态机表里「每个状态的允许集合都含 FAILED」是一致的。

### 4.7 补一个细节：`_ensure_session`

```python
def _ensure_session(self, session_id: str) -> None:
    session = self.db.get(ConversationSession, session_id)
    if session is None:
        self.db.add(ConversationSession(id=session_id))
        self.db.flush()
```

因为 `session_id` 是外键，指向的会话必须真实存在，否则数据库报错。这个方法：会话不存在就补建一条。`flush()` 和 `commit()` 的区别——`flush` 把 SQL 发给数据库但不提交事务（同一事务内后续能看到），`commit` 才真正落地。

## 5. 逐段讲 Alembic 迁移

### 5.1 什么是数据库迁移

问题：ORM 模型改了（比如加一列），数据库里已有的表怎么跟着变？

- **错误做法**：`Base.metadata.create_all()`——只能建**不存在**的表，改不了已有表，且没有版本、不能回滚。
- **正确做法**：**迁移工具**（Alembic）。每次表结构变更写成一个「迁移文件」，能升级（upgrade）能回滚（downgrade），团队协作时人人执行同样的变更。

> 💡 面试点：「为什么用 Alembic 不用 create_all」是高频问题。答案：create_all 改不了已有表结构、无版本、不可回滚；生产必须用版本化迁移。

### 5.2 迁移文件结构

```python
revision: str = "20260723_0006"          # 这个迁移的唯一编号
down_revision: Union[str, None] = "20260707_0005"  # 它的上一个迁移
```

- `revision`：本迁移的 id。
- `down_revision`：指向上一个迁移，形成一条**链**：`0001 → 0002 → ... → 0006`。Alembic 靠这条链知道按什么顺序执行。

```python
def upgrade() -> None:
    op.create_table(
        "aiops_diagnosis_tasks",
        sa.Column("id", sa.String(length=64), nullable=False),
        sa.Column("alert_name", sa.String(length=255), nullable=False),
        ...
        sa.ForeignKeyConstraint(["session_id"], ["conversation_sessions.id"]),
        sa.PrimaryKeyConstraint("id"),
    )
    op.create_index(op.f("ix_aiops_diagnosis_tasks_status"), "aiops_diagnosis_tasks", ["status"])
```

- `upgrade()`：升级时执行——建表、建索引。
- 注意这里的列定义要和 ORM 模型**一一对应**（模型说 `String(255)`，迁移也要 `String(length=255)`）。它们是两处独立定义同一张表，必须手动保持一致。

```python
def downgrade() -> None:
    op.drop_index(...)
    op.drop_table("aiops_diagnosis_events")
    op.drop_table("aiops_diagnosis_tasks")
    diagnosis_task_status.drop(op.get_bind(), checkfirst=True)
```

- `downgrade()`：回滚时执行——把 `upgrade` 做的事反着撤销。注意**顺序相反**：先删有外键依赖的子表（events），再删主表（tasks），最后删枚举类型。删反了会因外键约束报错。

### 5.3 怎么跑迁移

```bash
alembic upgrade head      # 升级到最新
alembic downgrade -1      # 回滚一个版本
alembic history           # 看迁移链
```

我们当时还用「离线模式」验证生成的 SQL 正确（不真连库）：

```bash
alembic upgrade head --sql   # 只打印 SQL，不执行
```

### 5.4 别忘了注册模型

新模型要在 `migrations/env.py` 里 import，Alembic 才能感知到：

```python
from app.models import aiops_diagnosis  # noqa: F401
```

`# noqa: F401` 是告诉代码检查工具「这个 import 没直接用到，但别报警告」——它的作用是让 SQLAlchemy 的 `Base.metadata` 收集到这张表。

## 6. 这天的测试讲什么

`tests/unit/test_aiops_diagnosis_repository.py` 用**内存 SQLite** 跑真实 SQL：

```python
@pytest.fixture
def db():
    engine = create_engine("sqlite:///:memory:")   # 内存数据库，测完即焚
    Base.metadata.create_all(engine)               # 建表
    session_factory = sessionmaker(bind=engine, expire_on_commit=False)
    session = session_factory()
    try:
        yield session
    finally:
        session.close()
        engine.dispose()
```

- `sqlite:///:memory:`：SQLite 的内存模式——不落磁盘，测试跑完自动消失，快且干净。
- 测试里验证：创建默认是 NEW、完整流转、**非法跳转被拦**、事件留痕、mark_failed。

关键测试——验证状态机拦截：

```python
def test_illegal_transition_blocked(db):
    repo = AiopsDiagnosisRepository(db)
    task = _create(repo)
    # NEW 不能直接跳到 DIAGNOSING
    with pytest.raises(ValueError, match="非法状态跃迁"):
        repo.advance_status(task, DiagnosisTaskStatus.DIAGNOSING)
```

`pytest.raises(...)`：断言「这段代码**应该**抛出这个异常」。如果没抛，测试失败。这是测试「错误路径」的标准写法——不只测成功，也要测该失败的地方真的失败了。

## 7. Day3 小结

- **ORM**：用 Python 类描述表，SQLAlchemy 翻译成 SQL。
- **状态机**：把「合法流转」这条业务规则用一张表 + `can_transition` 强制住，非法跳转抛错。
- **Repository**：专管数据库读写，`add→commit→refresh` 三步，业务层不碰 SQL。
- **Alembic 迁移**：版本化管理表结构变更，能升级能回滚，比 `create_all` 专业。
- **测试**：内存 SQLite 跑真实 SQL，既测成功路径也用 `pytest.raises` 测失败路径。
