## 1. 为什么要改

### 1.1 一个具体的故障

前面几篇已经把单次调用的防线搭好了：超时（第 16 篇）、失败隔离（第 17 篇）、
如实降级（第 14 篇）。这套组合拳在**偶发**故障上表现很好。

现在设想一个**持续**故障：Milvus 宕机，业务 QPS 10。

```
t=0s    请求 #1  → 检索卡住 → 等 60 秒超时 → 降级返回
t=0.1s  请求 #2  → 检索卡住 → 等 60 秒超时 → 降级返回
t=0.2s  请求 #3  → 检索卡住 → 等 60 秒超时 → 降级返回
...
t=60s   前 600 个请求陆续超时，同时又进来 600 个
```

每个请求的**行为都是对的** —— 它超时了，它降级了，它给了用户一个保守回答。
问题不在单个请求，在于这 600 次尝试**每一次都要先白等 60 秒**才能知道
「哦，还是不行」。

而这 600 个请求在等待期间，各自占着：

- 一个线程池 worker（`asyncio.to_thread` 派发的真线程）
- 一个数据库连接（FastAPI 的 `Depends(get_db)` 已经开好了）
- 一个 HTTP/SSE 连接
- 一份请求上下文内存

线程池默认大小是 `min(32, cpu_count + 4)`。也就是说**大约第 36 个请求开始，
新请求连线程都拿不到了** —— 它们在 `to_thread` 的队列里排着，
连「去撞墙」的机会都还没轮到。

下游已经明确挂了，我们却坚持每来一个请求就再去撞一次墙，
而墙上的坑是我们自己的资源。

### 1.2 还有一个反向的伤害

下游**往往正因为过载才挂**。

Milvus 因为查询压力太大而响应变慢 → 客户端超时 → 客户端重试 →
压力更大 → 彻底不响应。这时所有客户端还在坚持每秒 10 次地打它，
等于在它最虚弱的时候给它最大的负载。

它永远没有机会恢复 —— 因为恢复需要一段没有流量的时间来处理积压。

### 1.3 熔断器解决的到底是什么

一句话：**把「重复确认一个已知的坏消息」这件事的成本降到零。**

连续失败 N 次之后，我们已经知道下游是坏的。此后的每个请求不必再去验证
一次，直接走降级路径 —— 从 60 秒变成 0.0001 秒。等冷却期过去，
放**一个**探针试试：好了就恢复，还不行就再等一轮。

顺带就把 1.2 那个反向伤害也解决了：不打了，下游少了 10 QPS 的压力，
有了恢复窗口。

### 1.4 为什么还需要一个「手动开关」

熔断器是**被动**的 —— 它必须先失败 N 次才动作。

但有些时候我们**已经知道**某个环节是坏的：

- 正在迁移 Milvus，明知检索这半小时内不可用
- 质检模型的配额被别的业务吃光了，等明天才恢复
- 上线了一个有问题的 SOP 文档集，检索结果全是噪音

这些情况下等熔断器自己发现，要先付出 N × 60 秒的代价。
更重要的是有些情况熔断器**永远发现不了** —— 比如检索能正常返回，
只是返回的东西是错的。

所以还需要一个不用改代码、不用发版就能立刻关掉某个环节的开关。
关键在于：**关掉之后链路仍然如实声明降级原因**，
不会假装「知识库里没有」（那就是第 17 篇讲的撒谎链路）。

| 失败隔离 | 一个分支拖垮整张图 | 每个分支都要各自失败一次 |
| **熔断器** | **重复确认已知的坏消息** | 半死状态（一半成功一半失败） |

## 3. 改之后什么样

### 3.1 状态机（`app/core/circuit_breaker.py:74-108`）

```python
class CircuitState(StrEnum):
    CLOSED = "closed"        # 正常：全部放行
    OPEN = "open"            # 熔断：全部拒绝
    HALF_OPEN = "half_open"  # 试探：只放一个探针
```

```
    CLOSED ──连续失败达到阈值──> OPEN ──冷却期满──> HALF_OPEN
      ^                            ^                   │
      │                            └──探针失败─────────┤
      └──────────探针成功────────────────────────────┘
```

构造函数的每个字段都有讲究：

```python
    def __init__(
        self,
        name: str,
        *,
        failure_threshold: int,
        cooldown_seconds: float,
    ) -> None:
        self.name = name
        # max(1, ...) / max(0.0, ...)：防御配置写成 0 或负数。
        # 阈值 0 意味着「一次都不许失败」，第一个请求失败就全线熔断。
        self._failure_threshold = max(1, failure_threshold)
        self._cooldown_seconds = max(0.0, cooldown_seconds)

        # threading.Lock 而不是 asyncio.Lock —— 见 §4.3
        self._lock = threading.Lock()
        self._state = CircuitState.CLOSED
        self._consecutive_failures = 0

        # monotonic 而不是 time.time()：后者会被 NTP 校准往回拨，
        # 那会让「冷却是否结束」的判断出现负数间隔，熔断器卡在 OPEN 出不来。
        self._opened_at = 0.0

        # HALF_OPEN 期间是否已经有探针在路上。防惊群靠的就是这个标志。
        self._probe_in_flight = False

        # 注册进全局表，让 /metrics 能枚举所有熔断器状态
        _REGISTRY[name] = self
```

### 3.2 决策：`allow()`（`:135-153`）

```python
    def allow(self) -> bool:
        with self._lock:
            # 每次决策前先看冷却期是否已满。
            # 这是**惰性**转换：没有后台线程定时把 OPEN 推进到 HALF_OPEN，
            # 而是在被查询时顺带推进。省掉一个线程，代价是「没人问就不转换」——
            # 而没人问的时候状态是什么根本不重要。
            self._maybe_half_open()

            if self._state is CircuitState.CLOSED:
                return True

            if self._state is CircuitState.OPEN:
                return False

            # HALF_OPEN：只放一个探针
            if self._probe_in_flight:
                return False
            self._probe_in_flight = True
            return True
```

最后那四行是**防惊群**的全部实现。没有它，冷却期一到，
积压的几百个请求同时判定「可以试试了」，一起涌向一个可能还没恢复的下游。

### 3.3 记账：`record_success` / `record_failure`（`:155-192`）

```python
    def record_success(self) -> None:
        with self._lock:
            was = self._state
            self._consecutive_failures = 0      # ← 「连续」的含义就在这一行
            self._probe_in_flight = False
            self._state = CircuitState.CLOSED

        # 日志放在锁**外面**：logger 可能写文件、可能走网络 sink，
        # 持锁做 IO 会把所有并发调用者一起卡住。
        if was is not CircuitState.CLOSED:
            logger.info(f"熔断器已闭合（下游恢复）: name={self.name}, 原状态={was.value}")
```

```python
    def record_failure(self) -> None:
        with self._lock:
            self._consecutive_failures += 1
            failures = self._consecutive_failures

            if self._state is CircuitState.HALF_OPEN:
                # 探针失败：直接回 OPEN，不等再攒够阈值。
                # 半开态下已经知道「刚才连续失败到熔断」，探针再失败
                # 就是「还没恢复」的确证 —— 此时要求再失败 N 次，
                # 等于在下游明确没恢复时又放 N 个请求去白等。
                self._trip_locked()
                opened = True
            elif failures >= self._failure_threshold:
                self._trip_locked()
                opened = True
            else:
                opened = False

        if opened:
            logger.error(
                f"熔断器已打开: name={self.name}, 连续失败={failures}/"
                f"{self._failure_threshold}, 冷却={self._cooldown_seconds}s"
            )
```

### 3.4 使用姿势：`guard()`（`:204-242`）

这是整个模块唯一对业务代码暴露的接口：

```python
    @contextmanager
    def guard(self) -> Iterator[None]:
        if not self.allow():
            # 抛异常而不是返回布尔值 —— 见 §4.5
            raise CircuitOpenError(
                f"熔断器打开，已跳过 {self.name} 调用",
                context={"breaker": self.name},
            )
        try:
            yield
        except CircuitOpenError:
            # 不计失败：这次调用根本没发出去。
            # 把它算作下游的一次失败，会让熔断器自己制造的拒绝
            # 不断刷新失败计数，形成「一旦打开永不闭合」的自锁。
            raise
        except asyncio.CancelledError:
            # 取消**不计失败**，但原样往上抛。
            #
            # 取消的来源通常是总预算耗尽（chat_total_budget_seconds），
            # 而预算是整条链路一起花掉的：generate 花了 85 秒，
            # validate 刚开始 5 秒就被取消 —— 这笔账记到 validate 的
            # 下游头上，等于用「别人慢」去熔断一个健康的依赖。
            raise
        except BaseException:
            # 用 BaseException 而不是 Exception：真正的超时（TimeoutError）
            # 同样是「这次调用没成功」，熔断器该看见它。
            # 但仍然原样往上抛，不改变控制流。
            self.record_failure()
            raise
        else:
            self.record_success()
```

三个 `except` 分支的顺序是**语义性的**，不能调换：`CircuitOpenError`
和 `CancelledError` 都是 `BaseException` 的子类，如果 `except BaseException`
排在前面，前两条永远不会命中。

### 3.5 机制与策略分离（`app/core/breakers.py`）

`circuit_breaker.py` 是一个**不认识本项目任何业务**的通用机制。
它不 import `config`，也不知道「我们用的是 Milvus 和 DashScope」。
实例放在单独一个文件：

    "llm",

## 4. 背后的工程原理

> 这一节是面试时要能讲清楚的部分。每条都是「为什么这是标准做法」，
> 不是「我们碰巧这么写」。

### 4.1 熔断器是 Michael Nygard 在《Release It!》里定义的稳定性模式

原始动机就是 1.1 那个场景，Nygard 管它叫 **cascading failure**（级联失败）：
一个下游的故障通过「资源被占满」这条路径传染给上游，
最后整个系统一起死，而故障源只有一个。

熔断器的对偶是**舱壁模式**（bulkhead，隔离资源池）。两者常一起用：
舱壁限制单个依赖能占用多少资源，熔断器让它在明确坏掉后干脆不占。
第 17 篇的失败隔离本质上是舱壁的一种简化形式。

行业里的标准实现是 Netflix Hystrix（已停止维护）→ Resilience4j（Java）、
Polly（.NET）、gobreaker（Go）。**三态状态机是它们共同的形状** ——
这不是某个库的设计选择，是这个问题的正确解。

### 4.2 为什么用「连续失败 N 次」而不是「窗口内失败率 X%」

失败率是更精细的指标，Hystrix 和 Resilience4j 默认都用它。但它需要
额外配一条「最小样本数」规则：

```
没有最小样本数 → 第一个请求失败就是 1/1 = 100% → 熔断器立刻打开
```

对低 QPS 的内部服务，这种误触发会非常频繁。Resilience4j 的
`minimumNumberOfCalls` 默认是 100 —— 也就是说要先攒够 100 次调用，
熔断器才开始工作。本项目的 SOP 检索一天可能都到不了 100 次。

而「连续失败 N 次」天然自带最小样本：想触发就必须真的失败 N 次，
中间任何一次成功都会清零。

| | 连续失败 N 次 | 窗口失败率 X% |
|---|---|---|
| 偶发抖动 | 免疫（一次成功就清零） | 需配最小样本数 |
| 持续故障 | 灵敏（N 次就触发） | 灵敏 |
| 半死状态（50% 失败） | **不敏感** | 敏感 |
| 配置项数量 | 2 个 | 4 个以上 |

代价写清楚了：对「一半成功一半失败」不敏感。

这个代价是**可以接受的**，因为半死状态下下游仍在提供一半的服务能力，
切断它反而是净损失 —— 那种情况该由指标告警交给人判断，
不该由熔断器自动处置。这是个有意识的取舍，不是遗漏。

### 4.3 `threading.Lock` 而不是 `asyncio.Lock`

调用点跨两种执行模型：

```python
# 检索：真线程（asyncio.to_thread 派发到 ThreadPoolExecutor）
with retrieval_breaker.guard():
    docs = await asyncio.to_thread(...)

# LLM：协程
with llm_breaker.guard():
    response = await llm.ainvoke(messages)
```

`asyncio.Lock` 只在单个事件循环内有效，**保护不了线程池里的并发访问**。
而 `threading.Lock` 在两种场景下都正确。

在协程里持 `threading.Lock` 通常是要避免的（阻塞事件循环），
但这里安全，因为临界区只有几个整数赋值，不做任何 IO：

```python
with self._lock:
    self._consecutive_failures += 1      # 整数自增
    failures = self._consecutive_failures # 读一个整数
    ...
    self._state = CircuitState.OPEN       # 枚举赋值
# 日志在锁外面
```

争用时间是纳秒级，不会有实际阻塞。**如果临界区里有 IO（写日志、发指标、
查 Redis），这个结论就不成立了** —— 那时必须换成
「持锁读状态 → 出锁做 IO」的两段式。这也是为什么 `record_success`
的那行 `logger.info` 被刻意放在 `with` 外面。

### 4.4 `time.monotonic()` 而不是 `time.time()`

`time.time()` 是墙上时钟，会被 NTP 校准调整，**可以往回跳**。

```python
self._opened_at = time.time()          # 假设 = 1000.0
# NTP 把系统时间往回拨了 5 秒
time.time() - self._opened_at          # = -5.0 → 永远小于 cooldown
```

结果是熔断器卡在 OPEN 出不来，而下游早就恢复了。日志里一条错误都没有
（因为根本没去调用），排障时会非常困惑。

`time.monotonic()` 保证单调递增，专门用于测量间隔。**任何「两个时间点相减」
的场景都该用它** —— 第 20 篇的 `span_scope` 用 `perf_counter` 是同一个道理
（`perf_counter` 精度更高，适合短间隔；`monotonic` 适合长间隔，两者都是单调的）。

### 4.5 `guard()` 抛异常而不是返回布尔值

对比两种设计：

```python
# 方案 A：返回布尔值
if retrieval_breaker.allow():
    try:
        docs = retrieve(...)
        retrieval_breaker.record_success()
    except Exception:
        retrieval_breaker.record_failure()
        return [], RetrievalStatus.FAILED
else:
    return [], RetrievalStatus.FAILED       # ← 重复的降级代码
```

```python
# 方案 B：抛异常（本项目）
try:
    with retrieval_breaker.guard():
        docs = retrieve(...)
except Exception as exc:
    return [], RetrievalStatus.FAILED       # ← 一条分支处理两种情况
```

方案 B 的优势有三层：

1. **接入零成本。** 六个调用点原本就有 `except Exception → 降级` 分支，
   一行都不用改。
2. **忘不掉记账。** 方案 A 里 `record_success` / `record_failure`
   要手写，漏一个就是「只记失败不记成功」→ 熔断器永不闭合。
   `guard()` 用 `try/except/else` 把记账绑死在控制流上。
3. **错误分类自动正确。** `CircuitOpenError` 是 `AppError` 子类，
   `error_code_of` 给出 `circuit_open`、`degrade_reason_of` 给出
   `CIRCUIT_OPEN`，日志和降级原因都不用额外处理（第 14 篇）。

代价是「用异常表达非异常的控制流」，通常算反模式。这里可以接受，
因为熔断确实是一次**失败**（对调用方而言这次调用没成功），
不是一个正常返回值。

### 4.6 自锁：`CircuitOpenError` 为什么不能计入失败

这是熔断器最经典的一个 bug，值得单独讲。

假设 `guard()` 里没有那条 `except CircuitOpenError: raise`：

```
1. 连续失败 5 次 → OPEN
2. 冷却 30 秒 → HALF_OPEN
3. 探针发出，被某个更外层的 guard 拒绝 → 抛 CircuitOpenError
4. 这个异常被内层 guard 的 except BaseException 接住 → record_failure()
5. HALF_OPEN 下的失败 → 立刻回 OPEN，重新冷却
6. 回到步骤 2，永远循环
```

**业务永久降级，而下游一直是好的。** 更糟的是没有任何错误日志能提示原因，
因为「失败」全是熔断器自己制造的。

嵌套 guard 在本项目里真实存在的路径：`first_response_service` 的
`llm_breaker.guard()` 内部若调用了另一个也被 guard 保护的函数，
就会出现内外两层。

### 4.7 误伤：`CancelledError` 为什么不能计入失败

第 16 篇引入了总预算（`chat_total_budget_seconds = 90`）。
预算是整条链路**一起花掉**的：

```
rewrite     花 2 秒
retrieve    花 3 秒
generate    花 85 秒   ← 慢的是这个
validate    刚开始 5 秒 → 总预算耗尽 → asyncio.timeout 取消它
```

`validate` 的下游（模型服务）表现完全正常，它只是运气不好，
排在一个慢家伙后面。如果这笔账记到 `llm_breaker` 头上：

```
连续 5 个请求都在 generate 慢 → validate 被取消 5 次 →
llm_breaker 打开 → 所有 LLM 调用被跳过 → 而 DashScope 一直是好的
```

用「别人慢」去熔断一个健康的依赖，这是熔断器最容易造成的误伤。

判断标准：**熔断器只应对「下游给出的坏结果」记账。**
取消是我们自己的决定，不是下游的表现。

同理，`TimeoutError` **必须**计入 —— 那是下游真的没在规定时间内回应。
这就是为什么用 `except BaseException` 而不是 `except Exception`：
让所有异常默认计入，然后**显式**排除那两个不该计入的。
默认包含 + 显式排除，比默认排除 + 显式包含更安全 ——
新增的异常类型会自动被正确处理。

### 4.8 惊群：为什么半开只放一个探针

```
冷却期满的那一刻，积压了 300 个请求
  ↓ 没有 _probe_in_flight 标志
300 个请求同时判定「HALF_OPEN，可以试试」
  ↓
300 个请求同时涌向一个可能还没恢复的下游
  ↓
把它二次打死 → 熔断器再打开 → 冷却 → 再涌 300 个
```

形成一个**自激震荡**，而且每一轮积压都比上一轮更多，打得更狠。

一个探针的成本是有界的（一次调用），信息量却是完整的
（下游到底能不能应答）。放 300 个不会带来任何额外信息。

这也是为什么 `record_success` / `record_failure` / `_maybe_half_open`
三处都要 `self._probe_in_flight = False` —— 探针有结果之后必须释放槽位，
否则半开态永久卡死。

### 4.9 熔断器的单位是「一个下游依赖」

这是划分熔断器时唯一需要记住的判据：
**会同时坏、也会同时好的调用，共用一个熔断器。**

两个方向的错误：

```
只开一个（全局熔断器）
  → Milvus 挂了会把 LLM 调用一起切断
  → 两个健康状况完全独立的依赖被绑在一起
  → 向量库宕机时连降级答案都生成不出来，纯误伤
```

```
每个调用点开一个
  → rag 检索和 SOP 检索打的是同一个 Milvus，却各数各自的失败次数
  → 同一个故障要失败 2N 次才熔断，灵敏度减半
  → 而 SOP 检索 QPS 很低，可能永远攒不够 N 次 → 熔断器成了装饰品
```

本项目分成两个：检索类（Milvus + BM25）一个，LLM（模型服务）一个。

### 4.10 探针成功立刻闭合，不要求连续成功 M 次

有些实现要求半开态连续成功 M 次才闭合（Resilience4j 的
`permittedNumberOfCallsInHalfOpenState`）。本项目选择一次成功就闭合：

探针成功说明下游能应答了。此时若继续限流，被拒的请求本来是能成功的 ——
**那是我们自己造成的失败**。

真的没恢复，下一轮连续失败会重新打开，代价只是一个冷却周期（30 秒）。
两种错误的代价不对称：
「过早闭合」损失一个冷却周期，「过晚闭合」损失的是本来能成功的请求。

### 4.11 主动开关 vs 被动熔断

两者是互补的，不是重复：

| | 熔断器 | 运行时开关 |
|---|---|---|
| 触发方式 | 自动（失败 N 次） | 人工 |
| 反应速度 | N × 超时之后 | 立刻 |
| 能发现的问题 | 调用失败 | 调用成功但结果不对 |
| 恢复方式 | 自动（探针） | 人工 |
| 适用场景 | 意外故障 | 已知的计划内故障 |

「调用成功但结果不对」这一行是开关不可替代的理由：
上线了一批噪音 SOP 文档，检索每次都成功返回，熔断器永远不会动作，
但那些结果正在污染每一份诊断报告。

### 4.12 开关关闭时报 FAILED 而不是 EMPTY

这条直接继承第 17 篇的结论。`EMPTY` 的语义是
**「知识库里确实没有」—— 那是一个业务结论**。开关关着的时候
我们一次调用都没发，说「库里没有」就是撒谎，会让人跑去补 SOP 文档，
而实际要做的是把开关打开。

为什么不新增一个 `DISABLED` 状态：下游对它的处置和 `FAILED` 一模一样
（标降级 + 在报告里声明证据链断了），多一个状态会让每个消费者都多一条
分支，却没有任何行为差异（YAGNI）。真正需要区分「是坏了还是被关了」
的场合是排障，那看日志就够了。

而降级**原因**必须区分：`FEATURE_DISABLED` 而不是 `LLM_ERROR`。
后者会把值班同学送去查模型配额和鉴权，而那边一切正常，排障就此卡住。

### 4.13 为什么不引 pybreaker

pybreaker 是个成熟的库。但我们要的是六十行逻辑：一个计数器、
一个时间戳、三个状态。

引一个依赖来换这六十行，代价是多一个需要跟版本、跟安全公告、
跟 Python 版本兼容性的第三方包，而它的绝大部分功能
（Redis 共享状态、事件监听器、排除异常列表）本项目一个都用不上。

**YAGNI 不只是「别写用不到的代码」，也包括「别引用不到的库」。**

反例对照：`prometheus_client`（第 22 篇）我们引了 —— 因为那里有
真正难写对的东西（指标注册表的幂等、多进程模式、文本格式的转义规则）。
判断标准是「自己写会不会踩到不明显的坑」，而熔断器这六十行没有那种坑。

### 4.14 单进程状态的边界

本项目的熔断器状态活在**进程内存**里。多个 worker 进程各有一份：

```
uvicorn --workers 4
  → 4 个独立的 retrieval_breaker
  → Milvus 挂了，需要 4 × 5 = 20 次失败才能让全部 worker 熔断
```

这是**已知的、可接受的**限制：

- 灵敏度稀释是线性的，4 个 worker 就是 4 倍，不会指数放大
- 每个进程独立判断反而更鲁棒 —— 共享状态（Redis）意味着熔断器
  自己有了一个可能挂掉的依赖，而它是用来应对依赖挂掉的
- 真到了几十个实例的规模，正确的做法是服务网格（Istio/Envoy）
  在基础设施层做熔断，而不是每个应用自己实现一个分布式版本

面试时这条要主动说 —— 知道自己方案的边界在哪，比方案本身更重要。

## 6. 常见坑

### 6.1 观测动作自己改变了被观测的状态

`test_probe_failure_reopens_immediately` 这个用例最初是这么写的：

```python
breaker = _breaker(threshold=5, cooldown=0.0)     # ← 冷却期 0
for _ in range(5):
    breaker.record_failure()
assert breaker.state is CircuitState.OPEN          # ← 必然失败
```

`cooldown=0.0` 时，读一次 `state` 就会顺带把 OPEN 推进到 HALF_OPEN
（`_maybe_half_open` 的正常行为）。断言本身触发了状态转换。

修法是用非零冷却 + 手动推进：

```python
breaker = _breaker(threshold=5, cooldown=60.0)
for _ in range(5):
    breaker.record_failure()
assert breaker.state is CircuitState.OPEN

breaker._opened_at -= 61.0      # 等价于「等了 61 秒」，但不必真 sleep
assert breaker.state is CircuitState.HALF_OPEN
```

**惰性状态转换 + 有副作用的 getter 是这类坑的通用形状。**
写测试时要意识到 `state` 不是一个纯查询。

### 6.2 测试里 `MagicMock` 的属性永远是真值

```python
job = MagicMock()
# job.retries_left 是一个 MagicMock 对象
if job.retries_left > 0:      # ← MagicMock 支持 __gt__，返回另一个 MagicMock
    ...                       # ← 而 MagicMock 是真值，永远进这个分支
```

第 19 篇踩过同一个坑。熔断器测试里的 `_breaker()` 用真实对象而不是 mock，
从根上避开了它。

### 6.3 熔断器实例会互相顶掉

`CircuitBreaker.__init__` 最后一行是 `_REGISTRY[name] = self`。
测试里造同名熔断器会把生产实例从注册表里顶掉：

```python
# 危险：会覆盖 app.core.breakers.retrieval_breaker 在注册表里的位置
CircuitBreaker("retrieval", failure_threshold=1, cooldown_seconds=0.0)
```

所以测试辅助函数用自增计数器保证名字唯一：

```python
def _breaker(threshold: int = 3, cooldown: float = 60.0) -> CircuitBreaker:
    _breaker.counter = getattr(_breaker, "counter", 0) + 1
    return CircuitBreaker(f"test_{_breaker.counter}", ...)
```

### 6.4 跨用例状态泄漏是最难查的一类测试污染

```python
@pytest.fixture(autouse=True)
def _clean_breakers():
    """每个用例前后都清空全部熔断器状态。

    前后都做而不是只做一次：前面清是防止上一个用例污染，
    后面清是防止本用例污染下一个 —— 包括那些不在本文件里的用例。
    """
    reset_all_breakers()
    yield
    reset_all_breakers()
```

不加这个 fixture 的后果：用例 A 把 `llm_breaker` 打开，
用例 B 里所有 LLM 调用都被跳过 —— **B 失败的原因和 B 测的东西
毫无关系，而且取决于用例执行顺序**。单跑绿、全跑红，
或者今天绿、明天红（`pytest-randomly` 打乱了顺序）。

### 6.5 `reset_all_breakers` 在 `circuit_breaker`，不在 `breakers`

```python
from app.core.breakers import reset_all_breakers        # ✗ ImportError
from app.core.circuit_breaker import reset_all_breakers # ✓
```

命名直觉会指向 `breakers.py`（复数，听起来像「所有熔断器」），
但那个文件只放**策略**（开哪几个实例）。注册表和它的操作函数属于
**机制**，在 `circuit_breaker.py`。

### 6.6 计时器包在 guard 外面会让指标撒谎

已经在 §3.8 讲过，这里再强调一次因为它非常隐蔽：

```python
# ✗ 错误顺序
with observe_llm_call("rewrite"):
    with llm_breaker.guard():
        response = await llm.ainvoke(messages)
```

熔断打开时 `guard()` 第一行就抛，但计时器已经启动了，
会记下一个 ~0.0001 秒的样本。熔断期间几百个「没打出去的调用」
全以 0 秒计入直方图 → **P99 反而变好看** → 下游挂了，
耗时指标显示一切正常。

正确顺序是计时器在内侧。「熔断了多少次」由
`circuit_breaker_state` 和 `degrade_total{reason="circuit_open"}`
负责，各司其职（第 22 篇）。

### 6.7 `except` 分支的顺序不能调换

```python
        except CircuitOpenError:     # 必须在前
            raise
        except asyncio.CancelledError:  # 必须在前
            raise
        except BaseException:        # 必须在后
            self.record_failure()
            raise
```

前两个都是 `BaseException` 的子类。`BaseException` 排在前面的话，
自锁防护和误伤防护会双双失效，而且**没有任何测试会报错** ——
除了那两个专门测它们的用例。

### 6.8 一个已修掉的失效引用

`sop_retrieval_service.py:117` 的注释原本写着
「见 `first_response_service._record_degrade_metric`」，
而那个方法的真实名字是 `_count_report_degrade`。

```console
$ grep -rn '_record_degrade_metric\|_count_report_degrade' app/
app/services/sop_retrieval_service.py:117:  # (见 first_response_service._count_report_degrade)   ← 已修
app/services/first_response_service.py:256:  self._count_report_degrade(report)
app/services/first_response_service.py:281:  self._count_report_degrade(report)
app/services/first_response_service.py:297:  def _count_report_degrade(...)
```

注释里的跨文件引用**没有任何工具会校验**，重命名时最容易漏。
这四批的主题是「不说谎」，注释里的假引用也是一种谎 ——
它会让读代码的人去找一个不存在的方法，然后怀疑自己是不是看错了文件。

---

## 7. 一句话总结

超时让单次调用有下限，失败隔离让局部故障不扩散，
**熔断器让「已知的坏消息」不必反复用完整代价去确认**；
而运行时开关补上熔断器发现不了的那一类问题 ——
调用成功，但结果是错的。

三者叠加之后，持续故障下的行为从「每个请求白等 60 秒」
变成「前 5 个请求白等，之后立刻降级，30 秒后自动试探恢复」。
